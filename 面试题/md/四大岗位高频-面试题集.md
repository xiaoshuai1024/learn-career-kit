# 一、后端架构师（4 题 · 硬门槛，你的最大空白区）

## Q1. 设计一个秒杀系统

> **考察意图**：这是架构师面试的"压轴系统设计题"。面试官不是要你背答案，而是看你的**工程权衡能力**——会不会先问需求、懂不懂瓶颈分析、能不能在"高并发 vs 数据一致 vs 成本"之间做取舍。

### 1.1 先澄清需求（很多人栽在这步，直接开干）

开口前先问清楚三类需求：

| 类别 | 要问的问题 | 作用 |
|------|-----------|------|
| **功能需求** | 秒杀什么？一个商品还是多个？下单后要支付吗？多久不支付释放库存？ | 定边界 |
| **非功能需求** | 预期峰值 QPS？库存量级？响应时间要求？ | 定架构规模 |
| **规模估算** | 10万人抢100件？还是1000万人抢1万件？ | 决定要不要上 MQ |

**估算示例**：10 万人抢 100 件商品，活动持续 1 分钟 → 峰值 QPS ≈ 100000/60 ≈ 1666，但实际瞬时（前几秒）可能是平均的 5-10 倍 → **峰值 ~1.5w QPS**。这个量级单库扛不住，必须分层削峰。

### 1.2 核心思想：层层削峰（背下来）

> **秒杀的精髓不是让系统多快，而是让多少请求根本到不了数据库。** 每一层都在"扔请求"。

```
┌─ ① 前端层 ──────────────────────────────────────────┐
│  CDN 静态化 + 按钮防抖(点一次置灰) + 倒计时 + 答题/验证码   │  扔掉 60-70% 无效流量
└──────────────────────────────────────────────────────┘
                          ↓
┌─ ② 网关层 ──────────────────────────────────────────┐
│  令牌桶限流 + 风控(黑名单/设备指纹/IP频次) + 负载均衡      │  扔掉恶意/超量流量
└──────────────────────────────────────────────────────┘
                          ↓
┌─ ③ 应用层 ──────────────────────────────────────────┐
│  Redis 预扣库存(Lua 原子) + 一人一单去重 + MQ 异步下单     │  扔掉 99%，只放"抢到的"
└──────────────────────────────────────────────────────┘
                          ↓
┌─ ④ 存储层 ──────────────────────────────────────────┐
│  DB 按 MQ 消费速率匀速写库存(乐观锁 where stock>0 兜底)    │  最终一致
└──────────────────────────────────────────────────────┘
```

### 1.3 逐层详解

**① 前端层**：
- 活动页**静态化 + CDN**，动态数据（库存、倒计时）走接口；页面缓存到浏览器
- **按钮防抖**：点击后立即置灰 3-5 秒，防连点
- **倒计时**：前端校验时间，活动未开始按钮不可点
- **答题/验证码**：拉长用户下单时间，错开瞬时峰值（某头部电商早年用过）

**② 网关层**：
- **限流**：令牌桶算法（允许突发），单机或集群限流
- **风控**：黑名单 IP/账号、设备指纹去重、同 IP 频次限制，拦截黄牛脚本

**③ 应用层（核心）**：
- **库存预热**：活动开始前把库存写入 Redis（`stock:goodsId = 100`），活动期间**绝不查 DB 库存**
- **Redis 预扣库存（Lua 原子）**：判 `stock>0` 和扣减必须在一个 Lua 脚本里，保证原子性
- **一人一单**：`SETNX userId:goodsId`，已抢过直接拒绝
- **异步下单**：扣减成功后不直接写 DB，而是发一条 MQ 消息，消费端按 DB 承受速率匀速落库

**④ 存储层**：
- DB 库存用**乐观锁兜底**：`UPDATE stock SET stock=stock-1 WHERE goods_id=? AND stock>0`
- MQ 消费幂等（防重复扣减）

### 1.4 防超卖的 Lua 脚本（核心代码，会写会讲）

```lua
-- KEYS[1] = 库存key  KEYS[2] = 已购用户set的key  ARGV[1] = userId
-- 1. 判断是否已买过（一人一单）
if redis.call('sismember', KEYS[2], ARGV[1]) == 1 then
    return -2  -- 已购买
end
-- 2. 判断库存
local stock = tonumber(redis.call('get', KEYS[1]))
if stock == nil or stock <= 0 then
    return -1  -- 库存不足
end
-- 3. 扣库存 + 记录用户
redis.call('decr', KEYS[1])
redis.call('sadd', KEYS[2], ARGV[1])
return 1     -- 成功
```

> **为什么必须 Lua？** 因为 `get` 判断和 `decr` 扣减是两步，并发下会出现"两个请求都读到 stock=1，都扣减，变成 -1"的超卖。Lua 脚本在 Redis 里**单线程原子执行**，中间不会被其他命令打断。

### 1.5 库存一致性（Redis 与 DB 怎么同步）

Redis 扣减后，DB 最终要对齐。两种方案：
- **MQ 异步落库**（主流）：扣减成功发 MQ → 消费端写 DB；消息可靠投递 + 消费幂等
- **binlog 同步**（Canal）：DB 变更回写 Redis（反向，用于其他场景）

### 1.6 高频追问

**追问 1：如果 Redis 挂了怎么办？**
> 答：① Redis 做集群/哨兵高可用，主从切换；② 本地缓存（Caffeine）做二级缓存兜底；③ 极端情况降级——直接限流 + 提示"活动太火爆"，**宁可少卖不可超卖**。绝不能让流量直接打到 DB。

**追问 2：库存怎么预热？预热时活动已经开始了怎么办？**
> 答：活动开始前用脚本/定时任务把 DB 库存写入 Redis。预热和开始之间留缓冲；若预热未完成活动已开始，前端倒计时校验 + 网关挡住，等预热完成放行。

**追问 3：MQ 消息丢了怎么办？导致用户扣了库存却没下单成功？**
> 答：① 生产端开**confirm 机制**确认消息到 MQ；② MQ 开持久化；③ 消费端**手动 ack**，处理成功才确认；④ **消费幂等**（用订单唯一键/状态机防重复）；⑤ 超时未支付的订单走**延迟队列释放库存**回补。

**追问 4：怎么保证 MQ 消费顺序？（比如同一商品的下单顺序）**
> 答：同一商品的订单消息路由到**同一个 queue/分区**（用 goodsId 做分片 key），单 queue 内有序消费。跨商品不需要全局有序。

**追问 5：库存扣了但用户 30 分钟没支付，库存怎么回补？**
> 答：下单时发一条**延迟消息**（30 分钟延迟），到点检查订单状态——未支付则释放库存（Redis 加回 + DB 回滚），取消订单。本质是 TCC 的 Cancel 思想。

**追问 6：如果是 618 全站大促，不只是单个秒杀呢？**
> 答：全站级别要上**全链路压测 + 弹性扩容（K8s 自动扩缩容）+ 限流降级预案（Sentinel）+ 熔断**。核心思路不变（削峰），但要从单点设计上升到全站容量规划，提前压测摸清每个链路的容量水位。

## Q2. MySQL 为什么用 B+ 树？索引什么时候会失效？

> **考察意图**：索引是后端面试第一梯队的"必考八股"。面试官想确认你对存储引擎底层的理解深度——不只是会用，还要知道为什么这样设计。

### 2.1 B+ 树结构

```
B+ 树特点：
  · 非叶子节点：只存索引键 + 子节点指针（不存数据）→ 单节点能放更多索引项 → 树更矮
  · 叶子节点：存全部数据 + 双向链表连接 → 范围查询高效
  · 树高通常 3-4 层
```

### 2.2 为什么是 B+ 树（四个对比，逐个讲）

| 对比对象 | 为什么 B+ 树赢 |
|---------|---------------|
| **vs 二叉搜索树/红黑树** | 二叉树每个节点最多 2 个子节点，千万级数据要 20+ 层，每层一次磁盘 IO → 太慢 |
| **vs B 树** | B 树非叶子也存数据 → 单节点索引项少 → 树更高；B+ 树数据全在叶子 + 链表 → 范围查询（`between`、`>`）只需遍历链表 |
| **vs Hash 索引** | Hash O(1) 等值查询快，但**不支持范围查询、排序、最左前缀**；MySQL 内存表用 Hash，InnoDB 主索引不用 |
| **vs 跳表** | 跳表是内存结构（Redis zset 用），实现简单；B+ 树针对**磁盘按页（16KB）IO** 优化，磁盘场景更优 |

### 2.3 经典数字（必背）

> InnoDB 一页 **16KB**。假设主键 bigint（8B）+ 子指针（6B）= 14B/索引项 → 非叶子节点一页约 **1170** 个索引项；叶子节点假设一行 1KB → 一页约 **16** 行。
> **3 层 B+ 树 ≈ 1170 × 1170 × 16 ≈ 2000 万行**，查一行**最多 3 次磁盘 IO**（根节点常驻内存，实际 1-2 次 IO）。这就是为什么千万级表查询依然快。

### 2.4 聚簇索引 vs 二级索引（InnoDB）

| 类型 | 叶子存什么 | 例子 |
|------|-----------|------|
| **聚簇索引**（主键） | **整行数据**（数据和索引一体，一张表只有一个） | `id` 主键索引 |
| **二级索引**（非主键） | **索引列 + 主键值**，查到后要**回表** | `name` 索引 → 查到 id → 再查聚簇索引拿整行 |

> **回表**：二级索引查到主键 → 拿主键回聚簇索引查完整行（多一次 IO）。
> **覆盖索引**：查询的字段全在二级索引里，**不用回表**（如 `select id,name from t where name=?`，name 索引含 id 和 name，直接返回）。

### 2.5 最左前缀原则

联合索引 `(a,b,c)` 实际上按 `a→b→c` 排好序的 B+ 树，只能从最左列开始匹配：

| 查询条件 | 是否走索引 |
|---------|:---:|
| `where a=?` | ✅ |
| `where a=? and b=?` | ✅ |
| `where a=? and b=? and c=?` | ✅（完全匹配） |
| `where b=?` | ❌（缺最左 a） |
| `where a=? and c=?` | ⚠️ 只用到 a（中间断列 c 用不上，除非索引下推） |

### 2.6 索引失效的 6 大场景（必背）

1. **函数/计算运算**：`where year(create_time)=2024` → 改 `where create_time >= '2024-01-01' and < '2025-01-01'`
2. **隐式类型转换**：`where phone=13800000000`（phone 是 varchar，传了数字）→ MySQL 隐式转换导致全表扫描
3. **左模糊**：`where name like '%张'` → 索引有序，左模糊无法定位；`like '张%'` 可以
4. **`OR` 两侧非全索引**：`where a=? or b=?`，若 b 无索引则全表；必须两侧都有索引才走 index_merge
5. **`!=` / `<>` / `not in`**：通常走全表扫描（优化器判断扫描范围太大不划算）
6. **违反最左前缀**：联合索引中间列断层

### 2.7 高频追问

**追问 1：索引下推（ICP，Index Condition Pushdown）是什么？**
> 答：5.6 引入。没有 ICP 时，`where name=? and name like '%x'`，引擎先用 name 索引找到所有 `name=?` 的记录**全部回表**，再在 server 层过滤 like。有了 ICP，**like 过滤下推到存储引擎层**，在索引层就过滤掉不满足的，**减少回表次数**。

**追问 2：为什么主键建议自增整型？为什么不用 UUID？**
> 答：① 自增主键**顺序插入**，叶子节点顺序写，不会频繁触发**页分裂**（页分裂要移动数据、产生碎片，降低性能）；② 整型占用空间小（bigint 8B），非叶子节点能放更多索引项，树更矮。UUID 随机无序 + 占空间大（36 字符），插入时页分裂频繁，树更高。

**追问 3：`count(*)` / `count(1)` / `count(列)` 有什么区别？**
> 答：InnoDB 的 `count(*)` 不会取所有字段，优化器选最小索引扫描，**不一行行取值**；`count(1)` 类似；`count(列)` 要解析该列、过滤 NULL。三者中 `count(*)` 经优化器优化，**不一定比 count(1) 慢**。InnoDB 没有 MyISAM 那种行数缓存，所以大表 count 都慢——业务上用**单独的计数表/Redis 计数**维护。

**追问 4：深分页（limit 1000000, 10）为什么慢？怎么优化？**
> 答：MySQL 会扫描前 1000010 行再丢弃前 100 万行，越往后越慢。优化：① **延迟关联**——先走覆盖索引查出主键 `select id from t order by x limit 1000000,10`，再 join 原表取数据；② **记录上一页最大 id**，下次 `where id > last_id limit 10`（要求按主键有序）；③ 业务上限制最大翻页深度。

**追问 5：联合索引 (a,b,c)，`where a=? and c=? and b=?` 和 `where a=? and b=? and c=?` 效果一样吗？**
> 答：**一样**。MySQL 优化器会自动调整条件顺序匹配最左前缀，都能完全命中索引。优化器重排是基本能力，写 SQL 时不必死磕顺序（但可读性上建议按索引顺序写）。

**追问 6：怎么看一条 SQL 走没走索引？**
> 答：`EXPLAIN`。看 `type`（`const` > `ref` > `range` > `index` > `ALL`，`ALL` 是全表扫描）、`key`（实际用的索引）、`rows`（预估扫描行数）、`Extra`（`Using index` 覆盖索引、`Using filesort` 文件排序需优化、`Using temporary` 用了临时表需优化）。

## Q3. Redis 缓存穿透、击穿、雪崩的区别与解法

> **考察意图**：缓存是高并发系统的命脉。这三连问几乎是 Redis 面试的"开场必问"，考察你对缓存异常场景的理解和应对。

### 3.1 三者对比（先记这张表）

| 问题 | 场景 | 根因 | 解法 |
|------|------|------|------|
| **穿透** | 查一个**根本不存在**的数据，缓存和 DB 都没有 | 恶意攻击/bug，每次都打到 DB | ① 缓存空值（短 TTL）② **布隆过滤器** |
| **击穿** | **单个热点 key** 过期的瞬间，海量请求同时打穿 | 热 key 失效，瞬间高并发 | ① 互斥锁重建 ② 逻辑过期（不设 TTL） |
| **雪崩** | **大量 key 同时过期** / Redis 整个宕机 | 批量 key 同时失效或缓存服务挂 | ① 随机 TTL ② 多级缓存 ③ 集群高可用 ④ 服务端熔断降级 |

> **口诀**：穿透是"查没有的"（布隆挡）、击穿是"一个热的挂了"（加锁）、雪崩是"一大片挂了"（打散 + 兜底）。

### 3.2 布隆过滤器原理（穿透解法，常被追问）

- 本质是一个**位数组 + 多个哈希函数**
- 写入时：把 key 用 k 个哈希函数算出 k 个位置，位数组对应位置置 1
- 查询时：同样算 k 个位置，**全为 1 才"可能存在"**，有 0 则"一定不存在"
- **特点**：有误判（假阳性，说存在但实际没有），但不会漏判（说不存在就一定不存在）；空间极省；**不支持删除**（多位共用）

### 3.3 击穿的两种解法

- **互斥锁重建**：缓存失效时，只让一个线程查 DB 并回写缓存，其他线程等待/重试（用 `setnx` 加锁）
- **逻辑过期**：key **不设物理 TTL**，value 里存一个逻辑过期时间；查询时发现逻辑过期，返回旧值的同时**异步触发更新**

### 3.4 缓存与数据库一致性（进阶，必问）

四种缓存策略：

| 策略 | 做法 | 特点 |
|------|------|------|
| **Cache Aside**（旁路缓存，最常用） | 写：先更新 DB，再删缓存；读：查缓存，没有查 DB 回写 | 应用层维护，简单 |
| **Read/Write Through** | 应用只操作缓存，缓存层同步读写 DB | 缓存层负责同步 |
| **Write Back**（写回） | 只写缓存，异步刷 DB | 极快但有丢数据风险 |

**先删缓存还是先更新 DB？**

| 顺序 | 问题 |
|------|------|
| 先删缓存再更新 DB | 并发下：删缓存 → 另一线程读到旧 DB 写回旧缓存 → 更新 DB → **缓存长期是脏的** |
| **先更新 DB 再删缓存（推荐）** | 异常概率小；但仍有可能：删缓存失败 → 用**延迟双删**补救 |

**延迟双删**：更新 DB → 删缓存 → 休眠 N ms（覆盖读流程耗时）→ 再删一次缓存。

### 3.5 高频追问

**追问 1：布隆过滤器能不能删除元素？为什么？**
> 答：标准布隆过滤器**不能**——因为多个元素可能哈希到同一位，删一个会把别人的位也清掉。需要删除用**计数布隆过滤器**（Counting Bloom Filter），把位数组改成计数数组，删除时计数减 1（代价是空间翻倍）。

**追问 2：延迟双删的"延迟"时间怎么定？**
> 答：覆盖一次"读请求从 DB 读到写回缓存"的耗时，通常取**读业务逻辑的耗时 + 几百 ms 缓冲**。也可以统计线上一段时间的读耗时 P99 来定。

**追问 3：Redis 和 DB 能做到强一致吗？**
> 答：**理论上要引入分布式事务/分布式锁**（如更新时加锁，缓存和 DB 在一个事务里），但**性能代价大**，违背"用缓存提性能"的初衷。工程上接受**最终一致**（Cache Aside + 延迟双删 + 消息补偿），对强一致要求极高的数据（如余额）走 DB 或单独通道。

**追问 4：热点 key（hot key）怎么发现和处理？**
> 答：发现——Redis 4.0+ `--hotkeys` 参数、代理层统计、客户端采样；处理——① **本地缓存**（Caffeine）做二级缓存分担压力；② key 分片（一个热 key 拆成 `key_1`~`key_10`，分散到不同节点）；③ 集群扩容。

**追问 5：缓存预热怎么做？**
> 答：系统上线/活动前，把热点数据批量写入 Redis（脚本、定时任务、Canal 监听 binlog 同步），避免冷启动时大量请求直接打到 DB。

## Q4. 跨服务怎么保证数据一致性？（分布式事务）

> **考察意图**：微服务架构下的核心难题。考察你对 CAP/BASE 理论和各分布式事务方案的**选型能力**——不是背方案，而是知道什么场景用什么。

### 4.1 理论基础（先立框架）

**CAP 定理**：分布式系统三选二——一致性（C）、可用性（A）、分区容错（P）。网络分区（P）必然存在，所以只能在 **CP（强一致）** 和 **AP（高可用）** 间选。
- 注册中心对比：**Zookeeper/etcd 选 CP**（保证一致），**Eureka/Nacos(AP模式) 选 AP**（保证可用）

**BASE 理论**（CAP 的工程妥协）：**B**asically Available（基本可用）+ **S**oft state（软状态）+ **E**ventually consistent（最终一致）。大部分互联网业务追求的就是**最终一致**。

### 4.2 各方案详解

| 方案 | 原理 | 一致性 | 性能 | 业务侵入 | 适用场景 |
|------|------|:---:|:---:|:---:|------|
| **2PC / XA** | prepare + commit 两阶段，DB 层协议 | 强一致 | 低（长锁） | 无 | 金融监管、低并发 |
| **TCC** | Try(预留) + Confirm(确认) + Cancel(取消) | 强一致 | 高 | **极重**（每方法写3个） | 资金、库存 |
| **SAGA** | 长事务拆串 + 补偿，正向 T1…Tn，失败反向补偿 | 最终一致 | 高 | 中（写补偿） | 长流程订单 |
| **本地消息表** | 业务表+消息表同事务写入，定时扫消息表发 MQ | 最终一致 | 高 | 中 | **通用业务最常用** |
| **事务消息**（RocketMQ） | 半消息 + 回查机制，MQ 保证消息与本地事务原子 | 最终一致 | 高 | 中 | 用 RocketMQ 的团队 |

### 4.3 2PC 的三大病（为什么不用）

1. **同步阻塞**：prepare 后所有参与者锁不释放，直到 commit，期间资源被锁
2. **协调者单点**：协调者挂了，参与者卡死在等待
3. **数据不一致**：commit 阶段网络分区，部分 commit 部分没 commit

### 4.4 TCC 三大坑（必背）

| 坑 | 场景 | 解法 |
|----|------|------|
| **空回滚** | Try 因网络没到，TM 超时发 Cancel，Cancel 先到但本地无 Try | 事务状态表，识别"无 Try"则空 Cancel |
| **幂等** | Confirm/Cancel 可能重试 | 状态表标记已处理，重复请求返回成功 |
| **悬挂** | 空回滚后迟到的 Try 才到 | 查状态表发现已 Cancel，拒绝执行 Try |

### 4.5 选型决策树（背这个，面试直接答）

```
资金/监管要求强一致？
  ├─ 是 → TCC（愿意业务改造）或 XA（宁慢不可错，金融）
  └─ 否 → 接受最终一致
        ├─ 业务流程长、需补偿 → SAGA
        ├─ 通用跨服务调用 → 本地消息表 + MQ（首选）
        └─ 用 RocketMQ → 事务消息
```

### 4.6 高频追问

**追问 1：为什么互联网大多不用 2PC/XA？**
> 答：2PC 同步阻塞、性能差、协调者单点、分区下数据不一致，扛不住高并发。互联网追求高可用和高吞吐，所以用 BASE 思路做**最终一致**（本地消息表、TCC、SAGA），牺牲短暂不一致换性能。

**追问 2：TCC 的"业务侵入"到底侵入了什么？**
> 答：一个业务动作要写 **Try / Confirm / Cancel 三个接口**，还要维护**冻结字段**（如 `frozen_amount`）和**事务状态表**来防三大坑。开发量是普通接口的 3 倍。所以只在资金、库存等强一致场景才值得。

**追问 3：本地消息表怎么保证消息一定被消费？**
> 答：① 业务数据和消息表在**同一个本地事务**里写入（要么都成功要么都失败）；② 定时任务扫描消息表中"未发送"的消息，发到 MQ；③ 消费端**幂等**处理（防止重发导致重复消费）；④ 消费成功后更新消息表状态。本质是用本地事务 + 重试保证"消息最终一定发出"。

**追问 4：怎么保证接口幂等？（贯穿所有方案）**
> 答：① **唯一键约束**（订单号唯一，重复插入报错）；② **token 机制**（前端先获取一次性 token，提交时校验）；③ **状态机**（只允许从待支付→已支付，重复请求因状态不变被挡）；④ **乐观锁 version**；⑤ Redis `setnx` 防重。

**追问 5：最终一致性怎么知道"一致了"？长时间不一致怎么发现？**
> 答：① **对账系统**（定时比对各服务数据，如每天凌晨对账）；② **监控告警**（消息积压、补偿失败率）；③ **超时核查**（订单超时未完成的主动核查补偿）。最终一致不等于"不管"，而是"通过补偿和对账最终达成一致"。

**追问 6：你能讲讲 Seata 吗？它和上面这些什么关系？**
> 答：Seata 是阿里开源的分布式事务**框架**，把上面几种模式封装成开箱即用的实现——**AT**（无侵入，SQL 解析 + undo_log 反补偿）、**TCC**、**SAGA**、**XA** 四种模式都支持。核心三角色：TC（协调者，独立部署）、TM（事务发起方）、RM（资源管理者）。大多数团队用 Seata AT 模式（一个 `@GlobalTransactional` 注解搞定）。（详见生词本 Seata/AT/TCC 各词条）

# 二、技术总监（3 题 · 格局与决策）

## Q5. 怎么推动一个核心老系统的重构？

> **考察意图**：技术总监/架构师的核心能力——能不能把"技术债"翻译成业务语言、用低风险的方式推动变革、在"稳业务"和"改架构"间平衡。回答切忌"全盘推翻重写"这种天真答案。

### 5.1 先回答"为什么要重构"（论证价值）

**大忌**：以"技术太老、代码烂、想用新技术"为由推动重构——业务方不买账。

**正确做法**：把技术债翻译成**业务损失**：
- "每次需求平均多花 2 天，因为改一处崩三处"→ 交付慢
- "线上故障率每月 3 次，都是老代码引起"→ 质量差
- "招不到人愿意维护这套老框架"→ 团队风险

> 用 **ROI 思维**：重构成本 vs 不重构的持续损失，让业务方看到"重构是为了更快交付、更稳、更省"，而不是技术洁癖。

### 5.2 核心方法：绞杀模型（Strangler Fig Pattern）

来自 Martin Fowler，名字源于"绞杀榕"——新榕树在老树旁边生长，逐渐包裹取代老树，老树最终枯萎。

**步骤**：
1. **新功能进新系统**：新需求不再往老系统加，而是在新系统实现
2. **老功能逐步迁移**：把老系统功能按优先级一个个迁移到新系统（可按模块/领域拆）
3. **流量逐步切换**：用网关/路由把流量从老系统灰度切到新系统
4. **老系统下线**：当老系统没有流量了，安全下线

**关键优势**：**全程老新并存、可回退**，不是"停业重写"。任何阶段出问题都能切回老系统。

### 5.3 分阶段时间线（面试加分，体现规划能力）

| 阶段 | 工作 | 风险点 |
|------|------|--------|
| **准备期** | 补自动化测试、抽象接口（防腐层 ACL）、定义新架构 | 没测试不敢动 |
| **首批试点** | 选一个低风险、边界清晰的功能先迁移，验证方案 | 验证可行性 |
| **规模化迁移** | 按模块逐个迁移，双写校验、灰度切流 | 数据一致性 |
| **收尾下线** | 老系统流量归零后下线，清理遗留 | 别留僵尸系统 |

### 5.4 高频追问

**追问 1：老系统没有测试用例，不敢动怎么办？**
> 答：先补**"安全网"**——不追求完美的单元测试，先上**接口/契约测试和回归测试**，覆盖核心路径（"金主路径"）。重构时遵循"小步快跑"，每步改完跑一遍测试。也可以用"绞杀"绕过——新功能在新系统，老系统慢慢自然消亡，不必硬改老代码。

**追问 2：重构和业务需求冲突（业务要功能、你要重构）怎么平衡？**
> 答：**不要对立**。① 把重构融入需求交付——做某个需求时顺带重构相关模块（"童子军法则"：离开时比来时干净）；② 申请固定的**技术债预算**（业界 15-20% 研发产能用于技术优化），不挤压业务；③ 用数据说服——"不重构这个，下个月交付速度再降 20%"。优先级用**四象限**（紧急重要）排。

**追问 3：新老系统双写期间数据不一致怎么办？**
> 答：① **双写 + 对账**：新老系统都写，定时对账比对差异；② **以老系统为准**（过渡期），新系统可接受短暂延迟；③ 用 Canal 监听老库 binlog 同步到新系统，保证最终一致；④ 切流前做**全量数据校验**，差异清零才切。

**追问 4：怎么说服老板/业务方投入重构（他们只想做功能）？**
> 答：**用钱和数据说话**，不用技术术语。① 算 ROI：重构投入 X 人月，换来的交付提速/故障减少值 Y，Y > X；② 找**业务盟友**（被老系统拖累最狠的业务方）；③ 小步验证——先做一个试点拿结果，用结果要资源；④ 绑定业务目标（"为支持明年 GMV 翻倍，系统必须先扛住 10 倍流量"）。

**追问 5：什么是"大爆炸重写"（Big Bang Rewrite）？为什么不能这么干？**
> 答：即停掉所有业务，全部推翻重写，写完再切。Joel Spolsky 有篇名文专门警告过——**重写期间业务停滞、新系统又积累一堆新 bug、老问题没解决又来新问题、周期超长容易失败**。业界教训：Netscape 当年重写浏览器直接输掉浏览器战争。**渐进式绞杀是唯一稳妥的路。**

## Q6. 怎么度量研发效能？

> **考察意图**：技术总监必须懂**数据驱动的管理**。这是你 skill-test 暴露的最大短板（评分 2），但生词本已有 DORA 详解——这里把追问层面补全。回答的关键是"不只报指标，还懂陷阱"。

### 6.1 DORA 四指标（必背：两快两稳）

| 组 | 指标 | 衡量什么 | 精英团队基准 |
|---|------|---------|:---:|
| 速度 | ① **部署频率**（Deployment Frequency） | 多久部署一次到生产 | 多次/天 |
| 速度 | ② **变更前置时间**（Lead Time for Changes） | 代码提交到上线多久 | < 1 小时 |
| 稳定 | ③ **变更失败率**（Change Failure Rate） | 多少比例部署导致故障 | 0–15% |
| 稳定 | ④ **故障恢复时间**（MTTR） | 故障发生到恢复多久 | < 1 小时 |

**2021 加第 5 指标**：**可靠性（Reliability）**——用 SRE 的 SLI/SLO，从用户视角看系统稳不稳。

### 6.2 核心理念（面试官想听的）

> **速度和稳定不对立**——好的工程实践让两者同时提升。精英团队是"又快又稳"，四个指标都好。如果一个团队"快但故障多"或"稳但慢如牛"，都说明工程实践有问题。

### 6.3 四指标怎么落地测量

| 指标 | 数据来源 |
|------|---------|
| 部署频率 | CI/CD 平台部署日志 |
| 变更前置时间 | 从 Git commit 时间到生产部署时间的差值（CI/CD + Git） |
| 变更失败率 | 部署后回滚/热修/故障的次数 ÷ 总部署次数 |
| MTTR | 监控告警系统（从告警触发到恢复的时间） |

### 6.4 ⚠️ Goodhart 陷阱（面试最大加分点）

> **"当一个指标变成考核目标，它就不再是个好指标。"**（Goodhart's Law）

典型翻车：
- 为降"变更失败率"→ 故意**少发布** → 部署频率暴跌，前置时间暴涨
- 为提"交付率"→ 把需求**拆碎刷数** → 指标好看但业务没进展
- 为降 MTTR → 重新定义"故障"标准（小故障不算）→ 数据造假

**正确做法**：① 指标用于**诊断和改进**，**慎直接挂钩个人绩效**；② **四指标平衡看**，不单独优化某一个；③ 关注**业务结果**（用户价值、收入），而非纯粹的过程指标。

### 6.5 高频追问

**追问 1：除了 DORA，还有别的效能度量框架吗？**
> 答：① **SPACE 框架**（GitHub 提出）：Satisfaction（满意度）、Performance、Activity、Communication、Efficiency——更全面，含人的维度；② **业务指标**：交付率、需求吞吐量、线上故障数、用户 NPS。DORA 偏"工程交付效率"，SPACE 补了"人和协作"，两者结合更立体。

**追问 2：速度和稳定真的不冲突吗？我感觉改得快就容易出错？**
> 答：表面看快=乱，但 DORA 调研数万家团队发现：**精英团队又快又稳**。原因是他们有**自动化测试、CI/CD、小步快跑、灰度发布、快速回滚**——这些"快"的同时降低了风险（小变更易回滚、自动化测试挡 bug）。真正冲突的是"无工程实践的低效快"，那是真乱。

**追问 3：你们团队的 DORA 指标在什么水平？怎么改进的？**
> 答：（结合真实数据答）"我们部署频率从月度提到日级——靠容器化+CI/CD 自动化；MTTR 从几小时降到 30 分钟——靠完善监控告警和预案演练。变更失败率控制在 10% 以内——靠灰度发布和自动化测试。"（注：用自己真实数据，不编造）

**追问 4：怎么避免团队为了指标好看而"刷数据"？**
> 答：① 指标**不直接挂钩奖金**，只用于诊断；② **平衡看四指标**——某指标突涨要追问其他指标是否恶化；③ 引入**反向校验**（如部署频率涨了但前置时间也涨，说明在刷）；④ 终极标准是**业务结果**，效能指标只是手段。

**追问 5：研发效能度量最终是为了什么？**
> 答：不是为了"考核谁快谁慢"，而是为了**发现瓶颈、持续改进**——哪个环节慢（需求堆积？代码审查拖延？测试瓶颈？部署卡审批？），针对性优化。度量的价值在"诊断"而非"评判"。

## Q7. 重大技术选型，你的方法论是什么？

> **考察意图**：技术总监/架构师的决策力。考察你选型时**考量的维度全不全**、会不会留档、有没有回退预案。回答要有框架感，不能说"凭经验"。

### 7.1 用 ADR（Architecture Decision Record）留档

**ADR 标准模板**（背）：
```
1. 标题 + 状态（Proposed / Accepted / Deprecated / Superseded）
2. 背景（Context）：为什么要做这个决策？面临什么问题、什么约束？
3. 决策（Decision）：选了什么？为什么选它？
4. 替代方案（Alternatives）：还考虑了什么？为什么不选？
5. 后果（Consequences）：带来什么好处、什么代价、什么风险？
6. （不可变）：决策一旦 Accepted，要改只能新写一条 Superseded
```

> ADR 的价值：① 决策有据可查，新人能理解"为什么这么选"；② 防止反复推翻（不可变）；③ 形成团队的决策资产。

### 7.2 选型评估的 6 个维度（背这张表）

| 维度 | 要问的问题 |
|------|-----------|
| **业务匹配度** | 这个技术解决我们的问题吗？能力边界够吗？ |
| **性能** | 满足 QPS/延迟/数据量要求吗？有 benchmark 吗？ |
| **社区与生态** | 活跃度、star 数、Issue 响应、有没有大厂背书（避免踩坑无人救） |
| **招聘成本** | 市场上好招人吗？（"用 Rust 重写但招不到人"是经典翻车） |
| **学习曲线** | 团队能驾驭吗？培训成本？ |
| **可持续性** | 长期维护、许可证（GPL 有传染性风险）、被弃坑风险 |

### 7.3 决策流程

1. **明确问题**：先搞清楚要解决什么，不是"我想用某技术"
2. **候选方案**：列 2-3 个备选（含"保持现状"）
3. **POC 验证**：关键场景做个小验证，拿真实数据
4. **多维度打分**：用上面 6 维度评估
5. **写 ADR**：记录决策和理由
6. **留回退方案**：万一不行怎么退

### 7.4 高频追问

**追问 1：ADR 里最重要的是哪部分？**
> 答：**"替代方案"和"后果"**。替代方案说明你做过比较（不是拍脑袋）；后果诚实写代价和风险（体现成熟）。一个只写"选了 X"不写为什么、不写代价的 ADR 是无效的。

**追问 2：技术先进性和团队匹配冲突（技术上 A 更好，但团队只会 B）怎么选？**
> 答：**优先团队匹配**。技术再先进，团队驾驭不了、招不到人，就是"用了等于没用"。可以用"渐进引入"——先用 B 顶住业务，同时让小部分人学习 A 做 POC，成熟后再推广。**技术选型本质是人的决策，不只是技术决策。**

**追问 3：怎么评估"招不到人"的风险？**
> 答：① 看招聘平台该技术岗位的供需（岗位多 vs 简历少 = 不好招）；② 看本地市场（青岛和北上广技术栈热度不同）；③ 小众技术即使先进，也要算上"培养成本 + 人员离职无人接手"的隐性成本。**新技术在本地的可获得性是硬约束。**

**追问 4：开源方案 vs 自研怎么选？**
> 答：默认**能用成熟开源就用开源**（社区帮你踩坑、有人维护）。自研只在：① 开源方案都不满足核心需求；② 该组件是公司核心竞争力（如字节的推荐引擎）；③ 对可控性要求极高。**自研的代价是长期维护成本，不要低估"造轮子"的长期负担。**

**追问 5：决策做错了怎么回退？**
> 答：① 选型时就设计**回退路径**（抽象层/接口隔离，换实现不影响业务）；② 灰度引入（先小范围用，不行就退）；③ ADR 标记为 Superseded，新写一条记录为什么改。**成熟架构师永远先想"怎么退"再想"怎么进"。**

# 三、AI 应用开发（4 题 · 你的强项与差异化方向）

## Q8. 讲讲 RAG 的完整链路，怎么提升检索准确率？

> **考察意图**：RAG 是 AI 应用工程化的"基本功"。考察你对完整链路的掌握 + 检索优化的深度。这是你的强项方向，要能讲深、讲细。

### 8.1 完整链路（7 步）

```
① 文档加载 → ② 切片(Chunking) → ③ Embedding 向量化
   → ④ 存入向量库 → ⑤ 检索(Embedding query + 相似度)
   → ⑥ Rerank 重排 → ⑦ 拼 Prompt → LLM 生成
```

### 8.2 各环节详解

**① 文档加载**：PDF/Word/HTML/Markdown → 纯文本（难点：表格、图片、公式，多模态需 OCR/视觉模型）

**② 切片（Chunking，关键）**：
- **大小**：500–1000 token（太小丢上下文，太大稀释语义 + 浪费 token）
- **重叠率**：10–20%（防止把一个完整语义切断）
- **进阶**：按语义切（Semantic Chunking）、按标题层级切（Markdown 结构）、父子切片（Parent-Child：检索小块、喂大块保上下文）

**③ Embedding**：文本 → 高维向量（如 1536 维）。选模型：OpenAI text-embedding-3、bge-m3（中文好）、Cohere。**中英文场景选对应优化的模型**。

**④ 向量库**：Milvus（大规模）、Pgvector（PostgreSQL 扩展，小项目）、ES 向量检索、Chroma（轻量）。相似度：余弦相似度（Cosine）、点积（Dot Product）。

**⑤ 检索**：query 向量化 → 在向量库找 top-k 最相似片段。问题：纯向量检索对**关键词/专有名词**不敏感。

**⑥ Rerank 重排**：用 Cross-Encoder（如 bge-reranker）对 top-k 重新精排，把最相关的提到最前。向量检索是"粗召回"，Rerank 是"精排"。

**⑦ 拼 Prompt**：把检索到的片段塞进 Prompt（`context: {片段} question: {问题}`），控制 token 预算，超出则截断/压缩。

### 8.3 提升检索准确率（5 招，背下来）

| 招数 | 做法 | 解决什么 |
|------|------|---------|
| **混合检索** | 关键词（BM25）+ 向量，分数融合（RRF） | 向量漏关键词、关键词漏语义，互补 |
| **Rerank 重排** | Cross-Encoder 精排 top-k | 粗排不准，精排提升相关性 |
| **MMR（最大边际相关性）** | 在相关性和多样性间平衡 | 避免返回高度重复的片段 |
| **查询改写/扩展** | 把口语问题改成检索友好；或用 LLM 生成多个变体查询 | 用户问题表述差，召回低 |
| **元数据过滤** | 先按时间/类目/权限过滤，再向量检索 | 缩小范围、提升精度、做权限控制 |

### 8.4 高频追问

**追问 1：切片大小怎么定？有什么讲究？**
> 答：① 和 Embedding 模型的最大 token 对齐（别超）；② 覆盖一个完整语义单元（一段/一节）；③ 太小→语义不完整、检索准但上下文不足；太大→语义稀释、相关性下降、token 浪费。**实操：从 500 token + 10% 重叠起步，按效果调。** 进阶用 Parent-Child：检索用小块（精准），喂 LLM 用父块（上下文全）。

**追问 2：向量检索召回率低（该召回的没召回）怎么办？**
> 答：① 换更好的 Embedding 模型（中文用 bge-m3）；② 混合检索（加 BM25 关键词）；③ 查询改写（用户问题太模糊时，LLM 改写/扩展）；④ 调 top-k（先多召回再用 Rerank 筛）；⑤ 切片优化（大小/语义切片）。**先诊断是召回环节还是重排环节的问题，再针对性优化。**

**追问 3：RAG 和微调（Fine-tuning）怎么选？**
> 答：**RAG 用于"知识"**（动态、可更新、需溯源——如公司文档问答）；**微调用于"能力/风格"**（固定能力、特定格式、领域语感——如医学报告生成）。**知识频繁变化用 RAG（改库即可），不重训；能力/格式定制用微调。** 两者不冲突，可组合（微调让模型更懂领域 + RAG 注入实时知识）。

**追问 4：怎么评估 RAG 的效果？**
> 答：用 **RAGAS** 等框架，从四个维度评估：① **Faithfulness（忠实度）**：回答是否基于检索内容（不编造）；② **Answer Relevance（答案相关性）**：回答是否切题；③ **Context Precision（上下文精确率）**：检索的内容是否相关；④ **Context Recall（上下文召回率）**：该检索的是否都检索到了。也可用 **LLM-as-a-Judge** 自动打分 + 人工抽检。

**追问 5：表格、图片这种非文本内容在 RAG 里怎么处理？**
> 答：① 表格——转成 Markdown/HTML 文本、或用多模态模型理解；② 图片——OCR 提取文字、或视觉 Embedding 模型（如 CLIP）做图文检索；③ 复杂文档——用 Layout 解析（如 Unstructured、LlamaParse）保留结构。多模态 RAG 是当前难点，也是优化空间。

## Q9. ReAct、Tool Calling、多 Agent 编排是什么？

> **考察意图**：Agent 是 AI 工程化的核心。考察你对 Agent 范式的理解——单 Agent 怎么工作、多 Agent 怎么协作、什么场景用什么编排。

### 9.1 ReAct（Reasoning + Acting）

让 LLM **边推理边行动**的循环：

```
Thought（思考）: 我需要先查天气
Action（行动）: 调用 weather_tool("北京")
Observation（观察）: 25度，晴
Thought: 天气不错，可以回答了
Final Answer: 北京今天 25 度，晴天
```

- **核心**：LLM 不只是回答，而是"想一步做一步"，根据工具返回的结果再决定下一步
- ReAct 是早期靠**Prompt 约束**输出 Thought/Action 格式实现的

### 9.2 Tool Calling / Function Calling

**Function Calling**（OpenAI 最早提出）：LLM 输出结构化的"函数调用"（函数名 + 参数 JSON），由**外部框架执行**后把结果喂回 LLM。

```json
// LLM 输出
{ "name": "get_weather", "arguments": { "city": "北京" } }
```

- **Tool Calling 是 Function Calling 的演进/泛化**——现代模型（GPT-4、Claude、Qwen）原生支持，输出更规范、可靠
- 比 ReAct 的 Prompt 约束**更稳定**（原生训练支持，不靠解析文本）
- 现在主流 Agent 框架（LangChain、Spring AI）都基于 Tool Calling

### 9.3 多 Agent 编排

当任务复杂，单个 Agent 扛不住，用多 Agent 分工：

**两种主流模式**：

| 模式 | 做法 | 适用 |
|------|------|------|
| **Supervisor + Worker**（中心化） | 一个 Supervisor（主管）Agent 负责拆解任务、分派给 Worker，Worker 干完汇报，Supervisor 汇总 | 任务可清晰拆分、需协调（如"写一篇报告"=调研+写作+校对） |
| **去中心化 / Network**（编制式） | Agent 之间直接通信协作，无中心控制 | 角色对等的协作 |

### 9.4 编排工具

- **LangGraph**：基于状态图的有状态编排，能精确控制 Agent 流转、循环、分支、人在回路（Human-in-the-loop）
- **单 Agent**：ReAct + Tool Calling 足够；**复杂流程**（多步、有条件分支、需状态管理）用 LangGraph

### 9.5 高频追问

**追问 1：ReAct 和 Plan-and-Execute 有什么区别？**
> 答：**ReAct 是"边想边做"**——每步根据上一步结果决定下一步，灵活但可能跑偏；**Plan-and-Execute 是"先规划再执行"**——先用 Planner 生成完整计划，再 Executor 逐步执行，更有全局观但不够灵活。复杂任务常组合：先 Plan 出框架，执行中 ReAct 应对意外。

**追问 2：Tool Calling 和 Function Calling 到底啥区别？**
> 答：**本质是同一个东西的演进**。Function Calling 是 OpenAI 2023 最早的功能名（单函数调用）；后来各家扩展成"工具"概念（Tool Calling）——支持并行调用多个工具、更规范的 schema、更稳定。现在说 Tool Calling 基本指代这个能力，Function Calling 是旧称。**面试时可说"Tool Calling 是 Function Calling 的演进，本质是让 LLM 输出结构化工具调用"。**

**追问 3：什么时候该用多 Agent，什么时候单 Agent 够？**
> 答：**单 Agent 优先**——简单任务一个 Agent 配几个工具就行，多 Agent 是过度设计。用多 Agent 的信号：① 任务可清晰拆成不同角色（调研员/写手/审核员）；② 上下文太长塞不下（拆给子 Agent 各管一块）；③ 需要不同模型/配置（贵的模型做规划，便宜的做执行）。**别为了用而用。**

**追问 4：Agent 陷入死循环（反复调用同一工具）怎么办？**
> 答：① **限制最大迭代次数**（max_iterations）；② **检测重复**——记录已执行的动作，重复触发则终止；③ **设置超时**；④ Prompt 里加约束"不要重复相同动作"；⑤ 观察可观测性日志（trace）定位为什么会循环。**生产环境必须加熔断和兜底。**

**追问 5：怎么保证 Agent 在生产环境的稳定性？**
> 答：① **工具调用加超时和重试**；② **工具输入校验**（LLM 可能传错参数）；③ **异常捕获 + 降级**（工具失败时给用户合理反馈而非崩溃）；④ **可观测性**（LangFuse/Sentry 记录每一步 trace，便于排查）；⑤ **限流**（防滥用烧 token）；⑥ **人工兜底**（高风险动作如发邮件、扣款，需 Human-in-the-loop 确认）。

## Q10. AI 应用上线，怎么保证稳定性、控成本、可观测？

> **考察意图**：这是"AI 工程化"区别于"AI 玩 demo"的分水岭，也是你的**差异化亮点**。面试官想看你会不会把 LLM 当作一个不稳定、慢、贵的外部依赖来工程化治理。

### 10.1 稳定性：三道防线熔断降级

LLM 接口**又慢又不稳**（超时、限流、幻觉），必须像对待外部服务一样做熔断降级：

```
请求 → ① 主模型(大模型)
          ↓ 超时/失败/限流
       ② 降级：语义缓存命中？→ 返回历史相似回答
          ↓ 没有
       ③ 降级：小模型/规则引擎 → 兜底文案
```

- **熔断**：连续失败到阈值，直接熔断走降级，不再调主模型（Sentinel 思路）
- **超时控制**：LLM 调用设合理超时（如 30s），超时即降级
- **兜底**：永远有"抱歉，服务繁忙"的降级响应，**不能让用户看到 500 错误**

### 10.2 控成本：三个手段

| 手段 | 做法 | 效果 |
|------|------|------|
| **Token 计量** | 记录每次调用的输入/输出 token、按用户/功能统计 | 成本可看见、可归因 |
| **语义缓存** | 新请求先算 Embedding，与历史问题相似度超阈值则直接返回旧答案 | 相似问题不重复调模型，**省 30-50% 成本** |
| **模型路由** | 简单问题（如闲聊、FAQ）走便宜小模型，复杂问题才走大模型 | 按需用模型，大幅降本 |

**成本估算公式**：成本 = Σ(输入token × 输入单价 + 输出token × 输出单价)。要对每个功能设定**预算上限**和**告警**。

### 10.3 可观测性（Observability）

| 维度 | 工具/做法 |
|------|----------|
| **调用链追踪** | LangFuse / LangSmith / Arize Phoenix——记录 prompt、检索、工具调用、生成的完整 trace |
| **Token 消耗监控** | 按用户/功能/时间段统计，异常突增告警 |
| **质量监控** | LLM-as-a-Judge 采样打分、用户反馈（点赞/点踩）收集 |
| **延迟监控** | P50/P99 响应时间 |

### 10.4 高频追问

**追问 1：语义缓存怎么实现？相似度阈值怎么定？**
> 答：① 把历史"问题+答案"的**问题 Embedding** 存起来；② 新请求算 Embedding，与历史问题做**余弦相似度**；③ 超过阈值（如 0.92）直接返回缓存的答案。**阈值权衡**：太高→命中率低（省不了钱），太低→返回不相关答案（损害体验）。从 0.9 起步，结合人工抽检调整。还要设缓存有效期和容量上限。

**追问 2：模型路由的策略怎么做？**
> 答：① **规则路由**：按功能/意图分类（FAQ→小模型，复杂问答→大模型）；② **LLM 路由**：先用便宜的小模型判断问题难度，难的再升级到大模型；③ **分级降级**：大模型超时降级到小模型。关键是**简单问题不浪费大模型算力**。

**追问 3：Token 成本失控怎么排查和预防？**
> 答：排查——按用户/功能拆分 token 消耗，找异常大户（如某人刷接口、某功能 prompt 过长）。预防——① **每个接口设 token 预算和限流**；② **输入长度限制**（防超长 prompt）；③ **Prompt 精简**（去掉冗余上下文）；④ **告警**（日消耗超阈值告警）；⑤ **按租户/用户配额**。

**追问 4：LLM 超时怎么降级才能不影响用户体验？**
> 答：① 设**合理超时**（如首 token 5s、总 30s），超时即降级；② 降级优先级：语义缓存 > 小模型 > 规则引擎 > 兜底文案；③ **流式输出（SSE）**——边生成边返回，让用户感知到进展，减少"卡住"的焦虑；④ 降级时给**有价值的回复**而非"出错了"（如 FAQ 类降级到检索答案）。

**追问 5：AI 应用怎么做 A/B 测试？**
> 答：① **流量分流**：把用户随机分到不同组（不同 prompt/模型/参数）；② **核心指标**：用户满意度（点赞率）、回答质量（LLM-as-Judge/人工评分）、转化率、成本；③ **统计显著性**：样本够大才下结论；④ **灰度**：先小流量验证再全量。难点是"质量"是主观的，需 LLM-as-Judge 或人工标注校准。

## Q11. 怎么减少大模型的幻觉？

> **考察意图**：幻觉是 LLM 落地最大障碍。考察你对幻觉成因和治理手段的全面认识。

### 11.1 为什么会幻觉

- **训练数据**：数据本身有错、过时、冲突
- **知识截止**：模型不知道训练后发生的事，却可能"编"
- **概率本质**：LLM 是"预测下一个 token"的概率模型，不保证事实正确
- **Prompt 模糊**：问题不清，模型"猜"着答

> **关键认知**：幻觉**无法 100% 消除**，只能**降低概率 + 控制影响**。

### 11.2 五大治理手段

| 手段 | 做法 | 原理 |
|------|------|------|
| **① RAG** | 检索真实文档，让模型基于文档回答 | 给事实依据，减少"凭记忆编" |
| **② 强制引用** | Prompt 要求每条论断标注来源 | 可溯源，便于校验 |
| **③ 降低 Temperature** | 事实性任务用 0–0.3 | 减少随机性，输出更确定 |
| **④ 后处理校验** | 用另一个 LLM/规则做事实核查（LLM-as-Judge） | 二次把关 |
| **⑤ 产品兜底** | 不确定时回答"我不知道" | 比胡编好，降低信任损失 |

### 11.3 高频追问

**追问 1：幻觉能完全消除吗？**
> 答：**不能**。LLM 本质是概率生成模型，没有"真伪判断"能力。我们能做的是**降低幻觉概率**（RAG 给依据、低温减随机、引用可查）+ **控制影响**（不确定时拒答、关键场景人工审核）。对幻觉零容忍的场景（医疗、法律），必须**人工兜底**，不能让 LLM 直接拍板。

**追问 2：RAG 为什么能减少幻觉？它就完全不幻觉了吗？**
> 答：RAG 给模型**真实的外部知识**，让它"基于文档回答"而非"凭记忆编"，显著降低幻觉。但 RAG **不能完全消除**：① 检索没召回正确内容，模型仍可能编；② 召回了但模型理解错/过度发挥；③ 模型可能"混合"检索内容和自身知识产生新幻觉。所以 RAG + 引用 + 校验要组合用。

**追问 3：Temperature 和幻觉什么关系？怎么设？**
> 答：Temperature 控制输出随机性——**越高越发散（易幻觉），越低越确定**。事实问答/代码/抽取用**低 Temperature（0–0.3）**；创意写作/头脑风暴用**高（0.7–1.0）**。但低温不是万能——模型本身知识错的话，低温只会"确定地错"。

**追问 4：怎么检测一个回答是不是幻觉？**
> 答：① **引用校验**：检查引用的来源是否真实存在、是否支持论断；② **LLM-as-Judge**：用另一个模型判断"回答是否忠于检索内容"；③ **交叉验证**：多模型回答，不一致则存疑；④ **事实知识库比对**：对结构化事实做规则校验；⑤ **用户反馈**：收集点踩/纠错。生产环境组合用，关键场景人工抽检。

**追问 5：模型知识截止日期的问题怎么解决？**
> 答：① **RAG 接实时数据**（检索最新网页/数据库）——最主流方案；② **联网搜索**（如让 Agent 调搜索工具）；③ **微调更新**（成本高、不实时）；④ 对时间敏感的问题，Prompt 里**注入当前日期**让模型知道"现在"。**RAG + 联网是解决时效性的标准答案。**

# 四、全栈（3 题 · 端到端交付）

## Q12. 让你独立交付一个全栈项目，你怎么规划？

> **考察意图**：全栈岗的核心 = **端到端独立交付能力**。考察你能不能一个人把"需求→选型→开发→部署→监控"全链路扛下来，而不是只会写某一端。

### 12.1 全流程（背这个链路）

```
需求理解 → 技术选型(有依据) → API 契约先行 → 并行开发(前/后端)
   → 联调 → 部署 → 监控告警 → 迭代
```

### 12.2 各环节详解

**① 需求理解**：先搞清楚"解决什么问题"，再想"怎么做"。区分**核心功能**（MVP）和**锦上添花**，先做最小可用。

**② 技术选型（有依据）**：选型要能说出**为什么**（不是"我只会这个"）。
- 前端：Vue3/React + Vite + TypeScript + Pinia/Zustand
- 后端：Spring Boot（Java 生态成熟）/ FastAPI（Python、AI 场景友好）/ Node.js
- DB：MySQL（关系型主力）+ Redis（缓存）
- 部署：Docker + Docker Compose（单机）/ K8s（集群）
- 选型考量：业务匹配、团队熟悉度、生态、招聘（见 Q7）

**③ API 契约先行**（关键！）：**前后端先约定接口文档**（Swagger/OpenAPI），再并行开发。避免"前端等后端、联调时撕接口"。

**④ 并行开发**：后端用 Mock 数据先跑通逻辑；前端用 Mock 接口先做页面；接口 ready 后联调。

**⑤ 部署**：`docker-compose.yml` 编排前端（Nginx）+ 后端 + DB + Redis，**一条命令起全栈**。

**⑥ 监控告警**：基础监控（Prometheus + Grafana）+ 日志（ELK）+ 错误上报（Sentry）。

### 12.3 Docker Compose 全栈编排示例

```yaml
version: "3.8"
services:
  frontend:              # 前端 Nginx
    build: ./frontend
    ports: ["80:80"]
  backend:               # 后端 API
    build: ./backend
    ports: ["8080:8080"]
    depends_on: [mysql, redis]
    environment:
      - DB_HOST=mysql
      - REDIS_HOST=redis
  mysql:                 # 数据库
    image: mysql:8
    environment:
      MYSQL_ROOT_PASSWORD: ${DB_PASS}
    volumes: ["db_data:/var/lib/mysql"]
  redis:                 # 缓存
    image: redis:7
volumes:
  db_data:
```

> 一条 `docker-compose up -d` 起全栈，本地/测试/生产环境一致。

### 12.4 高频追问

**追问 1：前后端怎么高效协作，避免联调地狱？**
> 答：① **API 契约先行**——先定 OpenAPI/Swagger 文档（路径、参数、返回结构、错误码）；② **Mock 并行**——后端用 Mock 数据、前端用 Mock 接口，各自先跑通；③ **接口变更走文档**，不口头沟通；④ 用 Apifox/Postman 管理接口，自动生成 Mock。联调时因为契约一致，基本是无缝对接。

**追问 2：一个从零到部署的项目，你具体怎么拆解任务？**
> 答：① 先出**技术方案 + 接口文档 + 数据库设计**（评审）；② 按模块拆任务（用户/商品/订单），每个模块再拆前后端；③ **MVP 优先**——先跑通核心主链路（能注册登录、能下单），再补次要功能；④ 每个模块独立可测可部署；⑤ 定里程碑（周计划），风险点提前暴露。

**追问 3：怎么保证全栈项目的代码质量？**
> 答：① **代码规范**——ESLint + Prettier（前端）、Checkstyle/SpotBugs（Java）；② **Git Hook**（Husky）提交前自动检查；③ **CI 门禁**——PR 必须过 lint + 测试 + 构建；④ **Code Review**；⑤ **测试**——单元测试（核心逻辑）+ 接口测试；⑥ 文档同步（README、接口文档）。

**追问 4：项目里遇到你不懂的技术栈怎么办？**
> 答：① 先**评估必要性**——非核心能否换成熟悉的方案（见 Q7 选型）；② 必须用时——快速学习（官方文档优先 > 教程），**先跑通最小 demo 再用到项目**；③ 用 AI 辅助（Claude Code 等）加速理解和写代码；④ 找团队/社区求助。**关键是快速学习能力和判断"该学还是该换"。**

**追问 5：全栈项目和分工团队项目，开发方式有什么不同？**
> 答：全栈**一个人扛全链路**，更重**整体把控**（选型/部署/运维都要懂），沟通成本低但深度可能不如专精；分工团队**深度更强**但**协作成本高**（接口约定、联调、跨端沟通）。全栈的优势是**端到端闭环快**、**没有甩锅空间**（都是自己的），适合中小项目或早期产品。

## Q13. 一个接口慢，从全链路怎么排查？

> **考察意图**：全栈的**全链路问题排查能力**——不只是会查 DB 慢 SQL，而是能从前端到 DB 逐层定位。体现系统性思维。

### 13.1 方法论：先定位"慢在哪一层"，再深入

> **不要上来就猜**。先用**全链路追踪（APM）** 看耗时分布，找最大头，再针对性深入。

```
用户感知慢 → 看链路追踪，耗时花在哪？
   ├─ 前端层（网络/渲染）       → 浏览器 DevTools / Performance
   ├─ 网关层（DNS/Nginx）       → 网关日志
   ├─ 应用层（业务逻辑/RPC）    → APM 链路 / 日志
   ├─ DB 层（慢SQL/锁/连接池）  → 慢查询日志 / EXPLAIN
   └─ 系统层（CPU/内存/IO）     → 监控（top/iotop）
```

### 13.2 逐层排查清单

**① 前端层**：
- 网络：RTT 高？DNS 慢？带宽不够？→ CDN、HTTP/2、减少请求
- 资源：JS/CSS/图片太大？→ 压缩、分包、懒加载
- 渲染：回流重绘多？长任务阻塞？→ 虚拟列表、防抖节流、Web Worker

**② 网关层**：DNS 解析慢？Nginx 配置问题？SSL 握手？→ 网关访问日志

**③ 应用层**：
- 接口耗时分布：DB 查询占多少？RPC 调用占多少？业务计算占多少？
- **N+1 查询**（循环里查 DB，经典坑）→ 改批量查询
- 第三方接口超时（调外部 API 慢）→ 加超时 + 异步 + 缓存
- 序列化/反序列化开销

**④ DB 层（最常见根因）**：
- **慢 SQL**：开慢查询日志，找慢 SQL
- **EXPLAIN 分析**：`type=ALL`（全表扫描）？缺索引？`Extra=Using filesort`（文件排序）？
- **锁等待**：行锁/表锁争用 → `SHOW PROCESSLIST` 看锁
- **连接池打满**：连接数不够，请求排队
- **数据量大**：单表千万级 → 分库分表、读写分离、归档冷数据

**⑤ 系统层**：CPU 打满？内存泄漏？磁盘 IO 瓶颈？→ `top`/`vmstat`/`iotop` + 监控大盘

### 13.3 常见根因与解法速查

| 根因 | 现象 | 解法 |
|------|------|------|
| 慢 SQL（缺索引） | DB 耗时占大头 | 加索引、优化 SQL |
| N+1 查询 | 接口调很多次 DB | 改 JOIN 或批量查询 |
| 锁等待 | DB 连接堆积 | 优化事务、缩小锁粒度 |
| 第三方接口超时 | RPC 耗时高 | 超时 + 异步 + 缓存 + 降级 |
| 大数据量传输 | 网络耗时长 | 分页、压缩、按需返回字段 |
| GC 停顿（JVM） | 间歇性卡顿 | 调 GC 参数、排查内存泄漏 |

### 13.4 高频追问

**追问 1：怎么定位是 DB 慢还是应用慢？**
> 答：① 看 **APM 链路追踪**（如 SkyWalking/Jaeger），接口耗时自动拆解成 DB/RPC/业务各占多少；② 应用层打日志记录各阶段耗时（`DB耗时=Xms, 业务=Yms`）；③ DB 开**慢查询日志**（`long_query_time` 设阈值，如 200ms）。**链路追踪是最快定位手段**。

**追问 2：DB 慢 SQL 怎么排查和优化？**
> 答：① 慢查询日志找慢 SQL；② `EXPLAIN` 看执行计划——`type`（ALL 全表扫描要优化）、`key`（用的索引）、`rows`（扫描行数）、`Extra`（`Using filesort`/`Using temporary` 要优化）；③ 优化：加合适索引、避免 `select *`、避免索引失效（见 Q2）、大表分页用延迟关联、N+1 改批量。

**追问 3：怎么建立接口性能监控体系？**
> 答：① **APM 全链路追踪**（SkyWalking/Pinpoint/Jaeger）自动采集接口耗时和调用链；② **指标监控**（Prometheus + Grafana）——接口 P50/P99 响应时间、QPS、错误率；③ **慢查询监控**（DB 慢日志采集）；④ **告警**——P99 超阈值告警。**监控要覆盖前端（Web Vitals: LCP/FID/CLS）到后端到 DB 全链路。**

**追问 4：前端页面慢怎么排查？**
> 答：① **Chrome DevTools Network**——看请求瀑布图，哪个请求慢、资源多大；② **Performance 面板**——录制看长任务、回流重绘、JS 执行；③ **Lighthouse**——一键审计性能得分和优化建议；④ **Web Vitals**（LCP 最大内容渲染、FID 首次输入延迟、CLS 布局偏移）——核心用户体验指标。常见优化：CDN、资源压缩分包懒加载、图片优化、减少回流。

**追问 5：接口偶发性慢（时快时慢）怎么排查？**
> 答：偶发慢最难查，常见原因：① **GC 停顿**（JVM Full GC 导致间歇卡顿）→ 看 GC 日志；② **锁竞争**（高峰期锁等待）→ 看锁监控；③ **资源突发瓶颈**（CPU/连接池打满）→ 看资源监控；④ **DB 数据倾斜**（某些热点数据慢）；⑤ 缓存命中率波动（缓存击穿）。**靠持续监控 + 告警捕获慢的瞬间，再结合当时监控数据定位。**

## Q14. RESTful API 设计有哪些规范和最佳实践？

> **考察意图**：API 设计是全栈/后端的基本功。考察你的规范意识和工程素养。

### 14.1 核心规范

**① 资源用名词复数**：
```
GET    /users          # 查列表
GET    /users/123      # 查单个
POST   /users          # 新建
PUT    /users/123      # 全量更新
PATCH  /users/123      # 部分更新
DELETE /users/123      # 删除
GET    /users/123/orders  # 嵌套资源（用户的订单）
```

**② HTTP 动词语义**：

| 动词 | 语义 | 幂等性 | 安全性 |
|------|------|:---:|:---:|
| GET | 查询 | ✅ 幂等 | ✅ 安全（不改数据） |
| POST | 新建 | ❌ 不幂等 | ❌ |
| PUT | 全量更新 | ✅ 幂等 | ❌ |
| PATCH | 部分更新 | ❌（通常） | ❌ |
| DELETE | 删除 | ✅ 幂等 | ❌ |

> **幂等**：多次执行结果相同（如 DELETE 删两次，第二次没东西可删，结果一样）。

**③ 状态码**：
```
2xx 成功：200 OK / 201 Created / 204 No Content
3xx 重定向：301 / 302 / 304 Not Modified
4xx 客户端错：400 参数错 / 401 未认证 / 403 无权限 / 404 不存在 / 429 限流
5xx 服务端错：500 服务器内部错 / 502 网关错 / 503 不可用 / 504 网关超时
```

**④ 版本化**：`/v1/users`（URL 版本，最常见）/ Header 版本。

**⑤ 查询参数**：分页 `?page=1&size=20`、过滤 `?status=active`、排序 `?sort=-created_at`（- 降序）。

**⑥ 统一返回结构**：
```json
{
  "code": 0,           // 业务码，0=成功
  "message": "success",
  "data": { ... }      // 实际数据
}
```

### 14.2 高频追问

**追问 1：REST 和 RPC（如 gRPC）有什么区别？怎么选？**
> 答：**REST** 基于 HTTP + JSON，可读性好、通用、浏览器友好，适合对外 API/前后端交互；**RPC**（gRPC）基于 HTTP/2 + Protobuf，性能高、强类型、适合内部服务间高频调用。**对外/前端用 REST，内部微服务间高性能通信用 gRPC。** GraphQL 是第三种选择（前端按需取字段）。

**追问 2：RESTful 有什么缺点？**
> 答：① **过度/不足获取**（over/under-fetching）——固定返回结构，前端可能只要 2 个字段却返回 20 个（GraphQL 解决）；② **复杂操作难表达**——REST 是"资源+CRUD"，"批准订单""转账"这种动作型操作用 REST 表达别扭（常用 `POST /orders/123/approve` 妥协）；③ **多次请求**——需要关联数据时前端要发多个请求（BFF/GraphQL 缓解）；④ 无状态带来认证开销。

**追问 3：怎么处理批量操作和复杂查询？**
> 答：① 批量查询用 `GET /users?ids=1,2,3`；② 批量删除用 `DELETE /users?ids=1,2,3` 或 `POST /users/batch-delete`；③ 复杂查询参数化 `?status=active&role=admin&created_after=2024-01-01`；④ 特别复杂的可上 GraphQL 或专门的查询接口。**保持资源导向，特殊操作用子资源/动作端点妥协。**

**追问 4：API 怎么保证幂等？（防止重复提交）**
> 答：① **客户端生成唯一 requestId**，服务端记录已处理的 requestId，重复请求返回首次结果（**最通用**）；② **PUT/DELETE 天然幂等**；③ **唯一约束**（如订单号唯一）；④ **token 机制**（前端先获取一次性 token）；⑤ 状态机校验。**POST 类操作必须显式做幂等设计**（网络重试会导致重复创建）。

**追问 5：API 的认证授权怎么做？**
> 答：① **认证（你是谁）**——JWT（无状态、适合分布式）/ Session+Cookie（有状态）；② **授权（你能干嘛）**——RBAC（角色权限）/ ABAC（属性权限）；③ **传输安全**——HTTPS + Token 放 Header（`Authorization: Bearer <token>`）；④ **OAuth2**（第三方授权）；⑤ 敏感操作加二次验证。**认证解决身份，授权解决权限，两者都要。**
