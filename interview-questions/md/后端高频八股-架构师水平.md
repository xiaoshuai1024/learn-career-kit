### Q1. JVM 运行时内存区域怎么划分？JDK 8 为什么用元空间替换永久代？

> 考察：JVM 内存模型 · 难度 ⭐⭐⭐⭐ · 频率 ⭐⭐⭐⭐⭐

**【面试官问法】**
讲一下 JVM 运行时数据区。方法区和永久代、元空间是什么关系？JDK 8 为什么把永久代砍了？
变体：栈溢出和堆溢出，分别长什么样？怎么调？

**【一句话答案】**
运行时数据区分**线程私有**（程序计数器、虚拟机栈、本地方法栈）和**线程共享**（堆、方法区）两类；**方法区是 JVM 规范**，**永久代（PermGen）是 HotSpot 的旧实现**（固定上限易 OOM），**元空间（MetaSpace）是 JDK 8 的新实现**（改用本地内存，上限受机器内存约束）——换的核心动机是「永久代大小难调，元空间自动扩容、和 GC 解耦」。

**【深度解析】**

1. **运行时数据区全景**：

   | 区域 | 线程 | 存什么 | 异常 | 关键参数 |
   |------|:----:|--------|------|----------|
   | 程序计数器 PC | 私有 | 当前线程执行字节码行号 | 唯一不会 OOM | — |
   | 虚拟机栈 | 私有 | 栈帧（局部变量表/操作数栈/动态链接/返回地址） | SOF / OOM | `-Xss`（默认 512K-1M） |
   | 本地方法栈 | 私有 | native 方法栈帧 | SOF / OOM | — |
   | 堆 Heap | 共享 | 对象实例 + 数组（GC 主战场） | OOM | `-Xms -Xmx` |
   | 方法区 | 共享 | 类信息/常量池/静态变量/JIT 代码 | OOM | JDK8 元空间 `-XX:MaxMetaspaceSize` |

2. **方法区 / 永久代 / 元空间三者关系**：
   ```
   JVM 规范：方法区 (Method Area) ← 纯抽象
        │
        ├── JDK 7 及之前：永久代 PermGen (在堆里，固定上限 MaxPermSize)
        │      问题：①字符串常量池易 OOM；②GC 效率低；③大小难预估
        │
        ├── JDK 7 过渡：符号引用、静态变量迁出永久代到堆
        │
        └── JDK 8 至今：元空间 MetaSpace (用本地内存 Native Memory)
              好处：①上限=机器内存，难 OOM；②和堆 GC 解耦；③类卸载更干净
   ```

3. **为什么换元空间（核心 3 点）**：
   - **OOM 概率**：永久代有 `MaxPermSize` 上限，加载类多（动态生成、Spring 大量 Bean）就 `java.lang.OutOfMemoryError: PermGen space`；元空间用本地内存，默认无上限（生产建议显式设 `MaxMetaspaceSize` 防把机器内存吃光）。
   - **调参负担**：永久代大小和业务类数量强相关，每个应用都要单独调；元空间自动扩容，省心。
   - **JRockit 合并**：Oracle 把 JRockit 的优秀 GC 合并进 HotSpot，JRockit 本来就没有永久代，统一架构。

4. **堆内分代**：
   ```
   堆 = 新生代(1/3) + 老年代(2/3)
   新生代 = Eden(8/10) + Survivor0(1/10) + Survivor1(1/10)
   对象先分配在 Eden，Minor GC 后存活进 Survivor，年龄+1
   年龄达 15(-XX:MaxTenuringThreshold) 或 Survivor 装不下 → 进老年代
   ```

**【边界场景 / 陷阱】**

- **大对象直接进老年代**：`-XX:PretenureSizeThreshold` 控制超过多大直接进老年代（避免在新生代来回复制）。
- **元空间也会 OOM**：虽然用本地内存，但不断加载新类（如动态代理、Groovy 脚本、CGLIB）不卸载，照样 `OutOfMemoryError: Metaspace`。典型场景：频繁热部署。
- **栈深度**：递归无出口 → `StackOverflowError`（SOF）；不断开新线程 → 栈总占用超限 → `OOM`。
- **直接内存**：NIO 的 `DirectByteBuffer` 走堆外内存，不归堆管，由 `-XX:MaxDirectMemorySize` 控制，Netty/Kafka 大量用。

**【常见追问】**

- **Q：为什么 Survivor 是两个，不是一或三？**
  A：一个的话 Eden 和 Survivor 没法用复制算法（需要一块空的作为 To 区）。两个保证任何时候都有一个空的 To 区接收复制；三个是浪费，回收率没提升。
- **Q：对象一定分配在堆上吗？**
  A：不一定。**逃逸分析**（`-XX:+DoEscapeAnalysis`）证明对象不逃逸出方法/线程，会**栈上分配**（栈帧弹出即回收，省 GC）或**标量替换**（拆成基本类型直接放栈）。某头部电商这种性能敏感系统会刻意让短生命周期对象不逃逸。
- **Q：JIT（Just-In-Time 即时编译）代码存在哪？**
  A：方法区（元空间里有 Code Cache，`-XX:ReservedCodeCacheSize`）。热点方法被 C1/C2 编译成本地机器码缓存，解释执行 → 编译执行的切换是 JVM 性能关键。

**【易错点】**

- **方法区 ≠ 永久代**：方法区是规范，永久代/元空间是实现。说「方法区在永久代里」是 JDK7 及之前的口误。
- **字符串常量池位置**：JDK7 起从永久代移到了**堆**（不是元空间！）。`String.intern()` 在 JDK7+ 可以存堆里已存在的引用。
- **元空间在堆外**：元空间用本地内存，**不在堆**里，`-Xmx` 管不到它。

**【速记口诀】**
堆栈计元本，私有共享两半分；永久代换元空间，本地内存免调参；常量池 JDK7 搬进堆，元空间不在堆里存。

**【某创业项目 / 某头部电商实战关联】**
某头部电商线上把 `-Xms` 和 `-Xmx` 设成相等（避免运行期堆扩容抖动），元空间显式设 `MaxMetaspaceSize=512m` 防热部署泄漏吃光机器内存。某创业项目资金链路里，分润计算的短生命周期中间对象做了方法内联不逃逸优化（逃逸分析 + 栈上分配），减少老年代压力。诚实边界：超 32G 大堆的 ZGC 生产实践有限。

### Q2. 一个对象从创建到回收，完整经历什么？对象内存布局是怎样的？

> 考察：对象生命周期 + 内存布局 · 难度 ⭐⭐⭐⭐ · 频率 ⭐⭐⭐⭐

**【面试官问法】**
`new Object()` 在 JVM 里到底发生了什么？对象的内存是怎么布局的？指针压缩是什么，为什么堆超过 32G 反而可能变慢？

**【一句话答案】**
对象创建 5 步：**类加载检查 → 分配内存 → 内存零值 → 设置对象头 → 执行 `<init>`**；内存布局 3 部分：**对象头（Mark Word + Klass Pointer）+ 实例数据 + 对齐填充**；指针压缩（`UseCompressedOops`）把 8 字节指针压成 4 字节省内存，但**只在堆 < 32G 时生效**——超过 32G 指针变回 8 字节，对象变大反而更费内存、可能变慢（这是「堆超过 32G 性能拐点」的根因）。

**【深度解析】**

1. **对象创建 5 步**：
   ```
   ① 类加载检查：常量池定位类的符号引用，检查是否已加载/解析/初始化，没有则触发类加载
   ② 分配内存：在堆中划出一块确定大小的内存
      - 指针碰撞(Bump the Pointer)：内存规整 → 移动指针，Serial/ParNew 用
      - 空闲列表(Free List)：内存碎片 → 维护空闲块列表，CMS 用
      - 线程安全：CAS 失败重试 或 TLAB(-XX:+UseTLAB，每个线程预分配一小块)
   ③ 内存零值：除对象头外，内存空间初始化为零值（所以字段不赋值默认是 0/null）
   ④ 设置对象头：Mark Word(哈希/年龄/锁状态) + Klass Pointer(指向类元数据)
   ⑤ 执行 <init>：构造函数赋值、父类构造等
   ```

2. **对象内存布局**：
   ```
   ┌─────────────────────────────────────┐
   │ 对象头 (Object Header)              │
   │   ├── Mark Word (64bit)：哈希码/GC年龄/锁标志/偏向线程ID  │
   │   └── Klass Pointer (类型指针，指向 Class 元数据)         │
   ├─────────────────────────────────────┤
   │ 实例数据 (Instance Data)：字段值，父类字段在前            │
   ├─────────────────────────────────────┤
   │ 对齐填充 (Padding)：补齐 8 字节整数倍                    │
   └─────────────────────────────────────┘
   ```
   - 一个空 `Object` 在 64 位 JVM 开指针压缩后占 **16 字节**（12 字节头 + 4 字节填充）；不开压缩占 16 字节（头变 16）。
   - 数组对象头多 4 字节存 `length`。

3. **指针压缩（UseCompressedOops）**：
   - 64 位指针本来 8 字节，压缩成 4 字节（32 位寻址）。
   - **为什么能压缩**：对象默认 8 字节对齐，所以真实地址都是 8 的倍数，低 3 位永远是 0，存指针时右移 3 位（除以 8），4 字节能表示 `2^32 × 8 = 32G` 地址空间。
   - **拐点**：堆 **< 32G** 自动开启，省约 20-50% 内存；**≥ 32G** 自动关闭，指针回 8 字节，对象普遍变大，可能比 31G 堆占用更多内存——这就是「别把堆设成正好 32G，要么 31G 要么 48G+」的来源。

**【边界场景 / 陷阱】**

- **TLAB（Thread Local Allocation Buffer）**：默认开（`-XX:+UseTLAB`），每个线程在 Eden 预分配一小块，线程内分配无锁，是 `new` 极快的核心原因。
- **字段重排序**：JVM 会重排字段顺序以减少对齐填充（如把 long/double 放一起），`-XX:-RestrictContended` 涉及 `@Contended` 伪共享隔离（见并发章）。
- **finalize() 陷阱**：对象有 `finalize()` 会进 F-Queue，GC 要等 Finalizer 线程执行——拖慢回收，且只执行一次。JDK9+ 已废弃，别用。

**【常见追问】**

- **Q：怎么算一个对象占多少内存？**
  A：对象头 12 字节（开压缩）+ 字段（按类型）+ 对齐填充到 8 倍数。工具：`jol-core`（Java Object Layout）打印布局，`GraphLayout.parseInstance(obj).toFootprint()` 算总大小。
- **Q：为什么字段要内存对齐？**
  A：CPU 一次读 8 字节，未对齐要读两次再拼；对齐后一次读完。空间换时间。
- **Q：TLAB 用完了怎么办？**
  A：申请新的 TLAB（原子操作），或退回 Eden 公共区域用 CAS 分配。

**【易错点】**

- **指针压缩默认开（堆 < 32G）**，不是手动开。
- **Mark Word 内容随锁状态变化**（见 Q2 并发章锁升级），同一个 64bit 在无锁/偏向/轻量/重量级下复用。
- **对象头不存字段值**，字段值在实例数据区，别混淆。

**【速记口诀】**
创建五步查分零头造，头加数据加填充；指针压缩省一半，三十二 G 是拐点。

**【某创业项目 / 某头部电商实战关联】**
某创业项目统计中台曾用 `jol` 排查一个包装类数组内存占用（发现 Boolean 对象比 boolean 多 15 倍内存），改成基本类型数组 + 位压缩。某头部电商网关对象复用池（对象池化）减少高频 `new`，本质是控制 TLAB 外的分配。

### Q3. GC（垃圾回收）的核心原理？分代、GC Roots、三色标记分别是什么？

> 考察：GC 原理 · 难度 ⭐⭐⭐⭐⭐ · 频率 ⭐⭐⭐⭐⭐

**【面试官问法】**
JVM 怎么判断对象该回收？GC Roots 有哪些？三色标记听过吗，漏标怎么解决？为什么要有「安全点」？

**【一句话答案】**
判活用**可达性分析**从 **GC Roots** 出发遍历对象图；分代基于「朝生夕死」假设把堆分新生代/老年代用不同算法；并发标记用**三色标记（白/灰/黑）+ 写屏障**解决「漏标」；**安全点（Safepoint）**保证 GC 时所有线程在已知状态、栈不变，是 STW（Stop-The-World）能正确执行的前提。

**【深度解析】**

1. **判活算法：可达性分析 vs 引用计数**：
   - **引用计数**（Python 用）：对象被引用 +1，断开 -1，归零回收。**致命缺陷**：循环引用（A↔B）永远不归零 → JVM 不用。
   - **可达性分析**（JVM 用）：从 GC Roots 出发，能遍历到的活，遍历不到的死。

2. **GC Roots（4 类核心）**：
   ```
   ① 虚拟机栈中的局部变量表引用（方法内正在用的对象）
   ② 方法区中类的静态变量引用
   ③ 方法区中常量引用
   ④ 本地方法栈 JNI 引用
   补充：活动线程、内部引用（如 ClassLoader）、同步锁持有的对象
   ```

3. **分代假说与算法**：
   - **假说**：绝大多数对象朝生夕死（新生代）；老对象很难死（老年代）。
   - **新生代（复制算法）**：Eden+S0+S1，存活少，复制成本低，无碎片。
   - **老年代（标记-整理）**：存活多，复制贵，用标记-整理避免碎片（CMS 用标记-清除，所以有碎片）。
   - **跨代引用**：老年代引用新生代对象会让新生代 GC 时扫描整个老年代 → 用 **Remembered Set + 卡表（Card Table）**只记录「脏卡」，避免全扫。

4. **三色标记 + 写屏障（并发标记核心）**：
   ```
   白色：未访问（GC 结束仍白 = 垃圾）
   灰色：自己访问了，但引用还没扫完
   黑色：自己和引用都扫完（安全存活）

   并发标记时，业务线程还在改对象图，会产生「漏标」：
   漏标条件：① 黑色对象新增指向白色对象的引用  且  ② 灰色对象到白色对象的引用断开
   → 白色被误判为垃圾，回收了活对象！

   修复（破任一条件）：
   - 增量更新(Incremental Update)：CMS 用。黑→白新增时，记下这个黑对象，重新当灰扫一遍。
   - SATB(Snapshot At The Beginning)：G1 用。断开引用时，把白色快照下来，GC 结束当存活。
   两者都靠「写屏障 Write Barrier」在赋值时插桩记录。
   ```

5. **安全点（Safepoint）与安全区域**：
   - GC 需要 STW 时，不是立即停所有线程，而是等线程跑到**安全点**（方法调用、循环跳转等「长时间停留」的指令点）。
   - 安全点太少 → GC 等待时间长；太多 → 性能开销。`-XX:+PrintSafepointStatistics` 可看。
   - **安全区域（Safe Region）**：线程处于 sleep/blocked（无法跑到安全点）时，进入安全区域，GC 时认为这段代码不会改变引用关系。JNI、IO 阻塞靠它。

**【边界场景 / 陷阱】**

- **CMS 的 Concurrent Mode Failure**：并发回收时老年代满了 → 退化为 Serial Old 全堆 STW，停顿几秒，是 CMS 被弃用的核心痛点。
- **安全点偏向**：JDK10 前，计数循环（`int i=0; i<Big; i++`）没有安全点，长循环会卡住其他线程等 GC（「safepoint bias」问题）。JDK10+ 给循环加了安全点。
- **跨代引用遗漏**：Minor GC 只扫新生代 + 卡表标记的老年代脏卡，漏掉就会漏回收——卡表必须及时更新。

**【常见追问】**

- **Q：可达性分析里「不可达」的对象一定会立刻回收吗？**
  A：不一定。还有**引用强度**四级：强引用（永不回收）→ 软引用（`SoftReference`，内存不足回收，适合缓存）→ 弱引用（`WeakReference`，下次 GC 必回收，ThreadLocal/WeakHashMap）→ 虚引用（`PhantomReference`，跟踪对象回收，必须配合队列）。
- **Q：CMS 为什么用标记-清除不整理？**
  A：整理要移动对象、更新所有引用，STW 久。CMS 追求低停顿，宁可碎片也不整理，用 `-XX:CMSInitiatingOccupancyFraction` 提前触发 + 浮动垃圾容忍。
- **Q：G1 的 Remembered Set 为什么耗内存？**
  A：每个 Region 维护「谁引用我」，可能占堆 5-20%。这是 G1 小堆（<4G）不如 Parallel 的原因。

**【易错点】**

- **GC Roots 不是「所有引用」**，是有限的 4-5 类根。栈里局部变量是根，但堆里对象不是。
- **三色「漏标」是误回收活对象**（更严重），不是「标记了垃圾」。
- **安全点 ≠ 全停**，是「线程自愿停的检查点」。

**【速记口诀】**
可达分析判死活，GC Roots 四类根；分代基于朝生夕，复制整理各分区；三色漏标写屏障，增量更新 SATB；安全点停保一致，长循环会卡 GC。

**【某创业项目 / 某头部电商实战关联】**
某头部电商网关曾出现「GC 安全点等待过长」问题——某个统计接口的 `for` 循环千万次没安全点（JDK8），导致全局 STW 抖动，加 `-XX:+UseCountedLoopSafepoints`（或升 JDK11）解决。某创业项目用 `SoftReference` 做模板缓存，内存紧时自动让出。

### Q4. 垃圾收集器怎么演进和选型？G1 / ZGC / Shenandoah 各自原理？

> 考察：收集器选型 · 难度 ⭐⭐⭐⭐⭐ · 频率 ⭐⭐⭐⭐

**【面试官问法】**
Parallel / CMS / G1 / ZGC 各自什么特点？你们生产用什么、为什么？G1 怎么做到可预测停顿的？ZGC 又怎么做到亚毫秒停顿？

**【一句话答案】**
收集器演进主线是「**降低停顿、支撑更大堆**」：Parallel（吞吐优先）→ CMS（低停顿但有碎片）→ G1（Region 化、可预测停顿，4-32G 主流）→ ZGC/Shenandoah（并发整理、亚毫秒停顿、大堆）。**选型经验**：堆 < 4G 用 Parallel，4-32G 用 G1（JDK9+ 默认），> 32G 或对延迟极敏感用 ZGC（JDK15+ 生产可用）。

**【深度解析】**

1. **收集器演进对照**：

   | 收集器 | 分代 | 算法 | 并发 | 停顿 | 适用 | JDK 状态 |
   |--------|:----:|------|:----:|------|------|----------|
   | Serial / Serial Old | 有 | 复制/整理 | 否 | 长 | 单核、小堆 | 保留 |
   | ParNew / Parallel Scavenge | 有 | 复制 | 并行 | 中 | 多核吞吐 | 保留 |
   | CMS | 有 | 标记清除 | 并发标记 | 低(100ms级) | 低延迟中堆 | JDK9 弃用，JDK14 移除 |
   | **G1** | Region | 整体标记整理/局部复制 | 并发标记 | 可预测(默认200ms) | **4-32G 主流** | **JDK9 默认** |
   | **ZGC** | Region(着色) | 染色指针+读屏障 | 并发整理 | **<1ms(不随堆增长)** | 大堆/超低延迟 | JDK15 生产 |
   | Shenandoah | 有 | 读屏障(Brooks 转发指针) | 并发整理 | <10ms | 大堆/低延迟 | JDK12+ (RedHat) |

2. **G1 核心原理（Region 化 + 可预测停顿）**：
   ```
   G1 把堆切成 2048 个左右的 Region(1-32M，2 的幂)，每个 Region 动态归属：
   Eden / Survivor / Old / Humongous(大对象专属，占多个连续 Region)

   可预测停顿模型：
   - 用户设 -XX:MaxGCPauseMillis=200 (期望停顿 200ms)
   - G1 维护每个 Region 的「回收价值」(垃圾比例 × 预计耗时)
   - GC 时按价值排序，在 200ms 预算内回收价值最高的 Region(这就是 Garbage First 名字来源)
   - 混合回收(Mixed GC)：不只回收新生代，连同部分老年代 Region 一起回收
   ```

3. **ZGC 核心原理（染色指针 + 读屏障）**：
   ```
   ZGC 在 64 位指针的高位塞进「颜色位」(Marked0/Marked1/Remapped/Finalizable)
   转移对象时，不立即更新所有引用，而是：
   - 并发转移：拷贝对象到新 Region，旧指针的「颜色位」标记为待更新
   - 读屏障：每次读引用时检查颜色，若过期则「自愈」转发到新地址
   → 转移与应用线程并发进行，STW 只在极短的初始标记/再标记阶段(<1ms)
   → 停顿与堆大小无关（10G 和 10T 堆停顿都是亚毫秒）
   ```

4. **Shenandoah**：用 Brooks 转发指针（每个对象头多一个指针指向自己或副本），也是并发整理，思路和 ZGC 类似但实现不同，RedHat 维护，OpenJDK 可用。

**【边界场景 / 陷阱】**

- **G1 不是银弹**：小堆（<4G）G1 的 Remembered Set 开销 + Region 管理成本 > 收益，Parallel 更快。
- **ZGC 的代价**：吞吐量比 G1 低约 10-15%（读屏障开销），内存占用高；适合「延迟第一」场景（交易、实时）而非「吞吐第一」。
- **CMS 浮动垃圾**：并发标记期间产生的新垃圾这次回收不掉，叫浮动垃圾，需容忍。

**【常见追问】**

- **Q：G1 怎么触发 Full GC？**
  A：Mixed GC 跟不上、疏散失败（Evacuation Failure，To 空间不够）、Metaspace 不足 → 退化为单线程 Serial Full GC（STW 很长，生产要避免）。监控关键：避免 Humongous 对象、合理设 `-XX:InitiatingHeapOccupancyPercent`（默认 45%）。
- **Q：ZGC 为什么停顿不随堆增长？**
  A：因为对象转移是**并发**的（业务线程同时跑），STW 阶段只做「标记根集合」这种与堆大小弱相关的工作。堆再大，根集合大小（线程数 × 栈帧）也不大。
- **Q：生产 G1 怎么调？**
  A：①`-XX:MaxGCPauseMillis=200`；②`-XX:G1HeapRegionSize` 按堆算（4G→2M，16G→4M，32G→8M）；③`-XX:InitiatingHeapOccupancyPercent=35-45` 提前触发混合回收；④监控避免 Humongous（对象 > Region 一半就是大对象）。

**【易错点】**

- **G1 停顿是「预测」不是「保证」**，200ms 是目标，实际可能超。
- **ZGC/JDK 版本**：ZGC 在 JDK11 是实验性（`-XX:+UnlockExperimentalVMOptions`），JDK15 转正，JDK16 默认并发线程数自适应。
- **Parallel 和 ParNew 不同**：ParNew 配 CMS（老年代），Parallel Scavenge 配 Parallel Old，两者年轻代收集器并行实现不同，不能混搭。

**【速记口诀】**
吞吐用 Parallel，低延迟 CMS 已退；四到三十二 G 选 G1，Region 化可预测；大堆超低延 ZGC，染色指针读屏障。

**【某创业项目 / 某头部电商实战关联】**
某头部电商交易系统 JDK11 + G1（堆 16G，Region 4M，停顿目标 100ms），避免 CMS 碎片导致的 Concurrent Mode Failure。某创业项目创业期堆小（4G），用 Parallel 更划算。诚实边界：ZGC 生产未大规模落地，原理和选型讲得清。

### Q5. G1 的停顿预测模型、Remembered Set、混合回收具体怎么工作？

> 考察：G1 原理深度 · 难度 ⭐⭐⭐⭐⭐ · 频率 ⭐⭐⭐⭐

**【面试官问法】**
G1 怎么做到「在 200ms 内回收价值最高的 Region」？卡表（Card Table）和 Remembered Set 在 G1 里怎么用？Mixed GC 的触发条件是什么？

**【一句话答案】**
G1 维护每个 Region 的**回收成本模型**（基于历史 GC 数据预测回收耗时），按「回收价值 = 垃圾量 ÷ 预测耗时」排序，在用户设定的停顿预算内贪心选取 Region 回收；跨 Region 引用靠**卡表定位脏卡 + Remembered Set 记录「谁引用我」**，避免全堆扫描；**Mixed GC** 在老年代占用超 `IHOP`（默认 45%）时触发，连同新生代一起回收部分老年代 Region。

**【深度解析】**

1. **停顿预测模型**：
   ```
   G1 在每次 GC 时统计：
   - 每个 Region 的 GC 时间样本(RSet 扫描耗时、复制耗时)
   - 维护衰减均值(衰减因子 0.7~0.9，近期数据权重高)
   GC 决策时：
   candidates = 所有可回收 Region 按价值(垃圾字节/预测成本)降序
   while (累计预测耗时 < MaxGCPauseMillis 且还有 candidate):
       选下一个 Region 加入本次回收集合(CSet, Collection Set)
   → 在预算内贪心选收益最高的，实现「可预测停顿」
   ```

2. **卡表（Card Table）+ Remembered Set**：
   ```
   问题：Minor GC 只扫新生代，但老年代→新生代的引用让新生代对象「假活」
   暴力解：扫整个老年代 → 慢
   G1 解：
   - 卡表：堆按 512B 切成 Card，写老年代→新生代引用时，写屏障把该 Card 标「脏」
   - PRT(Per-Region Table)：每个 Region 维护 RSet，记录「哪些其他 Region 引用了我」
   - Minor GC 只扫新生代 + RSet 指向新生代的脏卡，O(新生代+脏卡) 而非 O(全堆)
   代价：RSet 占堆 1-20% 内存（堆越大占比越高），是 G1 内存开销大头
   ```

3. **Mixed GC（混合回收）流程**：
   ```
   ① 触发：老年代占用 > IHOP(-XX:InitiatingHeapOccupancyPercent，默认45%)
   ② 初始标记(STW，搭一次 Minor GC 的便车)：标记 GC Roots 直接引用
   ③ 并发标记：与业务并发，遍历对象图，SATB 写屏障处理漏标
   ④ 最终标记(STW)：处理 SATB 缓冲区
   ⑤ 筛选回收(STW)：按价值选 CSet(新生代全部 + 部分老年代 Region)，复制存活对象到空 Region
   → 这一步回收了「新生代 + 一部分老年代」，故名 Mixed
   ```
   `-XX:G1MixedGCCountTarget=8`：把老年代回收分 8 次 Mixed GC 完成，避免一次太久。

**【边界场景 / 陷阱】**

- **Humongous 对象**：> Region 一半的对象占多个连续 Region，直接进老年代且易引发 Full GC。大对象多的场景要调大 Region size 或避免（如分片处理大数组）。
- **RSet 内存膨胀**：引用关系复杂时 RSet 可能占 20%+ 堆，监控 `-XX:G1SummarizeRSetStats`。
- **Evacuation Failure**：复制存活对象时 To Region 不够 → 退化为 Full GC（长 STW）。调大堆或降低 IHOP 提前回收。

**【常见追问】**

- **Q：G1 的 Full GC 还能并发吗？**
  A：不能。G1 的 Full GC 是单线程 Serial（JDK10 前）/ 多线程 Parallel（JDK10+），是兜底，STW 很长。生产要靠调参避免触发。
- **Q：IHOP 设多少？**
  A：默认 45%。老年代涨得快的应用调低（35%）提前回收；RSet 大的应用调高（50%）减少回收频率。JDK9+ 有自适应 IHOP（`-XX:+G1UseAdaptiveIHOP`）。
- **Q：G1 怎么处理大对象？**
  A：> Region/2 的对象是 Humongous，占连续 Region，直接在老年代分配。建议控制对象大小 < Region/2，或调大 Region size。

**【易错点】**

- **CSet 在 Mixed GC 包含「全部新生代 + 部分老年代」**，不是只回收老年代。
- **RSet 记录的是「谁引用我」（入边）**，不是「我引用谁」（出边）——方向别记反。
- **SATB 是「开始时快照」**，并发标记期间新产生的对象（浮动垃圾）这次不回收。

**【速记口诀】**
价值排序贪心选，预算内收最高 Region；卡表标脏 RSet 找入边，混合回收新生加部分老。

**【某创业项目 / 某头部电商实战关联】**
某头部电商网关曾因 Humongous 对象（每次请求拼一个大 JSON 缓冲）频繁触发 Mixed GC，改成流式分片写后 GC 停顿从 200ms 降到 50ms。这是「数据结构选型直接影响 GC」的典型案例。

### Q6. 类加载机制？双亲委派是什么？为什么要打破、怎么打破？

> 考察：类加载 · 难度 ⭐⭐⭐⭐ · 频率 ⭐⭐⭐⭐⭐

**【面试官问法】**
类加载的完整流程？什么是双亲委派模型？为什么 Tomcat 要打破它？SPI（如 JDBC）又是怎么打破的？

**【一句话答案】**
类加载 7 步：**加载→验证→准备→解析→初始化**（使用/卸载不算加载阶段）；**双亲委派**是「子加载器先委托父加载器加载，父加载不到再自己加载」，保证**核心类（如 java.lang.Object）只被 Bootstrap 加载、不会被用户类篡改**；打破场景三例——**SPI**（Bootstrap 加载接口但实现是用户 jar，用线程上下文类加载器反向委托）、**Tomcat**（每个 webapp 独立类加载器实现应用隔离）、**热部署**（OSGi/JRebel 丢弃旧类重加载）。

**【深度解析】**

1. **类加载流程**：
   ```
   加载 Loading    ：通过类全限定名获取字节流(从 jar/网络/动态生成)，生成 Class 对象
   验证 Verification：字节码格式/元数据/符号引用检查(防恶意字节码)
   准备 Preparation ：静态变量分配内存并赋零值(注意：final 常量在此赋初值)
   解析 Resolution  ：常量池符号引用 → 直接引用(可选，延迟到首次使用)
   初始化 Init      ：执行 <clinit>，即静态变量赋值 + static 块
   ```
   `<clinit>` 由编译器按源码顺序收集 static 赋值和 static 块生成，**线程安全**（JVM 保证只执行一次，多线程初始化会阻塞）。

2. **双亲委派模型**：
   ```
   BootstrapClassLoader(加载 $JAVA_HOME/lib，rt.jar 的核心类如 java.lang.*)
        ↑ 委托
   ExtClassLoader/PlatformClassLoader(JDK9+, 加载 ext 或 jdk 内置模块)
        ↑ 委托
   AppClassLoader(加载 classpath，即你的应用 jar)
        ↑ 委托
   自定义 ClassLoader

   加载顺序：收到请求 → 先委派父加载器 → 父加载不到(抛 ClassNotFoundException) → 自己加载
   ```
   **意义**：①**安全**（java.lang.Object 只被 Bootstrap 加载，用户写的 java.lang.Hack 被忽略）；②**避免重复加载**（同一个类只会被加载一次）。

3. **为什么要打破 + 打破方式**：

   | 场景 | 原因 | 打破方式 |
   |------|------|----------|
   | **SPI（JDBC 等）** | 接口在 rt.jar 由 Bootstrap 加载，但实现（mysql-connector）在 classpath 由 App 加载，Bootstrap 看不到实现 | **线程上下文类加载器（TCCL）**：`Thread.currentThread().getContextClassLoader()` 让父类加载器反向用子类加载器加载实现 |
   | **Tomcat** | 多个 webapp 同名类要隔离，不能都用 AppClassLoader | **自定义 WebappClassLoader**：每个 webapp 一个，**先自己加载（部分打破）**，实现 `WEB-INF/classes` 优先 |
   | **OSGi / 热部署** | 模块化、不停机更新类 | **网状类加载**：每个模块一个加载器，按规则互相委托，丢弃旧加载器即卸载 |

4. **Tomcat 类加载器层次（打破双亲委派的核心案例）**：
   ```
   Bootstrap → Ext → App → Common(共享) → Catalina(Tomcat 自身)
                                  └── WebappClassLoader1(webapp1)  ← 打破：先查 WEB-INF/classes 再委派父
                                  └── WebappClassLoader2(webapp2)
   - Common 加载 $CATALINA_HOME/lib，所有 webapp 共享
   - WebappClassLoader 各自独立，实现应用隔离(同名类互不影响)
   - 但 java.lang.* 等核心类仍走双亲委派(不可打破底线)
   ```

**【边界场景 / 陷阱】**

- **打破有底线**：`java.*` 等核心包永远走双亲委派（JVM 强制），打破的是用户类。
- **热部署的类卸载难题**：`ClassLoader` 卸载的条件是该加载器加载的所有类都不再被引用—— leaking 引用导致 PermGen/Metaspace OOM 是热部署经典坑。
- **`<clinit>` 死锁**：静态块里互相初始化对方（A 的 static new B()，B 的 static new A()）可能死锁。

**【常见追问】**

- **Q：怎么自定义 ClassLoader 打破双亲委派？**
  A：继承 `ClassLoader`，**重写 `loadClass`（而不是 `findClass`）**——`loadClass` 是委派逻辑，`findClass` 是查找逻辑。重写 `loadClass` 不调 `super.loadClass` 即可先自己加载。Tomcat 的 WebappClassLoader 就是重写 `loadClass`。
- **Q：JDBC 的 Driver 怎么被加载的？**
  A：`DriverManager`（在 rt.jar，Bootstrap 加载）调用时用 **TCCL** 拿到 AppClassLoader，去 `ServiceLoader.load(Driver.class)` 扫 `META-INF/services` 找实现类。这就是 SPI 机制。
- **Q：一个类的「相等」用什么判断？**
  A：`instanceof` 看类对象，但 `Class.equals` / `Class.forName` 比较时，**同一个类被不同 ClassLoader 加载是两个不同的 Class**。这是 Tomcat 隔离的原理，也是「类转换异常 ClassCastException」的常见根因。

**【易错点】**

- **重写 `findClass` 不打破双亲委派**（只是自定义查找，仍先委派）；**重写 `loadClass` 才打破**。
- **准备阶段赋零值**，`static int a = 10` 在准备阶段 a=0，初始化阶段才 a=10；但 `static final int a = 10`（常量）在准备阶段就 a=10。
- **JDK9 模块化**后 ExtClassLoader 改名 PlatformClassLoader，且用模块系统，但双亲委派本质不变。

**【速记口诀】**
加载验准解初五步走，双亲委派父优先；核心类不可破底线，SPI 用上下文，Tomcat 各 webapp，热部署丢老类。

**【某创业项目 / 某头部电商实战关联】**
某创业项目支持多租户插件化扩展，参考 Tomcat 思路给每个租户的自定义插件独立 ClassLoader 实现隔离。某头部电商热部署场景踩过 Metaspace OOM（旧类加载器泄漏），加 `MaxMetaspaceSize` + 监控解决。

### Q7. 线上 OOM 怎么排查？内存泄漏怎么定位？

> 考察：OOM 排查方法论 · 难度 ⭐⭐⭐⭐⭐ · 频率 ⭐⭐⭐⭐⭐

**【面试官问法】**
线上服务突然 OOM 重启了，你怎么排查？内存泄漏怎么定位到是哪段代码？你用过哪些工具？

**【一句话答案】**
排查 OOM 三板斧：**①拿到堆 dump（`-XX:+HeapDumpOnOutOfMemoryError` 自动 dump 或 Arthas/jmap 手动 dump）→ ②用 MAT（Memory Analyzer Tool）分析支配树（Dominator Tree）找内存占用最大的对象 → ③结合 GC Roots 引用链定位是谁持有的引用没释放**。常见泄漏四类：**集合只进不出、静态容器持有、ThreadLocal 未 remove、连接/流未关**。

**【深度解析】**

1. **OOM 类型与定位（先分清是哪种 OOM）**：

   | OOM 类型 | 根因 | 排查方向 |
   |----------|------|----------|
   | `Java heap space` | 堆内存不够/内存泄漏 | 堆 dump 找大对象 |
   | `GC overhead limit exceeded` | GC 花费 >98% 时间回收 <2% 内存 | 内存泄漏濒临，同上 |
   | `Metaspace` | 加载类太多/类加载器泄漏 | 看动态代理/CGLIB/热部署 |
   | `Direct buffer memory` | NIO 直接内存泄漏 | 看 ByteBuffer/Netty |
   | `unable to create new native thread` | 线程数太多/栈太大 | 查线程泄漏、调 `-Xss` |
   | `StackOverflowError` | 递归过深 | 看栈 |

2. **排查标准流程**：
   ```
   ① 拿现场：OOM 时自动 dump
      JVM 参数：-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/data/dump/
      手动 dump：jmap -dump:format=b,file=heap.hprof <pid>
      或 Arthas：heapdump /data/heap.hprof

   ② 看指标(有没有真的内存涨)：
      jstat -gcutil <pid> 1000  看 OU(老年代使用率) 是否持续涨不降
      Arthas dashboard 看 GC 次数/耗时

   ③ 分析 dump(MAT 主力)：
      - Histogram：按类统计对象数和大小，看哪个类对象异常多
      - Dominator Tree：支配树，找「保留堆大小(Retained Heap)」最大的对象
      - Path To GC Roots：看谁持有这个对象(为什么没被回收)
      - Leak Suspects：MAT 自动猜的泄漏点

   ④ 结合代码定位：拿着引用链找代码，通常是某个 Map/List 只 put 不 remove
   ```

3. **常见内存泄漏模式**：

   | 模式 | 典型代码 | 修复 |
   |------|----------|------|
   | **静态集合持有** | `static Map<K,V> cache` 只 put 不 remove | 用 `WeakHashMap` / Guava Cache 设过期 / LRU |
   | **ThreadLocal 未 remove** | 线程池复用线程，ThreadLocal 残留 | `finally { tl.remove(); }` |
   | **监听器未注销** | `addListener` 后没 `removeListener` | 成对调用 |
   | **连接/流未关** | InputStream/Connection 没 close | try-with-resources |
   | **内部类持有外部类** | 匿名内部类隐式持有 this | 改静态内部类 / 弱引用 |
   | **缓存无界** | 自建 HashMap 缓存无上限 | 加 LRU 淘汰 / Caffeine |

4. **MAT 关键概念**：
   - **Shallow Heap（浅堆）**：对象本身大小。
   - **Retained Heap（深堆/保留堆）**：对象被回收后能释放的总大小（含其支配的所有对象）——**这个才是排查重点**。
   - **Dominator Tree**：体现「谁支配谁」，支配者回收则被支配者全释放。

**【边界场景 / 陷阱】**

- **生产 dump 要谨慎**：`jmap -dump` 在大堆（>8G）上 STW 可达分钟级，生产建议用 `-XX:+HeapDumpOnOutOfMemoryError` 让 OOM 时自动 dump（反正都要挂），或 Arthas 在低峰期 dump。
- **OOM 不一定是泄漏**：可能是瞬时流量打爆（一次查 10 万条数据加载进内存）——这种调小批次/分页即可，不是泄漏。
- **ThreadLocal + 线程池是经典坑**：线程池线程复用，ThreadLocal 的 value 持有大对象不释放，线程越多泄漏越严重。某创业项目资金链路用线程池时强制 `finally remove`。

**【常见追问】**

- **Q：Arthas 怎么用？**
  A：`java -jar arthas-boot.jar` attach 到进程。常用：`dashboard`(总览)、`thread`(线程)、`jad`(反编译)、`watch`(方法出入参)、`trace`(调用链耗时)、`profiler`(火焰图，`profiler start` / `profiler stop --format html`)。线上排查神器，无侵入。
- **Q：怎么监控内存趋势防止 OOM？**
  A：Prometheus + JMX Exporter 采 JVM 指标（堆使用率、GC 次数耗时、线程数），配告警（老年代 > 80% 持续 5 分钟）。某头部电商自研监控 + 鹰眼，某创业项目用 Prometheus + Grafana。
- **Q：内存溢出和内存泄漏的区别？**
  A：泄漏（Leak）= 对象不用了但还被引用无法回收，慢慢堆积；溢出（Overflow）= 内存不够（可能是泄漏导致，也可能是瞬时数据量大）。泄漏是慢性病，溢出是症状。

**【易错点】**

- **Retained Heap 比 Shallow Heap 重要**，排查看 Retained。
- **ThreadLocal 在线程池必须 remove**，不是设置 null 就行，要 `tl.remove()`。
- **OOM 时自动 dump 是生产标配**，别只靠手动 jmap（OOM 时进程已挂，来不及手动）。

**【速记口诀】**
OOM 先分堆元直连栈，自动 dump 是标配；MAT 支配树找大头，GC Roots 顺藤摸瓜；静态集合 ThreadLocal，连接未关是四害。

**【某创业项目 / 某头部电商实战关联】**
某头部电商生产必配 `-XX:+HeapDumpOnOutOfMemoryError`，OOM 自动 dump 到挂载盘。某创业项目踩过 ThreadLocal 泄漏（线程池 + 用户上下文对象未 remove），MAT 看到 `ThreadLocalMap` 占了 30% 堆，加 `finally remove` 解决。这是真实经历，面试可讲。

### Q1. JMM（Java Memory Model）是什么？happens-before 和内存屏障怎么理解？

> 考察：JMM · 难度 ⭐⭐⭐⭐⭐ · 频率 ⭐⭐⭐⭐⭐

**【面试官问法】**
讲一下 Java 内存模型。为什么多线程会有可见性问题？happens-before 是什么？内存屏障有哪几种？

**【一句话答案】**
JMM 是一套规范，定义多线程下**主内存与工作内存的交互规则**，解决可见性、有序性、原子性（三大特性）；CPU 和编译器为了性能会**重排序**指令，happens-before 是 JMM 提供的「**跨线程操作顺序的保证**」（满足这 8 条规则的前操作对后操作可见）；**内存屏障**是 CPU 层禁止重排序的硬件指令，volatile/synchronized 靠它实现 happens-before。

**【深度解析】**

1. **JMM 的内存结构**：
   ```
   所有共享变量在主内存
   每个线程有自己的工作内存( CPU 缓存/寄存器的抽象)
   线程对变量的操作：先从主内存读到工作内存 → 修改 → 刷回主内存
   8 大原子操作：read/load/use/assign/store/write/lock/unlock
   问题：线程 A 改了工作内存没刷回主内存，线程 B 读到旧值 → 可见性问题
   ```

2. **三大特性**：
   - **原子性**：一个或多个操作不可分割。`synchronized`、`Lock`、原子类保证。
   - **可见性**：一个线程修改了共享变量，其他线程能立即看到。`volatile`、`synchronized`、`final` 保证。
   - **有序性**：程序执行顺序符合预期（防重排序）。`volatile`（禁止重排）、`synchronized`（加锁串行）保证。
   - **as-if-serial**：单线程下，不管怎么重排序，执行结果不能改变——所以单线程无感知。

3. **happens-before 8 大规则**（核心：前操作的结果对后操作可见）：
   ```
   ① 程序顺序规则：单线程内，代码顺序在前的操作 happens-before 后面的
   ② 监视器锁规则：unlock 操作 happens-before 后面对同一把锁的 lock
   ③ volatile 规则：volatile 写 happens-before 后面对该变量的读
   ④ 线程启动规则：Thread.start() happens-before 该线程的所有操作
   ⑤ 线程终止规则：线程所有操作 happens-before Thread.join() 返回
   ⑥ 线程中断规则：interrupt() 调用 happens-before 被中断线程检测到
   ⑦ 对象终结规则：构造函数执行结束 happens-before finalize()
   ⑧ 传递性：A happens-before B，B happens-before C，则 A happens-before C
   ```

4. **内存屏障（Memory Barrier）4 种**：
   ```
   LoadLoad：Load1; LoadLoad; Load2 → Load1 必须先于 Load2 完成
   StoreStore：Store1; StoreStore; Store2 → Store1 必须先于 Store2 刷回内存
   LoadStore：Load1; LoadStore; Store2 → Load1 先于 Store2
   StoreLoad：Store1; StoreLoad; Load2 → Store1 刷回且对其他处理器可见，才能 Load2
        ↑ 最强也最贵(全能屏障)，volatile 写末尾就插这个
   ```
   - **volatile 写**：前面插 StoreStore（禁止前面普通写与 volatile 写重排），后面插 StoreLoad（禁止与后面 volatile 读/写重排）。
   - **volatile 读**：后面插 LoadLoad + LoadStore。

**【边界场景 / 陷阱】**

- **happens-before ≠ 时间先后**：它是「可见性保证」的规则，不是物理时间顺序。A happens-before B 不代表 A 物理上一定先执行，只保证 A 的结果对 B 可见（如果 B 读 A 写的变量）。
- **volatile 不保证 i++ 原子**：i++ 是「读-改-写」三步，volatile 只保证可见和有序，三步之间可能被其他线程插入 → 用 `AtomicInteger` 或 `synchronized`。
- **final 的可见性**：构造函数内的 final 写 happens-before 对象引用被其他线程获取（前提是构造函数没把 this 逃逸）。

**【常见追问】**

- **Q：volatile 和 synchronized 怎么选？**
  A：volatile 适合「一写多读」的状态标志（如 boolean running），轻量（无锁）；synchronized 适合复合操作（读-改-写）。volatile 不阻塞，synchronized 会阻塞。
- **Q：为什么 StoreLoad 屏障最贵？**
  A：它要保证 Store 刷回主内存且对其他 CPU 全局可见后才能 Load，需要 CPU 刷新写缓冲 + 内存栅栏，开销最大。但也是最关键的全能屏障。
- **Q：指令重排会让单例失效吗？**
  A：会。见 Q3 DCL 单例——构造函数的赋值和对象引用发布可能重排，导致拿到未初始化完的对象。volatile 修饰实例禁止重排。

**【易错点】**

- **happens-before 是「可见性保证」不是「执行顺序」**。
- **volatile 不保证原子性**，只保证可见 + 有序。
- **8 大原子操作是 JMM 规范**，不是必须的 8 个 CPU 指令（实际 JVM 用屏障实现）。

**【速记口诀】**
主存工作八操作，可见有序加原子；happens-before 八规则，前操作对后可见；内存屏障四种拦，StoreLoad 最贵最强；volatile 可见有序，原子不保证。

**【某创业项目 / 某头部电商实战关联】**
某创业项目资金链路的「停机标志位」用 volatile（一写多读，主线程置 running=false，工作线程立即感知），比 synchronized 轻量。某头部电商全局配置热更新用 volatile + 双重检查，保证多线程读到最新配置。

### Q2. synchronized 的锁升级全过程？Mark Word 怎么变化？

> 考察：synchronized 原理 · 难度 ⭐⭐⭐⭐⭐ · 频率 ⭐⭐⭐⭐⭐

**【面试官问法】**
synchronized 是重量级锁吗？JDK 6 之后做了什么优化？讲一下锁升级的过程。偏向锁为什么在 JDK 15 被废弃？

**【一句话答案】**
JDK 6 后 synchronized 大幅优化，**不是上来就重量级**，而是按竞争程度**逐级升级**：无锁 → 偏向锁（单线程访问，CAS 记线程 ID）→ 轻量级锁（多线程交替，自旋 CAS）→ 重量级锁（激烈竞争，monitor 阻塞）；锁状态记录在**对象头 Mark Word** 里；JDK 15 逐渐废弃偏向锁（维护成本高、现代多线程竞争场景收益小）。

**【深度解析】**

1. **锁升级链**：
   ```
   无锁 → 偏向锁 → 轻量级锁 → 重量级锁
   （升级不可逆，降级只有在 safepoint 整体安全点检查时批量重偏向/撤销）

   偏向锁(Biased)：只有第一个线程访问，对象头 Mark Word 记下该线程 ID
                   → 下次该线程进入，CAS 比较 ID 相等即进入(几乎无开销)
                   → 出现第二个线程竞争 → 撤销偏向(等 safepoint) → 升级轻量级

   轻量级锁：多线程交替访问(无真并发)，栈帧 Lock Record + CAS
              → CAS 抢锁成功 → 持有；失败 → 自旋(自适应自旋)
              → 自旋超阈值/多核竞争激烈 → 升级重量级

   重量级锁：激烈竞争，基于 ObjectMonitor(C++)，未抢到的线程进 cxq/EntryList 阻塞(操作系统 mutex)
              → 用户态/内核态切换，开销大
   ```

2. **Mark Word 在各锁状态下的布局（64 位）**：

   | 锁状态 | 25bit | 31bit | 1bit | 4bit | 1bit(偏向标志) | 2bit(锁标志) |
   |--------|-------|-------|------|------|:--------------:|:------------:|
   | **无锁** | unused | hashCode | unused | 分代年龄 | 0 | 01 |
   | **偏向锁** | 线程 ID | epoch | unused | 分代年龄 | 1 | 01 |
   | **轻量级锁** | 指向栈中 Lock Record 的指针 | | | | | 00 |
   | **重量级锁** | 指向 ObjectMonitor 的指针 | | | | | 10 |
   | **GC 标记** | — | | | | | 11 |

3. **重量级锁的 ObjectMonitor**（HotSpot C++ 实现）：
   ```
   ObjectMonitor {
     _owner      // 持有锁的线程
     _cxq        // 刚进来的 contention 队列(单向)
     _EntryList  // 等待获取锁的线程(双向)
     _WaitSet    // 调用 wait() 后的线程队列
     _count      // 重入计数
   }
   流程：线程抢锁失败 → 进 cxq → (阻塞) → EntryList → owner 释放后唤醒 → 竞争 → 持有
   wait()/notify() 操作 _WaitSet
   ```

4. **JDK 15 废弃偏向锁的原因**：
   - 维护成本高（涉及 safepoint、对象头复杂状态）。
   - 现代应用多线程竞争普遍，偏向锁「撤销」开销反而成为负担。
   - `-XX:-UseBiasedLocking` JDK15 后默认关闭，JDK18 移除相关代码。

**【边界场景 / 陷阱】**

- **锁升级不可逆**：升级到重量级后不会自动降回轻量（除非 GC safepoint 批量处理）。
- **偏向锁撤销开销**：出现竞争时撤销偏向要等 safepoint，STW 一下，批量重偏向（`-XX:BiasedLockingBatchRebiasThreshold`）缓解。
- **自旋的代价**：轻量级锁自旋占 CPU，单核自旋纯浪费（没有其他线程能释放锁），所以自适应自旋会根据历史成功率动态调整。

**【常见追问】**

- **Q：synchronized 和 ReentrantLock 区别？**
  A：①synchronized 是关键字（JVM 层），ReentrantLock 是 API（AQS 实现）；②synchronized 自动释放，ReentrantLock 必须 `finally unlock`；③ReentrantLock 支持公平锁、可中断、多 Condition、超时；④synchronized 锁升级优化后性能接近，简单场景用 synchronized，高级功能用 ReentrantLock。
- **Q：synchronized 锁的是什么？**
  A：锁的是**对象**。同步方法锁 `this`，静态同步方法锁 `Class` 对象，同步块锁括号里的对象。所以两个线程访问同一对象的同步方法互斥，访问不同对象不互斥。
- **Q：为什么不要用 String/Integer 当锁？**
  A：String 有常量池（多个地方可能拿到同一对象）、Integer 有缓存（-128~127），用它们当锁可能被意外共享导致死锁或意外互斥。应该用 `private final Object lock = new Object()`。

**【易错点】**

- **synchronized 不是「上来就重量级」**，JDK6+ 有锁升级。
- **轻量级锁适用于「交替访问无真并发」**，激烈竞争直接重量级。
- **wait/notify 必须在 synchronized 块内**（操作的是 ObjectMonitor）。

**【速记口诀】**
无偏轻重四级升，竞争加剧逐级加；Mark Word 记状态，偏向单线记 ID，轻量自旋 CAS 抢，重量 monitor 阻塞挂。

**【某创业项目 / 某头部电商实战关联】**
某创业项目资金链路用 `private final Object lock` 做细粒度锁（分润账户锁），避免锁 String 常量池导致的意外互斥。某头部电商网关高并发场景监控 synchronized 升级到重量级的频率（JFR / Arthas），过高说明锁竞争激烈需拆分。

### Q3. volatile 原理？DCL（双重检查）单例为什么要 volatile？

> 考察：volatile + 指令重排 · 难度 ⭐⭐⭐⭐⭐ · 频率 ⭐⭐⭐⭐⭐

**【面试官问法】**
volatile 能干什么、不能干什么？双重检查锁的单例，为什么要加 volatile？不加会出什么问题？

**【一句话答案】**
volatile 保证**可见性**（写后立即刷主存、读前失效工作内存）和**有序性**（插入内存屏障禁止指令重排），但**不保证原子性**（i++ 仍不安全）；DCL 单例必须加 volatile，因为 `new Object()` 不是原子操作（分**分配内存→初始化→引用赋值**三步），指令重排可能把「引用赋值」排到「初始化」之前，导致另一个线程拿到**未初始化完的半成品对象**。

**【深度解析】**

1. **volatile 两大作用**：
   ```
   可见性：
   - 写：JMM 把工作内存值刷回主内存 + 发 StoreLoad 屏障 → 其他 CPU 缓存行失效
   - 读：JMM 把工作内存值失效 → 强制从主内存重新 load
   → 写完其他线程立即可见

   有序性：
   - 写前插 StoreStore 屏障，写后插 StoreLoad 屏障
   - 读后插 LoadLoad + LoadStore 屏障
   → 禁止编译器/CPU 对 volatile 变量相关的指令重排
   ```

2. **DCL 单例与指令重排（核心面试题）**：
   ```java
   public class Singleton {
       private static volatile Singleton instance;  // ← 为什么必须 volatile？
       public static Singleton getInstance() {
           if (instance == null) {                   // 第一次检查(无锁)
               synchronized (Singleton.class) {
                   if (instance == null) {           // 第二次检查(持锁)
                       instance = new Singleton();   // ← 问题在这
                   }
               }
           }
           return instance;
       }
   }
   ```
   `instance = new Singleton()` 在字节码层是三步：
   ```
   ① 分配对象内存               memory = allocate()
   ② 调用构造函数初始化对象       ctorInstance(memory)
   ③ 将 instance 指向该内存       instance = memory
   ```
   **重排风险**：步骤 ② 和 ③ 可能被重排序成「①→③→②」：
   ```
   线程 A 执行到 ③(已赋值，但还没初始化)，此时 instance != null 但对象未构造完
   线程 B 第一次检查 instance != null → 直接返回 → 用了半成品对象 → NPE 或数据错乱！
   ```
   **volatile 的作用**：在 `instance` 写操作后插 StoreLoad 屏障，禁止 ②③ 重排，保证对象完全构造好后才发布引用。

3. **为什么用 DCL 而不是直接 synchronized 整个方法？**
   - 直接 `synchronized getInstance()` 每次调用都加锁，性能差。
   - DCL 只在首次创建时加锁，后续读无锁——但要 volatile 防重排。
   - **更优方案**：静态内部类（**延迟初始化 holder**，JVM 保证类加载线程安全）或枚举单例（防反射破坏）。

**【边界场景 / 陷阱】**

- **volatile 不保证原子性**：`volatile int i; i++` 仍不安全（读-改-写三步）。要用 `AtomicInteger` 或加锁。
- **volatile 数组不保护元素**：`volatile int[] arr` 保证 arr 引用可见，但不保证 `arr[0]` 的修改可见。要用 `AtomicIntegerArray`。
- **DCL 在 JDK5 之前不安全**：JMM 在 JDK5 才完善，之前的 volatile 语义不够强。现代 JDK 已修复。

**【常见追问】**

- **Q：单例还有哪些实现？**
  A：①**饿汉式**（类加载即创建，简单但无延迟）；②**懒汉式+synchronized**（线程安全但慢）；③**DCL**（延迟+高效，需 volatile）；④**静态内部类 holder**（推荐，JVM 保证类初始化锁，天然线程安全 + 延迟）；⑤**枚举**（Effective Java 推荐，防反射和反序列化破坏）。
- **Q：volatile 和 CAS 配合能实现什么？**
  A：`AtomicInteger` 等原子类就是 **volatile（保证可见）+ CAS（保证原子）** 的组合。volatile 让值对其他线程可见，CAS 保证读-改-写原子。
- **Q：什么时候用 volatile？**
  A：①状态标志位（一写多读，如 boolean running）；②DCL 单例；③发布「安全发布」对象引用。

**【易错点】**

- **volatile 不保证原子性**是最常考的坑。
- **DCL 加 volatile 是为了「有序性」防重排**，不是可见性。
- **静态内部类单例不需要 volatile**（JVM 类加载机制保证）。

**【速记口诀】**
volatile 可见加有序，原子不保证 i++；DCL 三步分配初化赋值，二三重排拿半成品；写后 StoreLoad 屏障拦，对象构造完才发布。

**【某创业项目 / 某头部电商实战关联】**
某创业项目配置管理用静态内部类 holder 单例（比 DCL 更简洁安全）。某头部电商停机信号用 volatile boolean，优雅停机时置 false，工作线程立即感知退出。

### Q4. CAS 和 AQS 原理？ABA 问题怎么解决？

> 考察：CAS + AQS · 难度 ⭐⭐⭐⭐⭐ · 频率 ⭐⭐⭐⭐⭐

**【面试官问法】**
CAS 是什么？它有什么问题？AQS 怎么实现锁的？讲一下 CLH 队列。ReentrantLock 的公平和非公平区别？

**【一句话答案】**
**CAS（Compare-And-Swap，比较并交换）**是 CPU 原子指令（`cmpxchg`），「期望值==当前值则更新为新值」，是乐观锁和无锁编程的基石，但存在 **ABA 问题**（值从 A→B→A，CAS 误以为没变，用版本号 `AtomicStampedReference` 解决）；**AQS（AbstractQueuedSynchronizer）**是并发工具的模板框架，核心是 **`volatile int state` + CLH 变种双向队列**，ReentrantLock/Semaphore/CountDownLatch 都基于它。

**【深度解析】**

1. **CAS 原理**：
   ```
   CAS(V, expected, new)：V 是内存值，expected 期望值，new 新值
   if (V == expected)  V = new;  return true;   // 原子操作
   else return false;                            // 重试或放弃

   底层：Unsafe.compareAndSwapXxx → CPU 的 lock cmpxchg 指令(保证原子)
   JDK9+ 用 VarHandle 替代 Unsafe
   自旋 CAS：失败就循环重试(自适应自旋)，无锁但消耗 CPU
   ```

2. **CAS 三大问题与解决**：

   | 问题 | 描述 | 解决 |
   |------|------|------|
   | **ABA** | 值 A→B→A，CAS 以为没变过，实际中间变过 | 版本号：`AtomicStampedReference`（带 stamp）/ `AtomicMarkableReference`（带 boolean） |
   | **自旋开销** | 长时间 CAS 失败空转浪费 CPU | 限制自旋次数 + 退化为阻塞锁 |
   | **只能保证单变量原子** | 多变量无法一起 CAS | 用对象封装 + `AtomicReference`，或加锁 |

3. **AQS 核心**：
   ```
   AQS = volatile int state(同步状态) + CLH 变种 FIFO 双向队列(等待队列)

   state 语义因实现而异：
   - ReentrantLock：state=0 无锁，>0 持有，>1 重入次数
   - Semaphore：state=剩余许可数
   - CountDownLatch：state=剩余计数

   CLH(Craig, Landin, Hagersten) 队列变种：
   - Node 封装线程引用 + 等待状态 + 前驱后继
   - 抢锁失败的线程包装成 Node 入队，park 阻塞
   - 前驱释放锁后 unpark 后继，后者被唤醒重新竞争

   两种模式：
   - 独占 Exclusive：ReentrantLock，同一时刻一个线程(state 加减)
   - 共享 Shared：Semaphore/CountDownLatch，允许多线程(state 计数)
   ```

4. **AQS 模板方法模式**：
   ```
   AQS 定义了「如何入队、如何阻塞、如何唤醒」(模板)
   子类只需实现「如何获取/释放 state」(钩子)：
   - tryAcquire / tryRelease      (独占)
   - tryAcquireShared / tryReleaseShared  (共享)
   - isHeldExclusively
   
   ReentrantLock 的非公平 tryAcquire：
   ① CAS state 0→1，成功则设当前线程为 owner
   ② owner==当前线程，state++（重入）
   ③ 失败返回 false → AQS 入队阻塞
   ```

5. **公平 vs 非公平锁**：
   - **非公平锁**（默认）：tryAcquire 直接 CAS 抢，不管队列有没有人在等 → 吞吐高（减少线程切换），可能饿死等待线程。
   - **公平锁**：tryAcquire 先 `hasQueuedPredecessors()` 检查队列有无前驱，有则排队 → 不会饿死，但吞吐低（多一次检查 + 线程切换）。
   - ReentrantLock 默认非公平：`new ReentrantLock()` = `new ReentrantLock(false)`。

**【边界场景 / 陷阱】**

- **ABA 在什么场景真有害？**：栈/链表的复用场景（节点 A 出栈后被回收重用为新节点 A，CAS 误判）。普通计数场景 ABA 通常无害。资金/库存场景用版本号防 ABA。
- **CAS 自旋在高竞争下恶化**：多个线程同时 CAS，大部分失败空转，CPU 飙高。高竞争用 `LongAdder`（分段累加，见下）替代 `AtomicLong`。
- **AQS 队列是「CLH 变种」**，不是原版 CLH（原版是单向、自旋），AQS 改成双向 + park/unpark 阻塞。

**【常见追问】**

- **Q：synchronized 和 ReentrantLock 怎么选？**
  A：简单互斥用 synchronized（自动释放、JVM 优化好）；需要公平/可中断/超时/多 Condition/尝试获取用 ReentrantLock。生产优先 synchronized（够用且不易错），ReentrantLock 用于高级场景。
- **Q：CountDownLatch 和 CyclicBarrier 区别？**
  A：CountDownLatch 是「**一次性**」，N 个线程 countDown 后主线程 await 放行，**不可重置**；CyclicBarrier 是「**可循环**」，N 个线程互相等齐再一起走，**可 reset 重用**。前者是「主等从」，后者是「从等从」。
- **Q：LongAdder 为什么比 AtomicLong 快？**
  A：AtomicLong 高并发下所有线程 CAS 同一个 value，竞争激烈；LongAdder 分段（base + Cell[]），线程分散到不同 Cell 各自累加，最后 sum 合并，**空间换时间降低竞争**。高并发计数用 LongAdder。

**【易错点】**

- **CAS 只保证单变量原子**，多变量要加锁或 `AtomicReference` 封装。
- **AQS 是「框架」不是「锁」**，ReentrantLock 是基于 AQS 的实现。
- **非公平锁吞吐高**，因为允许「插队」减少线程切换。

**【速记口诀】**
CAS 比较交换原子操，ABA 用版本号挡；自旋空转费 CPU，单变量多变量加锁；AQS state 加 CLH 队，独占共享两模式；公平查前驱不饿死，非公平插队吞吐高。

**【某创业项目 / 某头部电商实战关联】**
某创业项目分润计数用 LongAdder（高并发累加分润次数），比 AtomicLong 吞吐高 3-5 倍。某头部电商库存扣减用 CAS + 版本号（防 ABA），扣减失败自旋重试 + 一定次数后退化为快速失败返回「库存不足」。资金场景绝不用裸 CAS，必有版本号兜底。

### Q5. ConcurrentHashMap 1.7 和 1.8 实现原理有什么区别？

> 考察：并发容器 · 难度 ⭐⭐⭐⭐⭐ · 频率 ⭐⭐⭐⭐⭐

**【面试官问法】**
ConcurrentHashMap 怎么保证线程安全？1.7 和 1.8 实现有什么不同？为什么 1.8 放弃分段锁？1.8 的链表转红黑树是怎么回事？

**【一句话答案】**
1.7 用**分段锁（Segment，继承 ReentrantLock）**，默认 16 段，每段一个独立 HashMap，锁粒度是段，并发度=段数；1.8 放弃分段锁，改成 **CAS + synchronized 锁单个桶（Node）**，锁粒度细化到桶，并发度大幅提升，且链表长度 ≥ 8 且数组 ≥ 64 时转**红黑树**（避免哈希冲突退化为 O(n)）。核心演进逻辑：**锁粒度从「段」细化到「桶」+ 数据结构优化（链表→树）**。

**【深度解析】**

1. **1.7 分段锁实现**：
   ```
   结构：ConcurrentHashMap → Segment[] (默认16) → 每个 Segment 内 HashEntry[]
   每个 Segment 继承 ReentrantLock，是独立的小 HashMap
   写操作：定位 Segment → Segment.lock() → 操作 → unlock()
   读操作：volatile 保证可见，大部分不加锁
   并发度 = Segment 数量(默认16，构造时定，不能动态扩)
   问题：①并发度固定16，大并发不够；②Segment 本身是数组，内存开销；③二次 hash 定位
   ```

2. **1.8 实现（CAS + synchronized + 红黑树）**：
   ```
   结构：Node[] table (去掉了 Segment)
   写操作(put)：
   ① 计算 hash 定位桶
   ② 桶为空 → CAS 插入(无锁)
   ③ 桶非空 → synchronized 锁住桶头节点 → 链表/树尾追加
   ④ 链表长度 ≥ 8 且 table.length ≥ 64 → 转红黑树(否则先扩容)
   
   并发度 = 桶数(随扩容增长)，远超 1.7 的 16
   锁粒度：单个桶，更细
   ```

3. **1.8 链表转红黑树**：
   ```
   阈值：链表长度 ≥ 8 且数组容量 ≥ 64 → 树化
        若数组 < 64，优先扩容不树化(小数组扩容比树化更划算)
   退化：红黑树节点 ≤ 6 → 退化回链表
   原因：哈希冲突严重时链表查找 O(n)，红黑树 O(logn)
   红黑树节点 TreeNode 占用大(TreeNode 含 prev/parent/left/right/red)，所以阈值设8(泊松分布下概率极低)
   ```

4. **1.8 的 size() 计算**：
   ```
   不用 1.7 的原子计数，而是：
   - baseCount + CounterCell[](分散计数，类似 LongAdder 思路)
   - size() 时累加，可能不精确(并发 put 中)
   - 高并发下 size 是「估算值」，强一致用 containsKey 判断
   ```

**【边界场景 / 陷阱】**

- **1.8 仍用 synchronized 而不是 ReentrantLock**：synchronized 在 JDK6+ 锁升级后性能不输 ReentrantLock，且内存占用小（无 AQS 队列），所以回归 synchronized。
- **HashMap 多线程死循环（1.7）**：1.7 HashMap 扩容时头插法会导致链表成环，get 时死循环 CPU 100%。1.8 改尾插法解决了，但 HashMap 仍非线程安全（数据丢失），并发必须用 ConcurrentHashMap。
- **ConcurrentHashMap 不允许 null key/value**：HashMap 允许。原因是多线程下 `containsKey` 和 `get` 之间有歧义（null 是没有还是值就是 null），无法区分。

**【常见追问】**

- **Q：ConcurrentHashMap 的 get 需要加锁吗？**
  A：不需要。Node 的 val 和 next 是 volatile，保证可见性；读不加锁，可能读到旧值（弱一致），但不会读到「部分构造」的对象。
- **Q：1.8 put 为什么桶为空用 CAS，非空用 synchronized？**
  A：桶为空用 CAS（乐观，无锁，快）；非空说明有竞争或已有元素，用 synchronized 锁桶头（保证该桶安全）。混合策略兼顾性能和正确性。
- **Q：为什么树化阈值是 8？**
  A：泊松分布下，哈希冲突链表长度达到 8 的概率约 0.00000006，几乎不会发生；真发生了说明哈希函数差或被攻击，树化兜底。退化阈值 6（留缓冲防抖动）。

**【易错点】**

- **1.8 不是「完全无锁」**，桶非空时用 synchronized。
- **null key/value 被 ConcurrentHashMap 禁止**。
- **size() 在并发下不精确**，强一致判断用 containsKey。

**【速记口诀】**
1.7 分段锁 Segment，默认十六并发锁；1.8 弃段锁单桶，CAS 加 synchronized；链表八树六退，数组六四才树化；get 无锁 volatile，size 估算不强求。

**【某创业项目 / 某头部电商实战关联】**
某创业项目统计中台用 ConcurrentHashMap 做在线用户会话表（key=userId，高并发读写），1.8 的细粒度锁扛住了峰值。强调：选 ConcurrentHashMap 不是「它快」，是「它线程安全」——HashMap 并发会丢数据和死循环，这是架构师必须守的底线。

### Q6. 线程池的执行流程？线程数怎么算？为什么阿里规约禁用 Executors？

> 考察：线程池 · 难度 ⭐⭐⭐⭐⭐ · 频率 ⭐⭐⭐⭐⭐

**【面试官问法】**
线程池的 7 个参数是什么？提交一个任务的执行流程？核心线程数怎么设置？为什么阿里规约禁止用 Executors.newFixedThreadPool？

**【一句话答案】**
线程池 7 参数：**corePoolSize、maximumPoolSize、keepAliveTime、unit、workQueue、threadFactory、handler**；执行流程：**核心线程未满→创建核心线程；满了→进队列；队列满→创建非核心线程到 max；max 满→触发拒绝策略**；线程数经验公式：**CPU 密集型 N+1，IO 密集型 2N 或 N×(1+等待时间/计算时间)**，但**最终靠压测**；阿里规约禁用 Executors 是因为 `newFixedThreadPool`/`newSingleThreadExecutor` 用**无界队列**（OOM 风险）、`newCachedThreadPool` 最大线程数 Integer.MAX_VALUE（线程数爆炸），必须用 `ThreadPoolExecutor` 手动建并明确队列上限和拒绝策略。

**【深度解析】**

1. **7 个参数**：
   ```
   ① corePoolSize        核心线程数(即使空闲也不回收，除非 allowCoreThreadTimeOut)
   ② maximumPoolSize     最大线程数(核心+非核心的上限)
   ③ keepAliveTime       非核心线程空闲存活时间
   ④ unit                时间单位
   ⑤ workQueue           任务队列
        - LinkedBlockingQueue(默认无界！)
        - ArrayBlockingQueue(有界)
        - SynchronousQueue(不存，直接交接，CachedThreadPool 用)
        - PriorityBlockingQueue(优先级)
   ⑥ threadFactory       线程工厂(命名线程，便于排查)
   ⑦ handler             拒绝策略
   ```

2. **执行流程（必背）**：
   ```
   提交任务 execute(task)：
   ① 当前线程数 < corePoolSize？→ 创建核心线程执行
   ② 否则 → 尝试加入 workQueue
   ③ 队列满 → 当前线程数 < maximumPoolSize？→ 创建非核心线程执行
   ④ 线程数已达 max → 触发拒绝策略 handler
   注意：核心线程满 → 先排队 → 再扩非核心 → 最后拒绝（先队列后扩容，不是先扩容）
   ```

3. **4 种拒绝策略**：

   | 策略 | 行为 | 适用 |
   |------|------|------|
   | **AbortPolicy**（默认） | 抛 RejectedExecutionException | 重要任务，要感知到过载 |
   | **CallerRunsPolicy** | 由提交任务的线程自己执行 | 不丢任务 + 反压(提交者忙了就不提交了) |
   | **DiscardPolicy** | 静默丢弃 | 可丢弃的次要任务 |
   | **DiscardOldestPolicy** | 丢弃队列最老的任务再提交 | 只要最新任务 |

4. **线程数计算公式**：
   ```
   CPU 密集型(纯计算，无 IO/锁等待)：
      线程数 = N(cpu 核数) + 1
      （多 1 是为了线程偶尔缺页/故障时仍能充分利用 CPU）
   
   IO 密集型(网络/磁盘/DB 等待多)：
      线程数 = 2N  或更精确  N × (1 + WT/ST)
      WT = 线程等待时间，ST = 线程计算时间
      （等待时 CPU 空闲，多开线程让 CPU 不闲）
   
   混合型：拆成 CPU 密集和 IO 密集两个池，分开调
   
   终极原则：公式只是起点，必须压测调优
      看 CPU 利用率(目标 70-80%)、GC、线程切换、响应时间
   ```

5. **阿里规约为什么禁用 Executors**：
   ```
   Executors.newFixedThreadPool(n) / newSingleThreadExecutor()：
      → 内部用 LinkedBlockingQueue(无界！默认 Integer.MAX_VALUE)
      → 任务堆积 → OOM(java.lang.OutOfMemoryError)
   
   Executors.newCachedThreadPool()：
      → maximumPoolSize = Integer.MAX_VALUE
      → 突发流量创建无限线程 → OOM(unable to create new native thread) 或 CPU 打满
   
   Executors.newScheduledThreadPool(n)：
      → 同样无界队列
   
   正确做法：用 ThreadPoolExecutor 显式构造
      new ThreadPoolExecutor(core, max, keepAlive, unit,
          new ArrayBlockingQueue<>(1000),  // 有界队列！
          new ThreadFactoryBuilder().setNameFormat("biz-%d").build(),  // 命名
          new ThreadPoolExecutor.CallerRunsPolicy());  // 明确拒绝策略
   ```

**【边界场景 / 陷阱】**

- **核心线程不会被回收**：除非 `allowCoreThreadTimeOut(true)`，否则核心线程即使空闲也保留。
- **先排队后扩容**：很多人以为「先扩到 max 再排队」，错！是「核心满→排队→队列满→扩非核心到 max→拒绝」。
- **submit vs execute**：execute 无返回值，submit 返回 Future（可拿结果/异常）。submit 的异常被封装在 Future，不调 `future.get()` 不会抛出，易吞异常。
- **预启动核心线程**：`prestartAllCoreThreads()` 提前创建核心线程，避免冷启动延迟。

**【常见追问】**

- **Q：线程池怎么优雅停机？**
  A：`shutdown()`（不再接受新任务，处理完队列再停）；`shutdownNow()`（停止所有，返回未处理的任务列表）。配合 `awaitTermination(timeout)` 等待。优雅停机：先 shutdown → awaitTermination → 超时则 shutdownNow。某创业项目资金链路用这个保证停机时正在处理的分润不丢。
- **Q：父子任务用同一个线程池会死锁吗？**
  A：会。父任务提交后等待子任务结果，子任务在队列里，但父任务占着线程不释放 → 队列满 → 死锁。解决：父子用不同线程池，或用 CompletableFuture 的非阻塞编排。
- **Q：动态调整线程池参数？**
  A：`setCorePoolSize` / `setMaximumPoolSize` 可运行时调（美团动态线程池方案）。队列容量不可直接改（final），需自定义可变队列。某头部电商有动态线程池中间件，监控 + 动态调参。

**【易错点】**

- **执行流程是「先队列后扩容」**，不是「先扩到 max 再排队」。
- ** Executors 的坑是无界队列/无限线程 → OOM**，不是性能问题。
- **CallerRunsPolicy 是反压**，让提交者自己跑，自然降低提交速度。

**【速记口诀】**
七个参数核最队活工拒，核心满先排队后扩非核心；CPU 密集 N 加一，IO 密集二 N 起；Executors 无界 OOM，手建 ThreadPoolExecutor 有界拒。

**【某创业项目 / 某头部电商实战关联】**
某创业项目资金链路严格遵守阿里规约——用 `ThreadPoolExecutor` 显式构造，`ArrayBlockingQueue` 有界（容量按压测峰值×1.5 设），拒绝策略用 `CallerRunsPolicy`（分润任务绝不丢，反压保护下游）。线程命名 `funds-transfer-%d`，出问题 Arthas `thread` 一眼定位。某头部电商有动态线程池平台，运行时调参不重启。

### Q1. InnoDB 架构是怎样的？一条 UPDATE SQL 的完整执行流程？什么是 WAL 和两阶段提交？

> 🔥🔥🔥 ｜ 考察：InnoDB 存储引擎 ｜ 难度 ⭐⭐⭐⭐⭐ ｜ 高频

**一句话答案**：InnoDB 架构分**内存结构**（Buffer Pool / Change Buffer / Adaptive Hash Index / Log Buffer）和**后台线程**（Master/IO/Purge/Page Cleaner）；一条 UPDATE 走 **WAL（Write-Ahead Logging，预写日志）**——先写 redo log（顺序写，快）再改内存脏页，磁盘随机写脏页异步进行；redo log 和 binlog 用**两阶段提交**保证两者一致性，崩溃恢复时能准确判断事务是否真正提交。

**深度解析**：

1. **InnoDB 内存结构**：
   | 组件 | 作用 | 关键点 |
   |------|------|--------|
   | **Buffer Pool** | 缓存数据页和索引页（最核心） | LRU 变种：midpoint 插入，分 young/old 区，防全表扫描污染 |
   | **Change Buffer** | 针对非唯一二级索引的写缓存 | 先记 change buffer，页读入时 merge，减少随机 IO |
   | **Adaptive Hash Index** | 自适应哈希索引（热点页自动建） | 监控热点，InnoDB 自动管理，无需手动 |
   | **Log Buffer** | redo log 写缓存 | 定期刷入 redo log file |

2. **一条 UPDATE 的全流程（WAL 核心）**：
   ```
   ① 找数据页：Buffer Pool 命中？读内存；未命中则从磁盘读入 Buffer Pool
   ② 写 undo log：记录修改前的旧值（用于回滚 + MVCC 版本链）
   ③ 更新数据页：在 Buffer Pool 中改（成为脏页 dirty page，此时未刷盘）
   ④ 写 redo log（prepare 状态）：记录「页 X 偏移 Y 改成 Z」，顺序写，很快
   ⑤ 写 binlog（Server 层）：记录逻辑变更，用于复制/归档
   ⑥ 提交事务：redo log 改为 commit 状态
   ⑦ 脏页异步刷盘：Page Cleaner 线程后台把 Buffer Pool 脏页随机写到数据文件
   ```

3. **为什么用 WAL（预写日志）而不是直接写数据文件**：
   - 随机写慢（数据页随机位置），顺序写快（redo log 追加写）。
   - 先写 redo log（顺序）保证持久性，内存脏页慢慢刷——**性能提升核心**。
   - 崩溃恢复：读 redo log 重放未刷盘的修改，保证不丢数据。

4. **两阶段提交（redo log + binlog 一致性）**：
   ```
   阶段一：redo log 写入 → 状态 prepare
   阶段二：binlog 写入 → redo log 状态 commit

   崩溃恢复判断：
   - redo log 有 commit 标记 → 事务已提交，恢复
   - redo log 是 prepare 但 binlog 完整(有完整事务结束标记) → 视为已提交(binlog 可能已被从库消费)
   - redo log 是 prepare 且 binlog 不完整 → 回滚
   → 保证 redo 和 binlog 不出现「一个有一个没有」的不一致
   ```

**易错点 & 追问**：
- **易错**：脏页是改在 Buffer Pool 内存里，不是直接改磁盘文件——数据丢失风险靠 redo log 兜底。
- **Q：Buffer Pool 的 LRU 为什么不用普通 LRU？** A：普通 LRU 全表扫描会把热点页全挤出。InnoDB 用 midpoint：新读入的页放 old 区头部，只在 old 区停留超过 `innodb_old_blocks_time`（默认 1s）后再次访问才升到 young 区，全表扫描的页基本待不满 1s 就被淘汰，保护了热点。
- **Q：redo log 和 binlog 区别？** A：redo log 是 InnoDB 引擎层、物理日志（页的变更）、循环写；binlog 是 Server 层、逻辑日志（SQL 或行变更）、追加写。redo 保证 crash safe，binlog 用于复制和归档。

**速记口诀**：内存缓冲池最核心，WAL 先 redo 后脏页；redo prepare 再 binlog，两阶段提交保一致；崩溃 redo 看 commit，prepare 看 binlog 补判断。

> **某创业项目/某头部电商关联**：某创业项目分润写操作严格走事务（redo log + binlog 两阶段提交），保证资金不丢。某头部电商大促前调大 Buffer Pool（堆内存 60-70%），减少磁盘 IO。

### Q2. InnoDB 为什么用 B+树？聚簇索引/二级索引/覆盖索引/最左前缀怎么理解？索引什么时候失效？

> 🔥🔥🔥 ｜ 考察：索引底层 ｜ 难度 ⭐⭐⭐⭐⭐ ｜ 高频

**一句话答案**：B+树相比 B 树**非叶子节点不存数据只存索引**，扇出更大、树更矮（3-4 层存千万级数据，3 次 IO 搞定）；**聚簇索引**叶子存整行（InnoDB 主键索引，一张表一个），**二级索引**叶子存主键值（查到要**回表**），**覆盖索引**查询字段全在索引里免回表；联合索引用**最左前缀**匹配；索引失效七场景（函数/隐式转换/最左缺失/左模糊/!= / OR / 运算）。

**深度解析**：

1. **为什么是 B+树（对比其他）**：
   | 结构 | 为什么不选 |
   |------|-----------|
   | Hash | O(1) 查单值快，但不支持范围查询和排序（`> < between order by` 全废）|
   | 二叉树/红黑树 | 树太高（千万数据 20+ 层），每层一次磁盘 IO，慢 |
   | B 树 | 非叶子也存数据，扇出小，树比 B+树高 |
   | **B+树** | 非叶子纯索引 → 扇出极大（上千）→ 树矮（千万数据 3-4 层）→ IO 次数少；叶子有序链表 → 范围查询和排序高效 |

2. **聚簇索引 vs 二级索引**：
   ```
   聚簇索引(Clustered Index)：
   - 叶子节点存「整行数据」
   - InnoDB 主键索引就是聚簇索引，一张表只有一个
   - 没主键时 InnoDB 选唯一非空索引，再没有就生成隐藏 ROWID

   二级索引(Secondary Index / 非聚簇)：
   - 叶子节点存「主键值」+ 索引列值
   - 查到主键后，需要「回表」：用主键再查一次聚簇索引拿整行
   - 一张表可有多个

   覆盖索引(Covering Index)：
   - 查询的所有字段都在某个索引里 → 不用回表
   - explain 的 Extra 显示 Using index
   - 高频优化手段：把 SELECT * 改成只查索引字段，或建联合索引覆盖
   ```

3. **最左前缀（联合索引）**：
   - 联合索引 `(a, b, c)` 按 a→b→c 排序存储。
   - 能用：`a` / `a,b` / `a,b,c` / `a,b(范围),c(范围后失效)`。
   - 不能用：跳过 a 直接 `b`（缺最左）。
   - **范围查询后失效**：`a=1 and b>5 and c=3`，c 用不上索引（b 是范围，c 在 b 之后无法有序）。

4. **索引失效 7 场景**（必背）：
   | 场景 | 例子 | 原因 |
   |------|------|------|
   | 索引列做函数/计算 | `WHERE YEAR(create_time)=2026` | 无法用 B+树有序性 |
   | 隐式类型转换 | 字符串列 `WHERE phone=13800000000`(没引号) | 转成字符串比较，索引失效 |
   | 最左前缀缺失 | `(a,b,c)` 只查 `b` | 缺最左 a |
   | 左模糊 | `WHERE name LIKE '%张'` | 无法定位起点 |
   | != / <> / NOT IN | `WHERE status != 1` | 范围太大，优化器放弃索引 |
   | OR 连接非索引列 | `WHERE a=1 OR b=2`(b 无索引) | 必须全表扫 b |
   | 索引列参与运算 | `WHERE id + 1 = 10` | 等价 id=9 但优化器不一定转换 |

**易错点 & 追问**：
- **易错**：`LIKE '张%'`（右模糊）能用索引，`'%张'`（左模糊）不能用。
- **Q：索引下推 ICP 是什么？** A：5.6 引入。联合索引 `(a,b)`，`WHERE a=1 AND b LIKE '%x'`，引擎层先按 a 过滤，再把 b 的 like 条件下推到引擎层过滤（而非回表后再过滤），减少回表次数。
- **Q：为什么建议用自增主键？** A：自增主键顺序写入，B+树叶子节点顺序追加，避免页分裂（随机主键如 UUID 会导致频繁页分裂，写放大 + 碎片）。

**速记口诀**：B+非叶纯索引，矮胖三层千万级；聚簇叶存整行数据，二级回表查主键；覆盖索引免回表，最左前缀不能断；函数转换左模糊，七种失效要记牢。

> **某创业项目/某头部电商关联**：某创业项目分润查询高频按 `(tenant_id, status, create_time)` 建联合索引，覆盖索引避免回表，查询从 200ms 降到 5ms。强调：建索引不是越多越好（写放大），按查询模式针对性建。

### Q3. MVCC 是什么？ReadView 怎么判断版本可见性？RC 和 RR 的本质区别？

> 🔥🔥🔥 ｜ 考察：MVCC 多版本并发控制 ｜ 难度 ⭐⭐⭐⭐⭐ ｜ 高频

**一句话答案**：MVCC（Multi-Version Concurrency Control，多版本并发控制）让**读不加锁、读写不阻塞**，靠**隐藏字段 + Undo Log 版本链 + ReadView** 实现；每行有隐藏的 `DB_TRX_ID`（事务 ID）和 `DB_ROLL_PTR`（指向 undo 旧版本），形成版本链；**ReadView** 记录生成时的活跃事务列表，按可见性规则判断看哪个版本；**RC（读已提交）每次 SELECT 都生成新 ReadView，RR（可重复读）事务首次 SELECT 生成后复用**——这是两者本质区别。

**深度解析**：

1. **三要素**：
   ```
   ① 隐藏字段：
      - DB_TRX_ID：最近修改该行的事务 ID
      - DB_ROLL_PTR：回滚指针，指向 undo log 中的上一版本
      - DB_ROW_ID：隐藏主键(无主键时)

   ② Undo Log 版本链：
      每次更新生成一条 undo，DB_ROLL_PTR 串成链表：
      当前行(v3, trx=300) → undo(v2, trx=200) → undo(v1, trx=100)

   ③ ReadView（读视图）：
      - m_ids：生成时所有活跃(未提交)事务 ID 列表
      - min_trx_id：m_ids 中最小值
      - max_trx_id：下一个将分配的事务 ID
      - creator_trx_id：创建该 ReadView 的事务 ID
   ```

2. **可见性判断规则**（对某版本的 trx_id 判断）：
   ```
   trx_id == creator_trx_id          → 自己改的，可见
   trx_id < min_trx_id               → 在 ReadView 生成前已提交，可见
   trx_id >= max_trx_id              → ReadView 生成后才开启的事务，不可见
   min_trx_id ≤ trx_id < max_trx_id：
      在 m_ids 里                      → 生成时还活跃(未提交)，不可见
      不在 m_ids 里                    → 已提交，可见
   不可见 → 顺 DB_ROLL_PTR 找上一个 undo 版本，重复判断，直到可见或链尾
   ```

3. **RC vs RR 本质区别**：
   | 隔离级别 | ReadView 生成时机 | 效果 |
   |----------|-------------------|------|
   | **RC（Read Committed）** | 每次 SELECT 都新建 ReadView | 能看到别的事务最新提交，不可重复读 |
   | **RR（Repeatable Read）** | 事务第一次 SELECT 时生成，后续复用 | 事务内多次读结果一致，可重复读 |
   - 同一套 MVCC 机制，**唯一的区别就是 ReadView 生成时机**——这是面试点睛。

**易错点 & 追问**：
- **易错**：MVCC 只解决「快照读」（普通 SELECT），「当前读」（`SELECT ... FOR UPDATE` / `UPDATE` / `DELETE`）读最新值并加锁，不走 MVCC。
- **Q：为什么 RR 下普通 SELECT 不会幻读？** A：快照读用 MVCC，始终看 ReadView（首次生成）对应的快照，新插入的行 trx_id 更大不在可见范围，所以快照读不幻读。
- **Q：那 RR 下幻读在什么情况出现？** A：当前读（`SELECT FOR UPDATE`）会读到新插入行——但 InnoDB 用 Next-Key Lock 锁住间隙阻止插入来解决（见 Q4）。所以 InnoDB 的 RR 基本解决了幻读。

**速记口诀**：隐藏字段加 undo，版本链串旧数据；ReadView 记活跃事务，四条规则判可见；RC 每次建新视图，RR 首次生成后复用；本质区别就一点，视图时机定隔离。

> **某创业项目/某头部电商关联**：某创业项目分润对账报表用 RC 隔离（看最新数据），资金扣减事务用 RR + FOR UPDATE（可重复读 + 当前读加锁防并发改余额）。理解 MVCC 让我们在「读多写少」统计场景敢用普通 SELECT 不加锁，吞吐高。

### Q4. InnoDB 的锁有哪些？记录锁/间隙锁/Next-Key/意向锁怎么配合？怎么排查死锁？

> 🔥🔥🔥 ｜ 考察：锁机制 ｜ 难度 ⭐⭐⭐⭐⭐ ｜ 高频

**一句话答案**：InnoDB 行级锁分**记录锁**（锁单行）、**间隙锁**（锁区间，RR 防插入）、**Next-Key Lock**（记录锁+间隙锁，左开右闭，RR 默认）三种；表级有**意向锁**（IS/IX，快速判断表内有无行锁）；锁加在**索引**上——没走索引会锁全表（退化为表锁）；死锁靠**死锁检测**（`innodb_deadlock_detect`）自动回滚代价小的事务，排查看 `SHOW ENGINE INNODB STATUS` 的 LATEST DETECTED DEADLOCK。

**深度解析**：

1. **行锁三分**（RR 隔离级别下）：
   | 锁 | 范围 | 作用 |
   |----|------|------|
   | **记录锁 Record Lock** | 锁单条记录 | 防止该行被并发改 |
   | **间隙锁 Gap Lock** | 锁两记录间的「间隙」(不锁记录本身) | 防止范围内插入新行（防幻读） |
   | **Next-Key Lock** | Record + Gap，左开右闭 `(a, b]` | RR 默认行锁，锁记录 + 锁左侧间隙 |
   - **唯一索引等值查询命中**：退化为记录锁（已确定唯一，无需锁间隙）。
   - **唯一索引等值未命中**：退化为间隙锁（锁住两个值之间）。

2. **意向锁（表级）**：
   ```
   意向锁 IS/IX(Intent Shared/Exclusive)：表级锁
   作用：事务要加行锁前，先在表上加意向锁
   意义：其他事务想加表锁(如 LOCK TABLES)时，看表有没有意向锁就知道有没有行锁在用，
         不用逐行检查 → 快速判断表锁冲突
   ```

3. **锁加在索引上（关键）**：
   - InnoDB 行锁基于索引。`WHERE` 走索引 → 锁匹配的行（精确）。
   - **没走索引（全表扫）→ 锁全表所有行**（退化为表锁），这是「锁升级」误区的真相。
   - 所以**索引失效不仅慢，还会锁全表**——资金场景致命。

4. **死锁与排查**：
   ```
   死锁：事务 A 持有锁 1 等 锁 2，事务 B 持有锁 2 等 锁 1 → 互相等待
   InnoDB 死锁检测(innodb_deadlock_detect=ON，默认)：
      发现死锁 → 回滚 undo 量(代价)较小的事务，让另一个继续
   排查：
      SHOW ENGINE INNODB STATUS;  → 看 LATEST DETECTED DEADLOCK 段
      找到两个事务持有的锁、等待的锁、执行的 SQL
   避免：
      ① 多表/多行更新，事务内按固定顺序加锁(如统一按 id 升序)
      ② 大事务拆小(锁持有时间短)
      ③ 业务允许时降低隔离级别(RC 间隙锁更少)
      ④ 必要时显式 SELECT FOR UPDATE 一次性加锁
   ```

**易错点 & 追问**：
- **易错**：RC 隔离级别下没有间隙锁（只有记录锁），所以 RC 会有幻读，但并发度更高。RR 有间隙锁防幻读但锁更多。
- **Q：行锁一定锁一行吗？** A：不一定。Next-Key 锁一个区间（多行 + 间隙）。范围查询 `WHERE id BETWEEN 1 AND 100` 会锁住这个范围的所有记录和间隙。
- **Q：怎么定位是哪条 SQL 持锁？** A：`SELECT * FROM information_schema.INNODB_TRX`（当前事务）、`INNODB_LOCKS`（锁）、`INNODB_LOCK_WAITS`（等待关系）。MySQL 8.0 改用 `performance_schema.data_locks`。

**速记口诀**：记录锁单行，间隙锁区间，Next-Key 两合一；意向锁表级先加，快速判断行锁在；锁加索引上，无索引锁全表；死锁检测回滚小的，固定加锁序可避。

> **某创业项目/某头部电商关联**：某创业项目分润并发扣余额曾出现死锁——两个账户互相转账，加锁顺序不一致。修复：所有资金操作按账户 ID 升序加锁（`SELECT FOR UPDATE ORDER BY id`），死锁消失。某头部电商大表加索引避免全表锁，是基本素养。

### Q5. explain 怎么看？哪些字段决定 SQL 好不好？怎么优化慢 SQL？

> 🔥🔥 ｜ 考察：执行计划 + 慢 SQL 优化 ｜ 难度 ⭐⭐⭐⭐ ｜ 高频

**一句话答案**：explain 重点看 **type**（访问类型，最好到 ref/range 以上）、**key**（实际用的索引）、**rows**（预估扫描行数）、**Extra**（Using index 覆盖索引好，Using filesort/temporary 要优化）；慢 SQL 优化方法论：**先看 type 判断是否走索引 → 看 rows 判断扫描量 → 看 Extra 判断有无临时表/文件排序 → 针对性加索引/改写 SQL/拆大事务**。

**深度解析**：

1. **explain 核心字段**：
   | 字段 | 含义 | 优化判断 |
   |------|------|----------|
   | **type** | 访问类型 | `system > const > eq_ref > ref > range > index > ALL`，至少要到 `range`/`ref`，禁止 `ALL`（全表扫）|
   | **possible_keys** | 可能用的索引 | 有值但 key 为空 = 索引可选但没用，可能统计信息过期 |
   | **key** | 实际用的索引 | NULL = 没走索引 |
   | **key_len** | 索引使用字节长度 | 判断联合索引用了几个字段（联合索引优化利器）|
   | **rows** | 预估扫描行数 | 越小越好，与实际行数差距大说明统计信息需 `ANALYZE TABLE` |
   | **filtered** | 过滤后剩余比例 | 100% 最好，低说明扫描多但结果少 |
   | **Extra** | 附加信息 | `Using index`(覆盖索引好) / `Using where` / `Using filesort`(需优化) / `Using temporary`(需优化)|

2. **type 详解**：
   - `const`：主键/唯一索引等值查，最多一条，最快。
   - `eq_ref`：JOIN 时被驱动表用主键/唯一索引，一行对一行。
   - `ref`：普通索引等值查。
   - `range`：索引范围查（`> < between in like 右模糊`）。
   - `index`：扫整个索引树（比 ALL 好但仍要全扫索引）。
   - `ALL`：全表扫描，**必须优化**。

3. **慢 SQL 优化流程**：
   ```
   ① 定位：开启慢查询日志(slow_query_log)，找慢 SQL(pt-query-digest 分析)
   ② explain：看 type/key/rows/Extra
   ③ 加索引：WHERE/JOIN/ORDER BY/GROUP BY 的字段建索引，联合索引覆盖
   ④ 改写：SELECT * → 指定字段；深分页(偏移大) → 游标分页(where id > last_id limit n)
              OR → UNION ALL；子查询 → JOIN
   ⑤ 拆分：大事务拆小；超大表分库分表/冷热分离
   ⑥ 验证：再跑 explain，rows 下降、Extra 无 filesort/temporary
   ```

**易错点 & 追问**：
- **易错**：`Using filesort` 不一定用磁盘文件，小排序在内存（sort_buffer），大排序才落盘——但都说明没走索引排序，建议优化。
- **Q：深分页为什么慢？** A：`LIMIT 1000000, 10` 要先扫前 100 万行再丢掉。优化：游标分页 `WHERE id > last_id ORDER BY id LIMIT 10`（走索引，只扫 10 行）。
- **Q：统计信息为什么影响执行计划？** A：优化器基于统计信息（行数、基数 cardinality）估算成本选索引。统计过期会选错索引，`ANALYZE TABLE` 刷新。

**速记口诀**：type 要到 range 上，key 不空才算走索引；key_len 判联合用几个，rows 越小越省力；Extra 见 filesort 要优化，深分页游标来救场。

> **某创业项目/某头部电商关联**：某创业项目统计报表深分页优化（LIMIT 10万,20 → 游标分页），从 8s 降到 20ms。某头部电商用 pt-query-digest 每天分析慢查询 TOP，纳入治理。

### Q6. 事务的 ACID 和四大隔离级别？幻读怎么解决？MySQL 默认隔离级别是什么？

> 🔥🔥 ｜ 考察：事务与隔离级别 ｜ 难度 ⭐⭐⭐⭐ ｜ 高频

**一句话答案**：ACID = 原子性（Atomicity，undo 实现）、一致性（Consistency，业务约束）、隔离性（Isolation，锁+MVCC）、持久性（Durability，redo 实现）；四级隔离从低到高：**读未提交（RU）→ 读已提交（RC）→ 可重复读（RR，MySQL 默认）→ 串行化（Serializable）**；幻读在 InnoDB RR 下被解决——**快照读靠 MVCC、当前读靠 Next-Key Lock** 协作；MySQL 默认 RR（多数其他数据库默认 RC）。

**深度解析**：

1. **ACID 与实现**：
   | 特性 | 含义 | InnoDB 实现 |
   |------|------|-------------|
   | 原子性 A | 事务要么全做要么全不做 | **undo log**（回滚） |
   | 一致性 C | 事务前后数据满足约束 | 业务 + 其他三者共同保证 |
   | 隔离性 I | 并发事务互不干扰 | **锁 + MVCC** |
   | 持久性 D | 提交后永久不丢 | **redo log**（崩溃恢复）|

2. **四大隔离级别与并发问题**：
   | 级别 | 脏读 | 不可重复读 | 幻读 | 锁情况 |
   |------|:----:|:----------:|:----:|--------|
   | RU 读未提交 | ✓有 | ✓有 | ✓有 | 几乎不加锁 |
   | RC 读已提交 | ✗ | ✓有 | ✓有 | 行锁(无间隙锁) |
   | **RR 可重复读**(默认) | ✗ | ✗ | ✗(InnoDB解决) | 行锁 + 间隙锁 |
   | Serializable 串行化 | ✗ | ✗ | ✗ | 所有读加共享锁，串行 |
   - **脏读**：读到别的事务未提交的数据。
   - **不可重复读**：同一事务两次读同一行，结果不同（别的事务改了）。
   - **幻读**：同一事务两次范围查询，结果集不同（别的事务插入了新行）。

3. **InnoDB RR 如何解决幻读（双机制）**：
   ```
   快照读(普通 SELECT)：
      → 走 MVCC，看 ReadView 快照，新插入行 trx_id 更大不在可见范围 → 不幻读
   
   当前读(SELECT FOR UPDATE / UPDATE / DELETE)：
      → 用 Next-Key Lock 锁住查询范围(记录+间隙)
      → 别的事务想往间隙插入 → 被阻塞 → 无法插入新行 → 不幻读
   
   两者协作 → RR 下基本无幻读
   ```

**易错点 & 追问**：
- **易错**：MySQL 默认 RR，但 Oracle/PostgreSQL 默认 RC。Spring 的 `@Transactional` 默认用数据库默认级别（即 RR），但很多人以为 RC。
- **Q：为什么 MySQL 选 RR 而不是 RC？** A：历史原因——早期 MySQL binlog 的 Statement 格式在 RC 下复制会有数据不一致（顺序问题），RR 更安全。现在用 Row 格式其实 RC 也行，但默认保持 RR。
- **Q：Serializable 在 InnoDB 怎么实现？** A：所有普通 SELECT 隐式加共享锁（相当于 FOR SHARE），读写互斥，完全串行，性能差，基本不用。

**速记口诀**：原子 undo 持久 redo，隔离锁加 MVCC；读未提交脏读有，读已提交不可重复，RR 默认解幻读，串行加锁性能差；快照 MVCC 当前 Next-Key，双管齐下无幻读。

> **某创业项目/某头部电商关联**：某创业项目资金事务用 RR + FOR UPDATE（可重复读 + 当前读加锁），保证并发扣减余额的一致性。强调：选 RR 不是无脑跟默认，是资金场景强一致的必然选择。

### Q7. MySQL 主从复制原理？binlog 三种格式怎么选？主从延迟怎么解决？

> 🔥 ｜ 考察：复制与高可用 ｜ 难度 ⭐⭐⭐⭐ ｜ 中高频

**一句话答案**：主从复制流程：**主库写 binlog → 从库 IO Thread 拉取写 relay log → 从库 SQL Thread 回放**；binlog 三格式：**Statement**（记 SQL，小但有不安全函数如 NOW()）、**Row**（记行变更，大但准确，默认）、**Mixed**（混合）；主从延迟主因是从库单线程回放（5.7 前），解决靠**并行复制**（5.7+ 基于 group commit）、从库 SSD、拆大事务；**GTID**（全局事务 ID）替代 file+position，让主从切换更简单可靠。

**深度解析**：

1. **复制三线程**：
   ```
   主库：binlog dump thread —— 推送 binlog 给从库
   从库：IO thread —— 拉取 binlog 写入 relay log（中继日志）
         SQL thread —— 读 relay log 回放，更新从库数据
   同步方式：异步(默认，主库不等从库)、半同步(主库等至少一个从库收 ACK)
   ```

2. **binlog 三格式**：
   | 格式 | 记录内容 | 优点 | 缺点 |
   |------|----------|------|------|
   | Statement | 原始 SQL | 日志小、可读 | 不确定函数(NOW/RAND/UUID)主从不一致 |
   | **Row** | 每行变更前后值 | 准确、可还原 | 日志大（批量更新记每行）|
   | Mixed | 自动判断 | 折中 | 复杂 |
   - MySQL 5.7.7+ 默认 **Row**，配合 GTID 复制最稳。

3. **主从延迟原因与解决**：
   ```
   原因：
   ① 从库 SQL Thread 单线程回放(5.7 前) → 主库并发写，从库串行回放，必然落后
   ② 大事务(一次删百万行)→ 从库回放久
   ③ 网络抖动、从库性能差(机械盘)
   ④ 主库大并发，从库读压力大
   
   解决：
   ① MySQL 5.7+ 并行复制：基于 group commit(同一组提交的事务可并行回放)
      8.0 WRITESET 模式：基于写集合判断冲突，并行度更高
   ② 从库 SSD，提升 IO
   ③ 拆大事务(批量删除分批)
   ④ 读写分离时，强一致读走主库(或半同步 + 读主)
   ⑤ 关键业务短延迟容忍，配合监控告警(Seconds_Behind_Master)
   ```

4. **GTID（Global Transaction Identifier）**：
   - 格式 `server_uuid:transaction_id`，全局唯一。
   - 替代传统的「binlog file + position」定位，从库自动找位点。
   - 主从切换、故障转移更简单（不用手动算 position），MHA/MGR 等高可用方案依赖它。

**易错点 & 追问**：
- **易错**：主从复制是异步的（默认），主库提交不等从库——主库宕机未同步的数据会丢。金融场景用**半同步复制**（主库等至少一个从库 ACK）。
- **Q：读写分离后怎么避免读到从库旧数据？** A：①关键读走主库；②半同步复制 + 短延迟容忍；③客户端记上次写的事务 GTID，读从库时等该 GTID 回放完（`WAIT_FOR_EXECUTED_GTID_SET`）。
- **Q：主从延迟多少算正常？** A：看业务。报表场景秒级延迟可接受；实时交易（如订单状态查询）要求 < 100ms，否则走主库。

**速记口诀**：主推 binlog 从拉回放，三线程接力传数据；Statement 小 Row 准 Mixed 折，默认 Row 配 GTID；单线回放是延迟根，并行复制来解围。

> **某创业项目/某头部电商关联**：某创业项目创业期单库，扩张后读写分离（主写从读），强一致读（资金）走主库。某头部电商用半同步 + 并行复制保证主从延迟 < 1s，配合 MHA 故障转移。

### Q1. Redis 单线程为什么这么快？6.0 引入多线程改变了什么？

> 🔥🔥🔥 ｜ 考察：Redis 线程模型 ｜ 难度 ⭐⭐⭐⭐⭐ ｜ 高频

**一句话答案**：Redis 快的四大原因：①**纯内存操作**（纳秒级）②**IO 多路复用 epoll**（单线程处理海量连接）③**单线程避免锁竞争和上下文切换**④**高效数据结构**（SDS/跳表/压缩列表）；6.0 前「单线程」指**命令执行单线程**（网络 IO 也同线程），6.0 引入**多线程处理网络 IO（读写 socket）**，但**命令执行仍单线程**（避免数据竞争）——所以「Redis 是单线程」仍基本成立。

**深度解析**：

1. **快的四大原因**：
   | 原因 | 说明 |
   |------|------|
   | 纯内存 | 数据全在内存，读写纳秒/微秒级，无磁盘 IO |
   | epoll 多路复用 | 一个线程监听海量连接（select/poll 是 O(n) 遍历，epoll 是 O(1) 事件驱动）|
   | 单线程 | 无锁无竞争、无线程切换开销；CPU 不是瓶颈（内存和网络才是）|
   | 数据结构 | SDS O(1) 取长度、跳表 O(logN) 范围、压缩列表省内存 |

2. **epoll vs select/poll**（详见网络章）：
   ```
   select/poll：每次调用遍历所有 fd(O(n))，有上限(select 1024)
   epoll：内核维护就绪链表，epoll_wait 直接返回就绪 fd(O(1))，无上限，LT/ET 双模式
   → Redis 用 epoll，单线程高效处理 10 万+ 连接
   ```

3. **6.0 多线程的真相**：
   ```
   6.0 前：单线程 Reactor
      主线程：epoll_wait → 读请求 → 解析 → 执行命令 → 写响应，全串行
      瓶颈：大 value 读写 socket 耗时，阻塞其他命令执行
   
   6.0+：IO 多线程(默认关闭，需开启 io-threads)
      主线程：epoll_wait → 把 socket 读写分发给 IO 线程并行处理
      IO 线程：只做 read/write socket，不执行命令
      主线程：命令执行仍是单线程(串行，避免数据竞争)
      → 解决大 value 的网络 IO 瓶颈，命令执行逻辑不变
   ```

**易错点 & 追问**：
- **易错**：6.0 多线程只处理网络 IO，命令执行仍单线程，所以不是「Redis 变成多线程数据库」。
- **Q：单线程怎么利用多核 CPU？** A：单实例只用一核。要多核 → 部署多实例（每核一个）+ 集群分片，或一台机起多个 Redis 进程。
- **Q：哪些命令会阻塞单线程？** A：`KEYS *`（扫全库）、`HGETALL` 大 hash、`SORT`、`FLUSHALL`、`DEBUG`——生产禁用，用 `SCAN` 替代 `KEYS`。

**速记口诀**：内存加 epoll，单线无锁切换少；数据结构自带快，单核十万连接扛；6.0 多线只管 IO，命令执行仍串行；KEYS 扫库会阻塞，SCAN 增量是替代。

> **某创业项目/某头部电商关联**：某创业项目用 Redis 做会话和热点缓存，严格禁用 `KEYS`（运维通过 rename-command 禁掉），改用 `SCAN`。某头部电商大 value 优化（把 1MB 的 hash 拆成多个小 hash），配合 6.0 IO 多线程提升吞吐。

### Q2. Redis 五大数据结构的底层编码是什么？什么时候切换？

> 🔥🔥🔥 ｜ 考察：数据结构底层 ｜ 难度 ⭐⭐⭐⭐⭐ ｜ 高频

**一句话答案**：Redis 每种类型有多种**底层编码**，元素少用紧凑结构省内存、多时切到高效结构保性能；**String**：int/embstr/raw；**List**：listpack/quicklist（7.0 前是 ziplist）；**Hash/Set/ZSet**：listpack（少）→ hashtable/intset/skiplist（多）；切换阈值默认 `*-max-listpack-entries 128` / `*-max-listpack-value 64`（超阈值升级）。架构师要知道这些编码，才能解释「为什么同样数据内存差几倍」和「bigkey 的危害」。

**深度解析**：

1. **五大类型与编码**：
   | 类型 | 底层编码（少→多） | 切换条件 |
   |------|-------------------|----------|
   | **String** | int(数字) / embstr(≤44字节) / raw(>44字节) | 数字→int；短串→embstr(SDS+对象连续内存)；长串→raw |
   | **List** | listpack(7.0前ziplist) → quicklist | 元素>128 或单元素>64字节 → quicklist |
   | **Hash** | listpack → hashtable | 同上 |
   | **Set** | intset(全整数) / listpack → hashtable | 全整数→intset；有非整数→listpack→hashtable |
   | **ZSet** | listpack → skiplist+hashtable | 元素>128 或单元素>64字节 → 跳表+哈希(双结构) |

2. **关键数据结构原理**：
   - **SDS（Simple Dynamic String）**：`len + alloc + flags + buf`，O(1) 取长度、二进制安全、空间预分配（扩容翻倍）、惰性释放。
   - **listpack/ziplist**：连续内存的紧凑结构，省内存（无指针开销），但插入是 O(n) 搬移，元素多时性能差 → 所以有阈值切换。ziplist 有连锁更新问题（7.0 用 listpack 替代）。
   - **quicklist**：双向链表，每个节点是一个 listpack，兼顾内存和性能（List 的主力）。
   - **skiplist（跳表）**：多层链表，查找 O(logN)，**支持范围查询**（ZRANGE），比红黑树实现简单、范围操作高效——这是 ZSet 用跳表不用红黑树的原因。
   - **intset**：整数数组，有序、二分查找，全整数 Set 用，省内存。

3. **ZSet 为什么是「跳表+哈希」双结构**：
   - 跳表：支持按 score 范围查询（ZRANGEBYSCORE）。
   - 哈希表：O(1) 按 member 查 score（ZSCORE）。
   - 两者配合，member→score 用哈希、范围用跳表，覆盖所有 ZSet 操作。

**易错点 & 追问**：
- **易错**：embstr 是只读的（修改会转 raw），所以频繁改的字符串可能触发编码转换。
- **Q：为什么 ZSet 用跳表不用红黑树？** A：①跳表实现简单（无旋转）②范围查询高效（链表连续遍历）③内存灵活（层数概率分布）④并发友好（局部锁）。红黑树范围查询要中序遍历，不如跳表链表直接。
- **Q：怎么查一个 key 的编码？** A：`OBJECT ENCODING key`。运维排查内存用 `MEMORY USAGE key`。

**速记口诀**：String int embstr raw，List 压包快表两相宜；Hash Set ZSet 少用包，多则哈希跳表替；切换阈值一二八六四，紧凑省内存高效保性能；跳表范围哈希查，ZSet 双构覆盖全。

> **某创业项目/某头部电商关联**：某创业项目排行榜用 ZSet（跳表范围查询高效），会话用 Hash。某头部电商做过 Redis 内存优化——把超 128 元素的 Hash（已升 hashtable）拆分成多个小 Hash（listpack 编码），内存省 40%。这是理解编码切换的实际收益。

### Q3. 缓存穿透、击穿、雪崩分别是什么？怎么解决？布隆过滤器原理？

> 🔥🔥🔥 ｜ 考察：缓存经典问题 ｜ 难度 ⭐⭐⭐⭐⭐ ｜ 高频

**一句话答案**：**穿透**——查的数据 DB 也没有，每次打到 DB（缓存和 DB 都穿透），解法：缓存空值 / 布隆过滤器 / 参数校验；**击穿**——单个热点 key 过期瞬间，海量请求打到 DB，解法：互斥锁（只放一个查 DB）/ 热点永不过期（逻辑过期+异步更新）；**雪崩**——大量 key 同时过期或 Redis 宕机，解法：过期时间加随机 / 多级缓存 / 熔断降级 / Redis 集群高可用；**布隆过滤器**——位数组+多哈希函数，判断「一定不存在」或「可能存在」（有误判率但不会漏判），前置挡穿透。

**深度解析**：

1. **三问对比**：
   | 问题 | 触发 | 危害 | 解决 |
   |------|------|------|------|
   | **穿透** | 查 DB 也不存在的数据（恶意攻击/bug） | 每次穿透到 DB | ①缓存空值(短 TTL)②布隆过滤器前置③参数校验拦截非法 ID |
   | **击穿** | 单个热点 key 过期瞬间 | 高并发瞬间打到 DB | ①互斥锁(SETNX，只一个查 DB 重建)②热点永不过期+异步更新 |
   | **雪崩** | 大量 key 同时过期/Redis 宕机 | DB 瞬间过载 | ①过期时间加随机数②多级缓存(本地+Redis)③熔断降级④Redis 集群高可用 |

2. **布隆过滤器原理**：
   ```
   结构：m 位的位数组 + k 个哈希函数
   写入：把元素用 k 个哈希函数算出 k 个位置，置 1
   查询：同样算 k 个位置，全为 1 → 「可能存在」；有 0 → 「一定不存在」
   
   特性：
   - 不会漏判(存在的元素一定判存在)
   - 有误判(哈希冲突，不存在的可能判存在)，误判率可控(调 m 和 k)
   - 不能删除(标准版，置 1 的影响其他元素；可用 Counting Bloom Filter)
   
   用法：缓存前先查布隆过滤器，不存在直接返回，存在再查 Redis/DB → 挡掉绝大多数穿透
   ```

3. **互斥锁解击穿（伪代码）**：
   ```
   get(key)：
     value = redis.get(key)
     if value == null:
        if SETNX(lock_key, 1, NX, EX, 10):  // 抢锁，只有一个成功
           try:
              value = db.query(key)          // 只有持锁者查 DB
              redis.set(key, value, ttl)
           finally:
              redis.del(lock_key)
        else:
           sleep(50ms); return get(key)      // 其他线程稍后重试
     return value
   ```

**易错点 & 追问**：
- **易错**：缓存空值要设短 TTL（如 60s），避免 DB 后来有数据了还一直返回空。布隆过滤器 + 空值缓存常组合用。
- **Q：雪崩和击穿区别？** A：击穿是「单个热点 key」，雪崩是「大量 key」。击穿针对性强（一个 key），雪崩是面积广（一群 key 或整个 Redis 挂）。
- **Q：Redis 挂了怎么办？** A：①Redis 集群高可用（主从+哨兵/Cluster）②本地缓存兜底（Caffeine）③服务熔断降级（限流 + 默认值）——多级防御，不能让 DB 直接裸奔。

**速记口诀**：穿透查的 DB 也无，空值布隆加校验；击穿热点过期瞬间，互斥锁或永不过期；雪崩大面积同时挂，随机过期多级缓存加熔断；布隆位数组多哈希，一定不存在不会漏。

> **某创业项目/某头部电商关联**：某创业项目商品缓存用「布隆过滤器（挡穿透）+ 缓存空值（短 TTL）+ 热点 key 永不过期（逻辑过期+异步刷新）」三件套。某头部电商大促用「Redis 集群 + Caffeine 本地缓存 + Sentinel 熔断」防雪崩，DB 流量被挡在多级缓存之后。

### Q4. Redis 持久化 RDB 和 AOF 怎么选？混合持久化是什么？

> 🔥🔥 ｜ 考察：持久化 ｜ 难度 ⭐⭐⭐⭐ ｜ 高频

**一句话答案**：**RDB** 是二进制快照（bgsave fork 子进程写，恢复快、文件小，但宕机会丢最后一次快照后的数据）；**AOF** 是追加命令日志（三种 fsync：always 最安全慢 / everysec 默认宕丢1秒 / no 交给 OS，丢数据少但文件大、恢复慢）；**混合持久化**（4.0+）AOF 重写时前半段用 RDB 二进制 + 后半段增量命令，兼顾恢复速度和数据安全——**生产推荐混合 + everysec**。

**深度解析**：

1. **RDB vs AOF**：
   | 维度 | RDB | AOF |
   |------|-----|-----|
   | 原理 | 全量二进制快照 | 追加每条写命令 |
   | 触发 | 定时 bgsave（fork 子进程）| 实时追加（fsync 策略）|
   | 文件大小 | 小（压缩二进制）| 大（命令日志，重写压缩）|
   | 恢复速度 | 快 | 慢（重放命令）|
   | 数据丢失 | 多（丢最后一次快照后）| 少（everysec 丢 1 秒）|
   | 性能影响 | fork 时短暂卡顿（大内存明显）| 追加写 + fsync 持续开销 |

2. **AOF 三种 fsync 策略**：
   ```
   appendfsync always    ：每条命令都 fsync 刷盘，最安全，性能最差(几乎不用)
   appendfsync everysec  ：每秒 fsync 一次，宕机最多丢 1 秒(默认，推荐)
   appendfsync no        ：交给 OS 决定刷盘(通常 30s)，性能好但丢数据多
   ```

3. **AOF 重写**：
   - AOF 持续追加会越来越大（如 set k v1, set k v2, set k v3 实际只存 v3）。
   - 重写（bgrewriteaof）：fork 子进程，遍历当前内存生成最简命令，压缩文件。
   - 重写期间的新命令同时写旧 AOF 和重写缓冲，保证不丢。

4. **混合持久化（4.0+，aof-use-rdb-preamble）**：
   ```
   AOF 重写时：
   - 前半段：把当前内存数据用 RDB 二进制格式写入 AOF 文件
   - 后半段：重写期间的新增命令追加在 RDB 之后
   恢复时：先加载 RDB（快），再重放增量命令（少）→ 恢复快 + 丢数据少
   生产推荐：开启混合 + everysec
   ```

**易错点 & 追问**：
- **易错**：RDB 的 fork 在大内存实例（>10G）会短暂卡顿（fork 要复制页表），内存越大越明显，这是 RDB 的痛点。
- **Q：fork 为什么不复制全部内存？** A：Copy-On-Write（写时复制）。fork 只复制页表（元数据），父子进程共享物理内存页；只有某页被修改时才真正复制该页。所以 fork 快，但写操作多时内存可能翻倍（cow 页）。
- **Q：Redis 主从复制和持久化的关系？** A：从库首次全量同步时主库 bgsave 生成 RDB 发给从库；持久化是单机数据安全，主从是高可用 + 读扩展，两者互补。

**速记口诀**：RDB 快照快又小，宕丢一次快照后；AOF 追加丢得少，everysec 是默认；重写压缩省空间，混合 RDB 加增量；生产推荐混合加每秒，恢复快速数据安。

> **某创业项目/某头部电商关联**：某创业项目 Redis 用「RDB（每 5 分钟）+ AOF everysec + 混合持久化」，兼顾恢复速度和最小数据丢失。某头部电商大内存实例注意 RDB fork 卡顿，控制单实例内存 < 10G，大数据用集群分片。

### Q5. Redis 主从、哨兵、集群的区别？脑裂和数据丢失怎么防？16384 哈希槽怎么分？

> 🔥🔥 ｜ 考察：高可用架构 ｜ 难度 ⭐⭐⭐⭐ ｜ 高频

**一句话答案**：**主从**（一主多从，读写分离，主挂需手动切换）、**哨兵 Sentinel**（在主从基础上加监控+自动故障转移，主挂自动选新主，适合小规模）、**集群 Cluster**（去中心化，数据分片到多节点，16384 哈希槽，节点间 gossip 协议，支持大规模）；**脑裂**靠 `min-slaves-to-write`（从库数量不满足则拒绝写）缓解；**数据丢失**靠异步复制+`min-slaves-max-lag`（延迟超阈值拒绝写）控制；**哈希槽**用 `CRC16(key) % 16384` 路由到节点。

**深度解析**：

1. **三种架构演进**：
   | 架构 | 能力 | 节点数 | 适用 |
   |------|------|:------:|------|
   | **主从** | 读写分离、数据备份，无自动故障转移 | 少量 | 读多写少、可手动运维 |
   | **哨兵 Sentinel** | 主从 + 监控 + 自动选主 + 通知客户端 | 中量 | 中小规模、需自动高可用 |
   | **集群 Cluster** | 分片 + 高可用 + 去中心化 | 大量 | 大数据量、高并发 |

2. **哨兵故障转移流程**：
   ```
   ① 哨兵集群监控主从(每个哨兵定期 ping 主)
   ② 主客观下线：单个哨兵发现主不可达 → 主观下线(sdown)
                  超过 quorum 个哨兵都判定 → 客观下线(odown)
   ③ 选举 leader 哨兵(用 Raft)
   ④ leader 选新主：从库里挑优先级高、复制偏移量大(数据新)、runid 小的
   ⑤ 通知其他从库跟新主，客户端连新主
   ```

3. **集群 Cluster 哈希槽**：
   ```
   16384 个哈希槽(0-16383)分配到各节点
   路由：CRC16(key) % 16384 → 槽位 → 所属节点
   客户端：SMART 客户端缓存槽位映射，直接连目标节点
         连错节点 → 返回 MOVED 重定向 → 客户端更新缓存再连
   扩容：迁移部分槽位到新节点(在线迁移，逐 key)
   
   为什么是 16384(2^14) 而不是 65536？
     - gossip 消息每秒传输节点心跳，16384/8=2KB 槽位位图够用
     - 集群一般不超过 1000 节点，16384 够分
   ```

4. **脑裂与数据丢失**：
   ```
   脑裂：主从因网络分区，哨兵判定主下线选了新主，但老主还在接受写
        → 网络恢复后老主降级从库，老主的写丢失(被新主数据覆盖)
   防御：
   - min-slaves-to-write N：主库要求至少 N 个从库在线才接受写
   - min-slaves-max-lag S：从库延迟超 S 秒，主库拒绝写
   → 分区时老主因从库失联(不满足条件)自动拒绝写，防脑裂丢数据
   ```

**易错点 & 追问**：
- **易错**：Redis Cluster 不支持跨槽的多 key 操作（如 MGET 跨槽会报错），需用 hash tag（`{user}:1` `{user}:2` 强制同槽）。
- **Q：哨兵和集群能一起用吗？** A：不必要。Cluster 自带高可用（每个槽的主挂，其从自动顶上），不需要额外哨兵。哨兵用于「主从（不分片）」的高可用。
- **Q：一致性哈希 vs 哈希槽？** A：一致性哈希（环）扩容只影响相邻节点但数据分布可能不均（需虚拟节点）；Redis 用预定义 16384 槽，扩容迁移指定槽，可控性强。各有利弊。

**速记口诀**：主从读写可手切，哨兵监控自动转主，集群分片哈希槽，16384 去 CRC16；脑裂用 min-slaves 拒写防，数据丢失靠同步加 lag；跨槽操作不支持，hash tag 强制同槽位。

> **某创业项目/某头部电商关联**：某创业项目用哨兵（小规模 + 自动高可用），某头部电商用 Cluster（大数据 + 分片）。强调：Redis 高可用不是「装上就行」，要配 min-slaves 防脑裂、监控复制延迟、定期演练故障转移。

### Q6. 大 key 和热 key 怎么治理？Redisson 分布式锁的看门狗是什么？红锁为什么有争议？

> 🔥 ｜ 考察：运维与分布式锁 ｜ 难度 ⭐⭐⭐⭐ ｜ 中高频

**一句话答案**：**大 key**（单个 value 很大，如 10MB+ 的 list/hash）危害网络阻塞、内存不均、删除卡顿（`DEL` 阻塞），治理：拆分（按业务维度拆多个 key）、删除用 `UNLINK` 异步删、迁移用大 key 工具；**热 key**（单 key 访问量极大）危害单节点压力 + 击穿，治理：本地缓存（Caffeine）、多副本（key 加随机后缀分散多节点）；**Redisson 看门狗**默认 30s 锁，每 10s 自动续期，防业务没执行完锁过期；**红锁 Redlock**（多节点过半数加锁）有争议——Martin Kleppmann 批其依赖时钟、GC pause 会破坏正确性，生产慎用。

**深度解析**：

1. **大 key 治理**：
   ```
   危害：
   ① 网络阻塞：读 10MB value 占带宽，阻塞其他请求(单线程)
   ② 内存不均：集群某节点内存远超其他(单 key 不能跨槽)
   ③ 删除卡顿：DEL 大 key 同步释放内存，阻塞主线程(秒级卡顿)
   ④ 过期触发：大 key 同步删除时 ACTIVE 时间长
   治理：
   ① 拆分：大 hash 按字段拆成多个 key，大 list 按段拆
   ② 异步删：UNLINK(后台线程删)替代 DEL
   ③ 监控：redis-cli --bigkeys / MEMORY USAGE 找大 key
   ④ 迁移：拆分后逐步切换，旧 key 用 UNLINK 清理
   ```

2. **热 key 治理**：
   ```
   危害：单 key 流量打满单节点(集群中该 key 所在节点)，且过期瞬间击穿
   治理：
   ① 本地缓存：客户端用 Caffeine 缓存热 key，减少打到 Redis
   ② 多副本：key 加随机后缀(key_1,key_2...key_n)，分散到不同节点，读时随机选一个
   ③ 读写分离：热 key 读走从库(但注意从库延迟)
   ④ 监控：redis-cli --hotkeys / 代理层统计
   ```

3. **Redisson 看门狗**：
   ```
   Redisson 加锁(默认 lockLeaseTime=30s)：
   ① SET key UUID:threadId NX PX 30000  (30s 过期)
   ② 启动看门狗：每 10s(1/3 周期)检查锁还持有 → 续期到 30s
   → 业务执行多久都不怕锁过期(只要客户端活着)
   → 客户端崩溃 → 看门狗停 → 30s 后锁自动释放(防死锁)
   可重入：Hash 结构存 {threadId: count}，同线程多次加锁 count++
   ```

4. **红锁 Redlock 与争议**：
   ```
   Redlock(Antirez 提出)：N(通常5)个独立 Redis master，加锁要 ≥ (N/2+1)=3 个成功
   目的：单 Redis 主从切换丢锁(异步复制)，多节点过半数降低风险
   
   争议(Martin Kleppmann 批评)：
   ① 依赖时钟：跨节点时间假设，时钟漂移/闰秒破坏正确性
   ② GC pause：客户端 STW 时锁过期被别人抢，醒来后还以为持有 → 两个客户端"同时持有"
   → 结论：Redlock 既不是 AP 也不是 CP，安全性和性能都不极致
   
   生产建议：资金/强一致用 ZK/etcd(ZAB/Raft 共识)；性能优先用单 Redis 锁 + 兜底(版本号/状态机)
   ```

**易错点 & 追问**：
- **易错**：`DEL` 大 key 是同步操作，会阻塞主线程（Redis 单线程），生产必须用 `UNLINK`（异步）。这是大 key 删除卡顿的根因。
- **Q：分布式锁必备特性？** A：①互斥（同一时刻一个持有）②防死锁（持锁者崩溃锁能自动释放，靠过期时间）③可重入（同线程多次加锁）④解铃还须系铃人（释放要验证是自己的锁，用 UUID/threadId）。Redis SET NX PX + Lua 释放满足。
- **Q：释放锁为什么要 Lua？** A：`get→判断 UUID→del` 三步必须原子，否则中间锁过期被别人抢，你 del 了别人的锁。Lua 保证原子。

**速记口诀**：大 key 拆分 UNLINK 删，热 key 本地缓存加副本；Redisson 看门狗每十秒续，可重入 Hash 计数；红锁过半数有争议，时钟 GC 破正确；资金强一致用 ZK，性能优先单锁加兜底。

> **某创业项目/某头部电商关联**：某创业项目资金分布式锁用「Redis（Redisson 看门狗）+ 状态机兜底」——锁只是优化并发，真正防超卖/重复扣款靠状态机+唯一索引。诚实边界：未生产用 Redlock，认同其争议，资金强一致靠 DB 约束而非分布式锁。某头部电商热 key 用 Caffeine 本地缓存 + 多副本，扛住明星秒杀。

### Q1. TCP 为什么要三次握手、四次挥手？TIME_WAIT 怎么治理？

> 🔥🔥🔥 ｜ 考察：TCP 协议 ｜ 难度 ⭐⭐⭐⭐⭐ ｜ 高频

**一句话答案**：**三次握手**是「客户端 SYN → 服务端 SYN+ACK → 客户端 ACK」，三次是为了**确认双方收发能力都正常 + 防止历史失效连接（旧 SYN）建立脏连接**（两次无法确认服务端的发送能力，四次冗余）；**四次挥手**是「主动方 FIN → 被动方 ACK → 被动方 FIN → 主动方 ACK」，四次是因为 **TCP 全双工，被动方收到 FIN 时可能还有数据要发，ACK 和 FIN 必须分开**；**TIME_WAIT** 是主动关闭方等 **2MSL**（Maximum Segment Lifetime，报文最长寿命），作用是**确保最后的 ACK 到达 + 让旧报文消失**，大量 TIME_WAIT 用 `SO_REUSEADDR` + 长连接 + 连接池治理。

**深度解析**：

1. **三次握手流程**：
   ```
   Client                           Server
     │ ── SYN(seq=x) ──────────────→ │  服务端 SYN_RCV，半连接队列
     │ ←─ SYN+ACK(seq=y,ack=x+1) ──  │
     │ ── ACK(ack=y+1) ────────────→ │  服务端 ESTABLISHED，全连接队列
   ```
   - **为什么三次不是两次**：两次握手时，客户端发的旧 SYN（网络延迟）延迟到达服务端，服务端以为是新连接，回 SYN+ACK 就建立连接并占用资源，但客户端根本不想连 → 脏连接。三次握手让客户端第三次确认「我确实要连这个连接」，过滤历史 SYN。

2. **四次挥手流程**：
   ```
   主动方                    被动方
     │ ── FIN ──→ │  被动方回 ACK，进入 CLOSE_WAIT（还能发剩余数据）
     │ ←─ ACK ──  │
     │ ←─ FIN ──  │  被动方发完数据才 FIN
     │ ── ACK ──→ │  主动方进 TIME_WAIT，等 2MSL 后 CLOSED
   ```
   - **为什么四次**：TCP 全双工，被动方收到主动方 FIN 只是表示「主动方不再发数据」，被动方可能还有数据要继续发，所以先 ACK，等自己发完再 FIN。

3. **TIME_WAIT 与 2MSL**：
   ```
   2MSL = 2 × Maximum Segment Lifetime（Linux 约 60-120s）
   作用：
   ① 确保最后那个 ACK 到达被动方：若被动方没收到 ACK，会重发 FIN，主动方在 2MSL 内还能响应
   ② 让本次连接的所有报文从网络消失：防止延迟的旧报文被下一个复用同四元组的新连接错误接收
   
   大量 TIME_WAIT 的危害：占端口(客户端)、占内存(每条记录约几 KB)、CPU 消耗
   治理：
   ① SO_REUSEADDR/SO_REUSEPORT：复用 TIME_WAIT 端口
   ② 短连接改长连接 + 连接池（根本解，减少挥手次数）
   ③ 服务端由「主动关闭方」变「被动关闭方」（TIME_WAIT 转移到客户端）
   ④ 调小 tcp_fin_timeout / tcp_max_tw_buckets（治标）
   ```

4. **半连接队列与 SYN Flood**：
   ```
   半连接队列(SYN Queue)：收到 SYN 未完成握手的连接
   全连接队列(Accept Queue)：完成握手等待 accept 的连接
   
   SYN Flood 攻击：恶意发海量 SYN，不回第三次 ACK → 半连接队列撑满 → 正常连接进不来
   防御：SYN cookies（不存半连接状态，把信息编码进 seq 返回，ACK 时反算验证）
   ```

**易错点 & 追问**：
- **易错**：TIME_WAIT 是**主动关闭方**的状态，不是被动方。服务端频繁主动关连接会导致 TIME_WAIT 堆积。
- **Q：握手可以携带数据吗？** A：前两次不行（还没建立连接），第三次 ACK 可以携带数据（TCP Fast Open，TFO）。第三次 ACK 后客户端即可发数据。
- **Q：SYN 攻击怎么检测？** A：`netstat -ant | grep SYN_RCV | wc -l` 看半连接数，异常暴涨就是疑似攻击。

**速记口诀**：三次握手确收发，防旧 SYN 建脏连；四次挥手因双工，ACK 与 FIN 分开行；TIME_WAIT 等两 MSL，保 ACK 达加清旧包；复用端口长连接，半连接队列 SYN 洪来扰。

> **某创业项目/某头部电商关联**：某头部电商网关曾因短连接爆发 TIME_WAIT（数十万），改长连接 + 连接池后降 90%。生产服务端尽量做被动关闭方（让客户端 TIME_WAIT），减轻服务端压力。

### Q2. IO 模型有哪些？BIO/NIO/多路复用/AIO 区别？Reactor 模式是什么？

> 🔥🔥🔥 ｜ 考察：IO 模型 ｜ 难度 ⭐⭐⭐⭐⭐ ｜ 高频

**一句话答案**：五大 IO 模型：**阻塞 IO（BIO）、非阻塞 IO、IO 多路复用、信号驱动 IO、异步 IO（AIO）**；Java 的 NIO（Non-blocking）核心是 **Channel + Buffer + Selector（多路复用）**；**Reactor 模式**是事件驱动架构，分**单 Reactor 单线程**（Redis）、**单 Reactor 多线程**、**主从 Reactor 多线程**（Netty 主力）；架构师要分清「同步/异步」「阻塞/非阻塞」两个正交维度。

**深度解析**：

1. **五个 IO 模型（Linux）**：
   | 模型 | 特点 | 代表 |
   |------|------|------|
   | 阻塞 IO (BIO) | recvfrom 阻塞直到数据就绪 + 拷贝完成 | 传统 Socket，一连接一线程 |
   | 非阻塞 IO | 没数据立即返回 EWOULDBLOCK，轮询（忙等浪费 CPU）| 轮询模式 |
   | **IO 多路复用** | 一个线程监听多个 fd，select/poll/epoll 等就绪 | Java NIO Selector、Redis、Netty |
   | 信号驱动 IO | 内核数据就绪发 SIGIO 信号，应用再读 | 较少用 |
   | 异步 IO (AIO) | 内核完成「就绪+拷贝」后回调通知应用 | Windows IOCP、Linux io_uring |

2. **同步 vs 异步 / 阻塞 vs 非阻塞**（两个正交维度）：
   ```
   阻塞/非阻塞：调用后是否立即返回（不阻塞线程）
   同步/异步：数据拷贝阶段是否需要应用参与
   
   BIO：同步阻塞
   NIO(Selector)：同步非阻塞（数据就绪后，应用自己拷贝）
   AIO：异步非阻塞（内核拷贝完才通知，应用不参与拷贝）
   ```

3. **Java NIO 三件套**：
   ```
   Buffer：数据容器，read/write 都先经过 buffer
           flip/clear/compact 翻转读写指针
   Channel：双向通道（替代单向 Stream），可读可写
   Selector：多路复用器，一个线程监听多个 Channel 的事件(读就绪/写就绪/连接)
   → 一个线程管上万连接，非阻塞轮询就绪事件
   ```

4. **Reactor 模式三种**：
   ```
   ① 单 Reactor 单线程：
      Reactor(1 个线程)：epoll 事件分发 + 处理 IO + 处理业务
      优点：简单无锁；缺点：单核瓶颈，业务慢拖垮 IO
      代表：Redis 6.0 前
   
   ② 单 Reactor 多线程：
      Reactor(1 个线程)：只管事件分发，IO 处理交给线程池
      优点：业务不阻塞 IO；缺点：Reactor 单线程接连接是瓶颈
   
   ③ 主从 Reactor 多线程（主从分配）：
      MainReactor(BossGroup)：只 accept 新连接
      SubReactor(WorkerGroup)：处理已连接的 IO 读写
      Worker 线程池：处理耗时业务(避免阻塞 IO 线程)
      代表：Netty 默认模型
   ```

**易错点 & 追问**：
- **易错**：Java 的 NIO 是「同步非阻塞」，不是真正的异步（AIO 才是）。Netty 是基于 NIO 的，也叫「同步非阻塞」。
- **Q：Netty 为什么放弃了 AIO？** A：Linux 的 AIO（Java AsynchronousChannel）底层用 epoll 模拟，性能不比 NIO 好且 API 复杂；Windows 的 IOCP 虽完善但 Netty 跨平台，统一用 NIO。所以 Netty 移除了 AIO 支持，专注 NIO。
- **Q：BIO 怎么扛并发？** A：BIO 一连接一线程，靠线程池扛（如 Tomcat BIO 模式）。但线程多（几千）→ 上下文切换开销大、内存占用高，所以高并发改 NIO（如 Tomcat NIO、Netty）。

**速记口诀**：阻塞非阻塞看返回，同步异步看拷贝；BIO 同步阻塞一连接一线程，NIO 多路复用一线程万连接；Reactor 单线 Redis 模，主从 Netty Boss 加 Worker；业务耗时入线程池，莫让业务阻 IO。

> **某创业项目/某头部电商关联**：某头部电商网关用 Netty（主从 Reactor）扛 10 万 QPS，IO 线程只做收发，业务逻辑丢到独立线程池。强调：IO 线程绝不做耗时操作（DB/远程调用），否则拖垮所有连接。

### Q3. epoll 为什么比 select/poll 快？LT 和 ET 模式有什么区别？

> 🔥🔥 ｜ 考察：epoll 原理 ｜ 难度 ⭐⭐⭐⭐ ｜ 高频

**一句话答案**：**select** 有 1024 fd 上限、O(n) 遍历、每次拷贝 fd 集合到内核；**poll** 取消上限但仍 O(n) 遍历；**epoll** 用**红黑树存监听 fd + 就绪链表存就绪 fd**，`epoll_wait` 只返回就绪的（O(1)），无需遍历全部，且支持**百万连接**；**LT（水平触发，默认）**只要可读每次都通知，**ET（边缘触发）**只在状态变化时通知一次，必须配非阻塞 IO + 循环读到 EAGAIN，效率更高但易漏读。

**深度解析**：

1. **三模型对比**：
   | 维度 | select | poll | epoll |
   |------|--------|------|-------|
   | fd 上限 | 1024（FD_SETSIZE）| 无（链表）| 无（红黑树）|
   | 时间复杂度 | O(n) 遍历 | O(n) 遍历 | O(1)（就绪链表）|
   | fd 拷贝 | 每次全拷贝到内核 | 每次全拷贝 | 只 epoll_ctl 时拷贝一次 |
   | 通知方式 | 每次返回需遍历找就绪 | 同 select | 直接返回就绪 fd 列表 |
   | 适用 | 连接少 | 连接少 | 大量连接（Redis/Nginx/Netty）|

2. **epoll 三 API + 数据结构**：
   ```
   epoll_create：创建 epoll 实例（内核分配红黑树 + 就绪链表）
   epoll_ctl：增删改监听的 fd（注册到红黑树，并注册回调函数）
       → 设备就绪时（如网卡数据到），内核回调把该 fd 加入就绪链表
   epoll_wait：阻塞等待，直接返回就绪链表里的 fd（O(1)，只拷贝就绪的）
   → 关键：就绪检测由内核回调完成，不是应用遍历
   ```

3. **LT vs ET**：
   ```
   LT（Level Trigger，水平触发，默认）：
   - 只要 fd 缓冲区有数据可读，每次 epoll_wait 都通知
   - 不会漏读，可阻塞/非阻塞 IO，编程简单
   - 缺点：可能重复通知
   
   ET（Edge Trigger，边缘触发）：
   - 只在缓冲区「状态变化」时通知一次（从无数据→有数据）
   - 必须配非阻塞 IO，循环 read 直到返回 EAGAIN（把数据读干净）
   - 否则下次不通知，剩余数据丢失
   - 效率高（通知少），但编程复杂、易出错
   - Nginx 用 ET 模式
   ```

**易错点 & 追问**：
- **易错**：epoll 不是「绝对 O(1)」，准确说是「就绪事件 O(1) 返回，但活跃 fd 多时仍需处理所有就绪 fd」。但相比 select 的「遍历全部 fd 找就绪」，epoll 高效得多。
- **Q：epoll 为什么用红黑树存 fd？** A：epoll_ctl 增删改 fd 需要查找，红黑树查找/插入/删除 O(logN)，且有序。就绪检测靠回调，不依赖树遍历。
- **Q：epoll 在什么场景不如 select？** A：连接数少且全部活跃（如几十个连接每秒都来数据），epoll 的红黑树维护开销相对不划算。但极少见，绝大多数场景 epoll 完胜。

**速记口诀**：select 千二上限 O(n) 遍，poll 解限仍遍历；epoll 红黑加就绪表，回调检测 O(1) 返；LT 有数就通知，ET 变化才通知一次；ET 必配非阻塞循环读，读到 EAGAIN 才罢休。

> **某创业项目/某头部电商关联**：某头部电商网关、Redis、Nginx 全用 epoll。强调：高并发网络编程的本质就是 epoll（Linux），理解 epoll 是 Java/Go 后端性能调优的基础。

### Q4. 零拷贝是什么？mmap、sendfile、splice 区别？Kafka/Netty 怎么用？

> 🔥🔥 ｜ 考察：零拷贝 ｜ 难度 ⭐⭐⭐⭐ ｜ 高频

**一句话答案**：**零拷贝（Zero-Copy）**指减少甚至消除 CPU 拷贝（数据在内核态和用户态之间）和上下文切换，提升 IO 密集场景性能；**mmap** 把文件映射到用户内存（减少一次 CPU 拷贝，适合读）；**sendfile** 内核内直接把读 buffer 拷到 socket buffer（不经过用户空间，减少 2 次上下文切换 + CPU 拷贝，Linux 2.4+ 配合 DMA gather 可零 CPU 拷贝）；**Kafka 用 sendfile** 做消息零拷贝读取，**Netty 用 CompositeByteBuf + FileRegion** 实现零拷贝。

**深度解析**：

1. **传统读文件发送到网络的代价**：
   ```
   read(file, buf) + send(socket, buf)：
   ① DMA 把磁盘数据拷到内核 buffer
   ② CPU 把内核 buffer 拷到用户 buffer（read 返回）
   ③ CPU 把用户 buffer 拷到 socket buffer
   ④ DMA 把 socket buffer 拷到网卡
   → 4 次上下文切换 + 4 次拷贝(2 次 DMA + 2 次 CPU)，CPU 参与了 2 次拷贝
   ```

2. **三种零拷贝技术**：
   | 技术 | 原理 | 减少的开销 | 适用 |
   |------|------|-----------|------|
   | **mmap** | 文件映射到用户空间内存，内核 buffer 和用户 buffer 共享 | 减少 1 次 CPU 拷贝（内核→用户）| 读文件（频繁改用，如用户态读）|
   | **sendfile** | 内核内直接从读 buffer 拷到 socket buffer，不经用户空间 | 减少 2 次上下文切换 + 1 次 CPU 拷贝 | 文件→网络传输（Kafka）|
   | **splice** | 用管道在两个 fd 间传输，无 CPU 拷贝 | 零 CPU 拷贝 | 管道场景 |
   - Linux 2.4+ sendfile 配合 **DMA Scatter-Gather**：socket buffer 只存描述符（地址+长度），DMA 直接从读 buffer 拷到网卡，**完全零 CPU 拷贝**。

3. **Kafka / Netty 应用**：
   ```
   Kafka：消费消息时用 sendfile 把日志段文件直接发到 socket（零拷贝）
        → 大幅提升消费吞吐，producer→broker→consumer 全链路高效
   Netty：
   - CompositeByteBuf：多个 ByteBuf 逻辑组合成一个，不拷贝（减少内存复制）
   - FileRegion：封装 sendfile，文件传输零拷贝
   - ByteBuf 池化（PooledByteBufAllocator）：复用内存，减少 GC
   ```

**易错点 & 追问**：
- **易错**：「零拷贝」不是「零次拷贝」，是「零 CPU 拷贝」（DMA 还在拷）。mmap/sendfile 都还有 DMA 拷贝，只是 CPU 不参与。
- **Q：mmap 和 sendfile 怎么选？** A：mmap 适合「需要用户态处理数据」的场景（读取后还要改）；sendfile 适合「纯转发」（文件到网络，不经处理），更高效。Kafka 消费是纯转发用 sendfile。
- **Q：mmap 的坑？** A：①大文件映射占虚拟内存 ②写 mmap 的页面可能在脏页刷盘时阻塞（page fault）③mmap 写时 Copy-On-Write。不适合频繁随机写。

**速记口诀**：传统四切加四拷，零拷贝减 CPU 搬；mmap 映射省一拷，sendfile 内核直接传；splice 管道零 CPU，Kafka 消费用 sendfile；Netty 组合缓冲池化复用，零拷贝提速 IO 密。

> **某创业项目/某头部电商关联**：某头部电商消息中间件（类似 Kafka）用 sendfile 零拷贝消费，吞吐达百万级 TPS。架构师选型中间件时，零拷贝是衡量 IO 性能的关键指标。

### Q5. HTTP/1.1、HTTP/2、HTTP/3 有什么区别？什么是队头阻塞？

> 🔥🔥 ｜ 考察：HTTP 演进 ｜ 难度 ⭐⭐⭐⭐ ｜ 高频

**一句话答案**：**HTTP/1.1** 引入持久连接（keep-alive 复用 TCP）、管道化（但有**应用层队头阻塞**）、Host 头；**HTTP/2**（基于 SPDY）用**二进制分帧 + 多路复用**（一个 TCP 并发多请求，解决应用层队头阻塞）+ HPACK 头部压缩 + 服务端推送，但仍有 **TCP 层队头阻塞**（丢包阻塞所有流）；**HTTP/3**（基于 QUIC，QUIC 基于 UDP）用**独立流**彻底解决队头阻塞 + 0-RTT 建连 + 连接迁移 + 内置 TLS 1.3。

**深度解析**：

1. **三代演进**：
   | 版本 | 核心特性 | 队头阻塞 | 其他 |
   |------|----------|:--------:|------|
   | **HTTP/1.0** | 每次请求新建连接（短连接） | 有 | 效率低 |
   | **HTTP/1.1** | 持久连接 keep-alive、管道化 pipeline、Host 头、缓存控制 | 应用层（管道化前请求慢阻塞后续）| 默认长连接 |
   | **HTTP/2** | 二进制分帧、多路复用、HPACK 头压缩、服务端推送 | TCP 层（丢包阻塞所有流）| 一个 TCP 多流并发 |
   | **HTTP/3** | QUIC（基于 UDP）、独立流、0-RTT、连接迁移 | 基本解决 | 内置 TLS 1.3 |

2. **队头阻塞（Head of Line Blocking）演进**：
   ```
   HTTP/1.1 应用层队头阻塞：
   - 管道化时，前一个请求响应慢，后续请求即使就绪也得等（响应必须按序）
   - 解法：多开 TCP 连接（浏览器一般 6 个），但浪费资源
   
   HTTP/2 多路复用解决应用层 HOL：
   - 一个 TCP 连接上多个流(stream)并发，响应可不按序返回
   - 但 TCP 层：一个包丢了，整个 TCP 连接阻塞等重传 → 所有流被阻塞
   
   HTTP/3 QUIC 独立流彻底解决：
   - 每个流独立（不同包序列），一个流丢包只影响该流
   - 基于 UDP，每个 stream 独立可靠传输
   ```

3. **HTTP/3 / QUIC 亮点**：
   - **0-RTT 建连**：复用之前的握手信息，第二次连接 0 往返即发数据（TCP+TLS 要 1-3 RTT）。
   - **连接迁移**：手机切 WiFi/4G 时 IP 变了，TCP 断连，QUIC 用 Connection ID 保持连接不断。
   - **内置加密**：TLS 1.3 内嵌在 QUIC，协议本身就是加密的。

**易错点 & 追问**：
- **易错**：HTTP/2 多路复用解决了「应用层队头阻塞」，但引入了「TCP 层队头阻塞」（这是 HTTP/3 要解决的）。
- **Q：为什么 HTTP/3 不直接用 TCP？** A：TCP 是内核态、面向连接（四元组），多流共享一个连接，丢包影响所有流；且 TCP 内核实现演进慢。QUIC 在用户态基于 UDP，可快速迭代，独立流解决 HOL。
- **Q：HTTP/2 服务端推送为什么后来被弱化？** A：推送的资源和客户端缓存难以协调（可能推了已有缓存），多数浏览器默认禁用了推送。HTTP/3 已移除服务端推送。

**速记口诀**：1.1 长连加管道，应用层有队头阻；2.0 二进制多路复，解决应用丢 TCP；3.0 QUIC 基于 UDP，独立流零 HOL；0-RTT 迁移加加密，建连快不断连。

> **某创业项目/某头部电商关联**：某头部电商 APP 用 HTTP/2（多路复用减少连接数），首屏接口并发拉取。HTTP/3 在弱网（移动网络切换）优势明显，大厂在试点。架构师要关注协议演进对性能的影响。

### Q6. Netty 的核心架构？EventLoop、Channel、Pipeline 怎么协作？

> 🔥 ｜ 考察：Netty 框架 ｜ 难度 ⭐⭐⭐⭐ ｜ 中高频

**一句话答案**：Netty 是基于 Java NIO 的异步事件驱动网络框架，核心组件：**EventLoop**（事件循环，绑定单线程，处理 Channel 的 IO 事件）、**Channel**（连接抽象）、**ChannelPipeline**（处理链，双向链表，入站/出站）、**ChannelHandler**（编解码/业务处理器）、**ByteBuf**（读写指针分离、可池化的字节缓冲）；采用**主从 Reactor 模型**——BossGroup 接连接、WorkerGroup 处理 IO、业务线程池处理耗时逻辑；架构师要懂「IO 线程不做业务」这条铁律。

**深度解析**：

1. **核心组件**：
   | 组件 | 职责 |
   |------|------|
   | **EventLoop** | 事件循环，绑定一个线程，负责其上所有 Channel 的 IO 事件（单线程串行，无锁）|
   | **EventLoopGroup** | EventLoop 池（BossGroup/WorkerGroup）|
   | **Channel** | 连接抽象（NioSocketChannel/NioServerSocketChannel），封装 Socket |
   | **ChannelPipeline** | 处理链，双向链表，入站（读）从 head 往 tail，出站（写）从 tail 往 head |
   | **ChannelHandler** | 具体处理器（编解码、业务逻辑），加到 Pipeline |
   | **ChannelHandlerContext** | Handler 和 Pipeline/EventLoop 的交互接口 |

2. **主从 Reactor 模型**：
   ```
   BossGroup：1 个 EventLoop，accept 新连接
       → 收到连接后，把 Channel 注册到 WorkerGroup 的某个 EventLoop
   WorkerGroup：N 个 EventLoop（默认 CPU×2），处理已连接的 IO 读写
       → 每个 EventLoop 绑定多个 Channel，单线程串行处理（无锁）
   业务线程池：IO 线程把耗时业务（DB/远程调用）丢给业务线程池
       → 避免阻塞 IO 线程（铁律：IO 线程不做耗时操作）
   ```

3. **ByteBuf vs NIO ByteBuffer**：
   ```
   NIO ByteBuffer：单指针（flip 翻转读写），固定容量，不池化
   Netty ByteBuf：
   - readIndex/writeIndex 分离（读写互不干扰）
   - 可动态扩容
   - 可池化(PooledByteBufAllocator，jemalloc 算法)→ 减少 GC
   - 支持零拷贝(CompositeByteBuf 组合多个，Heap/Direct 切换)
   ```

**易错点 & 追问**：
- **易错**：EventLoop 是**单线程**的，一个 EventLoop 绑定多个 Channel，串行处理——无锁但单线程是吞吐限制（所以用 WorkerGroup 多个 EventLoop）。
- **Q：Netty 怎么解决粘包/半包？** A：提供解码器——`LineBasedFrameDecoder`（换行）、`DelimiterBasedFrameDecoder`（分隔符）、`LengthFieldBasedFrameDecoder`（长度字段，最常用）、固定长度。本质是在 Pipeline 里加一个拆包 Handler。
- **Q：Netty 怎么处理空闲连接？** A：`IdleStateHandler` 检测读/写空闲，超时触发事件，业务可主动关闭。某头部电商网关用这个清理僵尸连接。

**速记口诀**：Netty 异步事件驱，EventLoop 单线串行；Boss 接连 Worker 管 IO，业务入池莫阻塞；Pipeline 双向链出入站，Handler 编解码加业务；ByteBuf 指针分加池化，粘包半包解码器拆。

> **某创业项目/某头部电商关联**：某头部电商网关用 Netty（BossGroup=1，WorkerGroup=CPU×2，业务单独线程池）。强调：IO 线程绝不做 DB/远程调用，否则一个慢请求拖垮所有连接。某创业项目 AI SSE 流式推送参考 Netty 的事件驱动设计。

### Q1. IoC 容器的启动流程？Bean 的完整生命周期是怎样的？

> 🔥🔥🔥 ｜ 考察：IoC 与 Bean 生命周期 ｜ 难度 ⭐⭐⭐⭐⭐ ｜ 高频

**一句话答案**：IoC 容器启动分**注册 BeanDefinition（Bean 定义）→ 实例化 → 属性填充 → 初始化 → 使用 → 销毁**；Bean 完整生命周期：**实例化（反射）→ 属性赋值（依赖注入）→ Aware 接口回调 → BeanPostProcessor 前置 → 初始化方法（@PostConstruct/InitializingBean/init-method）→ BeanPostProcessor 后置（AOP 代理在此生成）→ 使用 → 销毁**；**BeanPostProcessor 的 postProcessAfterInitialization 是 AOP 生成代理的入口**。

**深度解析**：

1. **IoC 容器启动流程**：
   ```
   ① 加载配置：注解扫描(@ComponentScan)或 XML
   ② 注册 BeanDefinition：解析成 BeanDefinition(含 class、scope、属性、依赖)，存入 beanDefinitionMap
      —— 此时还未实例化，只是「图纸」
   ③ 实例化非懒加载的单例 Bean：getBean → 反射 newInstance 创建对象
   ④ 属性填充 populate：依赖注入(@Autowired/@Resource)，触发依赖 Bean 的创建
   ⑤ 初始化 initialize：Aware 回调 + BeanPostProcessor + 初始化方法
   ⑥ 放入 singletonObjects(一级缓存)，对外可用
   ```

2. **Bean 完整生命周期**：
   ```
   实例化            newInstance()，对象创建(未设置属性)
        ↓
   属性赋值          populateBean，注入依赖(@Autowired)
        ↓
   Aware 回调       BeanNameAware.setBeanName / BeanFactoryAware / ApplicationContextAware
                   (让 Bean 感知容器信息)
        ↓
   BeanPostProcessor 前置   postProcessBeforeInitialization
                   (@PostConstruct 在此被 CommonAnnotationBeanPostProcessor 触发)
        ↓
   初始化方法        InitializingBean.afterPropertiesSet() / @PostConstruct / init-method
        ↓
   BeanPostProcessor 后置   postProcessAfterInitialization
                   ★ AOP 在此生成代理对象(AbstractAutoProxyCreator)
        ↓
   使用             Bean 就绪，对外提供
        ↓
   销毁             @PreDestroy / DisposableBean.destroy() / destroy-method
                   (容器关闭时)
   ```

3. **BeanPostProcessor 是 Spring 扩展核心**：
   - 几乎所有「增强」都基于 BeanPostProcessor：AOP（代理）、@Autowired（注入）、@Async（异步）、配置绑定。
   - `postProcessAfterInitialization` 返回的对象会**替换原对象**——AOP 就是返回代理对象替换原始 Bean。

**易错点 & 追问**：
- **易错**：BeanDefinition 注册（解析配置）和 Bean 实例化是两个阶段。`@ComponentScan` 只是注册定义，真正创建在首次 `getBean`（或容器刷新时对单例预实例化）。
- **Q：BeanFactory 和 ApplicationContext 区别？** A：BeanFactory 是顶层容器（懒加载，基础功能）；ApplicationContext 是其子接口（预实例化单例、事件、国际化、AOP 集成），实际开发用 ApplicationContext。
- **Q：@PostConstruct、InitializingBean、init-method 顺序？** A：@PostConstruct（最先，BeanPostProcessor 触发）→ InitializingBean.afterPropertiesSet → init-method（最后）。

**速记口诀**：注册定义先入图，实例反射后填注；Aware 回调感容器，前后置处理器是核心；后置生成 AOP 代理，初始化三步走；销毁三路逆序调，生命周期闭环全。

> **某创业项目/某头部电商关联**：某创业项目用 @PostConstruct 做配置加载预热（初始化时把字典缓存到内存），用 BeanPostProcessor 做统一日志切面。理解生命周期才能正确选择扩展点。

### Q2. Spring 怎么解决循环依赖？为什么是三级缓存？哪些情况解决不了？

> 🔥🔥🔥 ｜ 考察：循环依赖 ｜ 难度 ⭐⭐⭐⭐⭐ ｜ 高频

**一句话答案**：Spring 用**三级缓存**解决**单例 setter/字段注入**的循环依赖：一级 `singletonObjects`（完整 Bean）、二级 `earlySingletonObjects`（早期半成品）、三级 `singletonFactories`（ObjectFactory 提前生成引用）；流程：A 实例化后把 ObjectFactory 放三级缓存 → A 注入 B → B 注入 A 时从三级缓存拿 A 的早期引用（若需 AOP 在此生成代理）放入二级 → B 完成 → A 注入 B 完成；**三级而非二级是为了 AOP——只有出现循环依赖且需要代理时才提前生成代理，保证代理只生成一次**；**构造器注入和 prototype 作用域解决不了**。

**深度解析**：

1. **三级缓存**：
   ```
   singletonObjects(一级)：完整的单例 Bean
   earlySingletonObjects(二级)：早期暴露的半成品 Bean(实例化但未完成初始化)
   singletonFactories(三级)：ObjectFactory，lambda 生成早期引用(支持 AOP 提前代理)
   ```

2. **循环依赖解决流程（A 依赖 B，B 依赖 A）**：
   ```
   1. 创建 A：实例化 A，把 A 的 ObjectFactory 放入三级缓存
   2. A 填充属性：发现依赖 B，去 getBean(B)
   3. 创建 B：实例化 B，把 B 的 ObjectFactory 放入三级缓存
   4. B 填充属性：发现依赖 A，getBean(A)
      → 一级没有 → 二级没有 → 三级有 A 的 ObjectFactory
      → 调用 ObjectFactory.getObject()：若 A 需要 AOP，生成 A 的代理；否则返回 A 本身
      → 放入二级缓存 earlySingletonObjects，删除三级缓存
   5. B 注入 A（早期引用/代理），B 完成初始化，B 进一级缓存
   6. A 继续：注入 B，A 完成初始化，A 进一级缓存
   ```

3. **为什么三级而不是二级（关键）**：
   - 如果没有 AOP，二级缓存就够：一级存成品、二级存半成品。
   - 有 AOP 时，Bean 最终是代理对象。正常流程在 `postProcessAfterInitialization` 生成代理。但循环依赖时，B 注入 A 需要 A 的引用——此时 A 还没到后置处理阶段。
   - 三级缓存存 **ObjectFactory（延迟）**，只有真正出现循环依赖时才调用它生成代理（提前暴露代理）。这样：①代理只生成一次 ②无循环依赖时不提前生成（不影响正常流程）。
   - 二级缓存存已生成的早期代理/对象，避免重复生成。

4. **解决不了的情况**：
   | 场景 | 原因 |
   |------|------|
   | **构造器注入循环依赖** | 构造时就要依赖，此时 Bean 还没实例化，无法放入缓存 → 报错 |
   | **prototype 作用域循环依赖** | prototype 每次新建，不缓存，无法提前暴露 |
   | **@Async + 循环依赖** | 异步代理的特殊性，某些版本会报错（SpringBoot 2.6+ 默认禁用循环依赖 spring.main.allow-circular-references=false）|

**易错点 & 追问**：
- **易错**：三级缓存解决的是**单例 + setter/字段注入**的循环依赖，不是所有循环依赖。
- **Q：SpringBoot 2.6 为什么默认禁用循环依赖？** A：循环依赖是设计坏味道（紧耦合），Spring 鼓励重构。设 `spring.main.allow-circular-references=true` 可重新开启（不推荐）。
- **Q：怎么避免循环依赖？** A：①重构，提取公共依赖 ②用 @Lazy 延迟注入（注入代理）③改用 setter 注入（字段/setter 能解决，构造器不能）④事件驱动解耦。

**速记口诀**：三级缓存解循环，一级成品二级半，三级工厂生代理；A 注入 B B 注 A，三级取工厂提前暴露；三级而非二级为 AOP，代理只生一次保证一；构造器和 prototype 不解，@Lazy 重构是正道。

> **某创业项目/某头部电商关联**：某创业项目早期踩过循环依赖坑（A 服务注入 B，B 注入 A），用 @Lazy 解决，后重构为单向依赖。强调：循环依赖是设计问题，三级缓存是「兜底」不是「鼓励」，生产应尽量避免。

### Q3. AOP 的原理？JDK 动态代理和 CGLIB 怎么选？为什么同类调用 AOP 会失效？

> 🔥🔥🔥 ｜ 考察：AOP 代理 ｜ 难度 ⭐⭐⭐⭐⭐ ｜ 高频

**一句话答案**：Spring AOP 在运行时通过**动态代理**织入，`BeanPostProcessor` 的 `postProcessAfterInitialization` 生成代理；**JDK 动态代理**基于接口（目标类须实现接口，`Proxy.newProxyInstance` + `InvocationHandler`），**CGLIB** 基于继承（生成子类，不能代理 final 类/方法，`MethodInterceptor`），Spring Boot 2.x+ 默认用 **CGLIB**（`proxyTargetClass=true`）；**同类调用 AOP 失效**：方法 A 调方法 B（`this.B()`），`this` 是原始对象不是代理，绕过了代理 → B 的切面不生效，解决用注入自身/`AopContext.currentProxy()`。

**深度解析**：

1. **AOP 术语**：
   | 术语 | 含义 |
   |------|------|
   | 切面 Aspect | 横切关注点模块化（如日志切面），@Aspect |
   | 切点 Pointcut | 定义「哪些方法被增强」（表达式，如 execution(* com.xx.*.*(..))）|
   | 通知 Advice | 增强逻辑：Before/After/Around/AfterReturning/AfterThrowing |
   | 织入 Weaving | 把切面应用到目标：编译时/类加载时/运行时（Spring 运行时）|

2. **两种代理对比**：
   | 维度 | JDK 动态代理 | CGLIB |
   |------|--------------|-------|
   | 原理 | 基于接口 | 基于继承（生成子类）|
   | 要求 | 目标类必须实现接口 | 目标类可被继承（非 final）|
   | 性能 | 创建快，调用稍慢（反射）| 创建慢（生成字节码），调用快 |
   | 限制 | 只能代理接口方法 | 不能代理 final 类/方法、private 方法 |
   | Spring 选择 | 有接口用 JDK | Spring Boot 2.x+ 默认 CGLIB |

3. **AOP 失效的根本原因（self-invocation）**：
   ```java
   @Service
   public class OrderService {
       public void methodA() {
           this.methodB();  // ← this 是原始对象，不是代理！B 的切面失效
       }
       @Transactional  // 想让 B 有事务
       public void methodB() { ... }
   }
   ```
   - **原因**：Spring 注入到容器的是**代理对象**，外部调用 `orderService.methodA()` 走代理（增强生效）；但 methodA 内部 `this.methodB()` 的 `this` 是原始 OrderService 对象，不走代理 → B 的 @Transactional 不生效。
   - **解决**：
     - ① 注入自身：`@Autowired private OrderService self;` 然后 `self.methodB()`
     - ② `AopContext.currentProxy()` 拿当前代理（需开启 `@EnableAspectJAutoProxy(exposeProxy=true)`）
     - ③ 把 B 拆到另一个 Bean
     - ④ 直接把 B 的逻辑写在 A 里（如果简单）

**易错点 & 追问**：
- **易错**：private/protected/static 方法 AOP 也不生效（JDK 代理只管 public 接口方法，CGLIB 不能覆盖 final/private/static）。
- **Q：@Transactional 失效有哪些场景？** A：①同类调用（self-invocation）②非 public 方法 ③final/static 方法 ④异常被 catch 不抛出 ⑤异常类型不对（默认只回滚 RuntimeException/Error，checked 异常需 `rollbackFor=Exception.class`）⑥没走代理（new 出来的对象）⑦数据库不支持事务（如 MyISAM 引擎）。
- **Q：Spring AOP 和 AspectJ 区别？** A：Spring AOP 是运行时动态代理（只能方法级，性能有代理开销）；AspectJ 是编译时/类加载时织入（字节码增强，支持字段/构造器级，性能更好）。Spring AOP 借用了 AspectJ 的注解语法（@Aspect/@Pointcut）但实现不同。

**速记口诀**：运行时代理织入 AOP，JDK 基接口 CGLIB 基继承；Spring Boot 默认 CGLIB，final private static 不代理；同类 this 调用绕代理，失效注入自身 AopContext；事务失效七宗罪，同类非公异常吞。

> **某创业项目/某头部电商关联**：某创业项目踩过 @Transactional 失效坑——同类的非事务方法调事务方法，数据没回滚。修复后强制规范：事务方法独立、跨类调用、异常抛出。某头部电商统一日志/监控切面（@Aspect），但不能滥用 AOP（性能开销 + 调试难）。

### Q4. @Transactional 的传播机制有哪些？默认是哪个？怎么选？

> 🔥🔥🔥 ｜ 考察：事务传播 ｜ 难度 ⭐⭐⭐⭐⭐ ｜ 高频

**一句话答案**：Spring 事务 7 种传播机制（PROPAGATION）：**REQUIRED（默认，有则加入无则新建）**、REQUIRES_NEW（总新建，挂起当前）、NESTED（有则嵌套 savepoint，无则新建）、SUPPORTS（有则加入无则非事务）、NOT_SUPPORTED（非事务执行，挂起当前）、MANDATORY（必须在事务中否则抛异常）、NEVER（必须非事务否则抛异常）；核心记住 **REQUIRED（最常用）、REQUIRES_NEW（独立日志/审计）、NESTED（部分回滚）** 三个。

**深度解析**：

1. **7 种传播机制**：
   | 传播行为 | 当前有事务 | 当前无事务 | 典型场景 |
   |----------|:----------:|:----------:|----------|
   | **REQUIRED**（默认）| 加入 | 新建 | 99% 场景，最常用 |
   | **REQUIRES_NEW** | 挂起当前，新建独立事务 | 新建 | 日志/审计（主事务失败也要记日志）|
   | **NESTED** | 嵌套事务（savepoint，可部分回滚）| 新建 | 子操作失败不影响主（基于保存点）|
   | SUPPORTS | 加入 | 非事务执行 | 查询（有事务就加入，没有也无妨）|
   | NOT_SUPPORTED | 挂起当前，非事务执行 | 非事务执行 | 耗时操作不占用事务连接 |
   | MANDATORY | 加入 | 抛异常 | 强制要求在事务中调用 |
   | NEVER | 抛异常 | 非事务执行 | 强制要求非事务调用 |

2. **REQUIRED vs REQUIRES_NEW vs NESTED（重点）**：
   ```
   REQUIRED（默认）：方法 A 调方法 B，B 加入 A 的事务
      → A 或 B 任一异常，整个回滚（同生共死）
      → 适合「B 是 A 的必要组成」
   
   REQUIRES_NEW：B 新开独立事务，A 的事务挂起
      → B 提交后，A 恢复继续
      → B 失败不影响 A（独立）；A 失败不影响已提交的 B
      → 适合「日志/审计必须独立记录」
      → 注意：会占用两个数据库连接（A 挂起占一个，B 占一个），连接池要够
   
   NESTED：B 在 A 内部开嵌套事务（基于 savepoint）
      → B 失败回滚到 savepoint，A 可选择捕获继续或整体回滚
      → 比 REQUIRES_NEW 轻量（同一个事务，靠 savepoint）
      → 适合「子操作失败可容忍，主流程继续」
   ```

3. **隔离级别（4 种 + 默认）**：
   - `DEFAULT`（用数据库默认）、`READ_UNCOMMITTED`、`READ_COMMITTED`、`REPEATABLE_READ`、`SERIALIZABLE`。
   - 一般不覆盖数据库设置，保持 DEFAULT（即 MySQL 的 RR）。

**易错点 & 追问**：
- **易错**：REQUIRES_NEW 会**占用两个数据库连接**（外层事务挂起但连接不释放），高并发下可能导致连接池耗尽。慎用。
- **Q：@Transactional 注解加在 private 方法上有效吗？** A：无效。Spring AOP 代理只能增强 public 方法（JDK/CGLIB 限制）。private/protected 方法加 @Transactional 不报错但不生效。
- **Q：@Transactional 加在类上还是方法上？** A：类上对该类所有 public 方法生效；方法上只对该方法生效（方法级覆盖类级）。推荐加在方法上（精确控制）。

**速记口诀**：七种传播记三要，REQUIRED 默认同生共死；REQUIRES_NEW 独立记日志，NESTED 嵌套部分回滚；SUPPORTS 查询有就加，NOT_SUPPORTED 耗时不占连；MANDATORY 强制事务内，NEVER 强制非事务。

> **某创业项目/某头部电商关联**：某创业项目分润主事务用 REQUIRED，审计日志用 REQUIRES_NEW（分润失败也要记操作日志）。强调：REQUIRES_NEW 要注意连接池大小，高并发场景慎用，避免连接耗尽。

### Q5. Spring Boot 自动配置原理？怎么实现一个自己的 Starter？

> 🔥🔥 ｜ 考察：自动配置 ｜ 难度 ⭐⭐⭐⭐ ｜ 高频

**一句话答案**：`@SpringBootApplication` = `@SpringBootConfiguration` + `@EnableAutoConfiguration` + `@ComponentScan`；**@EnableAutoConfiguration** 通过 `@Import(AutoConfigurationImportSelector)` 加载 `META-INF/spring.factories`（2.x）或 `META-INF/spring/...AutoConfiguration.imports`（3.x）里的自动配置类；每个配置类用**条件装配**（`@ConditionalOnClass`/`@ConditionalOnBean`/`@ConditionalOnMissingBean`/`@ConditionalOnProperty`）决定是否生效；**「约定大于配置」**——引入 starter 依赖，自动配置就绪，用户可在 application.yml 覆盖；自己做 starter 就是写配置类 + 条件注解 + 注册到 imports 文件。

**深度解析**：

1. **启动注解拆解**：
   ```
   @SpringBootApplication
   = @SpringBootConfiguration  (本质是 @Configuration，标记配置类)
   + @EnableAutoConfiguration  (自动配置入口)
   + @ComponentScan            (扫描当前包及子包的 @Component/@Service/@Controller)
   ```

2. **自动配置加载链**：
   ```
   @EnableAutoConfiguration
   → @Import(AutoConfigurationImportSelector.class)
   → selectImports() 读取 META-INF/spring.factories (Spring Boot 2.x)
                      或 META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports (3.x)
   → 加载所有 AutoConfiguration 类(如 RedisAutoConfiguration、DataSourceAutoConfiguration)
   → 每个类根据 @Conditional 条件判断是否生效
   → 生效的注册对应 Bean
   ```

3. **条件装配注解**：
   | 注解 | 生效条件 |
   |------|----------|
   | `@ConditionalOnClass` | classpath 有指定类（如引入 redis 依赖才配 RedisTemplate）|
   | `@ConditionalOnMissingBean` | 容器中没有该 Bean（允许用户自定义覆盖）|
   | `@ConditionalOnBean` | 容器中已有指定 Bean |
   | `@ConditionalOnProperty` | 配置项满足（如 `prefix.enabled=true`）|
   | `@ConditionalOnWebApplication` | 是 Web 应用 |

4. **「约定大于配置」的体现**：
   - 引入 `spring-boot-starter-data-redis` → 自动配置 RedisTemplate、ConnectionFactory。
   - 用户不配，用默认（localhost:6379）；在 application.yml 配 `spring.redis.host` 则覆盖默认。
   - 用户自定义 RedisTemplate Bean → `@ConditionalOnMissingBean` 让自动配置的退让，用用户的。

5. **自定义 Starter 步骤**：
   ```
   ① 写自动配置类 @Configuration + @ConditionalOnXxx + @Bean
   ② 写配置属性类 @ConfigurationProperties(prefix="xxx")
   ③ 在 META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
      （2.x 是 META-INF/spring.factories，配 EnableAutoConfiguration=xxx）
      注册自动配置类全限定名
   ④ 打包成 starter（xxx-spring-boot-starter），引入即用
   ```

**易错点 & 追问**：
- **易错**：Spring Boot 3.x（Jakarta EE 9+，javax→jakarta）改用 `AutoConfiguration.imports` 文件替代 `spring.factories`（针对自动配置），注意版本差异。
- **Q：自动配置类为什么不全部生效？** A：靠 `@Conditional` 按需生效。如 `DataSourceAutoConfiguration` 只在 classpath 有数据库驱动 + 用户没自定义 DataSource 时才配。这样「引依赖即用，不引不报错」。
- **Q：怎么排查某个 Bean 是哪个自动配置来的？** A：`--debug` 启动会打印 `CONDITIONS EVALUATION REPORT`，列出所有自动配置类及其生效/不生效原因。

**速记口诀**：启动注解三合一，配置加扫描加自动配；EnableAutoConfig 导入选择器，读 imports 文件加载配置类；ConditionalOn 条件装配，OnMissingBean 让用户覆盖；引依赖即用是约定，自定义 starter 四步走。

> **某创业项目/某头部电商关联**：某创业项目 AI 助手平台封装了 `kangdou-ai-spring-boot-starter`（自动配置 ChatClient、多模型路由、熔断），各业务线引依赖即用。强调：理解自动配置才能写出好的内部 starter，这是架构师的基础能力。

### Q6. Spring Boot 怎么优化启动速度？Spring Native / GraalVM 是什么？

> 🔥 ｜ 考察：启动优化 + 云原生 ｜ 难度 ⭐⭐⭐⭐ ｜ 中高频

**一句话答案**：Spring Boot 启动慢主因是类扫描 + 大量 Bean 实例化 + 自动配置 + 依赖注入；优化手段：**开启懒加载**（`spring.main.lazy-initialization=true`）、**收窄扫描范围**（`@ComponentScan(basePackages)`）、**减少自动配置**（按需排除）、**分层 jar**（配合 Docker 缓存）；**Spring Native（Spring Boot 3 + GraalVM）**用 **AOT（Ahead-Of-Time，提前编译）**把应用编译成原生可执行文件，启动毫秒级、内存占用极低，但牺牲反射动态性（需配置）且编译慢——适合 **Serverless / Function / 容器弹性伸缩**场景。

**深度解析**：

1. **启动慢的原因**：
   ```
   ① 类路径扫描：@ComponentScan 扫描包下所有类
   ② Bean 实例化：所有非懒加载单例启动时创建
   ③ 自动配置：评估大量 AutoConfiguration（即使不生效也要判断）
   ④ 依赖注入：解析依赖关系，处理循环依赖
   ⑤ 初始化逻辑：@PostConstruct、InitializingBean 执行
   ```

2. **优化手段**：
   | 手段 | 做法 | 效果 |
   |------|------|------|
   | 懒加载 | `spring.main.lazy-initialization=true`（Spring Boot 2.2+）| Bean 首次使用才创建，启动快（但首次请求慢）|
   | 收窄扫描 | `@ComponentScan("com.kangdou.user")` 精确到子包 | 减少扫描范围 |
   | 排除自动配置 | `@SpringBootApplication(exclude={Xxx.class})` | 跳过不用的自动配置 |
   | 分层 jar | `spring-boot-jarmode-layertools`（2.3+）| Docker 分层缓存，依赖层不变不重拉 |
   | 减少依赖 | 定期清理无用 starter | 减少扫描和配置评估 |
   | CDS/AppCDS | 类数据共享（JDK 特性）| 多 JVM 共享类元数据，启动快 |

3. **Spring Native / GraalVM**：
   ```
   GraalVM：高性能 JDK，含 native-image 工具
   AOT 编译：启动前把字节码编译成原生机器码（不是 JIT 运行时编译）
   Spring Native：Spring Boot 3 官方支持，编译成原生镜像
   
   优势：
   ① 启动毫秒级（对比 JVM 几秒到几十秒）
   ② 内存占用低（1/5 ~ 1/10）
   ③ 即开即用，适合弹性伸缩
   
   代价：
   ① 牺牲动态性：反射/动态代理/动态类加载需在编译时声明（GraalVM 分析，复杂场景要 reachability metadata）
   ② 编译慢（几分钟）
   ③ 不支持运行时动态生成字节码的部分库（如某些 CGLIB/反射重的库需适配）
   
   适用：Serverless（AWS Lambda）、Function、微服务弹性伸缩、CLI 工具
   不适用：传统长驻服务（JIT 长期更优）、重度反射的遗留系统
   ```

**易错点 & 追问**：
- **易错**：懒加载让启动快，但**首个请求会触发 Bean 创建**（变慢），可能影响首请求延迟。生产要权衡——长驻服务可不懒加载，Serverless 才更需要快启动。
- **Q：Spring Native 会完全取代传统 JVM 吗？** A：不会。Native 适合「快启动 + 低内存 + 短生命周期」（Serverless），传统「长驻 + 高吞吐」服务 JIT 优化更好（预热后性能 > Native）。两者互补。
- **Q：CRaC（Coordinated Restore at Checkpoint）是什么？** A：JDK 17+/Linux 特性，JVM 可「快照」运行状态，重启时从快照恢复（秒级启动），兼顾 JIT 优化。是 Native 的替代方案之一，Spring Boot 3.2+ 支持。

**速记口诀**：启动慢因扫加建加配注，懒加载窄扫描排除配置；分层 jar 配 Docker 缓存，CDS 共享元数据快；Native 用 GraalVM AOT，启动毫秒内存低；牺牲反射编译慢，Serverless 弹性最相宜。

> **某创业项目/某头部电商关联**：某头部电商容器化弹性伸缩场景探索 Spring Native（快启动 = 快扩容）。某创业项目创业期单体未做启动优化（够用）。诚实边界：Spring Native 生产实践有限，是云原生的学习方向。
