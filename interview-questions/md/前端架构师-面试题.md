## 一、前端架构基础与设计原则（4 题）

### Q1. 前端架构怎么分层？为什么要分层？

> 🏷️ 考察：架构设计 · 难度 ⭐⭐⭐ · 架构师基础

**【题目】**：大型前端项目怎么分层架构？分层解决什么问题？

**✅ 答题框架**：关注点分离 + 单向依赖 + 可替换

**📖 详细讲解**

分层的核心目的：**关注点分离**——把不同职责放到不同层，层与层通过约定接口通信，降低耦合、提升可维护性和可测试性。

典型前端分层架构：

```
┌─ 表现层（View/Pages）──── 页面/路由/视图组件（只管渲染和交互）─┐
├─ 业务逻辑层（Domain/Store）─ 业务规则、状态管理（与UI解耦）────┤
├─ 服务层（Service/API）──── 接口请求、数据转换、BFF 编排 ──────┤
└─ 基础设施层（Infra/Utils）─ 工具、请求库、存储、错误处理 ─────┘
```

分层原则：
1. **单向依赖**：上层依赖下层，下层不依赖上层（避免循环依赖）。
2. **层内高内聚、层间低耦合**：每层职责单一，层间通过清晰接口通信。
3. **可替换**：某一层实现换了（如换请求库），不影响其他层。这正是「依赖倒置」——上层依赖抽象（接口），不依赖具体实现。

为什么分层重要：
- **可维护**：改一层不影响其他层（如改 UI 不动业务逻辑）。
- **可测试**：业务逻辑层可独立单测（不依赖 DOM）。
- **可复用**：业务逻辑/服务层可跨端复用（Web/小程序共享逻辑）。

鲁班实战：鲁班的「逻辑内核 + 渲染适配」就是分层——核心引擎（业务逻辑，平台无关）独立，各端只写渲染层。这让 Web/小程序/Flutter/Electron 共享同一套逻辑。

**📌 我的佐证**：鲁班 9 子项目按分层组织（核心引擎/BFF/Java后端/UI/SSR），逻辑内核复用、各端渲染适配。

**⚠️ 避坑**：
- ❌ 分层过度（每层很薄）——增加复杂度，简单项目别套。
- ❌ 层间耦合（上层直接操作下层内部）——分层形同虚设。
- ❌ 业务逻辑混进 View 组件——组件膨胀、难测试。

### Q2. 设计模式在前端怎么用？举几个实际的

> 🏷️ 考察：设计模式 · 难度 ⭐⭐⭐ · 中高频

**【题目】**：前端常用哪些设计模式？实际项目怎么用的？

**✅ 答题框架**：模式 + 场景 + 不过度

**📖 详细讲解**

设计模式不是炫技，是**解决反复出现的设计问题的经验总结**。前端常用的：

| 模式 | 解决什么 | 前端实例 |
|------|---------|---------|
| 单例 | 全局唯一实例 | 全局 Store（Vuex/Pinia）、登录态管理 |
| 观察者/发布订阅 | 一对多通知 | EventEmitter、Vue 响应式（观察者）、消息总线 |
| 策略 | 算法/规则可切换 | 表单校验规则、不同支付方式、出款渠道路由 |
| 装饰器 | 动态增强 | 高阶组件 HOC、AOP 拦截、TS 装饰器 |
| 工厂 | 创建对象解耦 | 组件工厂（低代码按 schema 创建组件） |
| 适配器 | 接口转换 | 多模型适配器（统一不同大模型 API）、浏览器兼容层 |
| 代理 | 控制访问 | Proxy 响应式、懒加载代理、缓存代理 |

鲁班/某创业项目的实际应用：
- **策略模式**：某创业项目出款渠道路由（`AbstractPayoutChannel`，租户偏好/微信/银行卡各一策略，按优先级路由）。鲁班不同端渲染策略。
- **工厂模式**：鲁班低代码按 Schema 的 componentName 从组件物料库动态创建组件。
- **适配器模式**：某创业项目多模型适配器（DeepSeek/Qwen/GLM 统一成 OpenAI 协议）。
- **发布订阅**：Vue 响应式（targetMap + track/trigger 本质是观察者）。
- **代理模式**：Vue3 Proxy 响应式、某创业项目多租户 MyBatis 拦截器（代理 SQL 自动注入 tenant_id）。

设计模式的原则：**不为模式而模式**。先有问题，再找模式解决；而不是拿模式套问题。过度设计模式是新手陷阱。

**📌 我的佐证**：某创业项目出款路由（策略）、鲁班渲染（工厂）、多模型（适配器）、多租户拦截（代理）都是真实模式应用。

**⚠️ 避坑**：
- ❌ 过度设计（简单逻辑硬套模式）——增加复杂度。
- ❌ 只背模式名不懂场景——面试官追问就露馅。

### Q3. SOLID 原则在前端怎么落地？

> 🏷️ 考察：设计原则 · 难度 ⭐⭐⭐ · 中频

**【题目】**：SOLID 五大原则，前端怎么应用？

**✅ 答题框架**：逐条 + 前端场景

**📖 详细讲解**

SOLID 是面向对象设计的五大原则，前端（尤其大型项目）同样适用：

- **S - 单一职责（SRP）**：一个类/函数/组件只做一件事。
  - 前端：一个组件只负责一块 UI，一个 Hook 只做一个逻辑（useUser 只管用户，不管订单）。
- **O - 开闭原则（OCP）**：对扩展开放、对修改封闭。
  - 前端：加新功能不改老代码。如策略模式加新策略不改原有；组件用插槽/配置扩展而非改源码。
- **L - 里氏替换（LSP）**：子类能替换父类不影响程序。
  - 前端：子组件兼容父组件的 props 契约；继承/组合时行为一致。
- **I - 接口隔离（ISP）**：不依赖用不到的接口。
  - 前端：Hook/接口按职责拆细（用 useUser 不强制依赖 useOrder）；Props 按需传递。
- **D - 依赖倒置（DIP）**：依赖抽象不依赖具体。
  - 前端：组件依赖接口（TypeScript interface）而非具体实现；依赖注入（Vue provide/inject、React Context）。

实战意义：SOLID 让代码**可维护、可扩展、可测试**。大型项目不遵守 SOLID，迟早变成屎山。

鲁班例子：低代码组件按 SRP 设计（每个组件单一职责）、用 OCP 扩展（新组件注册不改引擎）、依赖 DIP（渲染引擎依赖组件接口而非具体组件）。

**⚠️ 避坑**：别把它当教条——小项目/原型不必严格 SOLID，避免过度设计。但大型/长期项目必须遵守。

### Q4. 怎么做前端的模块化和代码组织？

> 🏷️ 考察：工程组织 · 难度 ⭐⭐ · 中频

**【题目】**：大型前端项目代码怎么组织？按什么维度分模块？

**✅ 答题框架**：按领域 vs 按类型 + 一致性

**📖 详细讲解**

两种主流组织方式：

**按类型分（type-based）**：
```
src/
  components/   所有组件
  pages/        所有页面
  utils/        所有工具
  api/          所有接口
```
问题：一个功能散在多个目录，改一个功能要跳好几个文件夹。

**按领域/功能分（feature-based）**：
```
src/
  features/
    user/       用户功能（components/pages/api/store 内聚）
    order/      订单功能
    payment/    支付功能
  shared/       跨功能共享
```
优势：一个功能的所有代码聚在一起，高内聚，易维护、易拆分（未来可独立成包/微前端）。

大型项目推荐 **feature-based**（领域驱动），因为：
- 高内聚：改一个功能只动一个目录。
- 易拆分：未来某 feature 独立成微前端/独立包，边界清晰。
- 团队协作：不同团队负责不同 feature，少冲突。

鲁班/某创业项目：某创业项目按业务领域组织（订单/商品/分润/统计/AI 各成模块），这是 DDD 思想在前端/全栈的体现，为未来拆分留余地。

**📌 我的佐证**：某创业项目前端（运营后台/小程序）按业务领域组织，某头部电商低代码按子项目组织（核心/BFF/UI 等）。

**⚠️ 避坑**：组织方式要**团队一致**，别一半 feature-based 一半 type-based，更乱。

### Q5. Webpack vs Vite 怎么选？构建工具架构决策

> 🏷️ 考察：构建工具 · 难度 ⭐⭐⭐ · 高频

**【题目】**：Webpack 和 Vite 怎么选？各自的原理和适用场景？

**✅ 答题框架**：原理差异 + 场景匹配 + 取舍

**📖 详细讲解**

核心差异（原理）：

| | Webpack | Vite |
|---|---------|------|
| 开发启动 | 全量打包（Bundle），慢 | 不打包，浏览器原生 ESM 按需加载，快 |
| 构建 | 成熟、生态全 | Rollup（生产构建） |
| HMR | 全模块图更新 | 精确模块 HMR，快 |
| 生态 | 最全（loader/plugin 海量） | 新但够用，兼容 Rollup 插件 |
| 适合 | 复杂大型项目、老项目 | 新项目、注重开发体验 |

为什么 Vite 开发快：开发时不打包，利用浏览器原生 ES Module（`import`），请求哪个模块编译哪个，按需。Webpack 要先把整个依赖图打包完才能启动。

选型决策：
- **新项目**：优先 Vite（开发体验好、生态够用）。
- **复杂大型/老项目**：Webpack（生态成熟、loader/plugin 全、迁移成本）。
- **库开发**：Vite/Rollup（产物干净，适合发 npm 包）。
- **CRA（Create React App）**：已衰落，新项目用 Vite。

构建工具的核心能力（架构师视角）：模块解析、代码转换（loader）、产物优化（tree shaking/压缩/分包）、开发服务器/HMR、插件机制。理解这些，换工具也能快速上手。

鲁班时代用 Webpack（当时 Vite 未成熟），百万行项目 Webpack 优化（splitChunks、DLL、缓存）是深度活。新项目我会选 Vite。

**📌 我的佐证**：某头部电商鲁班用 Webpack，做过深度优化（分包、缓存、构建提速）。新项目（如某创业项目）倾向 Vite。我懂构建工具原理，不只会用配置。

**⚠️ 避坑**：
- ❌ 盲目追 Vite 弃 Webpack——老项目迁移成本高，要评估。
- ❌ 只会改配置不懂原理——出问题排查不了，也做不了深度优化。

### Q6. Monorepo 怎么管理？什么时候用？

> 🏷️ 考察：工程架构 · 难度 ⭐⭐⭐ · 中高频

**【题目】**：多个相关的前端项目/包，用 Monorepo 还是 Multirepo？

**✅ 答题框架**：场景匹配 + 工具选型 + 治理

**📖 详细讲解**

Monorepo（单仓库多项目）vs Multirepo（每个项目独立仓库）：

| | Monorepo | Multirepo |
|---|---------|-----------|
| 优势 | 共享代码方便、原子提交、统一规范、依赖一致 | 隔离、权限独立、CI 快 |
| 劣势 | 仓库大、CI 慢、权限粗 | 跨仓改麻烦、版本同步痛 |
| 适合 | 强相关的项目群（组件库+应用、平台多子项目） | 独立项目、不同团队 |

Monorepo 适用场景：
- 组件库 + 多个应用共享组件。
- 平台型项目多子包（如鲁班 9 子项目、Babel、Vue 源码都是 Monorepo）。
- 微前端主子应用共享类型/工具。

工具演进：
- **pnpm workspace**（推荐）：原生 Monorepo 支持、硬链接省磁盘、快。
- **Turborepo**：构建缓存 + 任务编排（并行/增量构建），大型 Monorepo 提速。
- **Nx**：代码生成 + 依赖图分析 + 缓存，功能全但重。
- Lerna：老牌，已逐渐被 pnpm+turbo 取代。

Monorepo 的治理（架构师要考虑）：
- **依赖管理**：统一 vs 各包独立版本，用 workspace 协议（`"lib": "workspace:*"`）。
- **构建增量**：只构建变化的包（Turborepo 的 cache）。
- **发布**：统一版本（fixed）vs 独立版本（independent），changesets 管版本。
- **CI 优化**：按包变化触发对应构建。

鲁班 9 子项目本质是 Monorepo 思路（核心/BFF/UI/SSR 等强相关，共享类型和工具）。

**📌 我的佐证**：鲁班多子项目共享内核，是 Monorepo 思路。我懂 Monorepo 的治理（依赖/构建/发布），不只是 pnpm install。

**⚠️ 避坑**：
- ❌ 不相关项目硬塞一个 Monorepo——耦合不相关的代码，CI 爆炸。
- ❌ Monorepo 不做构建增量——改一个包全量构建，慢。

### Q7. 前端规范体系怎么建设？

> 🏷️ 考察：工程规范 · 难度 ⭐⭐ · 高频

**【题目】**：怎么让团队代码风格和质量统一？

**✅ 答题框架**：规范全链路 + 自动化强制

**📖 详细讲解**

规范的目的：**降低协作成本、保证质量底线、让代码像一个人写的**。

规范全链路：

| 环节 | 工具 | 作用 |
|------|------|------|
| 代码风格 | Prettier | 格式统一（缩进/引号/换行） |
| 代码质量 | ESLint | 语法规则、潜在错误、最佳实践 |
| Git 规范 | commitlint + Husky | commit message 规范、提交前校验 |
| 类型 | TypeScript | 类型安全 |
| 测试 | Jest/Vitest + 覆盖率门禁 | 质量保障 |
| Review | Code Review | 人工把关 |

自动化强制（关键——规范不能靠自觉）：
- **Husky + lint-staged**：commit 前自动跑 ESLint/Prettier，不通过不让提交。
- **CI 门禁**：PR 必须通过 lint + 测试 + 覆盖率才能合并。
- **commitlint**：commit message 符合规范（如 conventional commits）。

规范的落地难点：
- **既严格又不死板**：核心规则强制（错误/安全），风格类用 Prettier 自动修（别在 review 吵格式）。
- **渐进推行**：老项目别一次性全开规则（一堆报错），用 // eslint-disable 渐进迁移。
- **团队共识**：规范要团队讨论通过，不能一个人定，否则抵触。

鲁班/某创业项目：我建立了 TS 类型规范 + ESLint/Prettier + Husky + CR 机制。某创业项目更进一步用 CLAUDE.md/AGENTS.md 把规范固化成 AI 约束（"信息代码必须真实、微信代码必须查文档"），连 AI 生成的代码都受规范约束。

**📌 我的佐证**：某头部电商建 TS 体系 + 规范工具链。某创业项目把规范固化进 AI 约束文档。我的理念是「规范自动化强制，不靠人自觉」。

### Q8. 前端 CI/CD 怎么搭？

> 🏷️ 考察：DevOps · 难度 ⭐⭐⭐ · 中高频

**【题目】**：前端从代码到上线，CI/CD 怎么设计？

**✅ 答题框架**：流水线阶段 + 质量门禁 + 部署策略

**📖 详细讲解**

典型前端 CI/CD 流水线：

```
提交 PR
  → CI：lint + 类型检查 + 单测 + 构建（门禁，不通过不让合并）
    → 合并到 main
      → CD：构建产物 → 部署测试环境 → 自动化测试 → 灰度生产
        → 监控
```

关键设计：
1. **CI 门禁**：lint/类型/测试/构建全过才能合并，把问题挡在合并前。
2. **构建产物**：构建一次，多环境部署（别每个环境重新构建，保证一致性）。产物带 hash 文件名（缓存友好）。
3. **环境分层**：dev → test → staging → prod，逐级验证。
4. **部署策略**：
   - 静态资源上 CDN（带 hash 长缓存）。
   - HTML 不缓存或短缓存（保证拿到最新 hash 引用）。
   - 灰度发布（按比例/按用户）。
5. **回滚**：保留历史产物，出问题秒回滚（CDN 切换历史版本）。

前端特有：
- **缓存策略**：静态资源（JS/CSS/图片）强缓存（hash 文件名 + 长 max-age），HTML 协商缓存。
- **CDN 部署**：构建产物上传 CDN，HTML 部署到源站。
- **预渲染/SSR**：SSR 项目要部署 Node 服务（非纯静态）。

某创业项目的 AI 协同路径（创新）：传统 CI/CD 之外，我用自治多 Agent 评审（/kd-review）替代部分人工 review——变更拆 bucket 并行审查 + 流式修复 + 零红色收敛。这是小团队 CI/CD 的创新补充。

**📌 我的佐证**：某头部电商搭过前端 CI/CD（构建-测试-部署-CDN）。某创业项目用 AI 评审增强。我懂前端部署的缓存/CDN/灰度策略。

**⚠️ 避坑**：
- ❌ 每个环境重新构建——不一致风险 + 浪费。
- ❌ 没有回滚机制——出问题手忙脚乱。
- ❌ 静态资源不缓存或缓存策略错——性能差或更新不生效。

### Q9. 依赖管理与版本治理怎么做？

> 🏷️ 考察：工程治理 · 难度 ⭐⭐⭐ · 中频

**【题目】**：前端依赖又多又乱，怎么治理？怎么防止依赖出问题？

**✅ 答题框架**：锁版本 + 升级策略 + 安全审计

**📖 详细讲解**

前端依赖治理的痛点：依赖多（一个项目几百个）、版本碎片化、安全漏洞、升级破坏性变更。

治理手段：
1. **锁文件（lockfile）**：pnpm-lock.yaml/package-lock.json 锁定精确版本，保证团队/CI 安装一致（不会因依赖的 patch 更新导致行为变化）。
2. **版本范围策略**：
   - 应用项目：锁定主版本（`^1.2.3` 允许 1.x，不允许 2.x）。
   - 库项目：更严格，避免引入不必要的依赖。
3. **升级策略**：
   - 定期（如月度）升级依赖（安全 + 新特性）。
   - 自动化工具：Renovate/Dependabot 自动提 PR 升级。
   - 灰度升级（先升 patch，再 minor，major 谨慎评估破坏性变更）。
4. **安全审计**：`pnpm audit` / GitHub Dependabot 扫已知漏洞依赖。
5. **依赖精简**：定期清无用依赖（depcheck），避免 bundle 膨胀。
6. **统一依赖**：Monorepo 里共享依赖版本（workspace 协议 + 统一版本）。

破坏性升级的处理（如 Webpack 4→5、React 17→18）：
- 看 CHANGELOG / Migration Guide。
- 渐进迁移（codemod 自动改 + 人工兜底）。
- 灰度验证。

鲁班百万行 Vue2→Vue3 就是最大的「依赖/框架升级」治理——用 codemod 工程化处理破坏性变更，事务化可回滚。

**📌 我的佐证**：Vue2→Vue3 codemod 是顶级依赖治理案例。我用 lockfile + Renovate + audit 管依赖，定期升级。

**⚠️ 避坑**：
- ❌ 不锁版本（用 `*` 或最新）——构建不可复现，行为漂移。
- ❌ 从不升级——安全漏洞积累、技术债。
- ❌ 盲目升级 major——破坏性变更导致线上故障。

## 三、前端性能架构（5 题）

> 性能是前端架构师的核心战场。你的鲁班 SSR+CDN 10万QPS 是王牌。

### Q10. 前端性能优化体系怎么建？

> 🏷️ 考察：性能架构 · 难度 ⭐⭐⭐⭐ · 核心

**【题目】**：怎么系统化地做前端性能优化？

**✅ 答题框架**：指标定义 + 度量 + 优化 + 监控闭环

**📖 详细讲解**

性能优化不是零散技巧，是**「度量→优化→监控」的闭环**。

第一步：定义指标（不定义指标没法优化）：
- **加载性能**：FCP（首次内容绘制）、LCP（最大内容绘制，核心）、TTFB（首字节）。
- **交互性能**：INP（交互到下次绘制，替代旧 FID）、TTI（可交互时间）。
- **视觉稳定**：CLS（累积布局偏移）。
- Core Web Vitals：LCP + INP + CLS（Google 定的核心三指标）。

第二步：度量（先测再优）：
- 实验室：Lighthouse（模拟环境）、Chrome Performance（火焰图）。
- 真实用户（RUM）：web-vitals 库 + PerformanceObserver，采集真实用户数据（实验室和真实用户差异大）。

第三步：优化（对症下药，按瓶颈）：

| 瓶颈 | 优化手段 |
|------|---------|
| JS 体积大 | 路由懒加载、Tree Shaking、代码分包、按需引入 |
| 接口慢 | BFF 聚合、缓存、预加载、HTTP/2 |
| 图片大 | WebP/AVIF、懒加载、CDN 裁剪、响应式 srcset |
| 首屏慢 | SSR/预渲染、关键 CSS 内联、preload 关键资源 |
| 渲染卡 | 虚拟列表、防抖节流、合成层动画、减少回流 |
| 重复访问慢 | 强缓存（hash 文件名）、Service Worker |

第四步：监控（持续）：
- 线上 RUM 采集性能指标，P95/P99 看大盘。
- 性能劣化告警（如 LCP 突然升高）。
- 持续优化（不是一次性）。

**性能优化的架构师视角**：不只是加几个 trick，而是**体系建设**——指标 + 度量工具 + 优化规范 + 监控告警，形成可持续的 performance culture。

**📌 我的佐证**：鲁班 SSR+CDN 把吞吐 200→10万QPS，首屏快（SSR 直出）、加载快（CDN 边缘缓存），这就是性能架构的实战。可用性 99.99% 也靠性能/容灾保障。

**⚠️ 避坑**：
- ❌ 不度量就优化（拍脑袋）——不知道瓶颈，优化无效。
- ❌ 只看实验室数据——和真实用户差异大，要看 RUM。
- ❌ 一次性优化不监控——性能会劣化（依赖升级、代码膨胀）。

### Q11. 首屏加载（LCP）怎么优化？

> 🏷️ 考察：加载性能 · 难度 ⭐⭐⭐ · 高频

**【题目】**：SPA 首屏 LCP 4秒，怎么降到 2 秒内？

**✅ 答题框架**：定位瓶颈 + 分层优化

**📖 详细讲解**

（详细手段见高级前端 Q17，架构师视角补充）

架构师视角的 LCP 优化层次：

```
1. 减少要加载的（体积）
   - 代码分包（路由懒加载，首屏只加载首屏代码）
   - Tree Shaking + 按需引入组件库
   - 压缩（gzip/brotli）

2. 加快加载（网络）
   - CDN（静态资源就近）
   - HTTP/2 多路复用
   - preload 关键资源（首屏字体/关键 CSS/首屏 API）
   - 合理缓存（hash 文件名长缓存）

3. 减少执行（渲染）
   - SSR/预渲染（首屏直出 HTML，不等 JS）
   - 关键 CSS 内联（首屏样式不额外请求）
   - defer/async 非关键 JS

4. 减少阻塞（关键路径）
   - 字体 preload + font-display: swap（避免字体阻塞文字）
   - 图片 lazy load + 首屏图片优先
```

LCP 元素优化（最直接）：找到首屏最大元素（通常是 hero 图或大标题），优先优化它依赖的资源（preload、CDN、WebP、尺寸压缩）。

**📌 我的佐证**：鲁班 SSR + CDN + 关键资源 preload 是首屏优化的体系方案，支撑 10万QPS 下首屏快。

### Q12. 渲染性能怎么优化？虚拟列表原理？

> 🏷️ 考察：渲染性能 · 难度 ⭐⭐⭐ · 高频

**【题目】**：长列表/频繁交互卡顿，渲染性能怎么优化？

**✅ 答题框架**：减少回流重绘 + 虚拟列表 + 合成层

**📖 详细讲解**

（原理见高级前端 Q10/Q18，架构师视角）

渲染性能优化三层次：

1. **减少回流（Reflow）**——最贵：
   - 几何变化（宽高/位置）触发，重新 Layout。
   - 优化：批量改样式、避免强同步布局（读写分离）、用 transform 代替几何属性。

2. **减少重绘（Repaint）**——中等：
   - 外观变化（颜色/背景）触发。
   - 不可避免但要少。

3. **利用合成层（Composite）**——最便宜：
   - transform/opacity 走合成层（GPU），不触发回流重绘。
   - 动画用 transform（translate/scale/rotate）不用 left/top。

虚拟列表（长列表核心方案）：只渲染可视区 + 缓冲，占位撑滚动条，transform 定位。10万条数据只渲染几十个 DOM。（实现见高级前端 Q18）

React/Vue 渲染优化：
- React：React.memo + useMemo/useCallback 减少不必要重渲染、key 稳定、虚拟列表（react-window）。
- Vue：v-show vs v-if、key 稳定、computed 缓存、虚拟列表（vue-virtual-scroller）。

**📌 我的佐证**：鲁班大屏（15+ 数据大屏）有大量图表渲染，我用合成层动画 + 虚拟列表 + 按需渲染保证流畅。某创业项目小程序 400 页面也做了渲染优化。

### Q13. 前端性能监控体系怎么搭？

> 🏷️ 考察：监控架构 · 难度 ⭐⭐⭐ · 中高频

**【题目】**：线上前端性能怎么持续监控？

**✅ 答题框架**：采集 + 上报 + 分析 + 告警

**📖 详细讲解**

性能监控体系（不只是性能，含错误/行为）：

```
采集（前端 SDK）
  → 上报（sendBeacon/图片打点）
    → 聚合（服务端）
      → 分析（大盘/分维度）
        → 告警（劣化/异常）
```

采集维度：
- **性能**：Web Vitals（LCP/INP/CLS）+ 自定义（首屏时间、接口耗时）。
- **错误**：JS 异常（onerror）、Promise 异常（unhandledrejection）、资源加载错误、框架错误。
- **行为**：PV/UV、点击、路由、自定义埋点（复现用户路径）。

采集技术：
- PerformanceObserver API（性能 entry）。
- web-vitals 库（封装 Core Web Vitals 采集）。
- 自定义埋点（关键业务节点）。

上报：
- sendBeacon（页面卸载也能发）。
- 图片打点（1x1 gif，跨域友好）。
- 批量 + 采样（高频事件采样，错误全量）。

分析：
- P50/P95/P99 分位（不只看平均，平均掩盖尾部）。
- 分维度（按页面/浏览器/地域/版本）。
- 大盘 + 趋势。

告警：
- 性能劣化（LCP P95 超阈值）。
- 错误率突增。
- 分版本对比（新版本劣化）。

开源/商业方案：Sentry（错误+性能）、自建（更可控）。

**📌 我的佐证**：鲁班/某创业项目有性能和错误监控（接口延迟、Token、QPS 用 Prometheus）。前端侧我了解 Performance API + web-vitals + sendBeacon 体系。

**⚠️ 避坑**：
- ❌ 只看平均不看分位——尾部用户体验差被平均掩盖。
- ❌ 监控 SDK 自己报错导致死循环——要 try/catch + 失败静默。
- ❌ 全量采集高频事件——上报量爆炸，要采样。

### Q14. SSR/SSG 架构怎么设计？（你的王牌）

> 🏷️ 考察：SSR 架构 · 难度 ⭐⭐⭐⭐ · 王牌

**【题目】**：什么时候用 SSR/SSG？SSR 架构怎么设计？

**✅ 答题框架**：场景判断 + 架构 + 容灾

**📖 详细讲解**

渲染模式对比：

| 模式 | 说明 | 适合 |
|------|------|------|
| CSR | 浏览器渲染（传统 SPA） | 后台管理、交互重的应用 |
| SSR | 服务端渲染 HTML | 内容站、SEO、首屏要求高 |
| SSG | 构建时生成静态 HTML | 博客/文档/营销页（内容固定） |
| ISR | 增量静态再生（SSG+定时更新） | 内容站、频繁更新 |

什么时候用 SSR：
- 首屏要求快（不等 JS 下载执行）。
- SEO 需要（搜索引擎抓 HTML）。
- 内容型站点（电商详情页、活动页、新闻）。

SSR 的代价：
- 服务端压力（每次回源要 Node 渲染）。
- 开发约束（不能用 window/document，要同构）。
- 部署复杂（要 Node 服务，非纯静态）。

鲁班的 SSR+CDN 架构（王牌）：
```
活动页（内容相对静态）
  → SSR 服务端渲染 HTML（首屏快、SEO）
    → 渲染结果缓存到 CDN 边缘节点（命中率 90%+，回源少）
      → 全链路三级降级（CDN→SSR→静态页→兜底页，保可用）
```
吞吐 200→10万QPS、可用性 99.99%、P0 清零。关键是「SSR 直出首屏 + CDN 缓存化解服务端压力 + 多级降级保可用」。

SSR 框架：Next.js（React）、Nuxt.js（Vue）、自研（鲁班自研 SSR）。

**📌 我的佐证**：鲁班自研 SSR + CDN + 三级降级，扛 10万QPS。这是 SSR 架构的顶级实战。我能讲清「为什么 SSR、CDN 怎么化解压力、怎么容灾」。

**⚠️ 避坑**：
- ❌ 所有页面都 SSR——没必要，交互重的后台用 CSR。
- ❌ SSR 不做 CDN 缓存——Node 扛不住高并发。
- ❌ SSR 不做容灾——SSR 挂了全站白屏，要降级。

## 四、前端架构模式（4 题）

### Q15. 微前端架构怎么设计？qiankun vs Module Federation

> 🏷️ 考察：微前端 · 难度 ⭐⭐⭐⭐ · 架构核心

**【题目】**：多个团队多个技术栈整合，微前端怎么选型设计？

**✅ 答题框架**：场景判断 + 方案对比 + 难题处理

**📖 详细讲解**

（方案对比见全栈 Q22，架构师视角补充）

什么时候用微前端（场景判断）：
- 多团队协作的大型应用（每个团队独立开发部署）。
- 多技术栈共存（老 Vue + 新 React）。
- 巨型应用拆分（渐进式拆解单体）。
- ❌ 单团队小项目别用（杀鸡用牛刀）。

架构师要解决的微前端难题（不止选型）：

1. **JS 隔离**：子应用全局变量不污染主应用。
   - qiankun：Proxy 沙箱。
   - iframe：天然隔离（但通信/体验差）。

2. **CSS 隔离**：样式不冲突。
   - Shadow DOM（最强隔离，但样式继承问题）。
   - Scoped CSS / CSS Modules / BEM 约定。
   - qiankun 的样式隔离（不完美）。

3. **通信机制**：主子应用/子子应用怎么传数据。
   - 自定义事件（EventBus）。
   - 全局状态（共享 Store）。
   - URL/路由参数。
   - postMessage（iframe）。

4. **路由协调**：基座路由 + 子应用路由。
   - 基座控制主路由，子应用带前缀路由。

5. **公共依赖**：React/Vue 是否共享。
   - Module Federation：externals 共享。
   - qiankun：各子应用独立（包大但解耦）。

6. **部署/版本**：子应用独立部署、版本管理。

选型决策树：
- 多技术栈、独立部署、低耦合 → **qiankun**。
- 同技术栈（Webpack 5）、细粒度共享模块、运行时依赖共享 → **Module Federation**。
- 极致隔离需求 → iframe（牺牲体验）。

鲁班的多端是「内核复用 + 各端渲染适配」，不是传统微前端（那个是同端多应用），但隔离/复用思想相通。

**📌 我的佐证**：我懂微前端的难题（JS/CSS 隔离、通信、路由、公共依赖）和选型逻辑，能根据场景选 qiankun/MF/iframe。

**⚠️ 避坑**：
- ❌ 为微前端而微前端——小项目套微前端是灾难。
- ❌ 忽略隔离难题——样式/全局污染、路由冲突。
- ❌ 通信设计混乱——主子应用耦合，失去微前端解耦意义。

### Q16. 组件化与设计系统怎么建？

> 🏷️ 考察：组件架构 · 难度 ⭐⭐⭐ · 中高频

**【题目】**：怎么设计一个团队用的组件库/设计系统？

**✅ 答题框架**：分层 + 标准化 + 治理

**📖 详细讲解**

组件化的分层（设计系统金字塔）：

```
┌─ 业务组件（特定业务，如 OrderCard）─┐
├─ 复合组件（组合，如 Form/SearchTable）┤
├─ 基础组件（通用，如 Button/Input）──┤
└─ 原子/Token（颜色/间距/字体，设计规范）┘
```

设计系统的核心：**设计和代码的统一语言**——设计师用一套规范，开发用对应组件，保证视觉和交互一致。

建设要点：
1. **Token 层**：颜色/间距/字号/圆角等设计变量（CSS Variables / TS 常量），统一设计规范。
2. **基础组件**：Button/Input/Select 等原子组件，API 设计要稳定、一致、可组合。
3. **主题机制**：CSS Variables / 主题切换（明暗/品牌色）。
4. **文档**：Storybook 展示组件 + API + 用法（文档即测试）。
5. **版本管理**：语义化版本、changelog、平滑升级。

组件 API 设计原则：
- **一致性**：所有组件 API 风格统一（命名/事件/属性）。
- **可组合**：组件能组合（插槽/children）。
- **可配置**：用配置而非变种（variant="primary|ghost" 而非 PrimaryButton/GhostButton）。
- **低耦合**：组件不依赖具体业务（业务无关）。

治理：
- 组件库独立包（Monorepo 子包），应用按需引入。
- 贡责任命（谁维护、怎么提 PR）。
- 废弃策略（deprecated 标记 + 迁移指南）。

Element Plus/Ant Design 是成熟范例。鲁班有自研组件库（物料体系）。

**📌 我的佐证**：鲁班有自研物料体系（组件库 + 设计器集成）。我懂组件库的分层/Token/API设计/治理。

**⚠️ 避坑**：
- ❌ 组件耦合业务（业务一变组件就改）——组件要业务无关。
- ❌ API 不一致（每个组件用法不同）——学习成本高。
- ❌ 无文档无版本——用不起来。

### Q17. 状态管理架构怎么设计？全局还是局部？

> 🏷️ 考察：状态架构 · 难度 ⭐⭐⭐ · 中高频

**【题目】**：状态管理怎么组织？什么状态放全局，什么放局部？

**✅ 答题框架**：状态分类 + 单一数据源 + 局部优先

**📖 详细讲解**

状态管理的核心认知：**不是所有状态都要放全局 Store，过度全局化是反模式**。

状态分类（决定放哪）：

| 状态类型 | 例子 | 放哪 |
|---------|------|------|
| 组件局部状态 | 表单输入、开关、loading | 组件内（ref/useState） |
| 共享状态 | 用户信息、登录态、全局配置 | 全局 Store（Pinia/Redux） |
| 服务端状态 | 接口数据、缓存 | 服务端状态库（React Query/TanStack Query）或 Store |
| URL 状态 | 筛选条件、分页、tab | URL（路由参数） |
| 临时状态 | 弹窗开关、拖拽中 | 组件内或局部 Context |

原则：
1. **局部优先**：能放组件内的不放全局（避免全局污染、减少重渲染）。
2. **单一数据源**：同一数据只存一处（避免多处同步 bug）。如用户信息只在 Store，别组件又存一份。
3. **服务端状态用专门工具**：React Query/SWR 自动处理缓存/重新验证/加载态，别手动塞 Store。
4. **URL 即状态**：能放 URL 的放 URL（可分享、可刷新、可后退）。

架构层次：
- 全局 Store：跨页面共享的核心状态（用户/主题/权限）。
- 页面级状态：页面内共享（用 provide/inject 或页面 Store）。
- 组件级状态：组件内部（ref/useState）。

技术选型：Vue 用 Pinia（组合式、TS 友好、取代 Vuex）；React 用 Zustand/Redux Toolkit/Context（按规模）。

**📌 我的佐证**：鲁班/某创业项目的状态分层（全局 Store + 页面局部 + 组件内部）。我懂「局部优先、单一数据源」原则，不滥用全局。

**⚠️ 避坑**：
- ❌ 全塞全局 Store——Store 膨胀、重渲染扩散、难维护。
- ❌ 多处存同一数据——同步 bug。
- ❌ 接口数据手动塞 Store——用 React Query/SWR 自动管理。

### Q18. 低代码引擎架构怎么设计？（你的王牌）

> 🏷️ 考察：低代码架构 · 难度 ⭐⭐⭐⭐⭐ · 顶级王牌

**【题目】**：设计一个低代码平台，核心引擎怎么架构？

**✅ 答题框架**：Schema 驱动 + 递归渲染 + 协议统一 + 扩展性

**📖 详细讲解**

低代码的核心：**Schema 驱动 + 可视化设计 + 协议统一**。

整体架构：
```
┌─ 设计器（Designer）── 拖拽配置，产出 Schema ──┐
│   - 物料面板（可拖组件）                        │
│   - 画布（所见即所得，实时渲染）                 │
│   - 属性面板（配置选中组件的属性）               │
│   - 大纲/代码（Schema 树/JSON 编辑）            │
├─ Schema 协议（统一语言）─────────────────────┤
│   { componentName, props, children }            │
├─ 渲染引擎（Renderer）── 读 Schema 渲染 ────────┤
│   - 递归渲染（组件可嵌套）                       │
│   - 动态组件（componentName → 真实组件）        │
│   - 表达式引擎（{{ }} 绑定）                    │
├─ 物料体系（Components）── 组件库 ──────────────┤
│   - 基础组件 + 业务组件 + 容器组件              │
│   - 组件注册中心（按需加载）                    │
└─ 运行时（Runtime）── 预览/线上共用 Renderer ──┘
```

核心难点（架构师要解决的）：

1. **递归渲染**：组件无限嵌套（容器装子组件）。Vue 的 `<component :is>` 或 React 动态组件递归。

2. **Schema 协议设计**：稳定的协议是基础。要支持版本演进（Schema migration）。

3. **表达式引擎**：`{{item.price}}` 这类绑定。要沙盒执行（不能用裸 eval，用 AST 解析或受限 Function），支持作用域（循环变量、全局数据）。

4. **设计器 ↔ 运行时一致性**：抽出独立 Renderer，两端共用，避免实现分叉。

5. **扩展性**：
   - 自定义组件（注册物料）。
   - 自定义属性配置面板。
   - 插件机制（生命周期钩子）。

6. **数据源**：组件数据从哪来（API/静态/表达式），数据绑定。

7. **版本兼容**：老 Schema + 新组件怎么兼容（migration、组件向后兼容）。

鲁班实战：自研渲染引擎 + 设计器，Schema 驱动 + 双拖拽画布 + 递归渲染 + 多端（Web/小程序/Flutter/Electron 共用协议）+ AI 辅助配置。支撑 400+ 活动、研发成本 4 人天→0。

**📌 我的佐证**：鲁班是我主导的低代码平台，自研引擎。我能讲清「Schema 驱动、递归渲染、协议统一、表达式沙盒、多端复用」的核心架构和难点。这是顶级前端架构经历。

**⚠️ 避坑**：
- ❌ Schema 协议设计不稳——后期改动牵一发动全身。
- ❌ 设计器和运行时两套实现——不一致。
- ❌ 表达式用裸 eval——安全风险。

### Q20. 同构（Isomorphic）怎么实现？

> 🏷️ 考察：SSR/同构 · 难度 ⭐⭐⭐ · 中频

**【题目】**：SSR 的同构怎么处理？服务端和客户端怎么共用代码？

**✅ 答题框架**：同构原理 + 差异处理

**📖 详细讲解**

同构（Isomorphic/Universal）：**一套代码既能在 Node（服务端）又能在浏览器（客户端）运行**，SSR 的基础。

同构的核心挑战：服务端没有 DOM（window/document），客户端才有。所以代码要「环境无关」+「环境差异隔离」。

差异处理：
```js
// 环境判断
const isServer = typeof window === 'undefined';

// 环境差异隔离
if (!isServer) {
  // 只在浏览器执行的代码（操作 DOM、localStorage）
}

// 框架封装：Next.js/Nuxt.js 提供 mounted/onMounted（只客户端执行）
```

同构渲染流程：
```
1. 首次请求：服务端渲染 HTML（带数据）直出 → 用户看到首屏快
2. 浏览器加载 JS → hydration（注水）：把静态 HTML 变成可交互应用（绑定事件）
3. 后续：客户端接管（CSR）
```

hydration 的坑：
- **注水不匹配（hydration mismatch）**：服务端渲染的和客户端首次渲染的不一致（如用了 Date.now 随机值），报错/重渲染。要保证首屏服务端客户端一致。
- **数据传递**：服务端取的数据序列化到 HTML（window.__INITIAL_STATE__），客户端直接用，避免重复请求。

框架支持：Next.js（React SSR/同构）、Nuxt.js（Vue SSR/同构）封装了同构细节。

鲁班：自研 SSR，处理了同构（服务端渲染首屏 + 客户端 hydration + 数据预取）。

**📌 我的佐证**：鲁班自研 SSR 含同构处理。我懂「环境判断、hydration、数据预取、注水匹配」的同构要点。

**⚠️ 避坑**：
- ❌ 同构代码用了 DOM API（window/document）——服务端崩。
- ❌ hydration mismatch——首屏不一致，性能差/报错。

### Q21. 小程序架构有什么特点？

> 🏷️ 考察：小程序 · 难度 ⭐⭐ · 青岛特色（加分）

**【题目】**：微信小程序的架构和 Web 有什么不同？开发要注意什么？

**✅ 答题框架**：双线程架构 + 限制 + 适配

**📖 详细讲解**

微信小程序的双线程架构（和 Web 最大区别）：
```
┌─ 视图层（WebView，多个）── 渲染 WXML/WXSS ──┐
│                                              │
│         ↕ JSBridge（通信，异步）              │
│                                              │
└─ 逻辑层（JsCore，单线程）── 运行 JS ─────────┘
```

为什么双线程：安全（逻辑层不能直接操作 DOM，防止篡改）+ 性能（渲染和逻辑分离）。但代价是**视图层和逻辑层通信是异步的**（setData 跨线程），频繁大量 setData 性能差。

和 Web 开发的差异/限制：
- **不能用 DOM API**（document/window）。
- **setData 是异步跨线程**：要批量、精简（只传变化的数据，别整个对象）。
- **包体积限制**（主包 2M，分包 20M）——要做分包加载、按需注入。
- **不支持任意 HTML 标签**（用 WXML 组件）。
- **样式受限**（WXSS，部分 CSS 不支持，rpx 单位）。
- **API 受限**（用 wx.xxx 而非浏览器 API）。

性能优化要点：
- setData 精简（数据量小、频率低、合并调用）。
- 分包加载（按需）。
- 长列表用虚拟列表（小程序的 recycle-view）。
- 避免频繁跨线程通信。

跨端框架（Taro/uni-app）帮你用 React/Vue 写小程序，编译成小程序代码。某创业项目用 uni-app。

**📌 我的佐证**：某创业项目 C 端是微信小程序（uni-app，Vue3），400 页面、19 万行。我懂小程序双线程、setData 性能、分包等。

**⚠️ 避坑**：
- ❌ setData 频繁/大量——跨线程性能差。
- ❌ 主包塞满——超 2M 无法发布，要分包。

**✅ 答题框架**：分层 + 子系统 + 数据流 + 设计决策

**📖 详细讲解**

（详细见高级前端 Q11-Q16，架构师视角整合）

鲁班整体架构：
```
9 个子项目按职责分层：
  - 核心引擎（低代码渲染 + 设计器，Schema 驱动）
  - BFF（Node，接口聚合 + SSR 承载 + 端适配）
  - Java 后端（业务逻辑 + 数据）
  - Go 后端（高性能实时服务）
  - UI 库（物料体系）
  - SSR 站点（活动页 SSR + CDN，扛 10万QPS）
  - AI 助手（活动配置辅助）
  - Flutter（移动端）
  - Electron（桌面端）
```

关键架构决策（讲架构要讲决策）：
1. **多语言并存**（JS/Java/Go）：核心引擎前端主导、Java 做业务（生态）、Go 做高性能（并发）。语言选型匹配场景。
2. **BFF 解耦**：Node BFF 聚合后端 + 端适配 + SSR 承载。
3. **多端复用内核**：核心引擎 + Schema 协议跨端，各端渲染适配。
4. **SSR+CDN**：活动页性能/SEO，CDN 化解服务端压力。
5. **低代码引擎**：Schema 驱动递归渲染，运营自助配置。

成果：4 人天→0、400+ 活动、10万QPS、99.99%、P0 清零。

### Q26. SSR+CDN 10万QPS 的架构决策讲一下

**✅ STAR**：
> **Situation**：活动页吞吐 200 QPS，扛不住大促，P0 频发。
> **Task**：提升到 10 万 QPS，保可用性。
> **Action**：SSR + CDN + 三级降级。**决策取舍**：SSR（首屏快+SEO）+ CDN（化解服务端压力，命中率90%+）+ 三级降级（容灾）。
> **Result**：200→10万QPS、99.99%、P0 清零。
> **为什么这个决策对**：匹配活动页「内容相对静态、首屏要求快、瞬时高并发」的特点。

### Q27. 百万行 Vue2→Vue3 codemod 的架构决策

**✅ STAR**：
> **Situation**：百万行 Vue2，框架不维护了，必须升级 Vue3。
> **Task**：低成本、低风险完成百万行升级。
> **Action**：Babel codemod（AST 自动改写）+ 事务化（计划-预检-执行-回滚）+ 灰度迁移。**决策**：不用手动（不可行）、不用正则（脆弱）、用 AST（精确）。
> **Result**：百万行升级完成，事务化保证可回滚、灰度保证安全。
> **架构价值**：这是「工程化偿还技术债」的顶级案例——把破坏性变更抽象成可批量、可验证、可回滚的自动化流程。
