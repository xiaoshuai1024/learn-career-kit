> **定位**：完整呈现"一个合格的后端高级架构师"应该具备的能力结构。不是学习漏洞清单（那个在 `岗位能力图谱-严格版.md` 第 2.4 节「漏洞优先级表」），不是具体知识点讲解（那个在 `后端八股与架构师面试教材.md`）。
> **怎么用**：
> - 自检——扫一遍，标出自己哪几块是强项、哪几块是缺口。
> - 规划学习——按支柱补缺口，不要东学一块西学一块。
> - 面试对标——JD 上的能力要求，能在这张图里找到对应位置。
> **目标岗位**：高级架构师 / 资深架构师（T7+/P7+），偏工程落地与架构决策。
> **贯穿业务**：某创业项目商城订单系统（与八股教材一致，便于交叉对照）。

## 0. 先讲清楚：高级架构师和资深工程师到底差在哪

很多人误以为"架构师 = 会更多技术栈的资深工程师"。**这是最大的认知错误**。

真正的差别在三个维度：

```
            资深工程师                    高级架构师
┌──────────────────────────┐  ┌──────────────────────────────┐
│ 把既定方案做扎实          │  │ 从业务问题倒推出技术方案      │
│ 关注"代码怎么写好"        │  │ 关注"为什么这么设计 + 取舍"   │
│ 对自己模块负责            │  │ 对整个系统的结果负责          │
│                          │  │                              │
│  → 解决"怎么做"           │  │  → 解决"做什么 + 为什么不做X" │
└──────────────────────────┘  └──────────────────────────────┘
        ▲                              ▲
        │         能力跃迁              │
        └──────────────────────────────┘
   技术深度 ──→ 技术广度 + 架构判断力 + 业务抽象力 + 技术影响力
```

**架构师每天在做的三件事**：

1. **做权衡（Trade-off）**：任何架构决策本质都是取舍。CAP 选 AP 还是 CP？缓存强一致还是最终一致？同步调用还是异步消息？没有"对的方案"，只有"在这个业务场景下，牺牲 A 换 B 是否值得"。
2. **定边界**：服务怎么拆、粒度多细、API 怎么设计、数据库是分还是合——本质都是"在哪里画边界"。
3. **扛风险**：系统挂了谁负责？不是写代码的人，是做架构决策的人。所以架构师天然保守、天然关注失败路径。

**这份图谱的能力支柱就围绕这三件事展开**：

```
                          ┌─────────────────────┐
                          │   业务与技术规划力    │ ← 决定"做什么"
                          │  （第 8 支柱 软实力） │
                          └──────────┬──────────┘
                                     │
        ┌────────────────────────────┼────────────────────────────┐
        │                            │                            │
        ▼                            ▼                            ▼
┌───────────────┐           ┌────────────────┐           ┌───────────────┐
│  技术深度      │           │  架构设计力      │           │  稳定性保障    │
│ （支柱1-2）    │           │  （支柱3-5）     │           │  （支柱6）     │
│ 语言/存储/中间件│           │  分布式/高可用/  │           │  监控/容量/    │
│               │           │  高并发/系统设计 │           │  变更/SRE      │
└───────────────┘           └────────────────┘           └───────────────┘
        │                            │                            │
        └────────────────────────────┼────────────────────────────┘
                                     │
                          ┌──────────▼──────────┐
                          │  云原生 + AI 工程化  │ ← 时代增量
                          │   （支柱 7-8）       │
                          └─────────────────────┘
```

## 支柱 1：语言与运行时深度

> **为什么是支柱**：架构师做技术决策时，底层原理是判断依据。不懂 JVM 内存模型，就判断不了"这个并发方案会不会出问题"；不懂 NIO，就理解不了 Netty 为什么快、什么时候该用。

### 1.1 Java 核心语言

| 能力点 | 高级架构师应该掌握到什么程度 |
|---|---|
| 集合框架 | 不只会用，能讲清 HashMap/ConcurrentHashMap 的底层结构演进（JDK7 vs JDK8）、扩容、线程安全实现 |
| 并发（JMM + 锁 + 线程池 + AQS） | 能在白板画出 happens-before、synchronized 锁升级、AQS CLH 队列；能给出线程池参数的**业务化配置依据**（不是背八股的"CPU 密集 = N+1"） |
| IO/NIO/AIO + 零拷贝 | 能解释 Netty 为何用主从 Reactor、`sendfile` vs `mmap` 的差异、什么场景该上 NIO |
| 反射 / 注解 / 泛型 | 能讲清 Spring/MyBatis 怎么用这些机制做扩展，自己设计框架时知道什么时候用反射、什么时候避免 |
| Java 8+ 新特性 | Stream 不是"会写"，而是知道它的性能陷阱（装箱、短路、并行流默认 ForkJoinPool）；CompletableFuture 的编排 |

### 1.2 JVM

架构师要能在生产事故现场**用 JVM 工具快速定位问题**，不是只会背参数：

- **运行时数据区**：堆 / 栈 / 方法区 / 元空间 / 直接内存——每个区域出问题的现象不同（OOM 在哪、StackOverflow 在哪）
- **GC 算法与回收器**：Parallel / CMS / G1 / ZGC 的取舍。**关键判断力**：什么业务用什么回收器（低延迟选 ZGC，吞吐优先选 Parallel，通用选 G1）
- **类加载机制**：双亲委派 + 打破场景（Tomcat、SPI、热部署）
- **生产排查三板斧**：
  - CPU 飙高 → `top -Hp` + `jstack` 找线程 + 看是 GC 还是死循环
  - OOM → `jmap -dump` + MAT 分析支配树
  - 内存泄漏 → 监控 Old Gen 增长趋势 + Dump 比对

> 🔑 **架构师级金句**：「JVM 调参不是背 Xmx Xms 怎么设，是能从 GC 日志反推系统行为——比如 Full GC 频繁是因为大对象、还是内存泄漏、还是元空间不足，每种原因对应不同的解法。」

### 1.3 JVM 字节码与 JIT（差异化深度）

普通高级工程师可以不深究，**架构师级的差异化能力**：

- JIT 的 C1/C2 分层编译、逃逸分析（栈上分配、锁消除、标量替换）
- 怎么用 JMH 做基准测试，避免"我自己感觉快了"
- 字节码层面理解 `synchronized`、`volatile`、`final` 的真实语义

## 支柱 2：数据存储与中间件

> **为什么是支柱**：90% 的系统性能问题和故障，根因都在存储和中间件。架构师必须能在选型层做决策，而不是"团队用过什么就用什么"。

### 2.1 关系型数据库（MySQL 为主）

架构师要会的不是 SQL，是**存储引擎原理 + 工程化方案**：

| 能力点 | 架构师级别要求 |
|---|---|
| 索引 | B+ 树为什么是 B+ 树（不是 B 树/红黑树/跳表）；联合索引最左前缀；覆盖索引；索引下推 ICP |
| 事务与 MVCC | ACID 实现、四种隔离级别、MVCC 的 ReadView 机制、快照读 vs 当前读 |
| 锁 | 行锁/间隙锁/Next-Key Lock；死锁分析；意向锁；怎么用 `SHOW ENGINE INNODB STATUS` 看锁 |
| 性能调优 | EXPLAIN 全字段会读；optimizer trace；慢 SQL 不只会加索引，会判断"该不该改表结构" |
| 分库分表 | ShardingSphere 选型、分片键怎么选（避免数据倾斜和跨片查询）、迁移方案（双写/影子表） |
| 高可用 | 主从复制原理（binlog/relay log/SQL 线程）、半同步复制、MHA/Orchestrator |

> 🔑 **架构师级金句**：「分库分表不是性能优化手段，是容量规划手段。在单表 1000 万行还能跑的情况下，不要为了"看起来高级"而分库分表——它会带来跨片事务、聚合查询、迁移成本一堆问题。只有当单库容量、写入吞吐、单表数据量真的撞墙了，才上。」

### 2.2 缓存（Redis）

不只是会用 Redis，要能在架构层做缓存设计：

- **数据结构 + 底层**：SDS / 跳表 / quicklist / listpack（不是"5 种类型"，是底层数据结构）
- **三大经典问题**：穿透（布隆过滤器）、击穿（互斥锁/永不过期）、雪崩（随机过期、多级缓存）——但架构师级要能讲清"为什么这是问题、发生概率、不同方案的代价"
- **持久化**：RDB / AOF / 混合持久化的取舍。**判断力**：纯缓存场景可以关持久化，金融场景必须 AOF + everysec
- **集群**：主从 / 哨兵 / Cluster 的演进、Hash Slot、Gossip 协议、跨槽查询限制
- **分布式锁**：Redisson 看门狗、RedLock 争议（Martin Kleppmann vs antirez 的论战要懂）
- **缓存一致性**：Cache Aside / Read-Through / Write-Through / Write-Behind 四种模式的取舍，延迟双删解决什么、解决不了什么

### 2.3 消息队列

架构师必须能在 RocketMQ / Kafka / RabbitMQ / Pulsar 之间做**有依据的选型**：

| 场景 | 选型 | 原因 |
|---|---|---|
| 金融交易、订单、事务消息 | RocketMQ | 事务消息、低延迟、阿里大规模验证 |
| 日志、流处理、大数据管道 | Kafka | 顺序写、零拷贝、超高吞吐 |
| 复杂路由、企业集成 | RabbitMQ | Exchange 模型灵活 |
| 多租户、流批一体 | Pulsar | 计算存储分离、Topic 灵活 |

**架构师级深度要求**：

- 可靠性：生产端（同步/异步发送、重试、本地消息表）、消费端（幂等、位点管理、堆积处理）
- 顺序消息：全局顺序 vs 分区顺序的实现代价
- 事务消息：RocketMQ 半消息 + 回查机制的完整流程
- 延迟消息：时间轮原理、RocketMQ 18 个延迟级别 vs 任意延迟的实现

### 2.4 其他中间件

- **网关**：Spring Cloud Gateway / Kong / OpenResty，选型看团队语言栈和扩展需求
- **配置中心**：Nacos / Apollo，动态推送 vs 客户端拉取的差异
- **注册中心**：Nacos / Eureka / Consul / ZK，AP vs CP 的取舍（为什么注册中心应该选 AP）
- **搜索**：Elasticsearch 的倒排索引、分片、聚合分析能力

## 支柱 3：分布式系统（架构师的核心战场）

> **为什么是支柱**：单体系统里很多问题被进程内调用掩盖了，一旦分布式化，网络分区、超时、重试、幂等、一致性全冒出来。架构师必须能在分布式环境下做正确的工程设计。

### 3.1 分布式理论（不是背，是会用）

| 理论 | 架构师要知道什么 |
|---|---|
| CAP | 不是"三选二"那么简单。Partition 容错是必选，真正的取舍是 C vs A。能举例：ZK 偏 CP、Eureka 偏 AP、为什么注册中心应该选 AP |
| BASE | Basically Available + Soft state + Eventually consistent，是大规模互联网系统的实际选择 |
| ACID vs BASE | 强一致场景（金融账户）vs 最终一致场景（消息、库存）的选型依据 |

### 3.2 一致性算法

- **Raft**（必学）：leader election + log replication + safety。能讲清楚"为什么 Raft 比 Paxos 工程化更好"——分解成三个子问题、强 leader 简化流程
- **Paxos**：理论价值，了解即可，工程上多被 Raft 替代
- **ZAB 协议**：ZooKeeper 的算法，和 Raft 的对比

### 3.3 分布式协调与状态同步

- **Gossip 协议**：Cassandra / Redis Cluster 用它做状态同步，能讲清楚"最终一致、传播延迟、抗网络分区"
- **一致性 Hash**：Memcached / Redis Cluster 用，能讲清虚拟节点解决数据倾斜
- **分布式 ID**：雪花算法 / 号段模式（Leaf）/ UUID 的取舍

### 3.4 分布式事务（架构师必须能完整讲透）

不是只会说"用 Seata"，要能讲清**每种方案的适用场景和代价**：

```
┌──────────────────────────────────────────────────────────────┐
│                    分布式事务方案选型决策树                     │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  业务能接受最终一致？                                          │
│  ├─ 是 → 用什么传递消息？                                     │
│  │   ├─ RocketMQ 事务消息（推荐，原生支持）                    │
│  │   ├─ 本地消息表（无 RocketMQ 时用）                         │
│  │   └─ 最大努力通知（下游不需要强保证）                       │
│  │                                                          │
│  └─ 否（要强一致）                                            │
│      ├─ TCC（性能好但开发成本高，金融常用）                    │
│      ├─ Seata AT（侵入小但有全局锁，性能一般）                 │
│      └─ Saga（长事务，补偿机制，业务流程长用）                 │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

每种方案架构师要能答出：**性能、开发成本、可用性、补偿机制**四个维度的取舍。

## 支柱 4：架构设计能力

> **为什么是支柱**：这是"架构师"这三个字的安身立命之本。前面三个支柱是基础，这个支柱才是产出。

### 4.1 架构模式与演进

架构师要能讲清楚"为什么演进"，不是只列名词：

```
单体 → 集群 → 垂直拆分 → SOA → 微服务 → 云原生 → Serverless

每一步解决什么问题、带来什么新问题：
• 单体 → 集群：解决单点故障，但数据一致性问题来了
• 集群 → 垂直拆分：解决单库压力，但跨域调用问题来了
• SOA → 微服务：解决服务复用，但分布式事务/治理问题来了
• 微服务 → 云原生：解决部署运维标准化，但复杂度上来了
• 云原生 → Serverless：解决资源利用率，但冷启动/调试问题来了
```

### 4.2 DDD（领域驱动设计）

架构师做服务拆分的**核心方法论**：

- 战略设计：限界上下文（Bounded Context）、子域（核心/支撑/通用）
- 战术设计：聚合根、实体、值对象、领域服务、领域事件
- **判断力**：什么时候该用 DDD（业务复杂、长期演进），什么时候不该用（CRUD 简单业务用了就是过度设计）

### 4.3 高可用架构

```
                      高可用 = 冗余 + 自动故障转移 + 降级

┌──────────────────────────────────────────────────────────┐
│  容灾架构梯度                                            │
├──────────────────────────────────────────────────────────┤
│  主备      → 冷备，故障时切换，数据可能丢                 │
│  主从      → 热备，自动切换，单点写入                     │
│  同城双活  → 两机房同时写入，RPC 实时同步                 │
│  异地多活  → 单元化部署，按用户分流，数据按单元隔离        │
│                                                          │
│  架构师级判断：业务能接受 RTO/RPO 多少？据此选容灾级别   │
└──────────────────────────────────────────────────────────┘
```

- **限流**：令牌桶 / 漏桶 / 滑动窗口，Sentinel / Nginx 层选型
- **熔断降级**：Hystrix / Resilience4j / Sentinel，断路器三态（CLOSED/OPEN/HALF_OPEN）
- **隔离**：线程池隔离 vs 信号量隔离，写多读少的服务怎么隔离
- **超时**：超时级联、超时时间怎么设（不是拍脑袋，是看 SLA 倒推）

### 4.4 高并发架构

四大套路 + 背后的判断：

| 套路 | 解决什么问题 | 架构师要权衡的代价 |
|---|---|---|
| 缓存 | 读压力 | 一致性、雪崩、穿透 |
| 异步 | 写压力 + 解耦 | 消息可靠性、用户体验（异步通知 vs 同步等待） |
| 横向扩展 | 整体吞吐 | 会话一致性、无状态化改造成本 |
| 读写分离 | DB 读压力 | 主从延迟、写扩散 |

### 4.5 经典系统设计题（面试核心）

架构师面试的**重头戏**。每道题都要能讲出"需求拆解 → 容量估算 → 架构分层 → 关键决策 → 失败路径"五段式：

| 题目 | 核心考点 |
|---|---|
| 秒杀系统 | 限流 + 异步 + 库存预扣 + 防超卖（Redis Lua） |
| 短链系统 | 发号器 + 缓存 + 跳转 + Bloom 防穿透 |
| Feed 流 | 推模式 vs 拉模式 vs 推拉结合 |
| IM 系统 | 消息可靠投递 + 在线状态 + 消息顺序 |
| 订单系统 | 状态机 + 幂等 + 分布式事务 + 防重 |
| 排行榜 | Redis ZSet + 实时更新 + 分页 |
| 文件上传 | 分片 + 续传 + 秒传（MD5 比对） |
| 延迟任务 | 时间轮 / Redis ZSet / MQ 延迟消息 |

## 支柱 5：微服务与 Service Mesh

> **为什么是支柱**：现代后端系统的主流形态。架构师要能在"要不要拆微服务"和"怎么拆"上做决策。

### 5.1 服务治理全家桶

```
┌─────────────────────────────────────────────────┐
│  Spring Cloud Alibaba 生态                       │
├─────────────────────────────────────────────────┤
│  注册中心 + 配置中心  → Nacos                    │
│  服务调用            → Dubbo / OpenFeign        │
│  熔断降级            → Sentinel                 │
│  分布式事务          → Seata                    │
│  消息队列            → RocketMQ                 │
│  网关                → Spring Cloud Gateway     │
│  链路追踪            → SkyWalking               │
└─────────────────────────────────────────────────┘
```

### 5.2 服务拆分原则（架构师级判断力）

- **单一职责**：一个服务一个明确的业务边界
- **粒度**：不要太细（分布式事务噩梦），不要太粗（失去拆分意义）。"两个服务是否要合并"的判断：变更是否经常一起发生
- **数据隔离**：每个服务独占自己的数据库，禁止跨服务连表查询
- **API 设计**：RESTful vs RPC，同步 vs 异步

### 5.3 Service Mesh（云原生演进）

- Istio / Linkerd 的 Sidecar 模式
- 业务代码和治理逻辑解耦
- **判断力**：什么时候上 Service Mesh（多语言、治理逻辑复杂、业务无感升级）

## 支柱 6：稳定性与工程效能（架构师的护城河）

> **为什么是支柱**：架构师对系统的稳定性负责。代码写得再漂亮，系统挂了也是架构师的锅。

### 6.1 可观测性三支柱

```
┌────────────────────────────────────────────────────┐
│   Metrics  ──── Prometheus + Grafana   (聚合数字)  │
│   Logs     ──── ELK / Loki             (文本检索)  │
│   Traces   ──── SkyWalking / Jaeger    (调用链)    │
└────────────────────────────────────────────────────┘
                三者要能通过 TraceId 串起来
```

- **黄金信号**：延迟（P99/P999）、流量、错误率、饱和度
- **告警体系**：分级（P0 电话 / P1 短信 / P2 IM）、抑制、聚合、On-Call 轮值

### 6.2 容量规划与压测

- **容量估算**：日活 → QPS → 峰值 QPS → 单机容量 → 机器数
- **全链路压测**：JMeter / Wrk / 线上压测（影子库 / 影子表）
- **容量水位**：CPU / 内存 / 网络各到多少要扩容

### 6.3 变更管理

- **发布策略**：蓝绿 / 金丝雀 / 滚动 / 灰度（按用户/地域/比例）
- **回滚机制**：数据库变更怎么回滚（必须前向兼容）、代码回滚
- **变更评审**：哪些变更要架构师 review，哪些可以放开

### 6.4 故障应急与 SRE

- **故障定级**：P0（全站不可用）/ P1（核心功能不可用）/ P2（部分功能）
- **应急三板斧**：限流 → 降级 → 重启（永远先止血，再定位根因）
- **故障复盘**：5 Whys 找根因、改进项跟进、不追个人责任（追系统责任）
- **SRE 实践**：SLO / SLI / Error Budget，用错误预算驱动发布节奏

## 支柱 7：云原生与基础设施

> **为什么是支柱**：云原生是当下后端的"地基"。架构师不一定要亲自写 Dockerfile，但要能在基础设施层做技术决策。

### 7.1 容器与编排

- **Docker**：镜像分层、多阶段构建、BuildKit
- **Kubernetes**：Pod / Deployment / Service / Ingress / ConfigMap / StatefulSet
- **Helm**：包管理，Chart 模板化部署
- **判断力**：什么应用适合容器化（无状态服务天然适合），什么要谨慎（有状态服务、强依赖内核能力）

### 7.2 CI/CD

- Jenkins / GitLab CI / GitHub Actions / ArgoCD（GitOps）
- **Git Flow vs Trunk Based**：大团队 vs 小团队的策略差异
- **制品管理**：镜像仓库、版本号策略

### 7.3 IaC（基础设施即代码）

- Terraform / Pulumi
- 环境一致性：dev / staging / prod 用同一套代码描述

## 支柱 8：业务理解 + 技术规划 + 影响力（区分"高级"和"架构师"的关键）

> **为什么是支柱**：这是技术总监 / 架构师面试**最爱考察也最容易暴露**的部分。技术深度可以突击，业务理解和影响力突击不了。

### 8.1 业务理解力

- 能用业务语言（不是技术术语）和产品/业务方对话
- 能从业务目标（GMV、转化率、留存）倒推技术投入方向
- 能识别"伪需求"——业务说要 A，本质是要 B，技术方案可以更优雅

### 8.2 技术规划能力

- **年度技术规划**：从业务目标拆出技术路线图，分清"必须做 / 应该做 / 可以做"
- **技术债管理**：不是"没时间就不还"，是"主动评估债的利息，规划还债节奏"
- **预研**：新技术要不要跟？什么标准下从 PoC 转生产？

### 8.3 技术决策力

- **选型方法论**：不只看技术本身，要看团队接受度、社区活跃度、招聘难度、运维成本
- **决策记录**：ADR（Architecture Decision Record）让决策可追溯
- **承担后果**：决策错了承认，及时调整，不甩锅

### 8.4 技术影响力

- **跨团队协作**：推动一个需要 5 个团队配合的改造，靠的不是职权，是方案的说服力
- **技术分享 / 沉淀**：内部分享、技术博客、专利、开源贡献
- **人才培养**：能把初级工程师带成高级，是技术总监级能力的体现

## 支柱 9：AI 工程化（时代增量能力）

> **为什么是支柱**：2024 年后，AI 工程化是后端架构师的**差异化能力**。能设计 LLM 应用的架构师，市场溢价明显。

### 9.1 LLM 应用架构

- **RAG**：文档切分策略、Embedding 模型选型、向量检索、Rerank、上下文压缩
- **Agent**：Tool Calling / Function Calling、Memory（短期/长期）、Planning（ReAct / Plan-and-Execute）
- **Prompt Engineering**：不是"会写提示词"，是工程化的 Prompt 管理（版本化、A/B 测试、评测）

### 9.2 向量数据库与基础设施

- 选型：Milvus / Pinecone / Weaviate / pgvector
- 索引：HNSW / IVF / Flat 的取舍
- 工程化：Embedding 计算、向量更新、混合检索（向量 + 关键词）

### 9.3 LLM Ops

- **评测**：怎么定义"模型答得对不对"，自动化评测体系
- **监控**：Token 消耗、延迟、错误率、内容安全
- **成本控制**：模型路由（简单 query 走小模型，复杂 query 走大模型）、缓存

### 9.4 AI Coding 与研发提效

- Claude Code / Cursor / Copilot 的工程化集成
- 团队级 Prompt 沉淀、技能库（Skill）管理
- AI 辅助 Code Review、测试生成

## 一句话总结

架构师不是"会更多技术的资深工程师"，是**"能用技术解决业务问题、并对结果负责"的人**。技术深度是地基，架构能力是产出，稳定性保障是底线，业务理解和影响力是上限。这份图谱的九大支柱，对应的就是这条从"会写代码"到"能用技术驱动业务"的成长路径。
