## 贯穿业务场景:某创业项目商城订单系统

```sql
-- 用户表
CREATE TABLE `user` (
  `user_id`    BIGINT PRIMARY KEY,           -- 用户ID(雪花算法,如 1001)
  `phone`      VARCHAR(20) UNIQUE,           -- 手机号(登录用,唯一)
  `nickname`   VARCHAR(50),                  -- 昵称
  `balance`    DECIMAL(10,2) DEFAULT 0,      -- 账户余额
  `created_at` DATETIME DEFAULT NOW()
);

-- 商品表
CREATE TABLE `product` (
  `product_id` BIGINT PRIMARY KEY,           -- 商品ID(如 8001)
  `name`       VARCHAR(100),                 -- 商品名
  `price`      DECIMAL(10,2),
  `stock`      INT DEFAULT 0,                -- 库存数
  `category`   VARCHAR(50)
);

-- 订单表(本教材核心)
CREATE TABLE `t_order` (
  `order_id`     BIGINT PRIMARY KEY,         -- 订单号(雪花算法)
  `user_id`      BIGINT NOT NULL,
  `product_id`   BIGINT NOT NULL,
  `quantity`     INT NOT NULL,
  `amount`       DECIMAL(10,2) NOT NULL,
  `status`       VARCHAR(20) DEFAULT 'PENDING',
  `created_at`   DATETIME DEFAULT NOW(),
  INDEX idx_user(user_id),
  INDEX idx_status_created(status, created_at)
);
```

> **为什么 order_id 是数字**:雪花算法生成全局唯一 ID(时间戳+机器ID+序列号),**保证递增**。递增很重要——B+树叶子有序,新订单追加到末尾,**不触发页分裂**。如果用 UUID 这种乱序 ID,插入会频繁页分裂,写性能差。

**贯穿用例的三条订单数据**:

| order_id | user_id | product_id | quantity | amount | status | created_at |
|---|---|---|---|---|---|---|
| 2024070100001 | 1001(张三) | 8001(iPhone 16) | 1 | 9999.00 | PAID | 07-01 10:00 |
| 2024070100002 | 1002(李四) | 8002(iPad Pro) | 2 | 15998.00 | SHIPPED | 07-01 14:30 |
| 2024070100003 | 1001(张三) | 8003(AirPods) | 3 | 4497.00 | PENDING | 07-01 18:00 |

## 模块 1.1 索引

### 📖 原理 + 工程

**为什么索引要专门设计**:评价数据库索引的核心指标**不是 CPU 比较次数,而是磁盘 IO 次数**(磁盘比内存慢 1 万~10 万倍)。

**B+树三个设计决策,每个直指"减少 IO"**:
- 非叶子节点只存键值 → 节点更紧凑 → 树更矮 → IO 更少
- 数据全在叶子 → 查询性能稳定
- 叶子双向链表 → 范围查询快

**聚簇索引 vs 二级索引**:聚簇索引(主键索引)叶子 = 完整行;二级索引叶子 = 索引键 + 主键值。用二级索引查到主键后要**回表**到聚簇索引查完整行(多一次 IO)。

**覆盖索引**:查询字段都在索引里 → 不回表 → `Extra: Using index`。只给"高频 + 字段少(≤3)"的查询建覆盖索引,避免索引爆炸拖垮写入。

**联合索引最左前缀**:必须从最左列连续使用。**范围查询之后的列失效**,设计时等值列放前、范围列放后。

### 🎨 图解

```
查询 SELECT * FROM t_order WHERE user_id = 1001; (走 idx_user 二级索引)

              【根节点】(只存 user_id 导航, 1次IO)
              ┌──────────────────────────────────────┐
              │  user_id ≤ 1001 │ 1001 < id ≤ 2000 │ > 2000 │
              └──────┬──────────┼──────────────────┼────────┘
                     ▼          ▼                  ▼
              【中间节点】                            【中间节点】
              ┌────────────┐                       ┌────────────┐
              │ ≤1001 │...│                       │ ...        │
              └───┬────┬──┘                       └────────────┘
                  ▼    ▼
              【叶子节点】(存: user_id + order_id, 不存完整订单!)
              ┌──────────────────────────┐  ┌──────────────────────┐
              │ user_id=1001             │⇄│ user_id=1001         │⇄...
              │ order_id=2024070100001   │  │ order_id=2024070100003│
              │ (张三的iPhone订单)        │  │ (张三的AirPods订单)  │
              └──────────────────────────┘  └──────────────────────┘
                   ↑双向链表⇄(范围查询顺链表扫)

  查询路径: 3次IO定位到主键 → 还要回表聚簇索引拿完整订单!
```

### 🔥 面试连环追问

**Q1: 为什么 MySQL 用 B+树?**
> 为磁盘优化:非叶子只存键所以树矮(三层索引 25 亿行 3 次 IO)、叶子双向链表所以范围查询快、页对齐 16KB 对预读友好。

**Q2(追问):订单号怎么生成?为什么是数字?**
> 雪花算法(时间戳+机器ID+序列号),全局唯一且递增。递增很重要——B+树叶子有序,新订单追加到末尾,不触发页分裂。UUID 乱序插入频繁页分裂,写性能差。

**Q3(追问):`WHERE user_id=1001 ORDER BY created_at` 出现 Using filesort 怎么办?**
> 给 ORDER BY 字段加索引,顺序匹配联合索引。建 `(user_id, created_at)`,先用 user_id 定位,created_at 天然有序不 filesort。

**Q4(追问):`WHERE phone=13800138000`(phone 是 VARCHAR)为什么慢?**
> 隐式类型转换。MySQL 把字符串转数字(等价于对 phone 加 CAST 函数),破坏 B+树有序性,索引失效,全表扫。生产事故常见根因。

## 模块 1.2 事务与 MVCC

### 📖 原理 + 工程

**ACID**:A 靠 undo log、D 靠 redo log(WAL)、I 靠 MVCC+锁、C 靠前三者+业务约束。

**WAL(Write-Ahead Logging)**:先快速顺序写 redo log,再异步慢刷数据页。**用顺序 IO 换随机 IO**,是数据库性能魔法。

**双 1 配置**(金融铁律):`innodb_flush_log_at_trx_commit=1` + `sync_binlog=1`,每次提交都刷盘,绝对不丢数据。

**四种隔离级别**:RU/RC/**RR**(MySQL 默认)/Serializable。RR 靠 Next-Key Lock 基本解幻读。

**MVCC 核心**:版本链(每行有 trx_id 和 roll_ptr,旧版本进 undo log 串成链) + ReadView(记录活跃事务)。读数据时按可见性规则顺版本链找可见版本,**读不加锁、不阻塞写**。

**RC vs RR 本质区别**:ReadView 生成时机。RC 每次 SELECT 重建,RR 复用第一次——**"可重复读"就是 ReadView 复用**。

### 🎨 图解

```
订单 2024070100001 的版本链(status 多次变更):

  当前数据                              undo log(历史版本)
  ┌──────────────────────────┐
  │ status: SHIPPED(已发货) │ ← 当前版本 trx_id=500
  │ trx_id: 500              │
  │ roll_ptr: ────────────────────┐
  └──────────────────────────┘   │
                                 ▼
              ┌──────────────────────────┐
              │ status: PAID(已支付)    │ ← 版本2 trx_id=400
              │ roll_ptr: ────────────────────┐
              └──────────────────────────┘   │
                                             ▼
                          ┌──────────────────────────┐
                          │ status: PENDING(待支付) │ ← 版本3 trx_id=300
                          │ roll_ptr: null           │
                          └──────────────────────────┘

运营查这个订单(事务#600, ReadView m_ids=[500]):
  → trx_id=500 在 m_ids 里(未提交)→ 不可见 ✗
  → 顺 roll_ptr 找版本2, trx_id=400 < min_trx_id → 已提交 → 可见 ✓
  → 看到 status=PAID(读历史快照,不阻塞写操作)
```

### 🔥 面试连环追问

**Q1: 下单事务(插订单+扣库存+扣余额)的 ACID 怎么保证?**
> A 靠 undo log(回滚已插订单/已扣库存);D 靠 redo log(WAL 先写日志);I 靠 MVCC+锁(扣库存用 FOR UPDATE);C 靠前三者+业务校验。

**Q2(追问):下单提交后立即宕机,订单会丢吗?**
> 不会。redo log 在提交前已顺序写盘。重启重放 redo log,把变更重做到数据页。

**Q3(追问):MVCC 怎么实现读不加锁?**
> 版本链 + ReadView。读的是历史快照,不阻塞写。

**Q4(追问):你们生产用 RC 还是 RR?**
> 核心交易用 RR(强一致),高并发读多场景(商品列表)用 RC(避间隙锁死锁)。按业务决策不一刀切。

## 模块 1.3 锁机制

### 📖 原理 + 工程

**FOR UPDATE 锁范围**:
- 主键/唯一索引等值命中 → 记录锁(只锁一行)
- 唯一索引等值未命中 → 间隙锁
- 普通索引 → Next-Key + 后间隙
- **无索引 → 锁全表!**(生产大坑)

**死锁处理**:InnoDB 自动检测(wait-for graph),回滚 undo 量少的事务。生产预防三件套:统一加锁顺序、缩短事务、幂等重试。

**扣库存正确写法**:`@Transactional(rollbackFor=Exception.class)` + `FOR UPDATE`(WHERE 走主键)。

### 🎨 图解

```
product 表: product_id=8001(iPhone), 8002(iPad), 8003(AirPods)

场景: 无索引 FOR UPDATE 锁全表!
  SELECT * FROM product WHERE name='iPhone 16' FOR UPDATE;  (name 无索引)

  product_id: 8001        8002        8003
              [🔒X锁]     [🔒X锁]     [🔒X锁]
              ↑ MySQL逐行扫描逐行加锁 → 整表锁死!
              此刻任何事务不能改任何商品 → 业务卡死

正确: SELECT .. FOR UPDATE WHERE product_id=8001;  (走主键,只锁一行)

死锁场景:
  事务A: 锁8001 → 想锁8003    事务B: 锁8003 → 想锁8001
  → A等B的8003, B等A的8001 → 死锁!
  InnoDB 自动检测 → 回滚 undo 少的事务 → 报错让重试
  预防: 所有事务按 product_id 升序加锁,避免循环等待
```

### 🔥 面试连环追问

**Q1: 扣库存怎么防超卖?**
> `SELECT .. FOR UPDATE` 加行锁串行化。WHERE 必须走主键 product_id,否则锁全表。第二个事务等第一个提交后读到 stock=0,下单失败。

**Q2(追问):为什么普通 SELECT 不行?**
> 普通 SELECT 是 MVCC 快照读,读历史版本,两人都读到 stock=1,都扣减成功 → 超卖。

**Q3(追问):死锁怎么预防?**
> 统一加锁顺序(按主键升序)、缩短事务、降级 RC、核心交易配 @Retryable 幂等重试。

**Q4(追问):@Transactional 有什么坑?**
> (1)默认只回滚 RuntimeException,业务异常要加 `rollbackFor=Exception.class`;(2)方法内不要做外部调用(长事务占连接);(3)必须是 public 且通过 Spring 代理调用(同类内部调用不走代理,事务失效)。

## 模块 1.4 慢 SQL 优化

### 📖 原理 + 工程

**三层发现**:慢查询日志 + pt-query-digest 分析 + APM(SkyWalking)实时抓。

**EXPLAIN 关键字段**:type(至少 range,ALL 必须优化)、key(NULL 没走索引)、Extra(Using index 好 / Using filesort 坏 / Using temporary 坏)。

**深分页优化**:
- **延迟关联**:子查询走覆盖索引找 id,再 JOIN 回表只读 20 行
- **游标分页**:`WHERE order_id > 上次最大值 LIMIT 20`,只支持连续翻页

### 🎨 图解

```
张三查第 1000 页订单(每页 20):
  SELECT * FROM t_order WHERE user_id=1001 ORDER BY order_id LIMIT 20000, 20;
  → 要扫前 20000 行丢弃,极慢

方案A 延迟关联:
  SELECT o.* FROM t_order o
  INNER JOIN (
      SELECT order_id FROM t_order WHERE user_id=1001 ORDER BY order_id LIMIT 20000, 20
  ) t ON o.order_id = t.order_id;
  → 子查询走覆盖索引(不回表)快速扫到 20 个 id,再 JOIN 只回表 20 次

方案B 游标分页:
  SELECT * FROM t_order WHERE user_id=1001 AND order_id > #{last_id} ORDER BY order_id LIMIT 20;
  → WHERE order_id > last 直接走索引定位,不扫前面
  ⚠️ 只支持"上一页/下一页",不支持跳页

业务方案: 淘宝/微信订单列表都是"下拉加载更多"(游标),跳页是伪需求
```

### 🔥 面试连环追问

**Q1: 深分页为什么慢?怎么优化?**
> 要扫大量行丢弃。延迟关联(子查询覆盖索引找 id 再 JOIN)或游标分页(WHERE id > 上次最大)。

**Q2(追问):Using filesort 怎么消除?**
> 给 ORDER BY 字段加索引,顺序匹配联合索引。`WHERE user_id=X ORDER BY created_at` 建 (user_id, created_at)。

**Q3(追问):OLAP 查百万行订单怎么办?**
> 不该用 MySQL(OLTP)。用 ClickHouse/Doris。架构上把分析查询剥离到 OLAP 库。

## 模块 1.5 存储结构

### 📖 原理 + 工程

InnoDB 一张表 = 一个 .ibd 文件(聚簇存储)。四层:**表空间 → 段 → 区(1MB = 64 页) → 页(16KB)→ 行**。

**页是磁盘 IO 的最小单位**。读一条订单连带读整页(局部性原理)。

**行格式**:Compact 格式 = 变长长度列表 + NULL 标志 + 记录头 + 列数据 + 隐藏列(trx_id, roll_ptr)。**NULL 不占空间**,varchar 存"长度+值"。

### 🎨 图解

```
t_order.ibd 文件结构:

表空间(tablespace)
├── 段(segment) - 数据段(存叶子节点的数据)
│   └── 区(extent) 1MB = 64个连续页
│       └── 页(page) 16KB ⭐磁盘IO最小单位
│           ├── File Header(页号、前后页指针)
│           ├── 记录1: order_id=2024070100001 (张三iPhone订单)
│           ├── 记录2: order_id=2024070100002 (李四iPad订单)
│           ├── ...
│           ├── Page Directory(槽位数组, 二分查找用)
│           └── File Trailer(校验)
└── 段(segment) - 索引段(存B+树非叶子节点)
```

### 🔥 面试连环追问

**Q1: 为什么有"区"这个概念?**
> 区是 1MB = 64 个连续页,让连续页物理相邻,顺序读快,且减少空间碎片。

**Q2(追问):页内怎么查找一条记录?**
> Page Directory 槽位数组,二分查找 O(log n)。页间走 B+树定位。

**Q3(追问):VARCHAR(255) 实际占多大空间?**
> 实际长度 + 1~2 字节存长度。存 "PAID" 占 5 字节,不是 255。

## 模块 1.6 SQL 执行与 Buffer Pool

### 📖 原理 + 工程

**SQL 执行流程**:连接器 → 分析器 → **优化器**(选索引,生成执行计划) → 执行器 → InnoDB 读写 → 返回。Server 层(解析+决策) + 存储引擎层(读写)分离。

**Buffer Pool**:内存缓存热点数据页和索引页。给物理内存 50-70%。命中走内存(纳秒级),不命中读磁盘(微秒级)。

**改良版 LRU**:分 young/old 两区。新页进 old,**1 秒后再次访问才升 young**。防全表扫污染热点。

### 🎨 图解

```
改良 LRU 防污染:

  young 区(热)               old 区(冷)
  ┌────────────────────┐  midpoint  ┌────────────────────┐
  │ 张三订单页(热)    │   ◀──▶    │ 运营扫的冷页1      │
  │ 李四订单页(热)    │            │ 运营扫的冷页2      │
  │ 商品页(热)        │            │ ...                │
  └────────────────────┘            └────────────────────┘

  规则:
  1. 新页(含全表扫的冷页)→ 进 old 区头部
  2. old 区的页 1秒后再次被访问 → 才升 young
  3. 全表扫的冷页进 old 后快速淘汰,不污染 young 区热点
  4. 张三订单页稳坐 young 区 ✅
```

### 🔥 面试连环追问

**Q1: 优化器怎么决定走哪个索引?**
> 基于成本。统计每个索引的基数(不同值数量)和预估扫描行数,选成本低的。可用 EXPLAIN 看决策,FORCE INDEX 强制。

**Q2(追问):buffer pool 满了怎么办?**
> 改良 LRU(young/old 区)。新页进 old,1 秒后再次访问才升 young。全表扫的页进 old 快速淘汰,不污染热点。

**Q3(追问):redo log 满了会怎样?**
> 必须停下来强制刷脏页(checkpoint 推进),期间所有写入阻塞。所以 redo log 不能太小,生产给 1G+。

## 模块 1.7 读写分离与云数据库

### 📖 原理 + 工程

云数据库"读写不同域名 + 读不能写" = **主从复制 + 只读实例 + Proxy 代理**组合方案。

**三个技术**:
- **主从复制**:主库写 → binlog → 从库重放(三线程:dump / IO / SQL)
- **只读实例**:从库 `read_only=ON` + `super_read_only=ON`
- **Proxy 代理**:阿里云 RDS Proxy / ProxySQL(自建) / ShardingSphere-Proxy(含分库分表)

**双重保险**:Proxy 拦截写(快) + 只读实例 read_only 拒绝(兜底)。

### 🎨 图解

```
某创业项目商城订单服务
├─ 写(下单): 主域名 rm-xxx ──▶ Proxy ──▶ 主库(唯一写入点)
│                                              │ binlog 同步
│              ┌───────────────────────────────┼───────────────────┐
│              ▼                               ▼                   ▼
│         只读实例1(读)                  只读实例2(读)        只读实例3(读)
│         read_only=ON                   read_only=ON          read_only=ON
│
└─ 读(查订单): 读域名 rr-xxx ──▶ Proxy ──▶ 负载均衡选一个只读实例

用读域名执行 INSERT → Proxy 判断是写 → 拦截(快速失败)
  或绕过 Proxy 直连只读实例 → read_only=ON 拒绝(兜底)
```

### 🔥 面试连环追问

**Q1: 为什么读域名不能写?**
> 双重保险:Proxy 按"读域名禁止写"规则拦截;只读实例本身 `read_only=ON` 拒绝。防止误写从库导致主从不一致。

**Q2(追问):张三下单后立即用读域名查,看不到订单?**
> 主从延迟。写后短时间读走主域名(代码 `@Master` 注解),或半同步复制,或前端延迟刷新。

**Q3(追问):自建数据库读写分离用什么?**
> ProxySQL(只读写分离,轻量主流)或 ShardingSphere-Proxy(含分库分表,Apache 顶级)。

**Q4(追问):某创业项目订单系统怎么设计?**
> 主库写 + 3 只读实例读。ShardingSphere-JDBC 自动读写分离。核心交易半同步复制防延迟。订单超千万再按 user_id 分库分表。

# 第二部分:DDD 领域驱动设计

## 模块 2.1 战略设计:限界上下文

### 📖 原理 + 工程

**DDD 要治的病**:业务逻辑散落在 Service/SQL/Controller,改一个规则要动十几个文件。

**核心心法**:让软件结构贴合业务领域真实结构——代码划分跟着业务走,不跟着数据库表走。

**限界上下文**:一个**语义边界**,边界内某词有唯一明确含义。**是微服务拆分的理论依据**。

**三个域**:
- **核心域**(营销引擎、订单交易):投精英,完整用 DDD
- **支撑域**(库存、物流):中等投入
- **通用域**(用户认证、权限):直接用现成组件,别造轮子

### 🎨 图解

```
"商品"这个词在不同上下文含义不同:

┌─────────────────┐  ┌─────────────────┐  ┌─────────────────┐
│   商品上下文     │  │   订单上下文     │  │   物流上下文     │
│  Product {       │  │  OrderItem {     │  │  Package {       │
│    sku           │  │    snapshotTitle │  │    weight        │
│    name          │  │    dealPrice     │  │    volume        │
│    category      │  │    qty           │  │    address       │
│    onSale        │  │  }               │  │  }               │
│  }               │  │ "交易快照,不变" │  │ "包裹,物理属性" │
│ "可售卖物品"     │  │                  │  │                  │
└─────────────────┘  └─────────────────┘  └─────────────────┘

如果不区分(用一个大 Product 类贯穿全系统)→ 上帝类(几百字段)→ 灾难
正确: 一个限界上下文 ≈ 一个微服务
```

### 🔥 面试连环追问

**Q1: 微服务按什么拆?**
> 限界上下文(语义边界)。先做领域建模,找出哪些词在一个上下文里含义唯一。比如订单和库存,"商品"在订单里是交易快照、在库存里是可售数量,语义不同,拆两个服务。

**Q2(追问):限界上下文之间怎么通信?**
> 三种主流模式:领域事件(解耦,事件驱动)、ACL 防腐层(对接老系统隔离烂模型)、共享内核(慎用,耦合高)。

**Q3(追问):核心域/支撑域/通用域怎么分配资源?**
> 核心域投最精英的人完整用 DDD;通用域直接用开源/采购,别自己造权限系统;支撑域中等投入够用即可。

## 模块 2.2 战术设计:聚合根

### 📖 原理 + 工程

**聚合根**:一组紧密关联对象的"老大",保证聚合内一致性。外部只能通过聚合根访问。

**聚合设计 4 原则**:
1. 外部只引用聚合根
2. 聚合内强一致,聚合间最终一致
3. 一次事务只改一个聚合
4. 聚合要小

**充血 vs 贫血模型**:贫血(只有 getter/setter,业务全在 Service,DDD 批判);充血(数据+行为,业务规则在聚合根方法,DDD 追求)。

### 🎨 图解

```
Order 聚合(正确):

┌─────────────────────────────────────┐
│          Order (聚合根)              │  ← 唯一入口
│  - status、totalAmount、payTime     │
│  - List<OrderItem>                   │
│                                      │
│  void cancel() {                     │  ← 业务规则在这里
│    if (status==COMPLETED)            │
│      throw "已完成不能取消";         │
│    status = CANCELLED;               │
│    if (payTime!=null)                │
│      发布 OrderCancelledEvent;       │  ← 不直接调退款服务
│  }                                   │
└─────────────────────────────────────┘

反模式(大聚合):
Order → OrderItem → ItemAttr → AttrHistory (四层嵌套)
→ 加载一个订单要查整棵树 → 性能爆炸

正解: Order 只含 OrderItem, ItemAttr 单独成聚合, 用 ID 引用
```

### 🔥 面试连环追问

**Q1: 为什么聚合间用最终一致,不强一致?**
> 跨聚合强一致 = 分布式事务(代价高、锁长、易死锁)。订单和库存是两个聚合,扣库存可以异步。强一致是奢侈品,只在资金类场景用。

**Q2(追问):聚合根和实体什么关系?**
> 聚合根本身是实体(有唯一 ID),是聚合内对外的唯一入口,负责维护一致性。

**Q3(追问):@Transactional 加在哪?**
> 加在应用层 Service,只做"取出来 → 调聚合根方法 → 存回去"的编排。业务规则在聚合根方法里。Service 不含业务规则。

# 第三部分:高可用/高并发

## 模块 3.1 雪崩机理与三板斧

### 📖 原理 + 工程

**雪崩本质**:**资源耗尽 + 故障传播**。一个局部故障通过资源耗尽放大成全局故障。

**反雪崩核心思路**:快速失败(超时/熔断) + 隔离(舱壁/降级)。

**三板斧辨析**:
- **限流**(事前预防):入口限速,防过载
- **熔断**(事中止损):下游故障主动断开,保护自己
- **降级**(事后保命):整体压力下牺牲非核心功能

### 🎨 图解

```
雪崩发生过程:
数据库慢 2s
   ↓
服务B 线程池满(200线程全卡住等数据库)
   ↓
服务B 响应变慢, 队列堆积
   ↓
服务A 调B也变慢 → 服务A线程池满
   ↓
全线雪崩(起因只是数据库一个慢查询)

熔断器三态状态机:
        失败率>阈值
  Closed (正常) ──────▶ Open (熔断,直接失败)
  正常调用统计            │ 不调下游,1ms失败释放线程
        ▲                │ 等 10s
        │ 探活成功        ▼
  Closed ◀───── Half-Open (放少量请求试探)
                 成功转Closed, 失败转Open

关键: Half-Open 不能省! 防止全量流量打回再次压垮下游
```

### 🔥 面试连环追问

**Q1: 限流/熔断/降级三者区别?**
> 限流防患于未然(事前)、熔断及时止损(事中)、降级壮士断腕(事后)。限流入口限速,熔断下游故障主动断,降级全局压力牺牲非核心。

**Q2(追问):熔断 Half-Open 为什么不能从 Open 直接跳 Closed?**
> 直接跳 Closed 瞬间把全量流量打回下游,刚恢复一点的下游被再次压垮,反复震荡。Half-Open 放少量请求试探,确认真扛得住再放开。

**Q3(追问):重试有哪些坑?**
> (1)重试放大流量(下游已扛不住还重试 3 次 = 放大 3 倍);(2)多层重试风暴(指数级);(3)非幂等不能重试(扣款接口重试扣两次)。原则:只重试幂等、限 1-2 次、指数退避+抖动、熔断时不重试。

## 模块 3.2 限流的工业级落地

### 📖 原理 + 工程

**四层限流架构**:
1. **接入层 Nginx**(limit_req,漏桶):按 IP 限流,挡爬虫
2. **网关层 Sentinel**(动态规则):按 API/租户
3. **应用层 Sentinel 单机**:保护自身线程池
4. **分布式 Redis+Lua**:精确全集群配额

**令牌桶 vs 漏桶**:令牌桶允许突发(适合 Web API),漏桶绝对平滑(保护脆弱下游)。生产串联:令牌桶控总量 + 漏桶做匀速输出。

**Sentinel 滑动窗口**:默认 2 个 500ms 桶,统计时取最近 1 秒覆盖的桶求和。解决固定窗口边界双倍问题。

**令牌桶惰性计算**:不持续生成令牌,请求来时按时间差一次性算应得令牌。

### 🎨 图解

```
限流四层架构:

                     用户请求
                        │
        ┌───────────────▼───────────────┐
        │ ① Nginx (limit_req)            │  按 IP, 挡恶意
        │    rate=10r/s per IP           │
        └───────────────┬───────────────┘
                        │
        ┌───────────────▼───────────────┐
        │ ② 网关 Sentinel                │  按 API, 动态规则(Nacos)
        │    createOrder: 1000 QPS      │
        └───────────────┬───────────────┘
                        │
        ┌───────────────▼───────────────┐
        │ ③ 应用 Sentinel 单机           │  保护线程池
        │    库存扣减: 500 QPS/实例     │
        └───────────────┬───────────────┘
                        │
        ┌───────────────▼───────────────┐
        │ ④ Redis+Lua 分布式             │  保护外部依赖(精确配额)
        │    第三方API: 全集群 100 QPS  │
        └───────────────────────────────┘

令牌桶 + 漏桶串联(解决突发冲击下游):
  请求 ──▶ [令牌桶](控总量,允许有限突发) ──▶ [漏桶](强制匀速) ──▶ 下游
```

### 🔥 面试连环追问

**Q1: 令牌桶允许突发,会不会打垮系统?**
> 突发有上限(桶容量 burst)。burst 按"链路最弱环节容量"设。生产串联令牌桶+漏桶:令牌桶入口控总量,漏桶出口匀速保护下游。

**Q2(追问):分布式限流怎么做?**
> Redis+Lua。tokens 和 last_refill 存 Redis,Lua 保证惰性计算+扣减的原子性(单线程串行)。坑:时钟漂移(用 Redis TIME 命令)、Redis 故障(降级单机兜底)、热 key(分片或本地预扣减)。

**Q3(追问):Sentinel 和 Resilience4j 怎么选?**
> 国内微服务选 Sentinel(动态规则接 Nacos、自带控制台)。云原生 Spring Boot 3 选 Resilience4j(函数式、Spring 官方推荐)。Hystrix 已停维护不选。

## 模块 3.3 缓存三问的工业级落地

### 📖 原理 + 工程

| 问题 | 本质 | 工业解法 |
|---|---|---|
| **穿透**(查不存在) | DB 也没这数据 | 布隆过滤器(Redisson RBloomFilter)+ 缓存空值 |
| **击穿**(单热点失效) | 一个热 key 过期 | Redisson 分布式锁 + 双重检查(看门狗续期) |
| **雪崩**(大量同失效) | TTL 集中 | TTL 随机扰动(基础 ±10-20%) + Caffeine 二级 + Sentinel 熔断 |

**延迟双删**(缓存一致性):先删缓存 → 更 DB → 延迟 500ms 再删(清"读旧值回填"脏数据)。

### 🎨 图解

```
缓存三问对比:

穿透(查根本不存在):
  请求 id=-1 → Redis 没 → DB 没 → 返回null
  下次又查 → 又穿到底 → 攻击刷接口,DB被打死
  解法: 布隆过滤器拦截 + 缓存空值(短TTL)

击穿(单热点失效):
  热 key "iPhone价格" 过期 → 瞬间1万请求同时查DB
  解法: Redisson 分布式锁,只让1个查DB回填,其他等

雪崩(大量同失效):
  一批缓存都设 24:00 过期 → 24:00 集体失效 → DB过载
  解法: TTL加随机扰动(基础30min ± 5min)

Redisson 看门狗(分布式锁自动续期):
  拿锁(30s过期) → 看门狗每10s检查续期到30s
  → 业务完事unlock → 看门狗停
  → 宕机则看门狗也死,30s后锁自动释放
  → 比手写 SETNX 可靠(原子性/续期/释放校验三大坑全填)
```

### 🔥 面试连环追问

**Q1: 击穿为什么用 Redisson 不用手写 SETNX?**
> Redisson 看门狗自动续期,解决"业务执行时间不可预测"。手写 SETNX 三大坑:SETNX+EXPIRE 不原子、业务超时锁过期、释放锁要校验是不是自己的。Redisson 全填了。

**Q2(追问):布隆过滤器说"在"准确吗?**
> 不一定。布隆过滤器:说"不在"100% 不在,说"在"可能误判(假阳性)。预期元素数+误判率(1%)决定 bit 数组大小和 hash 函数数。删除是坑(标准布隆不能删),用布谷鸟过滤器或周期重建。

**Q3(追问):缓存一致性怎么保证?**
> 延迟双删(先删缓存-更DB-延迟500ms再删)。比只删一次可靠,比订阅 binlog 简单。延迟需大于一次读DB+写缓存耗时。

## 模块 3.4 TP99 与延迟度量

### 📖 原理 + 工程

**TP99**:第 99 百分位响应时间,99% 请求比它快,只盯最慢的 1%。

**为什么不用平均值**:平均值会被快请求稀释,掩盖 1% 慢请求(而这 1% 往往是 GC/慢SQL/缓存击穿的故障信号)。

**为什么选 99**:TP90 太宽松(10% 慢),TP100 太敏感(一次抖动爆表)。TP99 既盯长尾又抗噪声。

**TP99 对稳定性 5 层意义**:暴露长尾(故障预警)、反映真实体验(影响留存)、延迟 SLO 核心、容量水位线、优化指南针。

### 🎨 图解

```
平均值掩盖长尾:

100个请求里: 99个10ms, 1个10000ms(10秒)
平均值 = (99×10 + 1×10000)/100 = 109.9ms  ← 看起来正常!
TP99   = 第99位 = 500ms(或更高)          ← 暴露问题!

监控场景:
时间点     平均响应    TP99     状态
10:00      50ms       200ms    健康
10:05      55ms       2000ms   ⚠️ TP99飙升10倍! (平均才涨5ms)
10:10      80ms       5000ms   雪崩前兆

洞察: TP99比平均值更早暴露问题,是故障早期预警
     优化TP99 = 优化最差用户体验,而非刷好看的虚荣数字

工业测量: Prometheus Histogram + histogram_quantile(0.99, ...)
  (不能真排序百万样本,用分桶统计,内存固定)
```

### 🔥 面试连环追问

**Q1: 为什么用 TP99 不用平均值?**
> 平均值被快请求稀释,掩盖 1% 慢请求。长尾往往是 GC/慢SQL/缓存击穿的故障信号。TP99 专盯长尾。

**Q2(追问):TP99 怎么测?**
> 生产用 Prometheus Histogram 分桶统计,`histogram_quantile(0.99, ...)` 查询。不能真排序(内存爆炸)。

**Q3(追问):可用性 SLO + 延迟 SLO 的关系?**
> 完整的可靠性定义是"可用性 + 延迟"。`100% 成功但每个 10 秒`也是不可用。SLO = 99.9% 成功 + TP99 < 500ms。

# 第四部分:JVM 内存与 GC

## 模块 4.1 内存结构

### 📖 原理 + 工程

**OOM 真实事故**:订单服务双 11 报 `OutOfMemoryError: Java heap space`,懂 JVM 能用 jmap 定位是 Order 对象 2 亿个(没分页全量加载),否则只能盲目重启。

**运行时数据区 5 块**(Java 8+):

| 区域 | 存什么 | 线程共享? | OOM? |
|---|---|---|---|
| 堆(Heap) | 对象实例(订单/商品) | 共享 | **会,OOM 高发** |
| 方法区(Metaspace) | 类元数据/常量/静态变量 | 共享 | 会 |
| 虚拟机栈 | 方法栈帧(局部变量) | 私有 | 会(StackOverflow/OOM) |
| 本地方法栈 | Native 方法栈帧 | 私有 | 会 |
| 程序计数器(PC) | 当前执行字节码地址 | 私有 | **不会** |

**堆分代**:新生代(Eden:S0:S1=8:1:1) + 老年代(2/3)。分代假说:绝大多数对象朝生夕死。

**为什么 8:1:1**:IBM 研究新生代 98% 对象朝生夕死,Survivor 只是中转站不需大,Eden + 一个 Survivor = 90% 可用。

### 🎨 图解

```
JVM 运行时内存(订单服务):

┌─────────── 线程私有(每线程一份) ───────────┐
│ 线程1(张三下单)        线程2(李四下单)      │
│  PC(执行位置)           PC                  │
│  虚拟机栈(栈帧)         虚拟机栈            │
│   createOrder栈帧        createOrder栈帧    │
│   局部变量:req,order    局部变量           │
│  本地方法栈              本地方法栈          │
└─────────────────────────────────────────────┘
┌─────────── 线程共享 ───────────────────────┐
│ 堆(Heap) ⭐OOM 高发地                      │
│  新生代(1/3):                              │
│   Eden(8): [Order#001][Order#002]          │
│   S0(1)空 / S1(1)存活对象                  │
│  老年代(2/3):                              │
│   连接池/Spring单例/长期存活对象            │
│ Metaspace(方法区, 直接内存)                │
│  OrderService.class元数据/"PENDING"常量    │
└─────────────────────────────────────────────┘
```

### 🔥 面试连环追问

**Q1: JVM 运行时数据区?**
> 5 块:堆(对象)+方法区/Metaspace(类元)+栈(栈帧)+本地栈+PC。前两共享后三私有。PC 是唯一不会 OOM 的区域。

**Q2(追问):Java 8 为什么用元空间替代永久代?**
> 永久代固定大小易 OOM(PermGen space)。元空间用本地内存,不受 JVM 堆大小限制,解决 PermGen 易溢出。

**Q3(追问):对象什么时候晋升老年代?**
> (1)年龄超阈值(默认 15,对象头 4bit 最大 15);(2)大对象直接进(PretenureSizeThreshold);(3)动态年龄判断(Survivor 里同年龄总和 > 一半,该年龄以上全晋升)。

**Q4(追问):对象头 GC 年龄为什么最大 15?**
> Mark Word 里 GC 年龄占 4 bit,4 bit 最大值 = 15。所以 MaxTenuringThreshold 最大只能设 15。

## 模块 4.2 GC 算法与回收器

### 📖 原理 + 工程

**可达性分析**:从 GC Roots(栈局部变量+静态变量+常量+JNI 引用)出发,能到达的活,到达不了的回收。**循环引用不会被误判**(无 GC Root 指向的循环引用会被回收)。

**三种 GC 算法**:
- **标记-清除**:碎片多,CMS 老年代用
- **标记-复制**:无碎片但费空间,**新生代用**(存活少)
- **标记-整理**:无碎片但慢(移动对象),**老年代用**(存活多)

**Minor GC vs Full GC**:Minor 只新生代几十 ms;Full 全堆秒级,生产大忌(STW 卡顿)。

**主流回收器**:
- Parallel(JDK8 默认,吞吐优先)
- **G1**(JDK9+ 默认,分区化可预测停顿,大堆低延迟)
- ZGC(染色指针,STW<10ms,超大堆)

**G1 核心**:堆切 2048 个 Region(1-32MB),GC 时只回收"垃圾最多的几个 Region"(Garbage First),`-XX:MaxGCPauseMillis=200` 可设期望停顿。

### 🎨 图解

```
G1 分区(对比 CMS 传统分代):

CMS: ┌──新生代(连续)──┐┌──老年代(连续)──┐
     │ Eden S0 S1       ││                  │
     └──────────────────┘└──────────────────┘
     问题: 老年代满→Full GC扫整个老年代, 卡顿长

G1:  堆切2048个Region(每个1-32MB)
     ┌──┬──┬──┬──┬──┬──┬──┬──┬──┬──┐
     │E │E │O │S │O │E │H │H │O │E │  E=Eden O=Old S=Survivor H=大对象
     └──┴──┴──┴──┴──┴──┴──┴──┴──┴──┘
     GC时只回收垃圾最多的几个Region → STW可预测
     -XX:MaxGCPauseMillis=200 设期望停顿200ms
```

### 🔥 面试连环追问

**Q1: JVM 怎么判断对象能回收?**
> 可达性分析。从 GC Roots 出发能到达的活,到达不了的回收。循环引用但无 GC Root 指向会被正确回收。

**Q2(追问):JDK 9+ 为什么默认 G1?**
> G1 分区化,可预测停顿(MaxGCPauseMillis),回收垃圾最多的 Region 而不扫整个堆。大堆(>6G)STW 远好于 Parallel。

**Q3(追问):生产怎么避免 Full GC?**
> (1)调大新生代减少晋升;(2)避免内存泄漏(MAT 分析);(3)用 G1 混合回收;(4)大对象单独处理。

**Q4(追问):订单服务 OOM 怎么排查?**
> `-XX:+HeapDumpOnOutOfMemoryError` 自动 dump → MAT 分析 → 看占内存最多的对象 → 查 GC Root 链找回收不掉的原因。常见:大集合全量加载/静态缓存无限增长/ThreadLocal 没 remove。

## 模块 5.3 @Transactional

### 📖 原理 + 工程

**@Transactional 本质是 AOP 切面**,代理做 begin/commit/rollback。

**7 种失效场景**(必背):
1. 方法非 public
2. **同类内部调用**(this 非代理)
3. 异常被 catch 吞掉
4. **异常类型不匹配**(默认只回滚 RuntimeException)
5. 类没被 Spring 管理
6. 数据库不支持事务(非 InnoDB)
7. 传播行为错误

**最坑**:第 2(同类调用)和第 4(异常类型)。**所有 @Transactional 必须显式 `rollbackFor = Exception.class`**。

**七种传播行为**:
- **REQUIRED**(默认):有加入没新建,一荣俱荣
- **REQUIRES_NEW**:总新建挂起当前,日志用(主失败不影响日志)
- NESTED/SUPPORTS/NOT_SUPPORTED/MANDATORY/NEVER

### 🎨 图解

```
REQUIRED vs REQUIRES_NEW:

REQUIRED(B加入A事务):
  TX1: [A的业务 → B的业务(加入TX1) → A继续]  任一异常全回滚

REQUIRES_NEW(B独立新事务):
  TX1: [A的业务 → (挂起TX1, 开TX2: B业务commit) → A继续]
  A失败回滚TX1, 但TX2已commit不受影响 → 日志保留
```

### 🔥 面试连环追问

**Q1: @Transactional 什么时候失效?**
> 7 种:非 public/同类调用/异常吞/类型不匹配/非 Bean/非 InnoDB/传播错。

**Q2(追问):为什么默认只回滚 RuntimeException?**
> EJB 时代设计:checked exception 是"可预期业务异常"不回滚,RuntimeException 是"意外"才回滚。现代不实用,必须显式 `rollbackFor = Exception.class`。

**Q3(追问):REQUIRES_NEW 用了几个连接?**
> 两个。挂起当前事务(存 ThreadLocal),从连接池拿新连接开新事务。**连接池满可能死锁**。

## 模块 5.4 自动配置与三级缓存

### 📖 原理 + 工程

**自动配置**:`@EnableAutoConfiguration` 读 spring.factories(2.x)/AutoConfiguration.imports(3.x),用条件注解(`@ConditionalOnClass`/`@ConditionalOnMissingBean`)判断生效。用户自定义优先。

**三级缓存解决循环依赖**(仅字段/setter 注入,构造器无解):
1. singletonObjects(成品)
2. earlySingletonObjects(半成品)
3. singletonFactories(ObjectFactory,延迟生成代理)

**为什么三级而非二级**:有 AOP 时,早期引用也必须是代理(否则 B 持有的 A 和最终代理 A 不一致)。ObjectFactory 延迟生成代理。

### 🔥 面试连环追问

**Q1: 三级缓存怎么解决循环依赖?**
> 创建 A 时把 ObjectFactory 放三级缓存,B 需要 A 时从三级拿 A 的半成品提前曝光,B 完成后 A 完成。

**Q2(追问):构造器注入为什么解决不了?**
> 构造器在实例化阶段就需要对方,而半成品曝光在实例化之后。启动直接报错(好事,早暴露设计问题)。

# 第六部分:Redis

## 模块 6.1 数据结构与底层

### 📖 原理 + 工程

**Redis 快三大根基**:完全基于内存(纳秒级)+ 单线程无锁无切换 + IO 多路复用(epoll 监听上万连接)。6.0 多线程只处理网络 IO,命令仍单线程。

**5 种类型 + 底层 encoding 切换**:
- String → SDS(len 字段 O(1) 获取长度,预分配减内存分配,二进制安全)
- ZSet → **跳表 + 哈希表**(跳表范围有序,哈希表等值 O(1))
- Hash → listpack(小)/hashtable(大)

**ZSet 用跳表不用红黑树**:实现简单 + 范围查询快(链表顺指针走)+ 内存够用。

### 🔥 面试连环追问

**Q1: Redis 为什么快?**
> 内存 + 单线程无锁 + epoll 多路复用。单线程 10 万+ QPS。

**Q2(追问):ZSet 底层?**
> 跳表 + 哈希表双重。跳表按 score 有序支持范围查询,哈希表 member→score 等值 O(1)。

## 模块 6.2 持久化

### 📖 原理 + 工程

**RDB**:全量快照,小且恢复快,丢两次快照间数据。BGSAVE fork 子进程(COW 共享内存),**fork 本身阻塞**(大实例几百 ms)。

**AOF**:写命令日志,everysec 默认最多丢 1 秒。AOF 重写压缩(同 key 多次 set 只留最后一条)。

**混合持久化(4.0+)⭐生产主流**:RDB 全量 + AOF 增量,恢复先加载 RDB(快)再重放 AOF 增量。

### 🔥 面试连环追问

**Q1: BGSAVE 怎么不影响主进程?**
> fork 子进程做 dump,父子共享内存(COW),主进程修改某页才复制。但 fork 本身阻塞(复制页表),大实例卡顿明显。

**Q2(追问):AOF 三种刷盘?**
> always(每条刷盘慢不丢)/everysec(每秒默认最多丢1秒)/no(OS决定不可控)。

## 模块 6.3 缓存三问进阶

### 📖 原理 + 工程

**布隆过滤器**:bit 数组 + k 个哈希函数。写入对元素 k 次哈希置 bit;查询所有 bit 是 1 才"可能在",有 0 就"一定不在"。**说不在 100% 不在,说在可能误判**。k 由 bit 数组大小和元素数算最优值。标准布隆不能删(用布谷鸟过滤器)。

**Redisson 看门狗**:不传 leaseTime 默认 30s 过期,每 10s(30/3)检查续期。**显式传 leaseTime 看门狗不启动**。

**RedLock**:N(5)节点多数派(N/2+1=3)加锁,解决主从切换丢锁。强一致要求高用 ZK/etcd。

### 🔥 面试连环追问

**Q1: Redisson 看门狗怎么工作?**
> 默认 30s 过期 + 每 10s 续期。持有者宕机则看门狗也死,30s 后自动释放。显式传 leaseTime 不启动。

**Q2(追问):RedLock 的争议?**
> Martin Kleppmann 批评时钟漂移/GC 停顿时不可靠。强一致用 ZK,不强一致用 Redisson 单节点锁。

## 模块 6.4 集群

### 📖 原理 + 工程

**三种模式**:主从(读分离)、哨兵(自动故障转移)、**Cluster**(16384 槽分片水平扩展)。

**Cluster 路由**:`CRC16(key) % 16384` 算槽,找槽在哪个节点。16384 是因为心跳包小(2KB 位图)且节点数实际不超 1000。

**Hash Tag**:`{user:1001}:orders` 和 `{user:1001}:balance` 让 CRC16 只对花括号内哈希,相关 key 进同一槽支持事务。

### 🔥 面试连环追问

**Q1: Cluster 为什么 16384 槽?**
> 心跳包小(2KB 位图)+ 实际节点数不超 1000 够用。

**Q2(追问):跨槽事务怎么办?**
> Cluster 不支持跨槽事务。用 Hash Tag 让相关 key 进同一槽。

# 第七部分:Java 并发

## 模块 7.1 JMM

### 📖 原理 + 工程

**JMM 三性**:可见性(volatile)/原子性(sync/Lock/Atomic)/有序性(volatile/happens-before)。

**主内存 vs 工作内存**:线程读自己 CPU 缓存,主内存修改看不到 → 可见性问题。

**volatile 两个语义**:可见性(写刷主内存读主内存)+ 有序性(内存屏障禁重排)。**不保证原子性**(count++ 不安全)。

**happens-before**:**不是时间先后,是逻辑可见性保证**。A hb B 则 A 对 B 可见。8 大规则(程序顺序/管程锁/volatile/线程启动终止/中断/初始化/传递性)。

### 🎨 图解

```
可见性问题(订单计数器):
  主内存: stop=false
  线程1工作内存: stop=false(读到缓存就不读主内存)→ while(!stop)永远不停!
  线程2改主内存 stop=true → 线程1看不到!

volatile 修复: 强制读写主内存 → 线程1看到true → 停止

DCL 单例必须 volatile:
  new 三步(分配→初始化→赋值)可能重排成(分配→赋值→初始化)
  线程A重排后赋值了但没初始化, 线程B拿到半初始化对象
  volatile 禁止重排 → 安全
```

### 🔥 面试连环追问

**Q1: happens-before 是"时间先后"吗?**
> **不是**。是逻辑可见性保证。A hb B 则 A 对 B 可见,即使物理上重排了只要"看起来 A 先"就符合 hb。

**Q2(追问):volatile 保证什么不保证什么?**
> 保证可见性 + 有序性。**不保证原子性**(count++ 还是线程不安全,要 AtomicInteger)。

## 模块 7.2 synchronized vs Lock

### 📖 原理 + 工程

**synchronized 锁升级**:无锁→偏向锁(单线程 ID)→轻量级锁(CAS 自旋)→重量级锁(OS 挂起)。JDK 15 偏向默认关闭。

**ReentrantLock 多的能力**:可中断(lockInterruptibly)/可超时(tryLock)/可公平/多 Condition。**必须 finally unlock**。

**选型**:简单同步用 synchronized,复杂场景(可中断/超时/公平)用 ReentrantLock。

### 🔥 面试连环追问

**Q1: synchronized 锁升级?**
> 无锁→偏向→轻量(CAS自旋)→重量(OS挂起)。JDK6+ 优化让简单场景性能接近 Lock。

**Q2(追问):自旋是什么?**
> 线程获取不到锁时不挂起,循环检查锁状态。避免挂起/唤醒的内核态切换,适合短锁。JDK6+ 自适应自旋。

## 模块 7.3 线程池

### 📖 原理 + 工程

**七大参数**:corePoolSize/maximumPoolSize/keepAliveTime/unit/workQueue/threadFactory/handler。

**任务提交**:<core 新建 → 队列 → 非核心到 max → 拒绝策略。

**线程数**:CPU 密集 N+1,IO 密集 2N,精确 `N×(1+等待/计算)`。

**禁用 Executors**:newFixed 无界队列 OOM,newCached 无限线程 OOM。必须 ThreadPoolExecutor 显式有界队列 + 合理 max。

**四种拒绝策略**:Abort(默认抛异常)/CallerRuns(调用者执行反压)/Discard/DiscardOldest。

### 🎨 图解

```
任务提交流程:
  线程数<core? → 新建核心
  >=core? → 队列满? 否→进队列; 是→线程数<max? 是→新建非核心; 否→拒绝策略
```

### 🔥 面试连环追问

**Q1: 为什么禁用 Executors?**
> newFixed 用 LinkedBlockingQueue(无界)任务堆积 OOM;newCached maximumPoolSize=Integer.MAX_VALUE 无限线程 OOM。

**Q2(追问):订单服务用哪个拒绝策略?**
> CallerRunsPolicy。线程池满让 Tomcat 线程自己执行,反压(接收新请求变慢自然限流)。

## 模块 7.4 AQS 与 CAS

### 📖 原理 + 工程

**AQS**:volatile state(同步状态) + CLH 双向队列(等锁线程)。Node 封装线程 park 挂起,前驱释放 unpark 唤醒。ReentrantLock/Semaphore/CountDownLatch 都基于它。有 dummy 哨兵统一"释放=唤醒 head 后继"逻辑。

**公平 vs 非公平**:公平检查队列 FIFO,非公平直接 CAS 抢(默认,吞吐高)。

**CAS(Compare-And-Swap)**:CAS(内存, 期望旧值, 新值),比较+赋值原子(CPU cmpxchg 指令)。乐观锁无阻塞。

**CAS 三大问题**:ABA(AtomicStampedReference 版本号)/自旋开销(限制重试或 LongAdder)/只保证单变量(AtomicReference 包对象)。

### 🎨 图解

```
AQS CLH 队列(订单扣库存):
  state=1(线程1持有)
  队列: [dummy] ⇄ [Node2线程2 park] ⇄ [Node3线程3 park]
  线程1释放: state→0, unpark(线程2), 线程2 CAS抢state→1

CAS 库存扣减(AtomicInteger):
  do {
    old = stock.get();        // 读100
    next = old - 1;           // 算99
  } while(!stock.CAS(old, next));  // 失败重试
  // 两个线程同时CAS, 一个成功一个失败重试 → 无锁无超卖
```

### 🔥 面试连环追问

**Q1: AQS 原理?**
> volatile state + CLH 双向队列。获取不到锁的线程封装 Node 入队 park,释放时 unpark 队首。

**Q2(追问):CAS 怎么保证原子性?**
> CPU 硬件指令 cmpxchg,单条指令不可中断。

**Q3(追问):CAS 和 synchronized 怎么选?**
> CAS 乐观锁适合读多写少冲突少;synchronized 悲观锁适合写多冲突多(避免 CAS 自旋空转)。

## 模块 7.5 ThreadLocal

### 📖 原理 + 工程

**ThreadLocal**:每线程一份副本,线程隔离。Thread 有 ThreadLocalMap,key 弱引用 value 强引用。

**内存泄漏**:key GC 后变 null,但 value 强引用。线程池线程长期存活 → value 永远回收不掉。**用完必 remove**。

### 🔥 面试连环追问

**Q1: ThreadLocal 为什么泄漏?**
> key 弱引用(GC 后 null),value 强引用。线程池下线程长期存活,value 回收不掉。**用完必 remove**。
