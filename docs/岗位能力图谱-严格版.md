### 1.1 必备能力（一票否决项）

#### A. JavaScript / TypeScript 深度 `[frontend.js]` `[frontend.ts]`

**达标标准**：
- 能白板讲清 JS 原型链、闭包、`this` 绑定规则、事件循环（宏任务/微任务）
- 能讲清 ES6+ 核心特性：Promise 链、async/await 错误处理、Proxy/Reflect、Generator
- TypeScript：泛型（`<T extends XXX>`）、条件类型（`T extends U ? X : Y`）、工具类型（`Partial/Required/Pick/Omit/Record`）、类型守卫

**面试官追问链**：
1. `Promise.all` 和 `Promise.allSettled` 区别？→ 一个失败全部失败 vs 全部完成才返回
2. async/await 异常怎么捕获？→ try/catch 包裹，或 `.catch()` 链
3. 为什么 React 不能直接 `await`？→ 渲染同步性，Suspense 的边界
4. TS 的 `interface` 和 `type` 区别？→ 合声明 vs 计算属性
5. 工具类型 `Omit<T, K>` 底层怎么实现？→ `Pick<T, Exclude<keyof T, K>>`

**典型项目场景**：「你那个 AI 对话框的多轮上下文状态怎么设计的？」→ Zustand store + 持久化中间件 + 快照恢复

#### B. 框架原理（Vue 或 React 二选一精通）`[frontend.vue3]` `[frontend.react18]` `[frontend.framework-principle]`

**Vue 3 必备**：
- 响应式系统：Proxy vs defineProperty、`ref` vs `reactive` 区别（`.value` 包装、对象 vs 原始值）
- Composition API 设计动机（逻辑复用 vs Options API 的 mixin 命名冲突）
- 虚拟 DOM + Diff：双端 Diff 算法、key 的作用、静态提升
- 编译期优化：`v-memo`、Block Tree、PatchFlag

**React 18 必备**：
- Fiber 架构：为什么需要时间切片、可中断渲染
- Hooks 原理：闭包陷阱、依赖数组、`useEffect` vs `useLayoutEffect` 时机
- 并发特性：`useTransition`、`useDeferredValue`、Suspense
- 状态管理：Context 性能问题、Zustand/Redux Toolkit 选型

**面试官追问链**：
1. Vue 3 为什么用 Proxy 替代 defineProperty？→ defineProperty 不能监听新增属性/数组下标
2. React Fiber 的"可中断"怎么实现的？→ 协程式（shouldYield 判时间片）、双缓冲树
3. `useEffect` 死循环怎么排查？→ 依赖数组、依赖稳定值（ref/state）
4. Vue 模板编译做了什么优化？→ 静态提升、PatchFlag 标记动态节点

#### C. 浏览器原理与性能优化 `[frontend.browser]` `[frontend.load-perf]` `[frontend.render-perf]`

**必备要点**：
- 渲染流水线：HTML → DOM → CSSOM → Render Tree → Layout → Paint → Composite
- 回流（Layout）vs 重绘（Paint）的触发条件与避免方法
- 关键渲染路径：CSS 阻塞、JS 阻塞、defer/async 区别
- 性能指标：FP/FCP/LCP/TTI/CLS，怎么用 Lighthouse / Web Vitals 测
- 优化手段：分包/懒加载、CDN、预渲染、虚拟列表、防抖节流、Web Worker

**面试官追问链**：
1. 用户输入 URL 到页面渲染完整流程？→ DNS/TCP/请求/解析/渲染（这是面试万年题）
2. LCP 3 秒以上怎么排查？→ 看是图片/字体/JS 阻塞，对应改预加载/分包
3. 虚拟列表怎么实现？→ 可视区计算 + 滚动监听 + transform 偏移
4. 防抖和节流区别？什么场景用哪个？→ 搜索框防抖、滚动监听节流

### 2.1 必备能力（一票否决项）

#### A. Java 核心 + JVM `[backend.java]` `[backend.jvm]` `[backend.concurrency]`

**Java 集合**：
- HashMap：1.7（数组+链表）vs 1.8（数组+链表+红黑树）、扩容机制（阈值 0.75、2 倍、rehash 位运算优化）
- ConcurrentHashMap：1.7（Segment 分段锁）vs 1.8（CAS + synchronized + 链表/红黑树）、size 分散计数（`baseCount + CounterCell[]`）

**JVM**：
- 内存模型：堆/栈/方法区/元空间/直接内存，每个区域 OOM 的现象
- GC：Parallel/CMS/G1/ZGC 选型（低延迟选 ZGC、吞吐选 Parallel、通用选 G1）
- 类加载：双亲委派 + 打破场景（Tomcat、SPI、热部署）
- 生产排查三板斧：CPU 飙高（top -Hp + jstack）、OOM（jmap + MAT）、内存泄漏（Old Gen 监控）

**并发**：
- JMM：happens-before、内存屏障
- synchronized 锁升级：无锁 → 偏向锁 → 轻量锁 → 重量锁（4 级链路）
- AQS：volatile state + CLH 双向队列
- 线程池：调度顺序（核心 → 队列 → 非核心 → 拒绝）、参数业务化配置（不是背"N+1"）

**面试官追问链**（这是后端架构师面试的重头戏）：
1. HashMap 1.7 → 1.8 为什么加红黑树？→ 防止哈希冲突时链表退化成 O(n)
2. ConcurrentHashMap 1.8 size 怎么算的？→ baseCount + CounterCell 分散计数避免竞争
3. synchronized 锁升级流程？什么场景会直接升级到重量锁？→ 已有竞争直接升级
4. 线程池核心 5 最大 10 队列 100，来了 30 个任务怎么调度？→ 5 立即执行 + 25 入队 + 0 拒绝（队列没满不开非核心）
5. CMS 和 G1 区别？什么业务该用哪个？→ CMS 标记清除有碎片 / G1 Region 分块可预测停顿

#### B. Spring 全家桶（架构级）`[backend.springboot]` `[backend.springmvc]` `[backend.spring-tx]` `[backend.spring-security]` `[backend.spring-cloud]`

**Spring Boot**：
- 自动装配：`spring.factories` / `AutoConfiguration.imports`（2.7+）、`@Conditional` 系列
- 内嵌容器：Tomcat / Undertow 选型
- Actuator：健康检查、指标暴露

**Spring MVC**：
- DispatcherServlet 9 步流程（HandlerMapping → HandlerAdapter → ViewResolver）
- `@RequestBody`/`@ResponseBody` 原理（HttpMessageConverter）
- 拦截器 vs Filter：5 维度区别（时机/范围/容器/依赖/异常）

**Spring 事务**：
- 本质：AOP 动态代理 + PlatformTransactionManager（不是 MySQL 引擎层）
- 传播行为：REQUIRED / REQUIRES_NEW / NESTED 的区别（日志场景用 REQUIRES_NEW）
- 失效场景：自调用（this 非代理）、非 public、异常被吞、rollbackFor 不对

**Spring Cloud（微服务全家桶）**：
- 注册中心：Nacos（AP 默认）vs Eureka vs ZK（CP）
- 配置中心：Nacos 配置推送 vs Apollo 客户端拉取
- 网关：Spring Cloud Gateway（Route/Predicate/Filter）、GlobalFilter 统一鉴权
- RPC：Feign（动态代理 + 负载均衡）、fallbackFactory（生产用，能拿异常）

#### C. 数据库（MySQL + Redis）`[backend.mysql]` `[backend.redis]`

**MySQL 必备**：
- 索引：B+ 树为什么是 B+ 树（不是 B 树/红黑树/跳表）、最左前缀、覆盖索引、索引下推 ICP
- 事务：ACID、四种隔离级别、MVCC 的 ReadView 机制、快照读 vs 当前读
- 锁：行锁/间隙锁/Next-Key Lock、死锁分析、`SHOW ENGINE INNODB STATUS`
- 性能：EXPLAIN 全字段、慢 SQL 不只加索引要会判断"该不该改表结构"
- 分库分表：ShardingSphere、分片键选型（避免倾斜）、双写迁移

**Redis 必备**：
- 数据结构底层：SDS / 跳表 / quicklist / listpack
- 三大问题：穿透（布隆过滤器）、击穿（互斥锁/永不过期）、雪崩（随机过期/多级缓存）
- 持久化：RDB/AOF/混合，金融场景必须 AOF + everysec
- 集群：主从/哨兵/Cluster、Hash Slot、Gossip
- 分布式锁：Redisson 看门狗、RedLock 争议（Martin Kleppmann vs antirez）
- 缓存一致性：Cache Aside / Read/Write-Through / 延迟双删解决什么、解决不了什么

**面试官追问链**：
1. 为什么 MySQL 用 B+ 树不用 B 树？→ B+ 树叶子链表便于范围查询，非叶子不存数据便于 fanout
2. MVCC 怎么实现的？→ ReadView + undo log 版本链
3. Redis 分布式锁的坑？→ 看门狗续期、RedLock 是否真安全、业务超时释放锁问题
4. 缓存击穿你的方案？→ 互斥锁（SETNX）或逻辑过期，讲清各自代价

#### D. 架构设计 + 分布式 `[architecture.distributed]` `[architecture.microservice]` `[architecture.ha-hc-scale]` `[architecture.ddd]`

**分布式理论**：
- CAP：Partition 必选，真正取舍 C vs A（ZK 偏 CP / Eureka 偏 AP）
- BASE：大规模互联网实际选择
- Raft（必学）：leader election + log replication
- Gossip：Cassandra / Redis Cluster 状态同步

**分布式事务（必须能完整讲透）**：
```
业务能接受最终一致？
├─ 是 → RocketMQ 事务消息 / 本地消息表 / 最大努力通知
└─ 否 → TCC（金融常用）/ Seata AT（全局锁）/ Saga（长事务补偿）
```

**架构模式演进**：
```
单体 → 集群 → 垂直拆分 → SOA → 微服务 → 云原生 → Serverless
每步解决什么 + 带来什么新问题，要能讲清楚
```

**高可用架构**：限流（令牌桶/漏桶）、熔断降级（断路器三态）、隔离、超时级联
**高并发架构**：缓存、异步、横向扩展、读写分离（四大套路 + 权衡代价）
**DDD**：限界上下文、聚合根、领域事件、何时该用何时过度设计

**经典系统设计题**（必考）：秒杀 / 短链 / Feed / IM / 订单 / 排行榜 / 文件上传 / 延迟任务

### 2.2.1 分布式深度专题（架构师硬功夫·2026-07-07 基于青岛/济南 65 个高端岗 JD 反推补齐）

> 这一组不是"会用框架"，而是**"会做题"**：能把秒杀、订单、对账这类经典场景的分布式难题讲透到源码/算法层。65 个高端岗里，29 个架构师岗的 JD 都至少命中其中 3-4 项。

#### A. 分布式事务 `[architecture.distributed-tx]`

**业务场景**：电商下单 = 扣库存（item-svc）+ 扣余额（account-svc）+ 生成订单（order-svc），任一失败都要回滚。

**四种方案决策树**（必须能讲清各自代价）：
```
业务能接受最终一致？
├─ 是
│   ├─RocketMQ 事务消息  →  高吞吐、解耦；但实现复杂（半消息+本地事务+回查）
│   ├─本地消息表         →  最朴素可靠；DB 轮询/定时扫表；适合中小规模
│   └─最大努力通知       →  跨系统（如支付回调）；不强保证，要有对账兜底
└─ 否（强一致，金融核心）
    ├─TCC（Try-Confirm-Cancel）→  性能好但侵入业务，每个服务要写 3 套接口
    ├─Seata AT 模式          →  无侵入（代理 SQL 生成回滚 undo）；但全局锁影响并发
    └─Saga                  →  长事务补偿；每步都要写"正向+补偿"两套
```

**面试官连环追问链**（高频重灾区）：
1. **你们生产用哪种分布式事务方案？为什么？** → 不能只答"用了 Seata"，要讲业务为什么这么选（吞吐 vs 一致性 vs 团队能力）
2. **TCC 和 AT 的本质区别？** → AT 代理数据源自动生成 undo；TCC 业务层手写三段；AT 有全局锁 → 并发差；TCC 性能好但要写 3 套代码
3. **Seata AT 的全局锁怎么实现的？** → TC（事务协调器）维护 lock_table，分支事务注册时占锁，并发分支冲突时等待或失败
4. **本地消息表为什么可靠？** → 业务表 + 消息表同库本地事务，必一致；MQ 投递失败重试，幂等靠消费方去重表
5. **Saga 的补偿怎么设计？** → 每步正向操作配一个补偿；难点在"非幂等的正向"（如扣库存允许超卖 vs 不允许超卖补偿逻辑不同）
6. **如果 Confirm/Cancel 失败怎么办？** → Seata TC 有重试机制；超过阈值进死信人工介入；空回滚 + 幂等 + 悬挂问题（TCC 三大坑）

#### B. 限流熔断算法（源码级）`[architecture.rate-limit]`

**业务场景**：大促秒杀，QPS 从平时 1k 暴涨到 50k，必须限流；下游服务挂了，本服务不能被拖死。

**限流三大算法对比**（必须能画图、讲清时间复杂度）：

```
1. 计数器（固定窗口）       2. 滑动窗口                  3. 令牌桶 / 漏桶
┌──────────┐              ┌──────────┐                  ┌──────┐
│ 0-1s: 100│              │ 小格化    │                  │令牌池│ ← 按固定速率 r 投令牌
│ 1-2s: 100│              │ 每格独立 │                  │capacity│
│ ...      │              │ 滑动求和 │                  └──┬───┘
└──────────┘              └──────────┘                     │请求来 → 取令牌 → 通过
⚠️ 临界问题：0.99s 100次 + 1.01s 100次 = 200/s                                ← 没令牌 → 拒绝/排队
```

- **令牌桶**（Sentinel/Guava RateLimiter 默认）：允许突发（桶可存令牌），速率固定；**惰性计算**（不真的起线程投令牌，请求来时算"自上次到现在该有多少令牌"）
- **漏桶**（Leaky Bucket）：严格匀速出水，不允许突发；适合保护下游
- **滑动窗口**（Sentinel 数据结构）：把 1s 切成多个 sample（默认 500ms × 2），每个窗口独立计数；临界问题大幅缓解

**熔断器三态机**（Hystrix/Sentinel/Resilience4j 通用）：
```
   CLOSED ──── 错误率 > 阈值 ───► OPEN
     ▲                              │
     │                              │ 等待 sleepWindow
     │     半开试探成功              ▼
     └──────── HALF-OPEN ◄────── (放 N 个请求试探)
```

**面试官连环追问链**：
1. **令牌桶和漏桶的本质区别？** → 令牌桶允许突发（桶可攒令牌），漏桶匀速出水不允许突发
2. **令牌怎么"投"？真的有定时线程吗？** → 没有，**惰性计算**：记录上次计算时间，请求来时 `tokens = min(cap, prev + (now-prev)*rate)`
3. **滑动窗口比固定窗口好在哪里？** → 解决临界问题；Sentinel 用 LeapArray 实现，每个 sample 独立
4. **Sentinel 限流和熔断规则怎么落地？** → 限流规则（QPS/线程数）+ 熔断规则（慢调用比例/异常比例/异常数）；规则持久化到 Nacos
5. **熔断 HALF-OPEN 状态放几个请求？怎么判断恢复？** → 默认放 5-10 个；成功率/RT 达阈值转 CLOSED，否则回 OPEN
6. **熔断和降级有什么区别？** → 熔断是自动触发的"保护性失败"；降级是主动的业务降级（返回兜底数据/缓存）

#### C. 分库分表 `[architecture.sharding]`

**业务场景**：订单表 5 亿行，单库 IO 打满、单表 B+ 树层级过深查询慢。

**分片键选型决策树**：
```
查询模式是什么？
├─ 单用户维度高频查（用户看自己订单）
│   → shard by user_id  ✅ 90% 查询直击单库
│   ⚠️ 商家查"我所有买家的订单" → 需要商家维度反查表/ES
└─ 全局聚合查询（运营看大盘）
    → shard by order_id（均匀）+ 走数仓/Hologres 离线分析
```

**双写迁移流程**（必须能讲，这是真实架构师活）：
```
1. 旧库 → 双写（旧库主，新库影子写）
2. 全量同步（DataX/Canel 同步历史数据）
3. 增量对账（定时巡检两库一致性）
4. 灰度切读（5% → 50% → 100%）
5. 停旧库写（观察 1-2 周）
6. 下线旧库
```

**面试官追问链**：
1. **你怎么选分片键？** → 按最高频查询路径选；订单分 user_id 但要有商家反查表/ES 二级索引
2. **分多少片合适？** → 评估 3-5 年数据量，预留 5-10 倍；不是越多越好（每个分片都有运维成本）
3. **跨片查询怎么处理？** → 离线数仓做聚合；实时用 ES 做"反范式宽表"；不要在分片库上做跨片 JOIN
4. **分库分表后主键怎么生成？** → 雪花算法（Snowflake）；讲清时钟回拨问题及解决方案（百度 UidGenerator、美团 Leaf）
5. **ShardingSphere-JDBC 和 ShardingSphere-Proxy 区别？** → JDBC 是客户端直连 DB（轻量、零额外部署）；Proxy 是中间代理层（多一次网络跳转但语言无关）

#### D. 服务网格 Service Mesh `[architecture.service-mesh]`

**业务场景**：微服务从 50 个涨到 500 个，每个服务都要重复实现熔断/限流/可观测，希望把这些"基础设施能力"从业务代码剥离。

**Istio 架构**：
```
┌──────────────────────────────────────┐
│       Control Plane (istiod)          │  ← 配置下发（xDS 协议）
│       服务发现/路由规则/熔断策略        │
└────────────┬─────────────────────────┘
             │ xDS 推送
   ┌─────────┴──────────┐
   ▼                    ▼
┌─────────┐          ┌─────────┐
│Pod A    │          │Pod B    │
│┌───────┐│          │┌───────┐│
││App    ││          ││App    ││
│└───┬───┘│          │└───▲───┘│
│┌───▼───┐│          │┌───┴───┐│
││Envoy  ││◄────────►│Envoy  ││  ← 数据平面：拦截所有进出流量
││sidecar││  mTLS    │sidecar││
│└───────┘│          │└───────┘│
└─────────┘          └─────────┘
```

**面试官追问链**（云原生架构师岗高频）：
1. **Service Mesh 解决什么问题？** → 把流量治理（限流/熔断/灰度/可观测）从业务代码下沉到基础设施，业务代码只关心业务
2. **sidecar 性能损耗多少？** → 单跳 RT 增加约 1-3ms；可通过共享进程模式（Cilium eBPF）降低
3. **Istio vs Linkerd？** → Istio 功能全（多协议+复杂路由）但重；Linkerd 轻（Rust 写的）但功能少；国内多选 Istio
4. **Spring Cloud 和 Istio 怎么共存？** → 渐进迁移：业务层 Spring Cloud（应用层），Mesh 层 Istio（基础设施）；最终目标是 Spring Cloud 只剩业务逻辑

#### E. API 网关深入 `[architecture.api-gateway]`

**业务场景**：100+ 微服务统一入口，要做鉴权/限流/灰度/协议转换。

**主流选型对比**：
| 网关 | 类型 | 性能 | 适用 |
|------|------|------|------|
| Spring Cloud Gateway | Java 反应式 | 中（WebFlux）| Spring 全家桶团队首选 |
| APISIX | Lua + Nginx | 高（万级 QPS/单机）| 云原生/多语言团队 |
| Kong | Lua + Nginx | 高 | 国际化场景，插件生态丰富 |
| Higress（阿里）| Go + Wasm | 高 | 国内云原生，Tengine 系 |

**面试官追问链**：
1. **网关能做什么不能做什么？** → 能：鉴权/限流/灰度/日志/协议转换/聚合；不能：复杂业务逻辑（保持网关"薄"）
2. **GlobalFilter 和 GatewayFilter 区别？** → GlobalFilter 全局生效（鉴权/日志）；GatewayFilter 路由级（特定路由重写 URL）
3. **网关高可用怎么做？** → 多实例 + Nginx/LVS 前置负载均衡；配置中心动态路由；限流配置 Nacos 热更新

#### F. 异地多活容灾 `[architecture.disaster-recovery]`

**业务场景**：机房断电/光缆被挖断/区域故障，业务必须 1 小时内恢复（金融 SLA）。

**三种容灾架构**：
```
1. 同城双活（推荐入门）：北京可用区 A+B，双写主库，单 AZ 挂不丢数据
2. 两地三中心（金融常用）：北京双活 + 上海灾备，专线同步
3. 异地多活（互联网大厂）：单元化（LDC），按用户路由到单元，单元内闭环
```

**单元化架构（异地多活）**：
- 用户路由（user_id % N → unit_id）
- 单元内闭环（数据/缓存/MQ 都在单元内）
- 跨单元同步（中心化数据如全局配置，异步同步）
- 难点：跨单元调用、跨用户关系（A 在北京下订单，B 在上海评论）

**面试官追问链**：
1. **RTO 和 RPO 区别？** → RTO = 恢复时间目标（多久能恢复服务）；RPO = 数据丢失目标（最多丢多少数据）
2. **同城双活和异地多活差在哪？** → 同城延迟 < 2ms 可同步双写；异地延迟 20-30ms 只能异步；架构完全不同
3. **怎么做单元化？** → 路由层（按 user_id）+ 数据层（按 user_id 分片）+ 应用层（感知单元）；阿里 LDC、字节 Set 化都这套

#### G. 解决方案架构 `[architecture.solution-arch]`

> 这是 6 个"解决方案架构师"岗位（中国电子云/海纳云/阿里巴巴/浪潮/汉兴同衡/海博）的核心能力。

**解决方案架构方法论**（5 步法）：
```
1. 需求理解 →  客户业务目标（不是技术目标，是降本/增效/合规）
2. 业务拆解 →  拆解成功能模块 + 非功能需求（SLA/QPS/数据量）
3. 架构蓝图 →  画系统拓扑图（应用/数据/基础设施三层）
4. 选型论证 →  为什么选 A 不选 B（成本/团队/风险/合规四维度）
5. POC 落地 →  最小可行架构验证，给客户看到效果
```

**面试官追问链**（售前架构师常考）：
1. **客户要"上大模型"，你怎么设计方案？** → 先问业务场景（客服/知识库/分析）；再选 RAG/微调/Agent 模式；最后选模型（开源 vs 闭源，本地化 vs API）
2. **POC 怎么做？** → 限定场景（1-2 个高频痛点）+ 小数据集验证 + ROI 量化（节省多少人力/提升多少转化）
3. **方案怎么翻译给非技术决策者？** → 业务语言（GMV/转化率/合规风险）+ 对比图（现状 vs 方案）+ 同行业案例

#### H. 中台架构 `[architecture.platform-arch]`

**业务场景**：集团有 5 条业务线，每条线都在重复造轮子（用户/订单/支付/消息），希望把共性能力下沉成"中台"。

**两种中台**：
- **业务中台**：把共性业务能力下沉（用户中心/订单中心/商品中心/支付中心），各业务线复用
- **数据中台**：把数据能力下沉（One Data / 数据资产 / 数据服务 API），各业务线订阅

**中台的反模式**（必须能讲）：
- ❌ 为了中台而中台（业务线还不够多就上中台 → 沉没成本）
- ❌ 中台等于"造大轮子"（中台应是"治理+复用"，不是重写所有系统）
- ❌ 没有强有力的中台产品经理（中台是"内部产品"，需要产品化思维）

**面试官追问链**：
1. **中台和小服务化有什么区别？** → 中台 = 服务化 + 治理（数据/流程/能力统一）+ 复用（多业务线共用）
2. **什么时候不该上中台？** → 业务线 < 3 条；业务差异大无法抽象；团队规模不足以支撑中台运营
3. **数据中台怎么做？** → One Data（数据同源）+ One Model（指标统一定义）+ One Service（数据 API 化）；分层 ODS→DWD→DWS→ADS

#### I. 系统性能调优体系 `[architecture.perf-tuning]`

**业务场景**：系统 RT 从 200ms 涨到 2s，QPS 上不去，老板让你"调优"。

**全链路调优方法论**（从上到下）：
```
1. 压测定位瓶颈  →  全链路压测，找出最慢的节点
   │
2. 应用层优化    →  异步化（MQ/线程池）/ 算法优化（O(n²) → O(n log n)）/ 缓存
   │
3. 数据库优化    →  慢 SQL / 索引 / 分库分表 / 读写分离
   │
4. JVM 调优      →  GC 日志分析 / 堆内存配置 / GC 算法选择（G1/ZGC）
   │
5. OS / 网络层   →  TCP 参数（TIME_WAIT/keepalive）/ 文件句柄 / 内核参数
```

**面试官追问链**：
1. **你怎么定位线上 RT 突然变慢？** → 先看监控（SkyWalking 全链路）找最慢节点 → Arthas trace 定位方法 → 看 GC 是否 STW
2. **Full GC 频繁怎么排查？** → jstat 看 GC 频率 → jmap dump 堆 → MAT 分析大对象 → 定位内存泄漏（如 ThreadLocal 没清 / 静态集合膨胀）
3. **SQL 慢怎么优化？** → EXPLAIN 看执行计划 → 加索引（注意最左前缀）/ 改写 SQL（避免 select *）/ 限返回行数
4. **怎么决定用同步还是异步？** → 非核心链路异步（MQ 解耦）/ 核心链路同步（强一致）；下单 = 同步扣库存 + 异步发短信
5. **缓存击穿/雪崩/穿透区别？** → 击穿（热 key 过期）/ 雪崩（大量 key 同时过期）/ 穿透（查不存在的 key）；分别用互斥锁/TTL 随机/布隆过滤器

#### J. IoT 与工业互联网数据采集架构 `[architecture.iot-arch]`

> **青岛特色考点**：海尔卡奥斯（COSMOPlat）工业互联网平台是青岛最高薪架构师岗位（50-80K）的核心业务。2026-07 面经显示卡奥斯高频问"百万设备接入的数据采集层怎么设计"和时序库选型。本节补全这个盲区。

**业务场景**：海尔卡奥斯工业互联网平台需要接入 100 万+ 工厂设备（PLC/传感器/机器人），采集温度/震动/功率/产量等时序数据，做实时监控 + 异常告警 + 历史分析。

│  │ 时序库    │  │ 实时流    │  │ 离线数仓          │    │
│  │(详见下)   │  │ Flink    │  │ Hive/Hudi        │    │
│  │          │  │ 窗口聚合  │  │ 日报/月报/训练    │    │
│  └──────────┘  └──────────┘  └──────────────────┘    │
└──────────────────────────────────────────────────────┘
```

**协议选型要点**：
- **MQTT**（工业物联网首选）：轻量（2字节最小包头）、Pub/Sub 模型、QoS 0/1/2 三级、保留消息、遗嘱消息。适合低带宽不稳定网络
- **CoAP**：基于 UDP，类 HTTP 请求/响应，适合超低功耗传感器（电池供电）
- **Modbus TCP**：工业老协议，PLC 标配，需边缘网关做协议转换
- **OPC UA**：德国工业 4.0 标准，安全性高（认证+加密），但较重

**时序数据库选型对比 `[architecture.tsdb-selection]`**

**业务场景**：100 万设备 × 每设备 10 个指标 × 每 10 秒上报一次 = 每日 86 亿行数据。普通 MySQL 无法承载。

| 维度 | InfluxDB (v2.x) | TDengine (涛思) | TimescaleDB | Prometheus |
|:----:|:---:|:---:|:---:|:---:|
| 类型 | 专有时序库 | 专有时序库 | PostgreSQL 插件 | 监控专用 |
| 写入性能 | 百万点/秒（单机）| 千万点/秒（单机）| 十万级/秒 | 百万级/秒 |
| 压缩比 | 10:1 | 20:1（列式+Delta-of-Delta）| 5:1 | 7:1 |
| SQL 支持 | Flux (v2)/SQL(v3) | **标准 SQL + 时序扩展** | 完整 PostgreSQL SQL | PromQL（特有）|
| 集群 | 闭源（付费）| **开源集群** | 原生（PG 集群）| 无原生集群 |
| 部署难度 | 简单 | 简单 | 中（需 PG） | 简单 |
| 适用场景 | 通用监控/可观测 | **工业物联网**（国产/高压缩/高性能）| 需 SQL JOIN 时序+业务表 | K8s 监控标配 |
| 国产化 | ❌ | ✅（信创目录） | ❌ | ❌ |

**选型决策树**：
```
你的场景是什么？
├─ 工业物联网大规模（百万点/秒）+ 国产信创要求
│   → ✅ **TDengine**（海尔卡奥斯实际选型，千万级写入+20:1压缩+SQL兼容+国产）
│
├─ 通用监控/可观测性（Zabbix/Grafana 替换）
│   → ✅ **InfluxDB**（生态最好，Grafana 原生支持，社区资源多）
│   → ⚠️ 注意：v2 的 Flux 查询语言学习曲线陡；v3 切回 SQL 但仍年轻
│
├─ 业务数据有时序属性但需和交易表 JOIN（如 IoT 设备+用户订单）
│   → ✅ **TimescaleDB**（PG 生态，完整 SQL，hypertable 自动分区）
│   → ⚠️ 用 PG 存储时序数据，注意 chunk 大小配置和保留策略
│
└─ K8s 容器监控（Pod 指标）
    → ✅ **Prometheus + Thanos**（事实标准，Pull 模型+ServiceMonitor）
    → ⚠️ 不适用：业务类时序数据（长周期/历史回溯/复杂聚合）
```

**关键技术点**（必须能讲清）：
- **TDengine 为什么写入快**：一个采集点一张表（按设备建模）+ 超级表（STable）统一模式 + 列式存储 + Delta-of-Delta 编码（时间戳差值再差值）+ 无索引（按时间有序追加写入 = 天然有序）
- **InfluxDB TSM 引擎**：LSM-Tree 变体，WAL + 内存缓存 + TSM 文件合并；倒排索引按 tag 查
- **数据保留策略**：原始热数据 7 天（内存/SSD）→ 聚合 1h 数据 30 天（HDD）→ 原始数据归档冷存储（OSS/对象存储）
- **降采样**：Flink 实时窗口聚合（1min→1h→1d），写入不同保留策略的时序表

**面试官连环追问链**（海尔卡奥斯/海信 IoT 岗专属）：
1. **100 万设备同时上报，接入层怎么扛？** → MQTT Broker 水平扩展（EMQX 集群）+ 设备 Topic 按工厂哈希分片 + Kafka 削峰填谷 + 边缘网关预聚合降频
2. **TDengine 和 InfluxDB 怎么选？** → 见上表；海尔场景选 TDengine 的 3 个核心理由（国产信创 + 千万级写入 + SQL 兼容）
3. **时序数据写入瓶颈在哪？** → 磁盘 IO（顺序写 vs 随机写）+ 压缩 CPU；TDengine 一个设备一张表 + 追加写入 = 天然顺序写
4. **数据量太大怎么处理？** → 保留策略（原始7天/聚合30天/归档）+ 降采样（Flink 预聚合）+ 冷热分层存储（SSD+HDD+OSS）
5. **处理延迟怎么保证？** → 边缘层本地预处理（断网缓存 + 1min 聚合）+ 接入层 Kafka 解耦 + Flink 窗口聚合毫秒级
6. **如果数据在边缘网关丢了怎么办？** → Edge Gateway 本地 SQLite/SQLite 队列 + 断网缓存 + 上行确认（ACK）+ 补传机制（网关检测到断网恢复后从本地存储补传断网期间数据）
7. **Modbus 协议有个经典坑是什么？** → 寄存器大小端字节序不一致（大端 vs 小端），设备说明书会写，网关解析时必须根据设备型号配置字节序映射表

**🔑 金句**：「工业物联网架构的核心不是高大上的 AI 算法，而是'海量设备数据不丢、不乱、准时到'。TDengine 的'一个设备一张表'设计哲学——和设备打交道的系统应该按物理世界建模，而不是按 IT 系统建模。」

#### C. AI 工程保障（场景题必考）`[ai.ai-circuit-breaker]` `[ai.cost-control]` `[ai.observability]` `[ai.multi-tenant]`

**三道防线**（必背）：
```

   ↓ 超时/失败
② 语义缓存兜底（<100ms）—— 重复问题不调 LLM

③ 规则引擎兜底（<50ms）—— 关键词匹配/模板回复

**成本控制**：

- 模型路由（简单 query 走 DeepSeek，复杂走 GPT-4）

**可观测性**：
- LangFuse / LangSmith 调用链追踪
- Token 消耗监控（按租户/用户）
- 成功率/延迟/重试率

### 3.2.1 模型即服务与多模态专题（大模型架构师方向·2026-07-07 基于 65 高端岗 JD 补齐）

> **市场背景**：65 高端岗里"首席架构师/大模型架构师"岗位（海尔卡奥斯 50-80K、AI 解决方案架构师 51-71K）都要求**不止是"调 API"，而是"模型怎么部署、怎么路由、怎么调度"**。3 次"多模态"出现说明单纯文本 LLM 已不够差异化。

#### A. MaaS 模型即服务 `[ai.maas]`

**业务场景**：公司要本地化部署 70B 大模型给 1000 个员工用，怎么选部署方案？怎么调度 GPU？怎么控制成本？

**主流推理引擎选型**（必须能讲清取舍）：
```
┌─────────────────────────────────────────────────────────┐
│           大模型推理引擎选型决策树                          │
└─────────────────────────────────────────────────────────┘
你的优先级是什么？
├─ 极致吞吐（万级 QPS，公网服务）
│   → vLLM（PagedAttention + Continuous Batching）
│       ✅ 业界事实标准，吞吐最高
│       ⚠️ 显存占用大，需要 A100/H100
├─ 低延迟（实时对话，首 token < 200ms）
│   → SGLang（结构化输出优化，比 vLLM 还快 5x）
│       ✅ 适合 Agent 工具调用、JSON 输出
│       ⚠️ 较新，生态不如 vLLM 成熟
├─ 显存受限（消费级 GPU，3090/4090）
│   → llama.cpp（CPU+GPU 混合，GGUF 量化）
│       ✅ 一张 4090 跑 70B（4bit 量化）
│       ⚠️ 吞吐较低，适合小团队/个人
└─ 企业级（NVIDIA 推荐路径）
    → TensorRT-LLM（NVIDIA 官方，INT8/FP8 量化）
       ✅ 性能最佳，T4 也能跑
       ⚠️ 编译复杂，调试困难
```

**关键技术点**（必须能讲透）：
- **PagedAttention**（vLLM 核心）：借鉴 OS 虚拟内存分页机制，KV Cache 按 block 分配，避免显存碎片 → 吞吐提升 2-4 倍
- **Continuous Batching**：动态组 batch，新请求随时插入，不必等整个 batch 完成 → GPU 利用率从 30% 提到 80%+
- **量化方案**：INT8（精度损失 1-2%）/ FP8（H100 支持，几乎无损）/ INT4（显存省 4 倍，但精度损失 5-10%）
- **KV Cache 优化**：PagedAllocation / Prefix Caching（重复 Prompt 复用 KV）/ RadixAttention（SGLang）

**模型路由（多模型调度）`[ai.model-router]` 深化**：
```
请求来了 →
├─ 简单 QA / 分类     → 路由到 Qwen-7B（便宜快）
├─ 复杂推理 / 代码     → 路由到 DeepSeek-R1 / Claude（贵但准）
├─ 长文档摘要         → 路由到 128K 上下文模型（Qwen-Long）
└─ 视觉理解          → 路由到 Qwen-VL / GPT-4V
```
- **路由策略**：基于规则（关键词/长度）/ 基于模型（小模型先判断意图）/ 基于成本（Token 预算）
- **成本控制**：Token 计费 → 部门结算 + 语义缓存（相似问题复用答案）+ 限流配额

**面试官连环追问链**（大模型架构师岗必问）：
1. **vLLM 为什么快？** → PagedAttention（KV 分页）+ Continuous Batching（动态批）+ Prefix Cache（Prompt 复用）
2. **PagedAttention 借鉴了什么思想？** → OS 虚拟内存分页 + 页表映射；解决 KV Cache 显存碎片问题
3. **70B 模型本地部署需要什么硬件？** → FP16 需 2×A100 80G；INT8 需 1×A100；INT4 需 2×4090；讲清各自代价
4. **怎么估算大模型服务的成本？** → 显存 = 参数量 × 精度字节 + KV Cache + 激活值；throughput = 显存带宽 / 模型参数量字节 × 利用率
5. **vLLM 和 TensorRT-LLM 怎么选？** → vLLM 易用生态好（开源、迭代快）；TRT-LLM 性能极致但编译复杂（适合 NVIDIA 全家桶团队）
6. **怎么做模型路由？** → 不只是省钱，还要考虑延迟/可用性/合规（数据敏感的不走公网模型）；多模型故障降级（A 挂了切 B）
7. **为什么量化后精度会掉？** → 量化是"四舍五入"丢失精度；INT4 比 INT8 损失大；可以用 GPTQ/AWQ 算法降低损失

**🔑 金句**：「调 API 是 AI 应用工程师，能本地化部署 + 路由调度 + 成本控制才是大模型架构师。前者月薪 20K，后者 50K+，差别就在'工程化深度'。」

#### B. 多模态工程化（非算法方向）`[ai.multimodal]`

> **重要边界**：这里讲的是**多模态的工程化落地**，不是训练多模态模型（那是算法工程师的活）。3 次"多模态"在 JD 里出现，都是"能用多模态模型解决业务问题"。

**业务场景**：
- 电商商品审核（图文不一致检测）→ CLIP 算图文相似度
- 工业质检（图片 + 描述 → 缺陷分类）→ VLM（视觉语言模型）
- 医疗影像辅助诊断（CT 图 + 病史 → 建议）→ 多模态 RAG

**主流多模态模型选型**：
| 模型 | 类型 | 适用场景 | 部署方式 |
|------|------|----------|----------|
| CLIP | 图文匹配 | 商品搜索 / 内容审核 /图文一致性 | 开源，本地部署 |
| BLIP-2 | 图像描述 | 自动 alt 文本 / 无障碍 | 开源 |
| Qwen-VL | 视觉对话 | 图表理解 / 文档 OCR / 多轮对话 | 阿里云 API / 开源 |
| GPT-4V | 通用视觉 | 复杂视觉推理 | OpenAI API |
| LLaVA | 开源 VLM | 本地化视觉对话 | 开源 |

**工程化难点**（区别于纯文本 LLM）：
- **图片预处理**：尺寸归一化 / 分辨率权衡（高分辨率准但慢）/ 多图批处理
- **Token 消耗爆炸**：图片转 Token 数 = (分辨率 / patch_size)²；一张 1024×1024 图 ≈ 1000+ Token，成本是文本的 10-100 倍
- **缓存策略不同**：图片向量比文本向量维度高（768 vs 1536），存储成本高
- **延迟控制**：图片推理比文本慢 3-10 倍，要有异步队列 + 进度回调

**面试官追问链**：
1. **多模态 RAG 和文本 RAG 有什么区别？** → 切片不同（图片不能"切"成 token）/ Embedding 模型不同（CLIP vs BGE）/ 检索策略不同（图文联合检索）
2. **图片怎么入向量库？** → 用 CLIP 等模型生成图片向量 + 文本描述向量 + 联合索引；查询时图文都查
3. **怎么控制多模态的成本？** → 图片预处理（裁剪/压缩）+ 模型路由（简单图用便宜模型）+ 缓存（相似图片复用结果）
4. **CLIP 怎么做图文匹配？** → 双塔结构（图编码器 + 文编码器）→ 同一空间 → 余弦相似度；零样本分类能力强
5. **VLM 怎么处理图表？** → 高分辨率 patch + OCR 辅助 + 结构化输出（JSON）；Qwen-VL 在中文图表上表现最好

**🔑 金句**：「多模态工程化的核心不是'懂算法'，而是'懂成本'——一张图片的 Token 成本是文本的 10-100 倍，能不能做好缓存/路由/降级，决定了方案能不能落地。」

2. **客户要的功能明显不合理，你怎么处理？** → 不要硬刚，先确认背后的业务诉求，给替代方案 + 风险书面化 + 升级机制
3. **怎么测算项目成本？** → 人天 × 单价 + 软硬件采购 + 风险准备金（10-20%）+ 后期运维分成
4. **POC 失败了怎么办？** → 失败复盘 → 是方案问题 / 数据问题 / 客户预期问题 → 给替代方案或主动止损
5. **怎么和销售配合？** → 销售管商务关系，CTO 管技术承诺；技术红线不退让（不切实际的时间/不可能的功能）

**🔑 金句**：「售前方案最大的坑不是技术做不到，而是把'客户说要什么'当成了'客户真的需要什么'。技术总监的价值是把伪需求挡在合同签定之前。」

**F2. 项目集管理 Program Management `[management.program-mgmt]`**

与单项目管理（PM）的区别：项目集是**多个关联项目的战略协同**，目标是**战略收益**，不是单个项目按时交付。

**达标标准**：
- **项目集识别**：能识别哪些项目应该作为一个项目集管（共享目标 / 依赖关系 / 资源冲突）
- **依赖管理**：项目间依赖图谱（A 的产出是 B 的输入）+ 关键路径识别
- **资源调度**：跨项目的资源冲突仲裁（两个项目都抢同一个核心架构师）+ 优先级框架
- **收益管理**：项目集的"战略收益"度量（不是单项目 ROI，是组合 ROI）

**面试官追问链**：
1. **项目集和项目组合（Portfolio）有什么区别？** → 项目集 = 强相关项目协同（共享目标）；项目组合 = 战略层投资选择（选择做哪些项目）
2. **你怎么处理两个项目抢同一个核心员工？** → 优先级框架（战略价值 × 紧急度）+ 临时借调机制 + 长期补人/培养备份
3. **项目集怎么度量成功？** → 不是单项目都按时，而是组合收益达成（如"全公司数字化转型"项目集 = 5 个子项目 + 1 个总收益目标）
4. **PMO 该不该独立设？** → 看规模：50+ 项目或战略级项目集 → 必须独立 PMO；小公司可由 CTO 兼任

**🔑 金句**：「单项目管理是'按时按预算交付'，项目集管理是'组合起来打赢战役'。技术总监是战役指挥官，不是工头。」

**F3. 质量保障体系（QA 体系）`[management.qa-system]`**

与 `[management.engineering]`（工程化）的区别：engineering 关注**研发流程效率**（CI/CD/DORA），QA 关注**质量结果**（缺陷率/线上事故/用户满意度）。

**达标标准**：
- **测试金字塔落地**：单元测试 70%（开发写）+ 集成测试 20%（QA 写）+ E2E 测试 10%（QA 写）；不是倒金字塔（手工测试占大头）
- **质量门禁**：CI 强制门禁（覆盖率 < 60% 拦截 / SonarQube Critical Issues 拦截 / 安全扫描 SAST 拦截）
- **质量度量体系**：缺陷密度（Defect Density = 缺陷数/KLOC）+ 缺陷逃逸率（生产发现的 / 总发现的）+ MTBF（平均无故障时间）
- **质量文化**：不是 QA 兜底，是开发负责质量（QA 转型为"质量教练"，做工具/流程/自动化）

**面试官追问链**：
1. **你们线上缺陷率多少？怎么降的？** → 给具体数字（如：缺陷逃逸率从 15% 降到 5%）+ 三件套（左移测试 + 自动化回归 + 灰度发布）
2. **测试团队和开发团队怎么分工？** → 开发写单测 + 集成测；QA 写 E2E + 性能测 + 安全测 + 做测试平台；不是 QA 给开发"擦屁股"
3. **覆盖率 80% 就一定质量好吗？** → 不是，覆盖率只是"代码被执行过"，不等于"逻辑被验证过"；要看**分支覆盖率** + **断言密度**
4. **怎么衡量测试用例本身的质量？** → 变异测试（Mutation Testing，故意改代码看用例能不能发现）+ 线上缺陷回流成回归用例
5. **SonarQube 在你团队怎么用？** → CI 强制门禁（Critical 必须修）+ 技术债大盘（每个团队的 Square Rating）+ 周报对比

**🔑 金句**：「质量不是 QA 测出来的，是开发写出来的。CTO 的活是把'测试左移 + 自动化门禁'做成研发默认习惯，而不是用 QA 人海战术补质量。」

**G3. 安全合规深度 `[management.compliance-deep]`**

与 `[management.compliance]`（等保 2.0）的区别：原技能偏**网络安全等级保护**；高端岗要看**数据全生命周期合规**——这是 2021 年后国家强监管的核心。

**三大法律框架**（必须能讲清差异）：
| 法律 | 关注点 | 适用场景 | 罚则 |
|------|--------|----------|------|
| 《网络安全法》（2017）| 网络运行安全 / 关键信息基础设施 | 所有网络运营者 | 最高 100 万 + 停业 |
| 《数据安全法》（2021）| 数据分级分类 / 重要数据出境 | 处理数据的企业 | 最高 1000 万 + 停业 |
| 《个人信息保护法》PIPL（2021）| 个人信息处理 / 跨境传输 | 处理用户数据的企业 | 最高 5000 万 或 营业额 5% |

**达标标准**：
- **数据分级分类**：能落地"公开/内部/敏感/核心"四级分类 + 不同级别对应不同处理流程（存储/传输/销毁/审计）
- **个人信息保护**：用户授权（明示同意）+ 最小必要原则 + 用户权利保障（查询/删除/导出）+ 隐私政策合规
- **数据出境合规**：识别什么是"重要数据"/"个人信息"→ 是否需要安全评估（网信办）/ 标准合同 / 个人同意
- **AI 特有合规**：生成式 AI 备案（生成式 AI 服务管理办法）+ 训练数据合规 + 输出审核 + 算法登记

**面试官追问链**：
1. **PIPL 出台后你们做了哪些改造？** → 用户授权流程升级（明示同意）+ 数据分级（识别个人信息）+ 隐私政策重写 + DPO（数据保护官）任命
2. **数据出境怎么管？** → 先识别（哪些数据出境）→ 评估（重要数据？个人信息超量？）→ 选路径（安全评估 / 标准合同 / 个人同意）
3. **AI 大模型的合规风险在哪？** → 训练数据合规（版权 + 个人信息）+ 输出内容合规（生成式 AI 备案）+ 算法偏见（持续评估）
4. **如果用户要求删除所有数据，怎么做？** → 30 天内响应 + 全链路删除（数据库/日志/备份/缓存/CDN）+ 第三方共享数据通知删除
5. **怎么平衡业务诉求和合规红线？** → 不是"合规说不"，而是"合规说怎么做"——给业务可行路径，不是只挡道

**🔑 金句**：「合规不是'业务的对立面'，是'业务的护栏'。好的 CTO 能让合规变成竞争优势（用户信任 → 数据资产 → 业务护城河），而不是成本中心。」

### 5.3 上云选型与 TCO 评估（技术总监高频）`[management.cloud-arch]`

> **青岛特色考点**：看准网/脉脉技术总监面经高频题"上云选型：自建 vs 阿里云/腾讯云怎么评估"。青岛企业（海尔/海信/中车）传统自建机房多，技术总监常被问"要不要上云、上哪个云、怎么算账"。

**业务场景**：公司自建机房 200 台物理服务器，网络设备 5 年折旧到期，CIO 问"继续自建还是上云？上哪个云？"

---

**上云选型四维评估框架**（技术总监必须能给 CEO/CFO 一个量化回答）：

```
评估维度                    权重    自建IDC        阿里云         腾讯云         华为云
──────────────────────────────────────────────────────────────────────────────
TCO 总拥有成本（5年）         35%    基准 100%      70-80%        75-85%        80-90%
  ├─ 硬件采购（一次性）                  ✔ 折旧5年      ✘             ✘             ✘
  ├─ 运维人力                          ✔ 2-3人/百台   ✘             ✘             ✘
  ├─ 电费/机柜/带宽                     ✔ 月付         ✘             ✘             ✘
  └─ 云资源/带宽                                       月付          月付          月付
可用性 SLA                       30%    自行保障       99.95%        99.95%        99.99%
  ├─ 单AZ可用性                    99.5%           99.95%        99.95%        99.99%
  └─ 多AZ/跨region                难/贵           ✅ 原生        ✅ 原生        ✅ 原生
弹性伸缩能力                     15%    差（采购周期）   ✅ 秒级        ✅ 秒级        ✅ 秒级
产品生态/增值服务                  10%    ✘              ✅ 最丰富      ✅ 游戏/视频    ✅ 政企/信创
数据合规（等保/信创/数据出境）      10%    ✅ 完全可控     ⚠️ 等保协助    ⚠️ 等保协助    ✅ 国产化最全
```

**TCO 简易估算公式**（技术总监面试必背）：
```
TCO_5年 = 
  自建:  硬件费 + 软件许可 + 运维人力(2人×15万×5年) + 电费/带宽/机柜 + 网络设备 + 安全设备
  上云:  CPU/内存/存储月费×5年 + 带宽费 + 托管服务(RDS/Redis/MQ) + 数据出云费
         + 迁移一次性费用(数据搬迁+改造)
```

**典型结论**（行业基准，可当话术用）：
- **中小规模（<50 台物理机）**：上云 TCO 通常低 20-30%，弹性优势明显 → ✅ 上云
- **中大规模（200-500 台）**：TCO 接近或上云高 10%；但弹性/运维/可用性优势补差价 → 混合云
- **大规模（>1000 台/信创单位/金融）**：自建+私有云 TCO 更低，且可控性/合规性更强 → ✅ 自建/托管云

---

**混合云架构（大中型企业最常见选择）**：
```
┌───────────────────────────────────────────────────────────┐
│  私有云（IDC / OpenStack / 华为云Stack）                    │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐                  │
│  │ 核心交易   │ │ 用户数据  │ │ 合规敏感   │                  │
│  │ (MySQL)  │ │ (Redis)  │ │ (PII)    │                  │
│  └──────────┘ └──────────┘ └──────────┘                  │
└────────────────────────┬──────────────────────────────────┘
                         │ 专线/VPN (低延迟 1-2ms)
┌────────────────────────▼──────────────────────────────────┐
│  公有云（阿里云/腾讯云）                                     │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐     │
│  │ AI训练    │ │ 大促弹性  │ │ 静态页面  │ │ 开发测试  │     │
│  │ (GPU)    │ │ (ECS弹)  │ │ (CDN)    │ │ (环境)   │     │
│  └──────────┘ └──────────┘ └──────────┘ └──────────┘     │
└───────────────────────────────────────────────────────────┘
```

**上云十大坑**（技术总监必须能预警，否则显得没经验）：
1. ❌ **数据出云费**（Egress 费）：100TB 出云 ≈ 8 万/月，容易被忽略
2. ❌ **RDS 大实例单价**：自建 MySQL 一台物理机 10 万/5 年；RDS 同规格月费 ≈ 5000 → 5 年 30 万
3. ❌ **上云≠免运维**：OS 补丁/中间件配置/监控还是自己管（除非全托管服务）
4. ❌ **大厂锁定**：用了阿里云 RDS+Redis+MQ+DataWorks → 迁移成本高到不可逆
5. ❌ **专线费用**：混合云专线 1Gbps ≈ 1-2 万/月，规模小不合算
6. ❌ **GPU 实例难抢**：大促/训练时 A100/H100 实例可能买不到，需预留实例
7. ❌ **等保 2.0 责任共担**：云厂商只保"云平台安全"，客户保"云上系统安全"——边界常混淆
8. ❌ **数据出境风险**：选了跨国云厂商（AWS/Azure/GCP）+ 子公司数据跨境 = PIPL 合规问题
9. ❌ **多云管理复杂度**：同时用阿里+腾讯+华为 → 网络打通/身份统一/成本分账 管理成本暴涨
10. ❌ **信创要求**：党政/国企项目要求信创目录（华为云/天翼云/移动云），阿里云/腾讯云可能不满足

**面试官连环追问链**（技术总监/CXO 面高频）：
1. **你怎么评估上云还是自建？** → 四维评估框架（TCO + SLA + 弹性 + 合规），不是拍脑袋"上云好"
2. **CFO 问你 TCO 怎么算？** → 给简易公式；提"出云费""RDS 单价"两个容易被忽略的隐性成本
3. **混合云怎么打通网络？** → 专线（云托付 / 阿里云高速通道）或 VPN（小规模）；DNS 解析（PrivateZone）
4. **如果核心数据库已经上云了，怎么保证高可用？** → 跨 AZ 部署（RDS 主备跨可用区）+ DTS 灾备 + 备份恢复到 RDS
5. **阿里云和华为云怎么选？** → 阿里云生态最丰富但信创合规弱；华为云政企信创最强但生态年轻；党政/国企强制华为云/天翼云
6. **你们公司现有 200 台自建，怎么迁移？** → 绞杀者模型：先边缘应用（开发/测试/静态站）→ 再 AI/大数据（云上 GPU）→ 最后核心交易（分批灰度）
7. **云上成本失控怎么办？** → 预算管控（配额/预算池）+ 资源治理（闲置实例回收/弹性缩容）+ 购买策略（预留实例/RDS 节省计划省钱 20-60%）

**🔑 金句**：「上云决策不是技术决定，是财务决定。技术总监的价值是能用 TCO 算盘说清'自建 5 年花 500 万 VS 上云 5 年花 400 万但多出 200 万的弹性价值'——CEO 听得懂这个。」

## 七、面试准备建议（按岗位）

### 7.1 前端架构师面试准备清单

1. **必背**：JS 原型链/闭包/事件循环、Vue3 响应式原理、React Fiber、虚拟 DOM Diff、性能指标 FP/FCP/LCP
2. **必做**：跑通一个微前端 demo（qiankun）、搭过组件库、用过 SSE 流式接收
3. **项目深挖**：准备 1-2 个大型前端项目的架构决策故事（为什么这样选、踩了什么坑）
4. **AI 加分**：能讲 SSE + 流式 Markdown + 多轮对话状态管理

### 7.2 后端架构师面试准备清单

1. **必背**：HashMap/ConcurrentHashMap、JVM GC、synchronized 锁升级、AQS、Spring 事务传播、MySQL B+ 树/MVCC、Redis 三大问题
2. **必做**：跑通一个微服务 demo（Nacos + Gateway + Feign）、用过 Sentinel 限流、SkyWalking 链路追踪
3. **系统设计题**：秒杀系统五段式（需求拆解 → 容量估算 → 架构分层 → 关键决策 → 失败路径）
4. **AI 加分**：Spring AI + RAG demo

### 7.3 AI 应用开发面试准备清单

1. **必背**：RAG 全链路、ReAct 循环、Tool Calling、Transformer/Self-Attention、Top-K/Top-P/Temperature、LoRA 原理
2. **必做**：跑通一个完整 RAG 项目（PDF 问答）、写过 ReAct Agent、用过 LangGraph 或 Spring AI
3. **工程场景**：三道防线（LLM → 语义缓存 → 规则引擎）、成本控制（Token 计量/缓存/路由）
4. **青岛市场**：海尔偏好 Python/Go/Rust + LangGraph + MCP，海信偏好 Java + Spring AI

### 7.4 全栈面试准备清单

1. **前端**：Vue3 或 React + TypeScript + SSE（AI 交互层加分）
2. **后端**：Spring Boot 或 FastAPI + MySQL + Redis
3. **端到端项目**：能讲从 0 到 1 搭一个完整应用（UI → API → DB → 部署）
4. **AI 加分**：RAG + Agent 基础链路

### 7.5 技术总监面试准备清单

1. **管理**：搭团队/绩效/招聘/留人的方法论（带具体案例和数据）
2. **战略**：年度技术规划案例 + ADR 决策记录 + 技术债管理故事
3. **架构判断**：能 review 架构师方案、识别风险（绞杀者模型、容灾级别）
4. **AI 战略**：AI 落地路线图（试点 → 验证 → 推广）+ 治理（合规/安全/数据不出域）
5. **业务**：ROI 量化能力、能用业务语言和技术对话
