## 1.2 HashMap 结构演进:1.7 → 1.8

### 1.7 结构:数组 + 链表

```
HashMap<String, Order>(初始容量 16,加载因子 0.75)

内部:
Entry[] table = new Entry[16];   // Entry = {hash, key, value, next}

假设 put("order_001", orderObj):
  hash("order_001") = 0x3a4f        // 经过扰动函数 hash = (h = key.hashCode()) ^ (h >>> 16)
  index = 0x3a4f & (16-1) = 0xf = 15  // (capacity-1) 等价于 % capacity,位运算更快
  table[15] = null? 直接放
  table[15] 有? 头插法插到链表头(1.7 特有,1.8 改尾插)
```

**1.7 的头插法是个坑**:多线程 put 时,如果发生扩容 rehash,链表会反转,可能形成**环形链表** → 死循环 → CPU 100%。这就是为什么 1.8 改尾插。

```
1.7 头插法在扩容时的环形问题示意:

原 table[15]: A -> B -> C -> null
                 (A.hash % 16 == 15, B.hash % 16 == 15, C 同理)

扩容到 32 后:
  A.hash % 32 == 15 (留在 15 位)
  B.hash % 32 == 31 (去 31 位)
  C.hash % 32 == 15 (留在 15 位)

头插法逐个插:先插 A 到 15,再插 B 到 31,再插 C 到 15
但因为是头插,C 插到 15 位时,A 已经被移到 15 位,变成:
  table[15]: C -> A (原本 A -> C)

更糟的情况:两个节点互相 next 指向对方 → 死循环

所以 1.7 HashMap 在并发场景下**绝对不能当 Map 用**,要并发请用 ConcurrentHashMap。
```

> 🔑 **金句**:HashMap 1.7 头插法在并发扩容时会形成环形链表导致死循环,这是 1.8 改尾插法的根本原因。

### 1.8 结构:数组 + 链表 + 红黑树

```
HashMap<String, Order>

内部结构:
Node<K,V>[] table  // Node 实现 Map.Entry 接口,有 hash/key/value/next

单个 Node:
class Node<K,V> implements Map.Entry<K,V> {
    final int hash;
    final K key;
    V value;
    Node<K,V> next;  // 单链表,不是双向
}

当链表长度 ≥ 8 且 数组容量 ≥ 64:
  链表 → 红黑树(TreeNode)
  当树节点 ≤ 6:
  红黑树 → 退化回链表(防止频繁转换开销)

为什么阈值是 8 不是 5 也不是 10?
  根据泊松分布,在合理 hash 下,单桶命中 8 个元素的概率 < 千万分之六
  8 是空间(红黑树节点比链表节点大 1 倍)与时间(O(log n) vs O(n))的最佳平衡点

为什么树化条件还要容量 ≥ 64?
  容量小(比如 16)时,16 个桶可能都塞在几个桶里
  优先扩容而不是树化,因为扩容能把冲突分散开
  只有扩容也解决不了(容量已经 64)才考虑树化
```

```
1.8 结构可视化:

                    ┌─────────────┐
table[0] ─────────► │ Node(hash, k, v) ──► Node ──► null   (链表,长度<8)
                    └─────────────┘
                    ┌─────────────┐
table[1] ─────────► │ Node(hash, k, v) ──► null            (单元素)
                    └─────────────┘
table[2] ───► null
...
                    ┌─────────────┐
table[7] ─────────► │ TreeNode    │
                    │    root     │
                    │   /     \   │
                    │ Node    Node │
                    │/ \      \   │
                    │... ...   ...│
                    └─────────────┘
                    (树化,长度≥8 且容量≥64)
```

> 🔑 **金句**:HashMap 1.8 用数组+链表+红黑树三段结构,链表长度≥8 且容量≥64 时树化,长度≤6 时退化回链表——这是用空间换时间的经典工程权衡。

### 1.3 扩容机制(高频必考)

**触发条件**:`size > threshold` 时扩容,其中 `threshold = capacity × loadFactor`。

默认:capacity = 16,loadFactor = 0.75,threshold = 12。即 size 达到 13 时触发扩容。

**扩容过程(1.8 版本):**

```
原容量 16,扩容到 32

对于每个桶的每个元素 e:
  if (e.hash & oldCap) == 0
    留在原位(e 在新数组的索引 = 在旧数组的索引)
  else
    去高位(e 在新数组的索引 = 在旧数组的索引 + oldCap)

示例:
  元素 A: hash = 0x0f = 0000 1111, oldCap = 16 = 0001 0000
    0000 1111 & 0001 0000 = 0 → A 留在 table[15]
  元素 B: hash = 0x1f = 0001 1111, oldCap = 16 = 0001 0000
    0001 1111 & 0001 0000 = 0001 0000 ≠ 0 → B 去 table[15+16] = table[31]

这就是 1.8 的位运算 rehash 优化:
  1.7 要重新 hash 计算新索引: newIdx = e.hash % newCap
  1.8 只用判断"hash 值第 5 位是 0 还是 1"(因为 oldCap 是 2 的幂,新增的那一位就是 oldCap 那一位)

性能差异:
  1.7 每个元素都要算新位置(乘法/除法开销)
  1.8 用位运算 & 判断(比除法快 10 倍)
```

**为什么容量必须是 2 的幂?**
- `(capacity - 1)` 是连续 1 的二进制,`hash & (capacity-1)` 等价于 `hash % capacity`,位运算更快
- 扩容时 `e.hash & oldCap` 判断留原位还是去高位,依赖 oldCap 是 2 的幂
- 如果用户传入非 2 的幂(比如 10),JDK 自动向上取整到 16

**加载因子 0.75 的权衡**:
- 太小(0.5):频繁扩容,时间成本高
- 太大(1.0):冲突增加,链表变长,查询变慢
- 0.75 是时间和空间的经验值(Sun JDK 早期实验数据)

> 🔑 **金句**:HashMap 扩容是 2 倍扩容(因为 2 的幂方便位运算),1.8 用 `e.hash & oldCap` 判断元素留原位还是去高位,比 1.7 重新算 hash 快 10 倍。

### 1.4 关键源码级细节(面试深挖)

**hash 扰动函数**:
```java
// HashMap 的 hash() 方法
static final int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}
// 高 16 位 ^ 低 16 位,让高位也参与索引计算
// 因为 (capacity-1) 通常很小(比如 15),hash % 15 只用低 4 位
// 扰动让高位信息也影响低 4 位,减少冲突
```

**为什么 key 可以是 null?**
- null key 统一放 table[0](hash 计算返回 0)
- 这是个历史遗留设计,不推荐用

**equals 和 hashCode 的约定**:
- 两个对象 equals() 返回 true → hashCode() 必须相同
- hashCode() 相同 → equals() 不一定相等(哈希冲突)
- **重写 equals 必须重写 hashCode**,否则 HashMap 行为异常

```java
// 错误示范:业务里经常见到的 bug
class User {
    String id;
    String name;
    @Override
    public boolean equals(Object o) {
        return ((User)o).id.equals(this.id);  // 按 id 判等
    }
    // 漏了 hashCode!
}

// 结果:HashMap 里同一个 user 对象能找到,但新 new 一个 id 相同的就找不到了
// 因为 hashCode 默认用对象地址,不同对象地址不同,hash 到不同桶
```

> 🔑 **金句**:重写 equals 必须重写 hashCode,否则 HashMap 行为异常——这条在业务开发里是 80% 的"诡异 bug"源头。

### 1.5 ConcurrentHashMap:从分段锁到 CAS+synchronized

**为什么需要 ConcurrentHashMap?**:HashMap 并发不安全,Hashtable 全局锁性能差。

#### 1.7 版本:Segment 分段锁

```
ConcurrentHashMap 1.7 结构:

Segment[] segments = new Segment[16];  // 16 个段,默认并发度 16

每个 Segment 继承 ReentrantLock,管一个小的 HashEntry[]

put 流程:
  1. hash(key) 确定段号(比如 segments[5])
  2. 对 segments[5] 加锁(lock())
  3. 在 segments[5] 内做数组 + 链表操作(类似 HashMap)
  4. 解锁(unlock())

特点:
  - 并发度 = segments.length,默认 16
  - 不同段可以并发操作(不同锁)
  - 同一段内只能串行(同把锁)
  - 扩容只能全表扩(要锁所有段,代价大)
  - size() 要遍历所有段,统计每个段的 count

缺点:
  - 内存开销大(每段独立数组,小容量浪费)
  - 扩容要全表锁(高并发下性能抖动)
  - 单段内还是链表,冲突长时查询慢
```

#### 1.8 版本:Node 数组 + CAS + synchronized

```
ConcurrentHashMap 1.8 结构:

Node<K,V>[] table  // 和 HashMap 类似,但 Node 有 volatile 语义
                   // TreeNode 用于树化(同样 ≥ 8 且容量 ≥ 64)
CounterCell[] counterCells  // size 分散计数

put 流程(关键):
  1. 计算 hash
  2. if (table == null || len == 0) initTable()  // 懒加载,用 CAS 初始化
  3. int i = (n - 1) & hash  // 计算桶索引
  4. Node<K,V> f = table[i]
  5. if (f == null)
       // 桶空,CAS 写入(无锁!)
       if (U.compareAndSetObject(table, offset, null, new Node(...)))
         成功,put 完成
       else
         CAS 失败,说明有并发,重试
  6. else if (f.hash == MOVED)
       helpTransfer()  // 别的线程在扩容,我去帮忙
  7. else
       // 桶非空,用 synchronized 锁住 f 这个桶头
       synchronized (f) {
         遍历链表/树,找相同 key 替换 / 末尾插入 / 插入新节点
         if (binCount >= 8) treeifyBin(f, i)  // 树化判断
       }
  8. addCount(1L, binCount)  // 累加 size,用 CounterCell[] 分散竞争

size() 怎么算:
  baseCount + Σ counterCells[i].value
  // 借鉴 java.util.concurrent.atomic.LongAdder 思想
  // 多线程并发 put 时,每个线程 CAS 写不同的 counterCell
  // 避免单个 AtomicLong 成为热点(高竞争下 AtomicLong CAS 失败率高)

为什么不用 1.7 的 Segment 锁?
  - 锁粒度从 Segment(管一段)→ Node(管一个桶),并发度大幅提升
  - 桶空时 CAS 无锁写入,更快
  - 扩容用 ForwardingNode + helpTransfer,多线程协同扩容
  - 内存开销更小(不再每段独立数组)
```

> 🔑 **金句**:ConcurrentHashMap 1.8 用 Node 数组 + CAS 空桶写入 + synchronized 锁桶头,锁粒度从 1.7 的 Segment 段级细化到桶级,并发度大幅提升。size 用 baseCount + CounterCell[] 分散计数(借鉴 LongAdder),避免单 AtomicLong 热点。

### 1.6 ConcurrentHashMap 的扩容协作机制(面试深挖)

1.8 的扩容是**多线程协作**的,这是面试区分度最高的考点:

```
扩容流程:

1. 某个线程 put 时发现 size > threshold,触发扩容
2. 创建 nextTable = new Node[newCap]
3. 当前线程开始搬数据(从后往前遍历)
4. 在搬运过程中,搬过的桶位置放 ForwardingNode(转发节点)
   - 其他线程 put 时遇到 ForwardingNode,知道在扩容
   - 调用 helpTransfer() 加入搬运(不是旁观,是一起干)
5. 每个线程搬一段连续的桶(通过 advance 参数控制进度)
6. 所有桶都搬完(设置 sizeCtl 标记),扩容完成,table = nextTable

关键设计:
  - 单线程扩容,多线程协助搬运(主线程发起,其他线程 helpTransfer)
  - ForwardingNode 是信号量,告诉其他线程"我在扩容,来帮忙"
  - 扩容期间读操作无锁(节点有 volatile 语义,能读到最新值)
  - 扩容期间 put 操作:
    - 桶已搬走(看到 ForwardingNode)→ 去 nextTable 写入
    - 桶未搬走 → 锁住桶头写入旧表,后续被搬到新表
```

> 🔑 **金句**:ConcurrentHashMap 1.8 扩容是多线程协作:主线程发起,其他线程通过 helpTransfer 加入搬运;搬过的桶放 ForwardingNode 信号量,扩容期间读写都不阻塞。

### 1.7 泛型擦除与 TypeToken(面试高频)

**什么是泛型擦除?**

Java 的泛型是**编译期类型检查,运行时擦除为 Object(或上界)**。

```java
List<Order> orders = new ArrayList<>();
// 编译时:orders.add("string") 报错,类型安全
// 运行时:JVM 看到的是 List<Object>,没有 <Order> 这个信息

// 这就是"泛型擦除"
```

**为什么这样设计?**

> 为了向后兼容 Java 5 之前的代码(1996-2004 年的老代码没有泛型)。JDK 5 引入泛型时,如果 JVM 改类型系统,所有老代码都要重写。所以设计了"编译期检查 + 运行时擦除"的折中方案。

**擦除带来的问题**:

```java
// 不能 new 泛型数组
List<T>[] arr = new List<T>[10];  // 编译错

// 不能 instanceof 泛型
if (obj instanceof List<String>) { }  // 编译错

// 不能获取泛型类型参数
Type type = obj.getClass().getGenericSuperclass();
// 这里返回的是 ParameterizedType 才能拿到 <String>
```

**TypeToken 套路(Guava / Gson 常用)**:

```java
// 场景:反序列化 JSON 到 List<Order>
String json = "[{\"order_id\":\"O001\"}, {\"order_id\":\"O002\"}]";

// 错误:TypeReference 拿不到 List<Order> 的泛型
// 因为擦除,Gson.fromJson 不知道 Order 是什么

// 正确:用匿名内部类保留泛型信息
Type type = new TypeToken<List<Order>>(){}.getType();
List<Order> orders = gson.fromJson(json, type);

// 原理:
// new TypeToken<List<Order>>(){} 创建了 TypeToken 的匿名子类
// 匿名子类继承 TypeToken<List<Order>>,泛型信息保留在 .class 文件里
// TypeToken 内部:
//   Type type = ((ParameterizedType) getClass().getGenericSuperclass()).getActualTypeArguments()[0];
//   // getGenericSuperclass() 返回 ParameterizedType,能拿到 <List<Order>>
//   // getActualTypeArguments()[0] 拿到 Order.class

// 这就是"类型字面量"(Type Literal)套路:用继承 + 匿名内部类绕过擦除
```

> 🔑 **金句**:Java 泛型是编译期检查 + 运行时擦除为 Object;Gson/Guava 用 TypeToken 匿名子类 + getGenericSuperclass() 绕过擦除,保留泛型参数信息。Spring 的 ResolvableType、Jackson 的 TypeReference 都是这个套路。

### 1.8 工业级实践:HashMap 在生产里的坑

```java
// 坑 1:HashMap 当全局变量 + 多线程并发更新 → 数据丢失/CPU 100%
class OrderService {
    // ❌ 错误:全局 HashMap + 多线程 put
    private Map<String, Order> orderCache = new HashMap<>();

    public void cacheOrder(Order order) {
        orderCache.put(order.getOrderId(), order);  // 并发不安全
    }
}

// ✅ 正确 1:改用 ConcurrentHashMap
private Map<String, Order> orderCache = new ConcurrentHashMap<>();

// ✅ 正确 2:如果读多写少,用 Caffeine(本地缓存之王)
private Cache<String, Order> orderCache = Caffeine.newBuilder()
    .maximumSize(10_000)
    .expireAfterWrite(Duration.ofMinutes(10))
    .build();

// 坑 2:key 用可变对象,hashCode 变了找不到
class UserKey {
    String id;
    String name;  // 可变
    // hashCode 用 id 和 name
}
UserKey key = new UserKey("u1", "Alice");
map.put(key, order);
key.setName("Bob");  // 改了 name,hashCode 变了
map.get(key);  // 找不到!因为 hash 到不同桶了

// ✅ 正确:key 用不可变对象(immutable)
// Java 的 String / Integer / Long 都是不可变的
// 业务 key 推荐用 record / final class / Lombok @Value
```

> 🔑 **金句**:HashMap 生产三铁律:① 并发用 ConcurrentHashMap 或 Caffeine,② key 用不可变对象,③ 容量预估好避免频繁扩容(构造器传 initialCapacity)。

### 1.9 面试连环追问(先学完原理再看)

> 以下问题来自架构师面试真实追问链,难度从浅到深。先自己答,再看参考答案。

**Q1. HashMap 为什么用红黑树不用 AVL 树或 B 树?**

**答**:
- **vs AVL 树**:AVL 是严格平衡二叉树(左右子树高度差 ≤ 1),每次插入/删除都要旋转维护平衡,旋转开销大。红黑树允许最长路径 ≤ 2 × 最短路径,平衡宽松,插入/删除旋转次数少。HashMap 是"插多查少"场景,红黑树综合性能更好。
- **vs B 树**:B 树是"矮胖"结构,一个节点存多个 key,适合磁盘 IO(减少磁盘读取次数)。HashMap 是纯内存操作,B 树优势发挥不出来,反而节点复杂度高。红黑树节点简单(只存 1 个 key),内存操作快。
- **工程验证**:Linux 内核进程调度(CFS)、Java 8 之前的 TreeMap 都用红黑树,久经考验。

**Q2. HashMap 的负载因子 0.75 是怎么定的?能改吗?**

**答**:
- 0.75 是 Sun JDK 时代的经验值:太小(0.5)频繁扩容时间成本高,太大(1.0)冲突增加查询变慢。
- 可以改:`new HashMap<>(1000, 0.9f)` 传自定义 loadFactor。
- 业务里一般不改,只在特殊场景调:
  - 内存吃紧,扩容不可接受 → 提高到 0.9,但接受链表变长
  - 极致查询性能,冲突不可接受 → 降低到 0.5,但接受频繁扩容

**Q3. ConcurrentHashMap 1.7 的 segmentCount(并发度)和 1.8 的并发度有什么区别?**

**答**:
- 1.7 并发度 = segments.length,默认 16,构造时可指定。一旦创建不能改。
- 1.8 没有 Segment,并发度 = table.length(桶数)。默认 16,扩容时 2 倍增长。
- 关键区别:1.8 的并发度动态变化(随扩容增长),1.7 是固定的。
- 1.8 的实际并发度更高:因为桶空时 CAS 无锁,只有桶非空时才 synchronized 锁桶头。

**Q4. HashMap 在高并发场景下除了 CPU 100%(1.7 环链)还有什么问题?**

**答**:
- 1.8 解决了环链,但仍有问题:
  - **数据丢失**:两个线程 put 同时落到同一个空桶,CAS 只有一个成功,另一个被覆盖(1.8 的 put 在桶空时是 CAS,但 value 可能被覆盖)。
  - **size 不准确**:多个线程 addCount 并发,CAS 竞争失败会重试,但最终 size 可能略有误差(最终一致,不是强一致)。
  - **扩容期间状态抖动**:一个线程看到 table 是旧表,另一个线程已经切到新表,读到的数据不一致。
- 这些都不符合强一致要求,所以并发场景必须用 ConcurrentHashMap。

**Q5. 泛型擦除带来的业务坑有哪些?怎么规避?**

**答**:
- **坑 1:序列化/反序列化丢失类型信息**
  - Gson 反序列化 `List<Order>` 失败(因为擦除不知道 Order)
  - 解法:用 TypeToken / TypeReference / Jackson 的 ObjectMapper.readValue(json, new TypeReference<List<Order>>(){})
- **坑 2:不能创建泛型数组**
  - `new T[10]` 编译错
  - 解法:用 `List<T>` 代替,或用 `Array.newInstance(clazz, size)` 反射创建
- **坑 3:instanceof 不能检查泛型**
  - `obj instanceof List<String>` 编译错
  - 解法:检查原始类型 `obj instanceof List`,元素类型用业务逻辑判断
- **坑 4:泛型类的静态方法不能用类的泛型参数**
  ```java
  class Box<T> {
      static T get() { }  // 编译错!静态方法不属于类的实例,看不到 T
  }
  ```
  - 解法:静态方法自己声明泛型 `static <U> U get()`

# 主题 2 · JVM 内存 · GC · 生产排查

> **为什么学这个**:后端架构师面试,JVM 几乎是必问项(90% 概率)。不是要你背参数,而是要你能**从现象推到根因**:线上 CPU 飙高怎么定位、OOM 怎么排查、GC 怎么选型。这是"架构师能不能救火"的硬指标。

## 2.1 JVM 运行时数据区(5 块,必须会画)

先搞清楚一个根本问题:**为什么 JVM 要划分内存区域?**

> **痛点**:如果 JVM 把所有内存混在一起,就分不清哪些对象可以回收、哪些栈帧已经退出。划分区域 = 把"生命周期相同的数据"放在一起,各自用不同的管理策略。

```
JVM 运行时数据区 5 块:

┌─────────────────────────────────────────────────────────────────┐
│                       JVM 进程内存                               │
├──────────────────────┬──────────────────────────────────────────┤
│    线程私有(每线程一份) │        线程共享(所有线程共用)               │
├──────────────────────┼──────────────────────────────────────────┤
│ ① 程序计数器 PC       │ ③ 堆 Heap                                │
│   (当前执行到哪一行)    │   (对象实例、数组、GC 主战场)                │
│                      │   分代:Young(Eden+S0+S1) + Old           │
│ ② 虚拟机栈 VM Stack  │                                          │
│   (方法调用栈帧)      │ ④ 方法区 / 元空间 Metaspace(JDK 8+)      │
│   每帧:局部变量表     │   (类元信息、常量池、静态变量)              │
│       操作数栈       │   实现从永久代 PermGen → 本地内存           │
│       动态链接       │                                          │
│       返回地址       │ ⑤ 直接内存 Direct Memory(NIO 用)          │
│                      │   (堆外内存,ByteBuffer.allocateDirect)     │
│ ⑥ 本地方法栈 Native  │                                          │
│   (native 方法调用)   │                                          │
└──────────────────────┴──────────────────────────────────────────┘
```

**每块区域的职责 + OOM 现象**:

| 区域 | 存什么 | 生命周期 | OOM 现象 |
|------|--------|---------|---------|
| **PC 寄存器** | 当前线程执行的字节码行号 | 线程私有,极小 | 唯一**不会** OOM 的区域 |
| **虚拟机栈** | 每个方法调用对应一个栈帧(局部变量表/操作数栈/动态链接/返回地址) | 线程私有 | StackOverflowError(递归太深)或 OOM(线程数太多,每线程默认 1MB 栈) |
| **本地方法栈** | native 方法调用 | 线程私有 | 同上 |
| **堆** | 几乎所有对象实例、数组 | 线程共享,GC 主战场 | OutOfMemoryError: Java heap space |
| **方法区(元空间)** | 类元信息(Class 结构)、运行时常量池、静态变量、JIT 编译代码 | 线程共享 | OOM: Metaspace(类加载太多,比如动态代理类大量生成) |
| **直接内存** | NIO 的 DirectByteBuffer | 堆外,不受 -Xmx 控制 | OOM: Direct buffer memory |

> 🔑 **金句**:JVM 内存分 5 块,堆(对象)和元空间(类元信息)是 GC 主战场。PC 寄存器是唯一不会 OOM 的区域。线上 OOM 第一反应:看 heap 还是 metaspace 报错,定位方向完全不同。

### 2.2 堆的分代结构(8:1:1)

**为什么分代?**:不同对象生命周期不同,统一 GC 浪费。

```
Heap 分代:

┌──────────────────────────────────────┐
│            Young Generation          │  占堆 1/3
│  ┌─────────────────────────────────┐ │
│  │     Eden (8)                    │ │  新对象先放这
│  ├─────────────────────────────────┤ │
│  │     Survivor 0 (1)              │ │  Minor GC 后存活对象
│  ├─────────────────────────────────┤ │
│  │     Survivor 1 (1)              │ │  和 S0 轮流用(复制算法)
│  └─────────────────────────────────┘ │
├──────────────────────────────────────┤
│            Old Generation            │  占堆 2/3
│  (Young 区对象年龄达到阈值,默认 15,进入) │
│  (大对象直接进入 Old,避免在 Young 复制)  │
└──────────────────────────────────────┘
```

**对象晋升 Old 的 3 种情况**:
1. **年龄阈值**:对象在 Survivor 区待了 15 次 GC(可通过 `-XX:MaxTenuringThreshold` 调)
2. **大对象直接进入**:超过 `-XX:PretenureSizeThreshold`(只对 Serial/ParNew 有效,G1 没这参数)
3. **动态年龄判断**:Survivor 区相同年龄对象总大小 > Survivor 空间 50%,≥ 该年龄的对象直接晋升(不需要等 15 岁)

### 2.3 GC 算法(3 种,必须能画图)

**为什么需要 GC?**:C/C++ 手动 malloc/free,容易内存泄漏。JVM 自动回收不再使用的对象。

**如何判断对象"不再使用"?**

> **直觉误区**:很多人说"引用计数法"。引用计数法的问题是循环引用(A 引用 B,B 引用 A,但都没人用它们,计数永远不归零)。所以 JVM 实际用的是**可达性分析**。

#### 算法 1:可达性分析(主流)

```
可达性分析(GC Roots Tracing):

从一组根对象(GC Roots)出发,沿引用链向下搜索,能到达的对象 = 存活
不能到达的对象 = 可回收

GC Roots 5 类(必须记住,这是八股):
  ① 栈中局部变量(方法正在用的对象引用)
  ② 方法区中静态变量(static 字段引用的对象)
  ③ 方法区中常量(常量池里引用的对象)
  ④ 本地方法栈中 JNI 引用(native 方法持有的 Java 对象)
  ⑤ 同步监视器(synchronized 锁定的对象)
  ⑥ (补充)JVM 内部引用(classloader 加载的类、基本类型的 Class 对象、异常对象等)

示例:
  OrderService.service() {
      Order order = new Order(...);   // 局部变量 order → GC Root ①
      User user = userDao.find(1);     // user → GC Root ①
      // 方法执行期间,order 和 user 都可达,不会被回收
  }
  // 方法返回后,order/user 的栈帧出栈,不再可达 → 下次 GC 被回收

循环引用的解法:
  A ←→ B(互相引用),但没有 GC Root 指向它们
  → 从 GC Roots 出发,访问不到 A 和 B
  → 都被判定为可回收

引用 4 种强度(强度递减):
  强引用 Strong: Object obj = new Object();  // 不回收
  软引用 Soft: SoftReference<Object> ref;     // 内存不足时回收(适合缓存)
  弱引用 Weak: WeakReference<Object> ref;     // 下次 GC 必回收(ThreadLocalMap.key)
  虚引用 Phantom: PhantomReference<Object>;   // 跟踪对象被回收的活动(配合 ReferenceQueue)
```

#### 算法 2:3 种回收算法

```
算法 1:标记-清除 Mark-Sweep
  过程:标记存活对象 → 清除未标记对象
  问题:内存碎片(存活和清除的对象交错)
  适用:Old 区(CMS 用,因为碎片会导致大对象分配失败)

算法 2:标记-整理 Mark-Compact
  过程:标记存活对象 → 把存活对象向一端移动 → 清除边界外的内存
  优点:无碎片
  缺点:对象移动开销大(要更新所有引用)
  适用:Old 区(Serial Old / Parallel Old)

算法 3:复制 Copying
  过程:把内存分两半 → 每次只用一半 → GC 时把存活对象复制到另一半 → 清空原半
  优点:无碎片,分配快(指针碰撞)
  缺点:浪费一半内存
  改进:Eden + 2 个 Survivor(8:1:1),浪费 10%
  适用:Young 区(对象存活率低,复制量小)
```

### 2.4 GC 收集器(5 种主流,选型决策)

> 面试官必问:CMS vs G1 区别?什么业务该用哪个?

```
收集器演进图:

   单线程 ──────────────── 多线程(并行)─────────────── 低延迟
  Serial(1.3)          ParNew ──→ CMS(1.5)              
       │                  │          │(标记-清除,碎片问题)
       │                  │          ↓
       │                  │        G1(1.7+)  ──→ ZGC(11+)/Shenandoah
       │                  │        (分区收集,可预测停顿)    (Region, <10ms)
       ↓                  ↓
  Parallel(1.5)    Parallel Old(1.6)
  (吞吐量优先)     (Parallel 的 Old 版)
```

**每个收集器的特点 + 选型**:

| 收集器 | 算法 | 停顿 | 碎片 | 适用场景 |
|--------|------|------|------|---------|
| **Serial** | 复制(Young)/标记-整理(Old) | 长(STW) | 无 | 客户端模式,小内存(< 100MB) |
| **ParNew** | 复制(Young) | 中(多线程并行) | 无 | 配合 CMS 用(CMS 的 Young 搭档) |
| **Parallel** | 复制(Young)/标记-整理(Old) | 长(STW) | 无 | 后台计算/批处理,**吞吐优先** |
| **CMS**(Concurrent Mark Sweep) | 标记-清除 | 短(并发标记) | 有 | Web 服务,**低延迟优先**(JDK 9 废弃,JDK 14 移除) |
| **G1**(Garbage First) | 分区 + 复制/整理 | 短(可预测停顿) | 无 | **通用首选**(JDK 9 默认,大堆表现好) |
| **ZGC** | Region + 着色指针 | < 10ms(几乎不随堆增长) | 无 | 超大堆(TB 级),超低延迟(JDK 15+) |

**CMS 详细流程(面试必问,4 阶段)**:

```
CMS 4 个阶段:

1. 初始标记(STW,很快)
   标记 GC Roots 直接关联的对象
   只标记直接可达,不沿引用链

2. 并发标记(和应用线程并发,耗时最长)
   沿引用链遍历所有对象
   期间对象引用变化 → 用 SAT(Snapshot-At-The-Beginning)算法记录

3. 重新标记(STW,修正并发标记期间的变动)
   处理 SAT 记录的变更

4. 并发清除(和应用线程并发)
   清除未标记对象
   期间应用线程继续运行,可能产生新垃圾(浮动垃圾),下次 GC 清理

CMS 3 大痛点(必背):
  ① 内存碎片(标记-清除算法)
     → 碎片累积 → 大对象分配失败 → 触发 Full GC 用 Serial Old 整理
     → Full GC 停顿长,失去"低延迟"意义
  ② CPU 敏感(并发阶段占 CPU)
     → 默认启动 (CPU 核数+3)/4 个 GC 线程
     → 4 核机器只留 1 核给 GC,业务受影响
  ③ 浮动垃圾(并发清除阶段的新垃圾)
     → 需要预留内存(MSCMS Initating Occupancy Fraction 设置)
     → 预留不够 → 退化为 Full GC
```

**G1 vs CMS 深度对比(架构师必会)**:

```
G1 核心设计:Region 分区

┌────────────────────────────────────────┐
│                Heap                    │
│  ┌───┬───┬───┬───┬───┬───┬───┬───┐  │
│  │ E │ S │ O │ O │ E │ H │ O │ H │  │  每格 = 1 个 Region(1-32MB,默认 2048 个)
│  └───┴───┴───┴───┴───┴───┴───┴───┘  │
│  E=Eden  S=Survivor  O=Old  H=Humongous(大对象)
│
│  每个 Region 可以是 Eden / Survivor / Old / Humongous 之一
│  动态调整角色(不像 CMS 固定分代)
│
│  GC 时按"收益优先"回收:
│    回收价值 = 可回收空间 / 回收耗时
│    优先回收"收益高"的 Region(Garbage First 得名)
└────────────────────────────────────────┘

G1 4 种 GC 模式:
  ① Young GC(只回收 Eden + Survivor Region)
  ② Concurrent Marking(并发标记,类似 CMS 的并发阶段)
  ③ Mixed GC(Young + 部分 Old Region,核心)
  ④ Full GC(兜底,单线程整理,停顿长,要避免)

G1 vs CMS 对比:
  维度              CMS                          G1
  算法              标记-清除                    分区 + 复制/整理
  碎片              有(致命缺陷)                 无
  停顿预测          不能                         能(-XX:MaxGCPauseMillis=200)
  大堆表现          差(> 8G 浮动垃圾多)          好(分区处理)
  JDK 状态          JDK 14 移除                  JDK 9+ 默认
  适用场景          小堆低延迟(已过时)            通用首选
```

> 🔑 **金句**:CMS 用标记-清除算法有碎片,大堆退化 Full GC;G1 用 Region 分区 + 可预测停顿,大堆表现好,是 JDK 9+ 默认选择。**生产选型:JDK 8 用 G1(需手动开 -XX:+UseG1GC),JDK 11+ 默认 G1,超大堆用 ZGC**。

### 2.5 类加载机制(双亲委派 + 打破)

**类加载 7 步**:
加载 → 验证 → 准备 → 解析 → 初始化 → 使用 → 卸载

**双亲委派模型**:

```
类加载器层次(自下而上委派,自上而下加载):

Bootstrap ClassLoader(启动类加载器)
    ↑ 委派
Extension ClassLoader(扩展类加载器)
    ↑ 委派
Application ClassLoader(应用类加载器,也就是你代码的 ClassLoader)
    ↑ 委派
User ClassLoader(自定义,比如 Tomcat 的 WebAppClassLoader)

委派规则:
  "我能不能加载?不能就让我爹加载"
  User CL 收到 loadClass("com.example.OrderService")
    → 问 Application CL:"你能加载吗?"
    → Application CL 问 Extension CL
    → Extension CL 问 Bootstrap CL
    → Bootstrap CL:这是 rt.jar 里的吗?是就加载
    → 不是 → 返回给 Extension CL
    → Extension CL:是 ext 目录里的吗?是就加载
    → 不是 → 返回给 Application CL
    → Application CL 在 classpath 找,找到就加载
    → 找不到 → ClassNotFoundException

为什么这样设计?
  安全:防止用户自定义 java.lang.String 替换 JDK 的 String
  避免重复:父加载器加载过的,子加载器不会再加载

什么时候要打破双亲委派?
  1. OSGi / 热部署:同一个类不同版本共存
  2. Tomcat:每个 Web 应用独立 ClassLoader,互不干扰
  3. SPI 机制:JDK 核心类调用用户代码(JDBC Driver / SLF4J)
     → Bootstrap CL 加载的 java.sql.DriverManager 需要加载
        Application CL 下的 com.mysql.cj.jdbc.Driver
     → 用线程上下文类加载器(Thread.getContextClassLoader)打破
  4. JDK 9 模块化(Modules):不再严格双亲委派,但保持兼容
```

> 🔑 **金句**:双亲委派保证"核心类不会被替换",打破场景:SPI(JDBC/SLF4J 用线程上下文 CL)、Tomcat(每应用独立 CL)、热部署(OSGi)。面试被问"打破双亲委派"就举这 3 个例子。

### 2.6 生产排查三板斧(架构师硬功夫)

**场景 1:CPU 飙高 100%**

```
排查 4 步(必背):

1. top 找 PID 高的进程
   $ top -c
   PID   COMMAND     %CPU
   12345 java        98.5   ← Java 进程

2. top -Hp PID 找高 CPU 的线程
   $ top -Hp 12345
   PID    THREAD_ID  %CPU
   12345  12400      45.2   ← 线程 12400
   12345  12401      45.3   ← 线程 12401

3. 线程 ID 转 16 进制(给 jstack 用)
   $ printf "%x\n" 12400
   3070
   $ printf "%x\n" 12401
   3071

4. jstack PID | grep -A 30 nid=0x3070
   "http-nio-8080-exec-5" #12400 daemon prio=5
      java.lang.Thread.State: RUNNABLE
      at java.util.HashMap.resize(HashMap.java:723)  ← 死循环?
      at java.util.HashMap.putVal(HashMap.java:660)
      at com.example.OrderService.cacheOrder(OrderService.java:45)

可能原因:
  - 死循环(比如 1.7 HashMap 环链、业务代码死循环)
  - 频繁 GC(STW)
  - 正则回溯
  - 锁竞争激烈(synchronized 自旋)
```

**场景 2:OOM 排查**

```
OOM 时保留现场(必须配参数):
  -XX:+HeapDumpOnOutOfMemoryError
  -XX:HeapDumpPath=/var/log/app/heapdump.hprof

拿到 hprof 文件后:

方法 1:MAT(Eclipse Memory Analyzer)
  打开 hprof → Overview → Top Consumers
  看哪个类占内存最多
  看 Dominator Tree(支配树,找 GC Root 引用链)
  看 Leak Suspects(泄漏嫌疑报告)

方法 2:Arthas 在线诊断(线上首选,不用重启)
  $ arthas-boot.jar
  [1] 12345 java
  $ heapdump --live /tmp/live.hprof  # 只 dump 存活对象
  $ dashboard                         # 实时看 GC/内存/CPU
  $ heapdump --live | jmap -histo 12345 | head  # 类实例数统计

常见 OOM 原因:
  ① 内存泄漏(集合持续增长,比如 static Map 没清理)
  ② 大对象(一次性加载百万条记录到内存)
  ③ 线程栈溢出(递归太深)
  ④ metaspace 爆(动态代理类太多,CGLIB 每次生成新 Class)
```

**场景 3:Full GC 频繁**

```
排查思路:

1. 看 GC 日志
   -Xloggc:/var/log/app/gc.log -XX:+PrintGCDetails -XX:+PrintGCDateStamps
   关注:Full GC 频率、每次 GC 后 Old 区占用

2. 常见原因(按可能性排序):
   ① Old 区空间不足(大对象直接进入 Old,或 Young 晋升太快)
   ② metaspace 不足(加载太多类)
   ③ System.gc() 显式调用(代码里 / JMX / RMI 定时触发)
   ④ CMS concurrent mode failure(预留空间不够,退化 Full GC)
   ⑤ 显式调用 GC 后执行堆 dump

3. 解法:
   增大堆(-Xmx)
   调整 Young/Old 比例(-XX:NewRatio,默认 2 即 Old:Young=2:1)
   调大晋升阈值(-XX:MaxTenuringThreshold)
   换 G1(-XX:+UseG1GC)
```

### 2.8 面试连环追问

**Q1. 为什么 JDK 8 把永久代(PermGen)改成元空间(Metaspace)?**

**答**:
- **永久代问题**:大小固定(-XX:MaxPermSize),容易 OOM 或浪费;和堆共享 JVM 进程内存,调整麻烦。
- **元空间改进**:用本地内存(不受 -Xmx 限制),动态扩缩,和堆独立管理。
- **工程动机**:HotSpot 和 JRockit 合并,JRockit 没有永久代,统一为元空间更利于代码维护。

**Q2. G1 的 Mixed GC 怎么工作?和 Young GC 什么区别?**

**答**:
- **Young GC**:只回收 Eden + Survivor Region,触发条件:Eden 区满。
- **Mixed GC**:Young + 部分 Old Region,触发条件:并发标记完成后,根据 Old Region 的回收价值排序。
- **Mixed 选择 Old Region 的策略**:
  - 优先选"回收价值高"(垃圾多、回收成本低)的 Region
  - 满足 `-XX:G1MixedGCCountTarget`(默认 8 次 Mixed 内完成)
  - 每次 Mixed 回收的 Old Region 数量由 `-XX:G1MixedGCLiveThresholdPercent`(默认 85%,低于这个存活率才回收)控制

**Q3. 你线上用哪个 GC?为什么?**

**答**(标准答案,根据实际经验调整):
- **JDK 8 生产**:默认 Parallel,G1 手动开启。我们业务对延迟敏感(200ms SLA),用 G1,停顿控制 200ms 内。
- **JDK 11+ 生产**:默认 G1。如果堆 > 32G 且延迟要求 < 10ms,考虑 ZGC。
- **批处理/大数据**:用 Parallel,吞吐优先。
- **关键决策**:不是"哪个 GC 最好",而是"业务需要什么 SLA"。Web 服务低延迟 → G1/ZGC,后台计算高吞吐 → Parallel,小内存客户端 → Serial。

**Q4. 如何避免 Full GC?**

**答**:
- **调 Young 区大小**:避免对象过早晋升 Old
- **调晋升年龄**:MaxTenuringThreshold 设大一点(让对象多活一会)
- **避免大对象**:流式处理代替一次性加载
- **避免内存泄漏**:定期 heap dump 检查
- **CMS 用户**:设 `-XX:CMSInitiatingOccupancyFraction`(默认 92% 太晚,设 70-80%)
- **G1 用户**:设 `-XX:InitiatingHeapOccupancyPercent`(默认 45%)
- **避免 System.gc()**:代码里不要显式调用

**Q5. JVM 调优的 3 大误区?**

**答**:
- ❌ **误区 1:"堆越大越好"**
  - 堆太大 → Full GC 停顿太长(即使 G1 也会受影响)
  - 一般 8-16G 合适,超大堆用 ZGC
- ❌ **误区 2:"年轻代越大越好"**
  - 年轻代太大 → Old 区太小 → 频繁 Full GC
  - 一般 Young:Old = 1:2 或 1:3
- ❌ **误区 3:"GC 线程越多越好"**
  - GC 线程占 CPU,业务线程抢 CPU
  - 一般 GC 线程数 = CPU 核数 / 2 或 / 4

## 3.1 JMM(Java 内存模型,Java Memory Model)三性

> **痛点场景**:单线程下代码按你写的顺序执行。多线程下,A 线程写入 x=1,B 线程读到 x=0。为什么?因为**可见性**问题。JMM 就是为了解决"多线程下,谁能看到谁的写入、看到什么顺序"。

### 3.1.1 三性:原子性 / 可见性 / 有序性

```
JMM 三性:

① 原子性 Atomicity
   一个操作要么全部完成,要么全部不做
   例子:i++ 实际是"读 i → +1 → 写 i"3 步,不是原子操作
        如果两个线程同时 i++,可能结果不对
   保证:synchronized / Lock / AtomicXxx(CAS)

② 可见性 Visibility
   一个线程对共享变量的写入,其他线程能立刻看到
   问题:每个线程有自己的工作内存(CPU 缓存),写入先在工作内存,不一定立刻刷回主内存
   保证:volatile / synchronized / final

③ 有序性 Ordering
   程序的执行顺序按代码先后
   问题:编译器和 CPU 为了优化会做指令重排
   保证:volatile(禁止重排) / happens-before 规则
```

### 3.1.2 happens-before(发生在前)规则

> **核心认知**:happens-before **不是**时间先后,而是"逻辑可见性"——A happens-before B 表示 A 的结果对 B 可见,但 A 可能在 B 之后执行(编译器可以重排,只要结果等价)。

```
happens-before 8 条规则(必背,面试必问):

① 程序顺序规则(Program Order Rule)
   同一个线程内,前面的操作 happens-before 后面的操作
   (但允许编译器重排,只要结果等价——as-if-serial 语义)

② 监视器锁规则(Monitor Lock Rule)
   解锁 unlock happens-before 加锁 lock
   (保证 synchronized 块内的修改对下一个进入的线程可见)

③ volatile 变量规则(Volatile Variable Rule)
   写 volatile happens-before 读 volatile
   (保证 volatile 写之前的所有修改,对读 volatile 之后的线程可见)

④ 线程启动规则(Thread Start Rule)
   Thread.start() happens-before 新线程内的任何操作
   (主线程在 start() 之前的写入,对新线程可见)

⑤ 线程终止规则(Thread Termination Rule)
   线程内的任何操作 happens-before 检测到该线程终止
   (Thread.join() / Thread.isAlive() 返回 false 时,线程内的修改对调用方可见)

⑥ 中断规则(Thread Interruption Rule)
   调用 interrupt() happens-before 被中断线程检测到中断
   (Thread.interrupted() / InterruptedException / isInterrupted())

⑦ 终结器规则(Finalizer Rule)
   构造函数完成 happens-before finalize()
   (保证对象初始化对 finalize 可见)

⑧ 传递性(Transitivity)
   A happens-before B,B happens-before C,则 A happens-before C
```

> 🔑 **金句**:happens-before 是逻辑可见性,不是时间先后。8 条规则里最重要的是 ② (synchronized 解锁→加锁)和 ③ (volatile 写→读)——这 2 条是并发编程最常用的可见性保证。

### 3.1.3 重排的物理根因:Store Buffer + Invalidate Queue

> **为什么需要内存屏障?** 因为 CPU 硬件层有 Store Buffer(写缓冲)和 Invalidate Queue(失效队列),它们会让"看起来已完成的写入"在其他核看不到。

```
Store Buffer + Invalidate Queue 示意:

核 A 写 x=1:
  ① 写 Store Buffer(A 私有的)
  ② 发 Invalidate 消息给其他核,要求作废 x 的缓存副本
  ③ 其他核把 x 放入 Invalidate Queue(异步处理)
  ④ 其他核真正处理 Invalidate Queue 时,x 在其他核才真正失效

核 B 读 x:
  如果 B 还没处理 Invalidate Queue,会读到旧的 x( stale read)

内存屏障 Memory Barrier 的作用:
  ① StoreStore Barrier:确保前面的写都写入缓存(在 volatile 写之前)
  ② StoreLoad Barrier:确保写可见 + 失效其他核的缓存(在 volatile 写之后)
  ③ LoadLoad Barrier:确保读最新值(在 volatile 读之后)
  ④ LoadStore Barrier:确保读不被后面的写重排(在 volatile 读之后)

所以 volatile 的实现:
  写 volatile:插入 StoreStore + StoreLoad 屏障(强制刷新到主内存)
  读 volatile:插入 LoadLoad + LoadStore 屏障(强制从主内存读)
```

> 🔑 **金句**:volatile 的可见性底层靠内存屏障实现——写前插 StoreStore,写后插 StoreLoad(最昂贵),读后插 LoadLoad + LoadStore。这就是 volatile 比普通变量慢的原因。

## 3.2 volatile:可见性 + 禁止重排,**不保证原子性**

### 3.2.1 三个核心事实

```
volatile 的 3 个事实:

① 保证可见性
   写 volatile → 立刻刷到主内存
   读 volatile → 立刻从主内存读
   → 其他线程能看到最新值

② 禁止指令重排
   volatile 前后插入内存屏障(见 3.1.3)
   → 编译器和 CPU 不能把 volatile 操作和前后操作重排

③ 不保证原子性(必须记住!)
   i++ 不是原子操作(读 → +1 → 写 三步)
   即使 i 是 volatile,两个线程同时 i++ 还是可能丢更新
   解决:AtomicInteger(CAS 实现)或 synchronized
```

### 3.2.2 经典案例:DCL(双重检查锁)单例必须 volatile

```java
// DCL 单例(Double-Checked Locking)
public class Singleton {
    private static volatile Singleton INSTANCE;  // ⚠️ 必须 volatile

    public static Singleton getInstance() {
        if (INSTANCE == null) {                    // 第一次检查(无锁)
            synchronized (Singleton.class) {
                if (INSTANCE == null) {            // 第二次检查(有锁)
                    INSTANCE = new Singleton();    // ⚠️ 这一步有 3 个原子操作
                }
            }
        }
        return INSTANCE;
    }
}
```

**为什么 INSTANCE 必须 volatile?**

```
new Singleton() 这行的 3 个原子操作:
  ① 分配内存空间
  ② 初始化对象(调用构造函数)
  ③ 让 INSTANCE 引用指向分配的内存地址

如果没 volatile,编译器/CPU 可能重排为 ①③②:
  ① 分配内存
  ③ INSTANCE 指向内存(此时对象未初始化!)
  ② 初始化对象

并发场景:
  线程 A 执行到 ①③(还没执行 ②)
  线程 B 进入 getInstance(),看到 INSTANCE != null(因为 ③ 已执行)
  线程 B 直接使用 INSTANCE → 拿到一个未初始化的半对象 → NPE 或诡异 bug

加了 volatile:
  禁止 ①③② 重排,强制 ①②③ 顺序执行
  线程 B 看到 INSTANCE != null 时,对象一定初始化完成
```

> 🔑 **金句**:DCL 单例必须 volatile,因为 new 操作的"分配内存→初始化→赋值引用"三步可能被重排,导致其他线程拿到半初始化对象。volatile 禁止重排,保证安全。

## 3.3 synchronized 锁升级 4 级链路(纠正你的错误)

**你之前的错误**:漏了偏向锁,只说 3 级。

**正确的 4 级链路**:

```
锁升级链路(强度递增):

无锁 → 偏向锁 → 轻量级锁 → 重量级锁
                                  ↑
                             (JDK 15 默认关闭偏向锁,JDK 18 移除)

每级对应的底层结构(对象头 Mark Word):

Mark Word = 对象头的第一个 64 位(JDK 8)
  ┌──────────────────────────────────────────────────────────────────┐
  │ Mark Word (64 bits)                                             │
  ├──────────────────────────────────────────────────────────────────┤
  │ 无锁:    unused | hashcode(31) | unused(1) | age(4) | 01(2)    │
  │ 偏向锁:  threadId(54) | epoch(2) | age(4) | 1 | 01(2)         │
  │ 轻量锁:  ptr_to_lock_record(62) | 00(2)                        │
  │ 重量锁:  ptr_to_heavyweight_monitor(62) | 10(2)                │
  │ GC 标记: 空 | 11(2)                                             │
  └──────────────────────────────────────────────────────────────────┘

注意:后 2 位是锁状态标志位
  01 = 无锁 / 偏向锁(靠前 1 位区分,偏向锁时第 3 位=1)
  00 = 轻量级锁
  10 = 重量级锁
```

**每级的升级场景**:

```
① 无锁 → 偏向锁
   第一个线程用 synchronized 进入同步块
   → Mark Word 存储线程 ID(偏向该线程)
   → 该线程下次进入,只需比较 Mark Word 的线程 ID == 自己 → 无锁直接进入

② 偏向锁 → 轻量级锁
   第二个线程来竞争 → 偏向锁失效
   → 撤销偏向(等到安全点 SafePoint)
   → 升级为轻量级锁(自旋锁)
   → 两个线程用 CAS 自旋竞争

③ 轻量级锁 → 重量级锁
   自旋次数超过阈值(自适应自旋,默认约 10 次)或等待线程数超过阈值
   → 升级为重量级锁
   → 依赖 OS 的 Mutex Lock,线程阻塞/唤醒需要内核态切换

升级是单向的,不能降级!
(只有 GC 时才会重置为无锁)
```

**偏向锁在 JDK 15 默认关闭、JDK 18 移除**:
- 偏向锁撤销需要 SafePoint(整个 JVM 暂停),代价大
- 现代应用并发模式复杂,偏向命中率低,维护成本高
- OpenJDK 决定废弃

> 🔑 **金句**:synchronized 锁升级 4 级:无锁 → 偏向(单线程优化)→ 轻量(CAS 自旋)→ 重量(OS Mutex,线程阻塞)。JDK 15 默认关闭偏向,JDK 18 移除偏向锁。Mark Word 后 2 位是锁状态标志位:01=无锁/偏向,00=轻量,10=重量。

## 3.4 AQS(AbstractQueuedSynchronizer)—— 纠错 + 详解

**你之前的错误**:把 AQS 当成 mark word(对象头)。**完全错了!**

- **mark word** = synchronized 用的,存在对象头
- **AQS** = ReentrantLock / CountDownLatch / Semaphore 等并发工具的底层框架

```
AQS 本质 = volatile int state + CLH 双向队列

┌─────────────────────────────────────────────────────────────────┐
│ AQS 内部结构(以 ReentrantLock 为例)                              │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  volatile int state;   // 同步状态                              │
│                        // ReentrantLock:0=未锁,>=1=锁重入次数   │
│                        // Semaphore:可用许可数                   │
│                        // CountDownLatch:剩余计数值              │
│                                                                 │
│  transient Node head;  // CLH 队列头(dummy 节点)               │
│  transient Node tail;  // CLH 队列尾                            │
│                                                                 │
│  CLH 双向队列(变体,有 dummy 头节点):                            │
│                                                                 │
│  head(dummy) ←→ Thread A(waitStatus=-1) ←→ Thread B ←→ tail  │
│       ↑              ↑等待中,前驱是 SIGNAL 就尝试获取           │
│   (不真正排队,        (每个节点有 waitStatus:                    │
│    仅占位)            SIGNAL=-1 前驱唤醒我                       │
│                      CANCELLED=1 取消                           │
│                      CONDITION=-2 在条件队列)                    │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 3.4.1 ReentrantLock 的 AQS 应用

```java
ReentrantLock lock = new ReentrantLock();
lock.lock();
try {
    // 临界区
} finally {
    lock.unlock();
}

lock() 内部:
  1. 尝试 CAS 把 state 从 0 改为 1
  2. 成功 → 独占锁,记录当前线程(Exclusively Owned)
  3. 失败 → 看是不是自己重入(state 已 >= 1 且持有者是自己)
     → 是:state++(可重入)
     → 不是:把自己封装成 Node 加入 CLH 队列尾部
     → 在队列里自旋或 park(线程挂起,等待唤醒)

unlock() 内部:
  1. state-- (0 = 完全释放)
  2. 唤醒队列头的下一个节点(unpark)
```

### 3.4.2 AQS 的两种模式

```
AQS 两种共享模式:

① 独占模式 Exclusive(同一时刻只有一个线程持有)
   ReentrantLock / ReentrantReadWriteLock 的写锁
   state 语义:重入次数(0=未锁,>=1=持锁)

② 共享模式 Shared(多个线程可同时持有)
   Semaphore / CountDownLatch / ReentrantReadWriteLock 的读锁
   state 语义:可用许可数(Semaphore 初始=最大许可数)

AQS 子类化要重写的方法:
  tryAcquire(int)            // 独占:尝试获取,成功返回 true
  tryRelease(int)            // 独占:尝试释放
  tryAcquireShared(int)      // 共享
  tryReleaseShared(int)      // 共享
  isHeldExclusively()        // 是否被当前线程独占
```

### 3.4.3 AQS vs synchronized

```
对比:
  维度                synchronized            AQS(ReentrantLock)
  实现层              JVM 内置(monitorenter)  Java API
  锁升级              4 级(无锁→偏向→轻量→重量)  直接 fair/nonfair
  可中断              不能                      lockInterruptibly()
  超时                不能                      tryLock(time)
  公平                非公平                    可选 fair/nonfair
  条件变量            单条件(synchronized 块)   多条件(newCondition())
  性能                JDK 6+ 优化后接近         略高(避免 JVM 切换)

选型建议:
  默认用 synchronized(JVM 会自动优化,代码简单)
  需要可中断/超时/公平/多条件 时用 ReentrantLock
```

> 🔑 **金句**:AQS = volatile int state + CLH 双向队列,是 ReentrantLock / Semaphore / CountDownLatch 的底层框架。state 在不同类里语义不同(重入次数/许可数/计数值)。AQS 不是 mark word,mark word 是 synchronized 用的对象头,AQS 是 java.util.concurrent 包的底层。

## 3.5 线程池(纠错 + 实战)—— 你的核心硬伤

**你之前的错误**:线程池调度顺序"核心 → 非核心 → 队列"。**实际是"核心 → 队列 → 非核心 → 拒绝"**。这个顺序搞反在面试中会被直接判定"基础不牢"。

### 3.5.1 线程池 7 个参数

```java
public ThreadPoolExecutor(
    int corePoolSize,          // 核心线程数(即使空闲也不回收,除非 allowCoreThreadTimeOut)
    int maximumPoolSize,       // 最大线程数(核心 + 非核心)
    long keepAliveTime,        // 非核心线程空闲存活时间
    TimeUnit unit,             // 时间单位
    BlockingQueue<Runnable> workQueue,  // 任务队列
    ThreadFactory threadFactory,        // 线程工厂(给线程命名,方便排查)
    RejectedExecutionHandler handler    // 拒绝策略
)
```

### 3.5.2 任务调度顺序(必须记牢!)

```
当一个任务通过 execute(Runnable) 提交时:

   ┌───────────────────────────────────┐
   │ 当前工作线程数 < corePoolSize?    │
   └──────────────┬────────────────────┘
                  │
          ┌───────┴───────┐
          │是             │否
          ↓               ↓
   创建核心线程    ┌───────────────────────────┐
   执行任务       │ 队列满了吗?                │
                  └─────┬──────────┬──────────┘
                        │否        │是
                        ↓          ↓
                 任务入队    ┌───────────────────────────┐
                            │ 当前工作线程数 < maxPool? │
                            └─────┬──────────┬──────────┘
                                  │是        │否
                                  ↓          ↓
                          创建非核心线程   执行拒绝策略
                          执行任务        (默认 AbortPolicy 抛异常)

关键要点:
  ① 队列没满,不会创建非核心线程
     所以 maxPoolSize 在"队列无界"时等于 corePoolSize(非核心永远不会创建)
  ② 这就是为什么 Executors.newFixedThreadPool 用的是 LinkedBlockingQueue 无界队列
     → 永远不会触发创建非核心线程
     → 队列无限增长 → OOM
  ③ 这就是为什么 Executors 系列工厂方法被禁用(阿里规约强制)
```

**记忆口诀**:"核心先来,满了入队,队列满开非核心,都满了就拒绝"。

### 3.5.3 4 种拒绝策略

```
① AbortPolicy(默认):抛 RejectedExecutionException 异常
② CallerRunsPolicy:让提交任务的线程(调用方)自己执行(降级方案,削峰)
③ DiscardPolicy:直接丢弃任务,不抛异常
④ DiscardOldestPolicy:丢弃队列最老的任务,重试提交新的

生产常用:CallerRunsPolicy(降级)或 自定义拒绝策略(记日志 + 监控告警)
```

### 3.5.4 Executors 为什么禁用?

```java
// ❌ 禁用:Executors.newFixedThreadPool
ExecutorService pool = Executors.newFixedThreadPool(10);
// 内部:new ThreadPoolExecutor(10, 10, 0L, TimeUnit.MILLISECONDS,
//                              new LinkedBlockingQueue<Runnable>());
// 问题:LinkedBlockingQueue 是无界队列(Integer.MAX_VALUE)
// 任务堆积 → 队列无限增长 → OOM

// ❌ 禁用:Executors.newCachedThreadPool
ExecutorService pool = Executors.newCachedThreadPool();
// 内部:new ThreadPoolExecutor(0, Integer.MAX_VALUE, 60L, TimeUnit.SECONDS,
//                             new SynchronousQueue<Runnable>());
// 问题:maximumPoolSize = Integer.MAX_VALUE
// 任务提交快 → 创建大量线程 → OOM(线程栈占用)

// ❌ 禁用:Executors.newSingleThreadExecutor
// 内部也是无界队列 LinkedBlockingQueue,同样 OOM 风险

// ✅ 正确:直接 new ThreadPoolExecutor,参数自己定
ThreadPoolExecutor pool = new ThreadPoolExecutor(
    10,                          // 核心 10
    20,                          // 最大 20(核心 + 10 非核心)
    60L, TimeUnit.SECONDS,       // 非核心 60s 空闲回收
    new ArrayBlockingQueue<>(1000),  // 有界队列,容量 1000
    new ThreadFactoryBuilder().setNameFormat("order-pool-%d").build(),  // 命名
    new ThreadPoolExecutor.CallerRunsPolicy()  // 拒绝策略:降级到调用方执行
);
```

> 🔑 **金句**:Executors 工厂方法禁用——newFixedThreadPool / newSingleThreadExecutor 用无界队列(OOM 风险),newCachedThreadPool 用无界最大线程数(OOM 风险)。生产必须直接 new ThreadPoolExecutor 自定参数。

### 3.5.5 线程数配置

```
经验公式(不要死记,业务决定):
  CPU 密集型(CPU 占用高):线程数 = CPU 核数 + 1
    解释:多出的 1 个线程应对偶发的 page fault(缺页中断)等阻塞
  IO 密集型(IO 占用高):线程数 = CPU 核数 × 2 或 × (1 + IO/CPU 时间比)
    解释:线程大部分时间在等 IO,CPU 空闲可以跑更多线程

实际生产:
  通过压测(全链路)确定最优值
  不是靠公式,因为业务 IO 比例不同
  推荐:初始 = 公式值,压测后调整
  动态调整:阿 dynamicTp 或美团技术团的动态线程池方案(配置中心热更新)
```

### 3.5.6 任务提交:execute vs submit

```java
// execute:无返回值,异常直接抛出
pool.execute(() -> {
    orderService.createOrder();  // 抛异常 → 直接打印
});

// submit:有返回值(Future),异常被 Future 吞掉
Future<?> future = pool.submit(() -> {
    orderService.createOrder();  // 抛异常 → 异常被吞
});
future.get();  // 调用 get() 才抛 ExecutionException

⚠️ 坑:submit 不 get(),异常就丢了!排查问题时"任务静默失败"。
解决:
  ① 调用 get()
  ② 重写 afterExecute 钩子:
     protected void afterExecute(Runnable r, Throwable t) {
         super.afterExecute(r, t);
         if (t == null && r instanceof Future<?>) {
             try { ((Future<?>) r).get(); }
             catch (ExecutionException ex) { t = ex.getCause(); }
             catch (Exception ignored) { }
         }
         if (t != null) logger.error("pool task failed", t);
     }
```

## 3.6 CompletableFuture 实战(面试必写代码)

> **痛点**:多线程任务编排(比如查订单详情 + 查用户信息 + 查库存 + 查优惠,然后汇总),手写 Future.get() + 线程池 代码会乱成毛线。CompletableFuture 提供链式 API 编排异步任务。

### 3.6.1 核心 API 一图流

```
CompletableFuture 关键 API 分类:

创建阶段:
  CompletableFuture.supplyAsync(() -> result)  // 有返回值
  CompletableFuture.runAsync(() -> {})         // 无返回值
  new CompletableFuture<>()                    // 手动控制

链式处理(任务完成后做什么):
  thenApply(fn)          // 接一个同步转换(T → U),有返回值
  thenAccept(consumer)   // 接一个消费(T),无返回值
  thenRun(runnable)      // 接一个纯动作,不用上个任务结果
  thenCompose(fn)        // 接另一个 CompletableFuture(扁平化,避免嵌套)
  thenCombine(other, fn) // 和另一个 CF 合并结果

组合多任务:
  allOf(cf1, cf2, cf3)   // 全部完成
  anyOf(cf1, cf2, cf3)   // 任一完成

异常处理:
  exceptionally(fn)      // 出异常时兜底(T 兜底)
  handle(fn)             // 正常/异常都能处理
  whenComplete(consumer) // 完成时回调(正常/异常都能拿到,但不能改结果)
```

### 3.6.2 订单详情页场景(工业级代码)

```java
// 业务:订单详情页需要并发查询 4 个下游服务,然后汇总
public OrderDetailVO getOrderDetail(Long orderId) {
    // 自定义线程池(避免用 ForkJoinPool.commonPool)
    ExecutorService bizPool = ...;

    // 并发查询 4 个服务
    CompletableFuture<Order> orderFuture = CompletableFuture.supplyAsync(
        () -> orderService.getById(orderId), bizPool);

    CompletableFuture<User> userFuture = orderFuture.thenApplyAsync(
        order -> userService.getById(order.getUserId()), bizPool);

    CompletableFuture<List<Product>> productFuture = orderFuture.thenApplyAsync(
        order -> productService.batchGet(order.getProductIds()), bizPool);

    CompletableFuture<Coupon> couponFuture = CompletableFuture.supplyAsync(
        () -> couponService.getBest(orderId), bizPool);

    // 合并结果(4 个全部完成)
    CompletableFuture<OrderDetailVO> detailFuture = userFuture
        .thenCombine(productFuture, (user, products) -> {
            return new UserProductsHolder(user, products);
        })
        .thenCombine(couponFuture, (holder, coupon) -> {
            Order order = orderFuture.join();  // join() 阻塞取结果
            return assembleVO(order, holder.user, holder.products, coupon);
        });

    // 设置超时(防止死等)
    try {
        return detailFuture.get(3, TimeUnit.SECONDS);
    } catch (TimeoutException e) {
        throw new ServiceTimeoutException("order detail query timeout");
    }
}
```

### 3.6.3 默认 ForkJoinPool.commonPool 的坑

```java
CompletableFuture.supplyAsync(() -> ...);  // 没传 Executor → 用 commonPool

问题:
  ① commonPool 线程数 = CPU 核数 - 1
     IO 密集型任务 → 线程不够 → 任务排队 → RT 飙升
  ② commonPool 是全局共享
     你的慢任务会把别人的任务拖慢
  ③ 异常传播难追踪

解决:
  永远传自定义线程池:
  CompletableFuture.supplyAsync(() -> ..., myPool);
```

> 🔑 **金句**:CompletableFuture 永远传自定义线程池,不要用 ForkJoinPool.commonPool——线程数默认 = CPU-1( IO 密集不够用)、全局共享(互相影响)。链式编排优先 thenCompose(扁平化)、thenCombine(合并),异常用 exceptionally 兜底。

## 3.7 并发工具 3 件套(CountDownLatch / CyclicBarrier / Semaphore)

```
三个并发工具的对比:

工具                    用途                     是否可复用
CountDownLatch          一次性倒数,等别人       不可复用
CyclicBarrier           互相等,到齐了一起走      可复用(cyclic)
Semaphore               限流,允许 N 个并发      可复用

场景:
  CountDownLatch:
    主任务等 N 个子任务完成(比如启动时预加载 10 个缓存)
    模拟:火箭发射前等所有系统就绪

  CyclicBarrier:
    多线程互相等到齐再一起干(比如多线程模拟测试,要同时起跑)
    模拟:马拉松起跑线(所有人到齐后鸣枪一起跑)

  Semaphore:
    限流,同时只允许 N 个线程访问某资源
    模拟:停车场(只有 100 个车位,满了就得等)
```

### 3.7.1 CountDownLatch 实战

```java
// 业务:订单服务启动时并发预热 10 个 Redis 缓存
CountDownLatch latch = new CountDownLatch(10);
ExecutorService pool = ...;

for (String key : hotKeys) {
    pool.submit(() -> {
        try {
            redis.set(key, loadFromDB(key));
        } finally {
            latch.countDown();  // 完成一个减 1
        }
    });
}

latch.await();  // 主线程阻塞,等所有子线程完成
logger.info("缓存预热完成");
```

### 3.7.2 Semaphore 实战

```java
// 业务:限流,同时最多 10 个线程查外部接口(保护下游)
Semaphore semaphore = new Semaphore(10);

public ExternalResponse queryExternal(Request req) {
    try {
        semaphore.acquire();  // 拿不到许可就阻塞
        try {
            return httpClient.call(req);
        } finally {
            semaphore.release();  // 用完释放
        }
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
    }
}
```

**坑 1:ThreadLocal 泄漏**

```java
// 业务:拦截器存用户上下文,用 ThreadLocal
public class UserContext {
    private static final ThreadLocal<User> CTX = new ThreadLocal<>();

    public static void set(User user) { CTX.set(user); }
    public static User get() { return CTX.get(); }
    public static void clear() { CTX.remove(); }  // ⚠️ 必须调用
}

// 拦截器
public class AuthInterceptor implements HandlerInterceptor {
    @Override
    public boolean preHandle(...) {
        UserContext.set(loginUser);
        return true;
    }
    @Override
    public void afterCompletion(...) {
        UserContext.clear();  // ⚠️ 必须清理!
    }
}

// 为什么必须清理?
// Tomcat 线程池复用,线程 A 处理完用户张三的请求,没清理 CTX
// 下一次线程 A 处理用户李四的请求,get() 拿到张三 → 串号事故
// 而且 CTX 是强引用,线程不销毁,CTX 引用的对象也不回收 → 内存泄漏
```

**坑 2:CompletableFuture 异常被吞**

```java
// 见 3.6.4 节的 afterExecute 钩子
// 关键:get() 才抛异常,不 get 就丢了

// 另一个坑:thenApply 链里某一步抛异常,后续所有步骤都被跳过

    });
```

## 3.9 面试连环追问

**Q1. AQS 和 synchronized 的区别?**

**答**:
- **实现层**:synchronized 是 JVM 内置(monitorenter/monitorexit 字节码),AQS 是 Java API 层(jdk 源码实现)。
- **锁升级**:synchronized 有 4 级锁升级(无锁→偏向→轻量→重量),AQS 的 ReentrantLock 直接 fair 或非 fair。
- **功能扩展**:AQS 支持可中断锁(lockInterruptibly)、超时锁(tryLock)、多条件变量(newCondition)、公平锁; synchronized 不支持。
- **性能**:JDK 6 后 synchronized 有锁升级优化,性能接近 AQS;但高竞争场景 ReentrantLock 略优。
- **选型**:默认用 synchronized(简单),需要高级特性用 ReentrantLock。

**Q2. 线程池最大线程数怎么设?**

**答**(标准答案):
- 不是固定公式,要**压测**:
  - CPU 密集:初始 = CPU 核数 + 1
  - IO 密集:初始 = CPU 核数 × 2 或按 (1 + IO 时间 / CPU 时间) 计算
- 但实际业务千差万别,最终**靠压测**:
  - 压测工具:JMeter/wrk
  - 看 QPS、RT、CPU 利用率、GC 情况
  - 调到 CPU 利用率 70-80% 且 RT 在 SLA 内的值
- 推荐用**动态线程池**(美团技术方案 / dynamicTp 开源),配置中心热更新,不用重启

**Q3. 线程池的队列怎么选?**

**答**:
- **有界 vs 无界**:
  - 有界(ArrayBlockingQueue):容量固定,满了拒绝 → 保护系统(推荐)
  - 无界(LinkedBlockingQueue):容量 Integer.MAX_VALUE → 任务堆积 OOM 风险
- **FIFO vs LIFO vs 优先级**:
  - ArrayBlockingQueue / LinkedBlockingQueue:FIFO 默认
  - PriorityBlockingQueue:按优先级出队
  - SynchronousQueue:不存储,直接 hand-off(适合 CachedThreadPool)
  - DelayQueue:延迟任务(定时任务场景)
- **生产建议**:默认 ArrayBlockingQueue(有界、性能略高),需要公平用 LinkedBlockingQueue

**Q4. CompletableFuture 的 thenApply 和 thenCompose 区别?**

**答**:
- **thenApply(fn)**:同步转换,T → U,fn 返回 U。类似 Stream.map。
- **thenCompose(fn)**:扁平化,fn 返回 CompletableFuture<U>。类似 Stream.flatMap。
- **什么时候用 thenCompose?**:fn 本身是异步操作(内部有线程池、IO、DB 查询)。
  - 用 thenApply → 拿到 CompletableFuture<CompletableFuture<U>> 嵌套了
  - 用 thenCompose → 扁平化成 CompletableFuture<U>
- 例:
  ```java
  CompletableFuture<User> user = ...;
  // ❌ 用 thenApply 拿嵌套
  CompletableFuture<CompletableFuture<Order>> nested =
      user.thenApply(u -> orderService.asyncGetByUser(u.getId()));
  // ✅ 用 thenCompose 扁平化
  CompletableFuture<Order> flat =
      user.thenCompose(u -> orderService.asyncGetByUser(u.getId()));
  ```

**Q5. volatile 为什么不保证原子性?**

**答**:
- volatile 只保证可见性(写立刻刷主内存)和有序性(禁止重排)。
- 但 `i++` 是 3 步操作(读 i → +1 → 写 i),volatile 不把这 3 步打包成原子操作。
- 两个线程同时 i++,可能读到同一个旧值,各自 +1,写回,丢失一次更新。
- 解决:AtomicInteger(CAS 实现),或 synchronized。

**Q6. 线程池如何平滑关闭?**

**答**:
```java
// 正确关闭姿势:
public void shutdownGracefully(ExecutorService pool) {
    pool.shutdown();  // 不再接受新任务,但已提交任务继续执行
    try {
        if (!pool.awaitTermination(60, TimeUnit.SECONDS)) {
            // 60s 内没结束,强制关闭
            pool.shutdownNow();  // 发送 interrupt 信号
            if (!pool.awaitTermination(60, TimeUnit.SECONDS)) {
                logger.error("pool did not terminate");
            }
        }
    } catch (InterruptedException e) {
        pool.shutdownNow();
        Thread.currentThread().interrupt();
    }
}

// 坑:shutdownNow 不保证任务真的停止
// 任务里要响应 interrupt:
//   if (Thread.interrupted()) throw new InterruptedException();
//   或者用 while (!Thread.currentThread().isInterrupted()) 循环
```

# 主题 4 · Spring 事务(本质 + 传播 + 失效)

> **为什么学这个**:后端架构师面试,Spring 事务几乎 100% 会问。不是考你写 `@Transactional`,而是考你**知道底层怎么实现的、踩过什么坑**。你当前 40 分,**最大硬伤是"把 @Transactional 当成 MySQL 引擎层的 redo/undo log"**——这是根本错误,必须先纠正。

## 4.0 先纠正最大硬伤

| ❌ 你之前的错误认知 | ✅ 正确认知 |
|-------------------|------------|
| `@Transactional` 本质是 MySQL 引擎层的 redo/undo log | `@Transactional` 本质是 **Spring AOP 动态代理 + PlatformTransactionManager**,和 MySQL 引擎层是**两个独立的事务体系** |

**理解这个区分是理解 Spring 事务一切问题的起点**。

---

## 4.1 Spring 三层事务体系(必须先分清)

```
Spring 事务 3 层(不要混在一起!):

┌─────────────────────────────────────────────────────────────┐
│ ① Spring 声明式事务(Spring Framework 层)                      │
│    @Transactional 注解 + AOP 动态代理                        │
│    通过 PlatformTransactionManager 接口抽象                  │
│    业务代码里看不到任何事务 API                                │
├─────────────────────────────────────────────────────────────┤
│ ② Spring 编程式事务(Spring Template 层)                      │
│    TransactionTemplate / JpaTransactionManager              │
│    手动 begin/commit/rollback                                │
│    适合局部事务(某段代码需要精细控制)                          │
├─────────────────────────────────────────────────────────────┤
│ ③ 底层数据库事务(MySQL / PostgreSQL 等)                       │
│    InnoDB 的 redo log + undo log + MVCC + 锁                │
│    ACID 的物理基础                                           │
│    Spring 事务管理器最终通过 JDBC 调用底层数据库事务           │
└─────────────────────────────────────────────────────────────┘

关键认知:
  ① @Transactional 是 Spring 层的抽象,不直接操作 redo/undo log
  ② Spring 事务管理器最终会调用 JDBC 的 Connection.setAutoCommit(false)
     + commit() / rollback(),这才到底层数据库事务
  ③ 所以 @Transactional 的本质是"Spring AOP 在方法前后做 setAutoCommit/commit/rollback",
     不是"直接写 redo/undo log"

为什么这个区分重要?
  因为很多坑都是"以为 Spring 事务 == 数据库事务"导致的:
  ① 自调用失效(以为标了 @Transactional 就一定有事务)
  ② 跨方法传播搞错(以为 REQUIRES_NEW 是数据库层面)
  ③ 非 Spring 管理的连接池失效(比如手动 DriverManager.getConnection)
```

## 4.2 @Transactional 的本质:AOP 动态代理

### 4.2.1 实现机理

```
@Transactional 的底层执行流程:

1. 编译期/Spring 启动期:
   Spring 扫描到 OrderService.createOrder() 有 @Transactional 注解
   → 生成代理对象(通过 AOP)

2. 代理方式(两种):
   ① JDK 动态代理:目标类实现了接口
      Proxy.newProxyInstance(classLoader, interfaces, invocationHandler)
   ② CGLIB 代理:目标类没实现接口
      生成目标类的子类,重写方法

3. 调用流程:
   业务代码调用 orderService.createOrder(...)
   ↓
   实际调用的是代理对象的 createOrder()
   ↓
   代理对象执行 TransactionInterceptor.invoke():
   ① 获取事务属性(@Transactional 的 propagation/isolation/rollbackFor 等)
   ② 获取 PlatformTransactionManager(通常是 DataSourceTransactionManager)
   ③ transactionManager.getTransaction()
      → 从 DataSource 拿 Connection
      → Connection.setAutoCommit(false)  // 关键!禁用自动提交
      → 返回 TransactionStatus(事务状态)
   ④ try {
         执行目标方法(target.createOrder)  // 业务代码
         transactionManager.commit(status);  // 成功 → Connection.commit()
      } catch (RuntimeException ex) {
         transactionManager.rollback(status);  // 异常 → Connection.rollback()
         throw ex;
      }

这就是 @Transactional 的全部本质:
  开事务 = Connection.setAutoCommit(false)
  提交   = Connection.commit()
  回滚   = Connection.rollback()

注意:
  ① 事务真正生效的是数据库连接(Connection),不是 Spring 层
  ② Spring 只是帮你管理"何时开事务/何时提交/何时回滚"
  ③ 所以"同一个 Connection"的事务才能保证 ACID
  ④ 跨方法传播(比如 A 调 B,都用 @Transactional),靠的是"同一个 Connection"
     在 ThreadLocal 里传递
```

### 4.2.2 Spring 事务管理器体系

```
PlatformTransactionManager 接口(顶层抽象):

interface PlatformTransactionManager {
    TransactionStatus getTransaction(TransactionDefinition definition);
    void commit(TransactionStatus status);
    void rollback(TransactionStatus status);
}

常见实现:
  DataSourceTransactionManager        JDBC 数据源(最常用)
  JpaTransactionManager               JPA
  HibernateTransactionManager         Hibernate
  JtaTransactionManager               JTA(跨数据源分布式事务)
  ChainedTransactionManager           多数据源链式事务

Spring Boot 自动配置:
  配了 spring.datasource → 自动注入 DataSourceTransactionManager
  配了 spring.jpa → 自动注入 JpaTransactionManager
  配了多个数据源 → 需要手动声明哪个是 @Primary
```

## 4.3 传播行为 7 种(必背)

> **痛点场景**:订单服务 A 方法标 @Transactional,A 调用 B 方法也标 @Transactional。B 是挂起 A 的事务?还是加入 A 的事务?还是新建事务?——这就是传播行为。

```
7 种传播行为(Propagation):

┌──────────────────────────────────────────────────────────────────┐
│ 行为                   │ 含义                    │ 使用场景      │
├──────────────────────────────────────────────────────────────────┤
│ ① REQUIRED(默认)       │ 加入当前事务,没事务就新建 │ 绝大多数场景  │
│ ② SUPPORTS             │ 有事务就加入,没就非事务执行│ 查询方法      │
│ ③ MANDATORY            │ 必须在事务中,否则抛异常  │ 强制上游有事务│
│ ④ REQUIRES_NEW         │ 总是新建,挂起当前事务   │ 独立子事务(日志)│
│ ⑤ NOT_SUPPORTED        │ 总是非事务,挂起当前事务 │ 不需要事务    │
│ ⑥ NEVER                │ 总是非事务,有事务就抛异常│ 强制上游无事务│
│ ⑦ NESTED               │ 有事务就嵌套(savepoint),没就新建│ 部分回滚│
└──────────────────────────────────────────────────────────────────┘

3 个最常用的详解:

① REQUIRED(默认):
  A 有事务,B 标 REQUIRED → B 加入 A 的事务
  A 抛异常回滚,B 也跟着回滚(同个 Connection,同个事务)
  A 没事务,B 标 REQUIRED → B 自己新建一个事务

② REQUIRES_NEW:
  A 有事务,B 标 REQUIRES_NEW → B 挂起 A 的事务,B 开新事务
  B 提交/回滚和 A 无关
  A 回滚,B 已经提交的不会回滚(独立事务)
  典型场景:记录操作日志(不管主业务成功失败,日志都要记)

  例:
  @Transactional
  public void createOrder(Order order) {
      orderDao.save(order);  // 主事务
      try {
          logService.recordLog(order);  // REQUIRES_NEW
          // 即使后面抛异常,日志已经提交
      } catch (Exception e) {
          // 忽略日志失败
      }
      if (someCondition) {
          throw new RuntimeException("业务失败");  // 回滚订单,但日志保留
      }
  }

  @Transactional(propagation = Propagation.REQUIRES_NEW)
  public void recordLog(Order order) {
      logDao.save(new OrderLog(order));
      // 新事务,和主事务独立
  }

③ NESTED:
  A 有事务,B 标 NESTED → B 在 A 的事务里开一个嵌套事务(savepoint)
  B 回滚,只回滚到 savepoint,A 的其他操作不受影响
  A 回滚,B 也跟着回滚(嵌套事务是 A 的子集)
  底层:JDBC Connection 的 savepoint 机制

  例:
  @Transactional
  public void batchCreateOrders(List<Order> orders) {
      for (Order o : orders) {
          try {
              singleOrderService.createSingle(o);  // NESTED
          } catch (Exception e) {
              // 单个订单失败,只回滚这个,其他继续
          }
      }
  }

  @Transactional(propagation = Propagation.NESTED)
  public void createSingle(Order order) {
      orderDao.save(order);
      // 失败时回滚到 savepoint,不影响外层
  }

REQUIRED vs NESTED 区别:
  REQUIRED:B 加入 A 的事务,B 抛异常,A 整个事务标记 rollback-only
          A 提交时会报 UnexpectedRollbackException
  NESTED: B 失败只回滚到 savepoint,A 可以继续提交
          但前提是数据库支持 savepoint(MySQL InnoDB 支持)
```

> 🔑 **金句**:Spring 事务 7 种传播行为,最常用 3 种:REQUIRED(默认,加入当前事务)、REQUIRES_NEW(挂起开新事务,独立子事务)、NESTED(嵌套事务,savepoint 部分回滚)。选传播行为 = 选"子方法和父方法的事务边界"。

## 4.4 失效的 7 种场景(架构师必背)

> **痛点场景**:明明标了 `@Transactional`,线上出了 bug 一看日志,事务没回滚。这是最常见的 Spring 事务坑。

```
@Transactional 失效 7 种场景(按可能性排序):

① 自调用(同类方法内调用) —— 最常见!
   原因:同类方法调用不走代理,直接 this.method(),事务切面没机会织入
   例:
   @Service
   public class OrderService {
       public void outer() {
           this.inner();  // ❌ 直接调用,绕过代理,事务失效
       }
       @Transactional
       public void inner() { ... }
   }
   解法:
     ① 注入自己(Autowired 注入自己,通过代理调用)
     ② AopContext.currentProxy()(需要 @EnableAspectJAutoProxy(exposeProxy=true))
     ③ 拆到另一个 Service(推荐)

② 方法非 public
   原因:Spring AOP 默认只代理 public 方法(底层 JDK Proxy / CGLIB 的限制)
   例:
   @Transactional
   private void createOrder() { ... }  // ❌ private 失效
   解法:改 public

③ 异常被吞
   原因:catch 里没抛出,事务管理器看不到异常,不会触发回滚
   例:
   @Transactional
   public void createOrder() {
       try {
           orderDao.save(order);
       } catch (Exception e) {
           log.error("...", e);  // ❌ 异常被吞,不会回滚
       }
   }
   解法:catch 后 throw,或 throw new RuntimeException(e)

④ rollbackFor 配置错误(默认只回滚 RuntimeException)
   原因:@Transactional 默认 rollbackFor = {RuntimeException.class, Error.class}
        业务抛 checked Exception(如 IOException / Exception)不会回滚
   例:
   @Transactional  // ❌ 默认不回滚 checked Exception
   public void createOrder() throws Exception {
       throw new Exception("失败");
   }
   解法:
     @Transactional(rollbackFor = Exception.class)  // ✅ 推荐,所有异常都回滚

⑤ 数据库引擎不支持事务
   原因:MySQL MyISAM 不支持事务(早期表引擎)
   例:CREATE TABLE xxx ENGINE=MyISAM
   解法:用 InnoDB(默认,MySQL 5.5+)

⑥ 多线程跨 Connection
   原因:@Transactional 用 ThreadLocal 存 Connection,新线程拿不到
   例:
   @Transactional
   public void createOrder() {
       new Thread(() -> orderDao.save(order)).start();  // ❌ 新线程,事务外
   }
   解法:避免在事务里起新线程做 DB 操作

⑦ 传播行为不支持
   原因:标了 SUPPORTS / NOT_SUPPORTED / NEVER 等
   例:
   @Transactional(propagation = Propagation.NOT_SUPPORTED)  // ❌ 强制非事务
   解法:改成 REQUIRED 或其他合适的传播行为
```

> 🔑 **金句**:`@Transactional` 失效 7 场景:自调用(走 this 不走代理)、非 public 方法、异常被吞、rollbackFor 错(默认只回滚 RuntimeException)、MyISAM 引擎、多线程跨 Connection、传播行为错。**生产铁律**:`@Transactional(rollbackFor = Exception.class)` 一行都不能少。

## 4.5 工业级最佳实践(可抄代码)

### 4.5.1 标准事务用法

```java
// ✅ 标准写法
@Service
public class OrderService {

    @Autowired
    private OrderDao orderDao;
    @Autowired
    private InventoryDao inventoryDao;

    @Transactional(rollbackFor = Exception.class)  // ⚠️ 必须加 rollbackFor
    public Order createOrder(CreateOrderRequest req) {
        // 1. 校验
        if (req.getAmount() <= 0) {
            throw new IllegalArgumentException("amount must > 0");
        }

        // 2. 业务
        Order order = new Order(req);
        orderDao.insert(order);

        // 3. 扣库存
        int affected = inventoryDao.deductStock(req.getProductId(), req.getQuantity());
        if (affected == 0) {
            throw new IllegalStateException("insufficient stock");  // RuntimeException,会回滚
        }

        return order;
    }
}

// ❌ 反模式 1:事务方法太大
@Transactional(rollbackFor = Exception.class)
public void processEverything() {
    // 包含 10+ 个 DB 操作 + 远程调用 + MQ 发送
    // 事务时间长 → 锁持有久 → 并发差 → 可能超时
}
// 解法:拆分事务,只把必要的 DB 操作包在事务里

// ❌ 反模式 2:事务里包含外部 IO
@Transactional(rollbackFor = Exception.class)
public void createOrder() {
    orderDao.save(order);
    httpClient.callPaymentService(order);  // ❌ 远程调用在事务里,HTTP 慢 → 事务长
    paymentDao.save(payment);
}
// 解法:外部 IO 放事务外,或用编程式事务精细控制
```

### 4.5.2 事务隔离级别(了解即可)

```
Spring 事务隔离级别(对应 MySQL 4 种):

隔离级别                    脏读  不可重复读  幻读
DEFAULT(默认,用数据库默认)  -     -          -
READ_UNCOMMITTED           允许   允许       允许
READ_COMMITTED             阻止   允许       允许  (Oracle 默认)
REPEATABLE_READ            阻止   阻止       允许  (MySQL 默认,InnoDB 用 MVCC+Next-Key 几乎解决幻读)
SERIALIZABLE               阻止   阻止       阻止  (性能差,基本不用)

Spring 的 @Transactional(isolation = Isolation.REPEATABLE_READ)
  默认用 Isolation.DEFAULT = 数据库默认(MySQL = RR)
  一般不改,除非特殊场景
```

### 4.5.3 事务只读优化

```java
@Transactional(readOnly = true)  // ✅ 查询方法加 readOnly
public List<Order> listOrders(Long userId) {
    return orderDao.findByUserId(userId);
}

// readOnly=true 的好处:
// ① 数据库层优化(InnoDB 对只读事务不加行锁,性能更好)
// ② Spring 层检查,如果 readOnly 事务里执行写操作会报错
// ③ 表达意图,代码可读性提升
```

### 4.5.4 编程式事务(精细控制)

```java
@Service
public class OrderService {
    @Autowired
    private TransactionTemplate txTemplate;  // Spring 自动注入

    public void complexFlow() {
        // 场景:只有部分操作需要事务

        // 第一段:非事务操作(远程调用,慢)
        UserInfo user = userClient.getUser(order.getUserId());

        // 第二段:事务操作(DB)
        Order order = txTemplate.execute(status -> {
            orderDao.save(order);
            inventoryDao.deductStock(order.getProductId(), order.getQuantity());
            return order;
        });

        // 第三段:非事务操作(MQ 发送)
        mqProducer.send(new OrderCreatedEvent(order));
    }
}
```

## 4.6 面试连环追问

**Q1. @Transactional 的本质是什么?**

**答**:
- @Transactional 本质是 **Spring AOP 动态代理 + PlatformTransactionManager 接口**。
- Spring 启动时扫描到注解,为目标类生成代理(JDK/CGLIB)。
- 调用方法时,代理的 TransactionInterceptor 先调用 `PlatformTransactionManager.getTransaction()` 拿 Connection,执行 `Connection.setAutoCommit(false)` 开事务;然后执行目标方法;最后根据有无异常执行 `commit()` 或 `rollback()`。
- **和 MySQL 引擎层的 redo/undo log 是两套事务体系**:Spring 在应用层,MySQL 在数据库层;Spring 通过 JDBC 调用 MySQL 的事务 API 完成事务。

**Q2. 自调用失效怎么解决?**

**答**:
- 自调用失效是因为同类方法调用走 `this.method()`,绕过代理。
- 3 种解法:
  ① 注入自己:`@Autowired private OrderService self;` 然后 `self.inner()`(不推荐,循环依赖)
  ② `AopContext.currentProxy()`(需要 `@EnableAspectJAutoProxy(exposeProxy=true)`)
  ③ **拆到另一个 Service**(推荐,符合单一职责)

**Q3. REQUIRES_NEW 和 NESTED 的区别?**

**答**:
- **REQUIRES_NEW**:挂起当前事务,开新事务。两个事务**完全独立**,子事务提交/回滚不影响父事务。
  - 场景:日志记录(不管主业务成败,日志都要记)
  - 底层:新 Connection
- **NESTED**:在当前事务里开嵌套事务,通过 **JDBC savepoint** 实现。
  - 子事务回滚只回滚到 savepoint,父事务其他操作不受影响
  - 父事务回滚,子事务也跟着回滚(嵌套是父事务的子集)
  - 场景:批量处理(一条失败不影响其他)
  - 底层:同一个 Connection,使用 savepoint

**Q4. 生产里 `@Transactional` 必须加 `rollbackFor = Exception.class` 吗?**

**答**:
- **必须加**。默认 rollbackFor 只包含 RuntimeException + Error,业务抛 checked Exception(如 `IOException`、自定义 `throws Exception`)不会回滚,导致数据不一致。
- 阿里 Java 规约强制要求:`@Transactional(rollbackFor = Exception.class)`。
- 例外场景:如果你确定方法只抛 RuntimeException,可以不加(但不推荐,违反规约)。

**Q5. 事务嵌套时 REQUIRES_NEW 和 NESTED 怎么选?**

**答**(决策树):
```
需要子事务独立于父事务吗?
├─ 是(父事务回滚,子事务也要回滚吗?否)
│   → REQUIRES_NEW
│   例:日志记录,业务失败日志也要保留
└─ 否(父事务回滚,子事务也要回滚吗?是)
    └─ 需要子事务失败不影响父事务其他操作吗?
        ├─ 是 → NESTED(子事务失败回滚到 savepoint,父事务其他操作继续)
        └─ 否 → REQUIRED(子事务失败,父事务整体回滚)
```

**Q6. 事务里不能包含哪些操作?**

**答**:
- ❌ 远程调用(HTTP/RPC):慢 → 事务长 → 锁持有久 → 并发差
- ❌ MQ 发送:MQ 抖动 → 事务卡住;应该用事务消息或本地消息表
- ❌ 长时间计算:同上
- ❌ 多线程操作 DB:新线程不在原事务里
- ✅ 事务里只做:DB 操作 + 内存计算(快)

**Q7. 大事务怎么排查?**

**答**:
- 看监控:Druid/HikariCP 的事务持续时间
- 看慢日志:MySQL slow log 的 commit 时间
- 看日志:事务方法执行日志(打点时间戳)
- 解法:拆小事务,事务里只做必要 DB 操作,外部调用放事务外

# 主题 5 · Spring Security 认证授权体系

> **为什么学这个**:Spring Security 是后端架构师面试的"鉴权题"必备,青岛 JD 高频出现。你当前 20 分,"仅答对认证 vs 授权方向,三件套(AuthenticationManager/AuthenticationProvider/UserDetailsService)全空"。本次系统补齐,目标 60 分。

## 5.0 先分清楚两个核心概念

```
认证(Authentication) vs 授权(Authorization):

认证:你是谁?
  验证用户身份(登录)
  输入:用户名 + 密码 / 手机号 + 验证码 / JWT / 生物特征
  输出:Authentication 对象(包含 Principal 用户信息 + Authorities 权限集合)

授权:你能做什么?
  验证用户是否有权限访问某资源
  输入:Authentication + 请求资源(URL / 方法 / 数据)
  输出:允许 / 拒绝

顺序:
  先认证 → 再授权
  用户必须先登录(认证通过),才能判断他有没有权限访问某接口(授权)

常见混淆:
  ❌ "鉴权 = 认证 + 授权" 不严谨
  ✅ 鉴权 = authorization,只指"授权"部分
  ❌ "RBAC 是认证" 错
  ✅ RBAC(Role-Based Access Control)是授权的一种模型
```

---

### 5.1.1 三大核心组件(三件套,必背)

```
Spring Security 三件套(认证流程的核心):

┌─────────────────────────────────────────────────────────────────┐
│ ① AuthenticationManager(认证管理器·入口)                        │
│    接口,只有一个方法 authenticate(Authentication)               │
│    实际用的是 ProviderManager(实现类)                           │
│    职责:协调多个 AuthenticationProvider,找到能处理当前认证的      │
│         provider,返回认证结果                                    │
├─────────────────────────────────────────────────────────────────┤
│ ② AuthenticationProvider(认证提供者·执行者)                     │
│    接口,两个方法:                                               │
│      authenticate(Authentication):实际做认证                     │
│      supports(Class<?>):是否支持当前认证类型                    │
│    常见实现:                                                     │
│      DaoAuthenticationProvider(用户名 + 密码)                   │
│      JwtAuthenticationProvider(JWT token)                       │
│      LdapAuthenticationProvider(LDAP)                           │
│      OAuth2AuthenticationProvider(OAuth2)                       │
├─────────────────────────────────────────────────────────────────┤
│ ③ UserDetailsService(用户详情服务·数据来源)                     │
│    接口,只有一个方法 loadUserByUsername(String)                 │
│    职责:从数据库/缓存/LDAP 加载用户信息                         │
│    返回 UserDetails(包含 username/password/authorities)         │
│    业务里实现这个接口,查数据库返回用户                           │
└─────────────────────────────────────────────────────────────────┘

三者协作流程:
  UsernamePasswordAuthenticationFilter
    → 拿到 AuthenticationManager(ProviderManager)
    → ProviderManager 遍历所有 AuthenticationProvider
    → 找到 DaoAuthenticationProvider(supports 返回 true)
    → DaoAuthenticationProvider 调用 UserDetailsService.loadUserByUsername
    → 对比密码(DaoAuthenticationProvider 内置 PasswordEncoder)
    → 成功:返回 Authentication(已认证,带 authorities)
    → 失败:抛 BadCredentialsException
```

> 🔑 **金句**:Spring Security 三件套 = AuthenticationManager(入口,协调 provider)+ AuthenticationProvider(执行认证,判断用哪个)+ UserDetailsService(查用户数据)。认证流程是:Manager 调 Provider,Provider 调DetailsService,最后比对凭证。

## 5.2 认证流程完整走通(用户名密码)

```
用户名密码认证的 9 步流程(面试必讲清楚):

1. 客户端 POST /login (username + password)
   ↓
2. UsernamePasswordAuthenticationFilter 拦截请求
   ↓
3. Filter 把 username + password 封装成
   UsernamePasswordAuthenticationToken(未认证的 Authentication)
   ↓
4. Filter 调用 AuthenticationManager.authenticate(token)
   ↓
5. AuthenticationManager(实际是 ProviderManager)遍历所有 Provider
   ↓
6. 找到 DaoAuthenticationProvider(supports 返回 true)
   ↓
7. DaoAuthenticationProvider 调用 UserDetailsService.loadUserByUsername
   → 查数据库 → 返回 UserDetails(从数据库查的用户信息,含加密密码)
   ↓
8. DaoAuthenticationProvider 用 PasswordEncoder.matches(输入密码, 数据库密码)
   → 比对通过 → 创建已认证的 Authentication(含 authorities)
   → 比对失败 → 抛 BadCredentialsException
   ↓
9. 认证成功:
   SecurityContextHolder.getContext().setAuthentication(auth)
   默认存到 HttpSession
   返回 AuthenticationSuccessHandler 处理(重定向 / 返回 JSON)

后续请求:
  浏览器自动带 JSESSIONID cookie
  SecurityContextPersistenceFilter 从 Session 恢复 SecurityContext
  后续 Filter 直接判断 Authentication 是否已认证
```

## 5.3 JWT 集成(现代 Web 常用)

> **为什么 JWT?** 传统 Session- Cookie 模式有状态,不适合微服务(每次请求要查 Session,Session 跨服务要共享)。JWT 无状态,适合分布式/微服务。

```
JWT 认证流程:

1. 登录:
   POST /api/auth/login {username, password}
   ↓
   走 Spring Security 标准认证(UserDetailsService + PasswordEncoder)
   ↓
   认证成功 → 生成 JWT(用密钥签名,含用户 ID + 角色 + 过期时间)
   ↓
   返回 {token: "eyJhbGciOi..."}

2. 后续请求:
   GET /api/orders
   Header: Authorization: Bearer eyJhbGciOi...
   ↓
   JwtAuthenticationFilter(自定义 Filter) 拦截:
     ① 解析 JWT(Jwts.parser().setSigningKey(secret).parse(...))
     ② 验签 + 检查过期
     ③ 从 JWT 拿 username → loadUserByUsername 查 UserDetails
     ④ 创建 UsernamePasswordAuthenticationToken 放入 SecurityContext
   ↓
   后续 Filter 判断已认证 → 访问 Controller
```

### 5.3.1 JWT Filter 完整代码(工业级)

```java
// 自定义 JWT 过滤器(继承 OncePerRequestFilter,保证一次请求只执行一次)
public class JwtAuthenticationFilter extends OncePerRequestFilter {

    @Autowired
    private JwtTokenProvider tokenProvider;
    @Autowired
    private UserDetailsService userDetailsService;

    @Override
    protected void doFilterInternal(HttpServletRequest request,
                                    HttpServletResponse response,
                                    FilterChain filterChain)
            throws ServletException, IOException {

        // 1. 从 Header 拿 token
        String token = resolveToken(request);  // 解析 "Bearer xxx"

        // 2. 验证 token
        if (token != null && tokenProvider.validateToken(token)) {
            // 3. 从 token 拿用户名
            String username = tokenProvider.getUsernameFromToken(token);

            // 4. 加载 UserDetails(从数据库拿权限)
            UserDetails userDetails = userDetailsService.loadUserByUsername(username);

            // 5. 创建已认证的 Authentication
            UsernamePasswordAuthenticationToken authentication =
                new UsernamePasswordAuthenticationToken(
                    userDetails, null, userDetails.getAuthorities());

            // 6. 放入 SecurityContext
            SecurityContextHolder.getContext().setAuthentication(authentication);
        }

        // 7. 继续过滤链
        filterChain.doFilter(request, response);
    }

    private String resolveToken(HttpServletRequest request) {
        String bearer = request.getHeader("Authorization");
        if (bearer != null && bearer.startsWith("Bearer ")) {
            return bearer.substring(7);
        }
        return null;
    }
}

// JWT 工具类
@Component
public class JwtTokenProvider {
    @Value("${jwt.secret}")
    private String secret;
    @Value("${jwt.expiration-ms:86400000}")  // 默认 24 小时
    private long expirationMs;

    public String generateToken(UserDetails userDetails) {
        Date now = new Date();
        Date expiryDate = new Date(now.getTime() + expirationMs);

        return Jwts.builder()
            .setSubject(userDetails.getUsername())
            .claim("roles", userDetails.getAuthorities().stream()
                .map(GrantedAuthority::getAuthority).collect(Collectors.toList()))
            .setIssuedAt(now)
            .setExpiration(expiryDate)
            .signWith(SignatureAlgorithm.HS512, secret)
            .compact();
    }

    public String getUsernameFromToken(String token) {
        return Jwts.parser()
            .setSigningKey(secret)
            .parseClaimsJws(token)
            .getBody()
            .getSubject();
    }

    public boolean validateToken(String token) {
        try {
            Jwts.parser().setSigningKey(secret).parseClaimsJws(token);
            return true;
        } catch (JwtException | IllegalArgumentException e) {
            // 签名错误 / 过期 / 格式错误
            return false;
        }
    }
}

// Spring Security 配置
@Configuration
@EnableWebSecurity
public class SecurityConfig extends WebSecurityConfigurerAdapter {

    @Autowired
    private JwtAuthenticationFilter jwtFilter;
    @Autowired
    private UserDetailsService userDetailsService;

    @Override
    protected void configure(HttpSecurity http) throws Exception {
        http
            .csrf().disable()  // JWT 模式关闭 CSRF(见 5.6)
            .sessionManagement().sessionCreationPolicy(SessionCreationPolicy.STATELESS)  // 无 Session
            .and()
            .authorizeRequests()
                .antMatchers("/api/auth/**").permitAll()  // 登录接口放行
                .antMatchers("/api/admin/**").hasRole("ADMIN")
                .anyRequest().authenticated()  // 其他接口需认证
            .and()
            .addFilterBefore(jwtFilter, UsernamePasswordAuthenticationFilter.class);
            // 把 JWT Filter 加到 UsernamePasswordAuthenticationFilter 之前
    }

    @Override
    protected void configure(AuthenticationManagerBuilder auth) throws Exception {
        auth.userDetailsService(userDetailsService)
            .passwordEncoder(passwordEncoder());
    }

    @Bean
    public PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder();  // 推荐 BCrypt
    }
}
```

## 5.4 JWT 主动失效(面试高频追问)

> **痛点**:JWT 默认"发了就不能撤销"(24 小时内有效)。用户改密码、被踢下线、Token 泄漏 → 旧 Token 还能用?这是 JWT 最大问题。

```
JWT 主动失效 4 种方案:

① Token 黑名单(推荐,最常用)
   Redis 存已失效的 token(jti 唯一标识)
   JwtFilter 每次解析 token 后检查是否在黑名单
   退出登录:把 jti 加入黑名单,TTL = token 剩余有效期

   实现:
   // 生成 token 时带 jti
   String jti = UUID.randomUUID().toString();
   String token = Jwts.builder()
       .setId(jti)  // 唯一 ID
       ...

   // 退出登录
   public void logout(String token) {
       String jti = getJtiFromToken(token);
       long ttl = getExpirationFromToken(token) - System.currentTimeMillis();
       redis.setex("jwt:blacklist:" + jti, ttl / 1000, "1");
   }

   // JwtFilter 每次检查
   if (redis.exists("jwt:blacklist:" + jti)) {
       throw new AuthenticationException("token revoked");
   }

② Token 版本号(用户级)
   数据库/Redis 存每个用户的 token 版本号
   JWT 里带版本号
   用户改密码 → 版本号 +1 → 所有旧 token 失效

   实现:
   // JWT 里带 version
   int version = userService.getTokenVersion(userId);
   String token = Jwts.builder()
       .claim("version", version)
       ...

   // 改密码 → 版本号 +1
   public void changePassword(Long userId, String newPassword) {
       userService.incrementTokenVersion(userId);
       // 所有旧 token 因版本号不匹配自动失效
   }

   // JwtFilter 校验
   int tokenVersion = getVersionFromToken(token);
   int dbVersion = userService.getTokenVersion(userId);
   if (tokenVersion != dbVersion) throw ...;

③ 短 token + Refresh Token 双 token
   Access Token 很短(15 分钟)
   Refresh Token 较长(7 天),存 Redis
   Access Token 过期 → 用 Refresh Token 换新的
   退出 → 删 Refresh Token → 下次刷新失败 → 用户被迫重新登录

   优点:安全性高,Access Token 不存 Redis
   缺点:两次请求多一次刷新

④ 短过期时间(最简单)
   Access Token 15 分钟
   不主动失效,等自然过期
   缺点:15 分钟内 Token 泄漏无法撤销
```

> 🔑 **金句**:JWT 主动失效 4 方案:① Token 黑名单 Redis(jti 唯一 ID,退出登录加入,TTL=剩余有效期) ② Token 版本号(改密码 +1,旧 token 全失效) ③ 双 token(Access 短 + Refresh 长,退出删 Refresh) ④ 短过期时间(15 分钟,最简单但不严谨)。**生产推荐 ① 或 ③**。

## 5.5 RBAC 三表落地(工业级实现)

```
RBAC(Role-Based Access Control,基于角色的访问控制):

核心三表:
  ① t_user(id, username, password, ...)
  ② t_role(id, role_name, description)
  ③ t_permission(id, permission_name, resource, action)

关联表:
  ④ t_user_role(user_id, role_id)         — 用户-角色多对多
  ⑤ t_role_permission(role_id, permission_id) — 角色-权限多对多

用户 → 角色 → 权限(两级关系):
  一个用户可以有多个角色(张三 = 订单管理员 + 财务)
  一个角色可以有多个权限(订单管理员 = 创建订单 + 删除订单 + 查看报表)
  用户最终权限 = 所有角色权限的并集

SQL 查询用户权限:
  SELECT DISTINCT p.permission_name
  FROM t_user u
  JOIN t_user_role ur ON u.id = ur.user_id
  JOIN t_role r ON ur.role_id = r.id
  JOIN t_role_permission rp ON r.id = rp.role_id
  JOIN t_permission p ON rp.permission_id = p.id
  WHERE u.username = 'zhangsan'

Spring Security 集成:
  实现 UserDetailsService:
  @Service
  public class UserDetailsServiceImpl implements UserDetailsService {
      @Autowired
      private UserDao userDao;

      @Override
      public UserDetails loadUserByUsername(String username) {
          User user = userDao.findByUsername(username);
          if (user == null) {
              throw new UsernameNotFoundException("用户不存在");
          }

          // 查询用户的权限集合(走上面的 SQL)
          List<String> permissions = userDao.findPermissionsByUsername(username);

          // 转换为 GrantedAuthority
          List<GrantedAuthority> authorities = permissions.stream()
              .map(SimpleGrantedAuthority::new)
              .collect(Collectors.toList());

          return new org.springframework.security.core.userdetails.User(
              user.getUsername(),
              user.getPassword(),  // BCrypt 加密后的密码
              authorities
          );
      }
  }
```

## 5.6 URL 级 vs 方法级鉴权(必会区分)

```
两种鉴权方式:

① URL 级鉴权(配置层,粗粒度)
   http.authorizeRequests()
       .antMatchers("/api/admin/**").hasRole("ADMIN")
       .antMatchers("/api/orders/**").hasAuthority("order:read")
       .anyRequest().authenticated()

   优点:集中配置,一目了然
   缺点:和 Controller 代码分离,改 Controller 时容易漏改 URL 规则

② 方法级鉴权(注解,细粒度)
   @PreAuthorize("hasAuthority('order:create')")
   @PostMapping("/orders")
   public Order createOrder(@RequestBody OrderRequest req) { ... }

   @PreAuthorize("#id == authentication.principal.id or hasRole('ADMIN')")
   @GetMapping("/orders/{id}")
   public Order getOrder(@PathVariable Long id) { ... }
   // 支持 SpEL 表达式,能访问方法参数和当前用户

   @Secured("ROLE_ADMIN")
   public void deleteUser(Long id) { ... }
   // 老注解,功能弱,不支持 SpEL

启用方法级鉴权:
  @EnableGlobalMethodSecurity(
      prePostEnabled = true,  // 启用 @PreAuthorize/@PostAuthorize
      securedEnabled = true   // 启用 @Secured
  )
  public class SecurityConfig { ... }

@PreAuthorize vs @Secured 区别:
  @PreAuthorize
    - Spring Security 提供
    - 支持 SpEL(可以写复杂条件)
    - 可访问方法参数(#id)、当前用户(authentication)
    - 推荐用这个

  @Secured
    - JSR-250 标准
    - 只能写角色/权限列表
    - 不能写复杂条件
    - 不推荐(功能弱)
```

> 🔑 **金句**:方法级鉴权用 `@PreAuthorize`(支持 SpEL 复杂条件,能访问方法参数);不用 `@Secured`(功能弱,只能判断角色)。URL 级鉴权放 SecurityConfig 集中配,方法级用 `@PreAuthorize` 细粒度控制。

## 5.7 CSRF 开关判断(面试高频)

```
CSRF(Cross-Site Request Forgery,跨站请求伪造):

攻击原理:
  ① 用户登录银行网站,浏览器存了银行的 Cookie
  ② 用户访问恶意网站
  ③ 恶意网站有段代码:
     <img src="https://bank.com/transfer?to=hacker&amount=1000">
  ④ 浏览器自动带上银行的 Cookie 发请求 → 转账成功

防御方案:
  Spring Security 默认开启 CSRF,每次请求带 CSRF Token(存 Session)
  表单提交时自动带 _csrf 字段

什么时候关闭 CSRF?
  ✅ RESTful API + JWT 模式:
     因为 JWT 不存 Session,Cookie 不带认证信息,CSRF 攻击无从下手
     所以 JWT 模式一般关闭 CSRF 节省开销
  ✅ 微服务间调用:内部服务无 CSRF 风险
  ❌ 传统 Session-Cookie 模式:
     必须开 CSRF,否则会被攻击

关闭代码:
  http.csrf().disable()
```

### 5.8.2 异常处理(401 vs 403)

```java
// 统一异常处理
@Component
public class AuthenticationEntryPointImpl implements AuthenticationEntryPoint {
    @Override
    public void commence(HttpServletRequest request,
                         HttpServletResponse response,
                         AuthenticationException authException) throws IOException {
        // 401 未认证(没登录 / token 失效)
        response.setStatus(HttpServletResponse.SC_UNAUTHORIZED);
        response.setContentType("application/json;charset=UTF-8");
        response.getWriter().write("{\"code\": 401, \"msg\": \"未登录或 token 失效\"}");
    }
}

@Component
public class AccessDeniedHandlerImpl implements AccessDeniedHandler {
    @Override
    public void handle(HttpServletRequest request,
                       HttpServletResponse response,
                       AccessDeniedException accessDeniedException) throws IOException {
        // 403 无权限(登录了但没权限)
        response.setStatus(HttpServletResponse.SC_FORBIDDEN);
        response.setContentType("application/json;charset=UTF-8");
        response.getWriter().write("{\"code\": 403, \"msg\": \"无权限访问\"}");
    }
}

// 配置
http.exceptionHandling()
    .authenticationEntryPoint(new AuthenticationEntryPointImpl())
    .accessDeniedHandler(new AccessDeniedHandlerImpl());
```

## 5.9 面试连环追问

**Q1. Spring Security 认证流程是什么?**

**答**:
- 客户端发送登录请求(用户名+密码) → UsernamePasswordAuthenticationFilter 拦截
- Filter 把用户名密码封装成 `UsernamePasswordAuthenticationToken`(未认证的 Authentication)
- 调用 `AuthenticationManager.authenticate(token)`
- `AuthenticationManager`(实际是 ProviderManager)遍历所有 `AuthenticationProvider`,找到支持的(比如 `DaoAuthenticationProvider`)
- `DaoAuthenticationProvider` 调用 `UserDetailsService.loadUserByUsername` 从数据库查用户
- 用 `PasswordEncoder.matches` 比对密码
- 成功:创建已认证的 Authentication(含 authorities),放入 SecurityContext
- 失败:抛 `BadCredentialsException`

**Q2. JWT 主动失效怎么做?**

**答**(生产推荐):
- **Token 黑名单**:Redis 存已失效 token 的 jti,TTL = token 剩余有效期。退出登录/改密码时把 jti 加入黑名单。JwtFilter 每次检查黑名单。
- **双 token**:Access Token 短(15 分钟),Refresh Token 长(7 天,存 Redis)。退出删 Refresh Token → 下次刷新失败 → 用户被迫重登。
- **版本号**:JWT 里带版本号,改密码版本号 +1 → 旧 token 失效。

**Q3. @PreAuthorize 和 @Secured 区别?**

**答**:
- `@PreAuthorize`:Spring Security 提供,支持 SpEL 表达式(可以写 `#id == authentication.principal.id or hasRole('ADMIN')`),能访问方法参数、当前用户。**推荐**。
- `@Secured`:JSR-250 标准,只能写角色列表(`@Secured("ROLE_ADMIN")`),不能写复杂条件。**不推荐**(功能弱)。

**Q4. RBAC 三表怎么设计?**

**答**:
- 5 张表:`t_user` / `t_role` / `t_permission` + `t_user_role` / `t_role_permission`
- 用户→角色→权限两级关系
- 用户最终权限 = 所有角色权限的并集
- 实现 `UserDetailsService.loadUserByUsername`:查用户 → 查关联权限 → 返回 `UserDetails`(含 authorities)
- 权限命名:`resource:action`(如 `order:create`)
- 角色命名:`ROLE_xxx`(Spring Security 默认前缀)

**Q5. CSRF 什么时候关闭?**

**答**:
- RESTful API + JWT 模式:关闭 CSRF。因为 JWT 不用 Cookie 认证,CSRF 攻击无从下手。
- 传统 Session-Cookie 模式:必须开 CSRF。
- 代码:`http.csrf().disable()`

**Q6. 401 和 403 区别?**

**答**:
- **401 Unauthorized**:未认证(没登录 / token 失效)。对应 `AuthenticationEntryPoint`。
- **403 Forbidden**:已认证但无权限(登录了,但角色/权限不够)。对应 `AccessDeniedHandler`。

**Q7. Spring Security 的 Filter 链是什么?**

**答**:
- `FilterChainProxy` 是 Spring Security 的入口,内部维护 `List<Filter>` 按顺序执行
- 核心 Filter:
  - `SecurityContextPersistenceFilter`:从 Session 恢复 SecurityContext
  - `UsernamePasswordAuthenticationFilter`:处理 /login POST
  - `ExceptionTranslationFilter`:捕获认证/授权异常转 401/403
  - `FilterSecurityInterceptor`:核心授权过滤器(检查用户能否访问 URL)
- 自定义 Filter(如 JwtFilter)通过 `addFilterBefore` 插入到特定位置

**Q8. 密码怎么加密存?**

**答**:
- **推荐**:BCrypt(`BCryptPasswordEncoder`),加盐,每次加密结果不同,抗彩虹表攻击。
- **禁用**:MD5/SHA-256(无盐易破解)、`MessageDigestPasswordEncoder`(已废弃)。
- 存库:存 BCrypt 加密后的字符串,登录时用 `matches(rawPassword, encodedPassword)` 比对。
