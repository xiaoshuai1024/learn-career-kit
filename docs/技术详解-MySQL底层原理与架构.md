## 1. 为什么学原理(痛点推演)

**场景**:线上订单系统,大促前 DBA 找你说"MySQL 内存吃紧,想调 `innodb_buffer_pool_size`,但怕调出问题"。

如果你不懂原理:
- 不知道 Buffer Pool 是什么、为什么吃内存
- 不知道调大有什么好处、调小会怎样
- 不知道 `innodb_buffer_pool_instances` 为什么要跟着调
- 出了 OOM(Out Of Memory,内存溢出)只能重启,不会排查

**如果你懂原理**:
- Buffer Pool 是 InnoDB 缓存数据页/索引页的内存区,调大 → 命中率高 → 磁盘 IO 少 → 快
- 但不能超过物理内存 70-80%,要给 OS / 连接 / 临时表留
- 调大后要相应增加 instances(≥1G 时)减少锁竞争
- OOM 先看 Buffer Pool 占用 + 是否有超级大查询(临时表炸内存)

**面试官为什么深挖原理**——他在判断你是"会用 MySQL 的工程师"还是"懂 MySQL 的架构师"。技术总监/架构师岗必须能回答"一条 SQL 内部发生了什么"。这章就是把这个讲透。

> 🔑 这章学完,你要能画出 MySQL 的整体架构图、Buffer Pool 结构图、一条 UPDATE 的完整写流程图——这是架构师的基本功。

## 2. MySQL 整体架构:三层模型

MySQL 不是铁板一块,它是**分层架构**。理解架构是理解一切原理的前提。

```
┌──────────────────────────────────────────────────────────────┐
│  客户端层(JDBC / mysql cli / 各种语言驱动)                  │
│  → 建立连接、发送 SQL、接收结果                              │
└────────────────────────┬─────────────────────────────────────┘
                         │ TCP 连接
                         ▼
┌──────────────────────────────────────────────────────────────┐
│  Server 层(MySQL 通用,跨所有存储引擎)                      │
│                                                              │
│  ┌─────────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐ │
│  │ 连接器       │→│ 查询缓存  │→│ 解析器    │→│ 优化器    │ │
│  │ (鉴权/管理) │  │(8.0已删) │  │(词法语法) │  │(执行计划)│ │
│  └─────────────┘  └──────────┘  └──────────┘  └─────┬────┘ │
│                                                     │      │
│  ┌──────────────────────────────────────────────────┘      │
│  │  执行器(调引擎接口)                                       │
│  └──────────────────────────────┬──────────────────────────┘
└─────────────────────────────────┼────────────────────────────┘
                                  │ 统一 API
                                  ▼
┌──────────────────────────────────────────────────────────────┐
│  存储引擎层(可插拔,真正存数据的地方)                          │
│                                                              │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐       │
│  │ InnoDB   │ │ MyISAM   │ │ Memory   │ │  其他    │       │
│  │ (默认)   │ │ (老引擎) │ │ (内存表) │ │ (Archive)│       │
│  └──────────┘ └──────────┘ └──────────┘ └──────────┘       │
│  ↓ 各自实现:索引结构/锁/事务/日志/数据文件                     │
└──────────────────────────────────────────────────────────────┘
                                  │
                                  ▼
                          物理磁盘(.ibd 文件等)
```

**关键认知**:

| 层 | 干什么 | 跨引擎吗 | 例子 |
|----|--------|:------:|------|
| **Server 层** | 连接管理、SQL 解析、查询优化、执行调度 | ✅ 跨引擎 | 连接器、解析器、优化器、执行器、binlog |
| **存储引擎层** | 数据怎么存、怎么读、怎么锁、事务怎么做 | ❌ 每个引擎自己实现 | InnoDB 的 B+树/redo log/undo log/行锁 |

**为什么这么分**:Server 层定义了"怎么用 SQL",引擎层定义"怎么存"。换个引擎,SQL 不用改,但底层存储/锁/事务完全不同。这就是"可插拔存储引擎"架构。

**容易混淆的点**:
- **binlog 在 Server 层**(所有引擎共用)→ 所以 binlog 又叫"二进制日志"
- **redo log / undo log 在 InnoDB 引擎层**(MyISAM 没有)→ 这就是为什么 MyISAM 不支持事务
- **解析/优化跨引擎**,但**执行计划会考虑引擎特性**(优化器知道 InnoDB 是 B+树,Memory 是 Hash)

> 🔑 金句:**MySQL 是"Server 层(连接/解析/优化/执行,跨引擎) + 存储引擎层(数据/索引/锁/事务,引擎自实现)"的分层架构。binlog 属于 Server,redo/undo 属于 InnoDB——这是理解所有 MySQL 原理的起点。**

## 3. 一条 SELECT 的完整旅程(7 步)

以这条 SQL 为例,跟踪它从客户端到返回的全过程:

```sql
SELECT order_id, amount FROM `order` WHERE user_id = 88 AND status = 1;
```

### 第 1 步:连接器(Connector)—— 建立连接 + 鉴权

```
客户端 → TCP 三次握手 → MySQL → 鉴权(用户名/密码/权限)→ 建立连接
```

- **长连接**:客户端和服务端保持连接(MySQL 默认 `wait_timeout=28800s` 即 8 小时空闲断开)
- **连接池**:服务端为每个连接分配**一个线程**(线程池复用,避免每查询创线程)
- **权限缓存**:鉴权后把该用户的权限**缓存到内存**,后续 SQL 直接用缓存判断,不重复查库

**面试坑**:`show processlist` 看到的连接,Sleep 状态 = 空闲,Query 状态 = 执行中。连接数超 `max_connections` 报错 `Too many connections`。

### 第 2 步:查询缓存(Query Cache)—— ⚠️ 8.0 已删除

5.7 有查询缓存:SQL 当 key,结果当 value,命中直接返回。
**为什么 8.0 删了**:命中率太低(任何表改动都让该表所有缓存失效)、维护成本高、并发下锁竞争大。**生产从不用**(官方建议关闭)。

### 第 3 步:解析器(Parser)—— 词法 + 语法分析

```
SELECT order_id, amount FROM `order` WHERE user_id = 88
   ↓ 词法分析(切词)
   [SELECT][order_id][,][amount][FROM][order][WHERE][user_id][=][88]
   ↓ 语法分析(建解析树)
   SelectStmt { cols:[order_id,amount], table:order, where:(user_id=88) }
```

- **词法分析**:把字符串切成 token(关键字/标识符/字面量)
- **语法分析**:按 SQL 语法规则建**解析树**(Parse Tree)
- **报错在这步**:SQL 写错(如 `SELCT`)→ `You have an error in your SQL syntax`

### 第 4 步:预处理(Preprocessor)—— 语义检查

- 检查表名/列名**是否存在**(查询 `information_schema`)
- 检查**是否有权限**(对比连接器缓存的权限)
- 解析 `*` 为具体列、展开视图

**报错在这步**:`Unknown column 'xxx'` / `Table 'xxx' doesn't exist` / `Access denied`。

### 第 5 步:优化器(Optimizer)—— ⭐ 生成执行计划(最复杂)

优化器拿到解析树,**计算多种执行方案的成本(cost),选最优的**。

**它决定**:
- **用哪个索引**:user_id 索引还是全表扫?(看 cardinality + 估算行数)
- **JOIN 顺序**:多表 JOIN 时哪个表做驱动表?
- **是否用临时表/排序**:`GROUP BY` / `ORDER BY` 怎么实现?

**基于 cost 的优化**:
```
cost = IO 成本(读多少页) + CPU 成本(比较多少行)
优化器估算每种方案的 cost,选最小的
```

**优化器不是万能的**——它依赖**统计信息**(cardinality、数据分布)。统计信息陈旧 → 选错索引。这就是为什么生产要定期 `ANALYZE TABLE` 更新统计信息。

**怎么看优化器的选择**:`EXPLAIN`(看最终计划)/ `EXPLAIN FORMAT=JSON`(看 cost 估算)/ 优化器 Hint 强制(`FORCE INDEX` / `/*+ INDEX(order idx_user) */`)。

### 第 6 步:执行器(Executor)—— 调引擎接口

执行器按执行计划,**调用存储引擎的 API**,逐行获取数据。

```java
// 执行器伪代码(简化)
Iterator iterator = engine.init("order", "idx_user", condition="user_id=88");
while (iterator.hasNext()) {
    Row row = iterator.next();       // 调引擎拿一行
    if (row.status == 1) {           // WHERE 后置过滤(如果索引没覆盖 status)
        result.add(row);
    }
}
```

**重要**:Server 层的执行器**通过统一 API 调引擎**,引擎自己决定怎么读(InnoDB 走 B+树,Memory 走 Hash)。这就是为什么换引擎不改 SQL。

### 第 7 步:返回结果

执行器把结果集**逐行发给客户端**(不是攒齐再发),客户端边收边解析。

**完整流程图**:
```
SELECT → 连接器 → [查询缓存] → 解析器 → 预处理器 → 优化器 → 执行器 → 引擎 → 返回
            ↓                  ↓          ↓          ↓          ↓        ↓
         鉴权/权限          词法语法    语义检查    执行计划   调API    B+树/Hash
```

> 🔑 金句:**一条 SELECT 走 7 步:连接器鉴权 → 解析器建树 → 预处理语义检查 → 优化器选索引/JOIN顺序 → 执行器调引擎 → 引擎走 B+树 → 返回。优化器是基于 cost 的,统计信息陈旧会选错索引。**

## 4. 一条 UPDATE 的完整旅程(写流程核心)⭐

写流程是 MySQL 原理的**最深水区**,面试官最爱刨。以这条 SQL 为例:

```sql
UPDATE `order` SET amount = 399 WHERE order_id = 10086;
```

**完整写流程**(必须能画):

```
                    ① 执行器调引擎:查 order_id=10086 这行
                                          │
                                          ▼
        ② 引擎:Buffer Pool 找这页 → 命中? ─┬─ 命中 → 返回内存页
                                          └─ 没命中 → 从磁盘读 16KB 页到 Buffer Pool
                                          │
                                          ▼
        ③ 执行器:把 amount 改成 399(改的是 Buffer Pool 里的内存页)→ 这页变"脏页"
                                          │
                                          ▼
        ④ 执行器调引擎:记录 redo log(改了哪页哪偏移成什么)→ 写入 Log Buffer
                                          │
                                          ▼
        ⑤ 引擎:把 Log Buffer 刷到 redo log file(根据策略)
                                          │
                                          ▼
        ⑥ 执行器:生成 binlog(行变更事件)→ 写入 binlog cache
                                          │
                                          ▼
        ⑦ 引擎:两阶段提交(见 §9)
           ├─ redo log 写 prepare
           ├─ binlog 写盘
           └─ redo log 写 commit
                                          │
                                          ▼
        ⑧ 返回客户端"更新成功"
                                          │
                                          ▼
        ⑨ 后台线程异步:把 Buffer Pool 的脏页刷到磁盘(.ibd 文件)← 不是同步!
```

### 关键认知(每条都是面试点)

**① 为什么先改内存(Buffer Pool)不直接改磁盘?**
- 内存改是纳秒级,磁盘改是毫秒级(差 10 万倍)
- 直接改磁盘 = 每次更新一次随机 IO = 极慢
- 改内存 + 异步刷脏页 = 高吞吐

**② 什么是脏页(Dirty Page)?**
- 内存里的页被改了,但**还没刷到磁盘**,内存和磁盘不一致 → 这页"脏"了
- 脏页在 Buffer Pool 里,后台线程**异步**刷到磁盘
- 崩溃时脏页丢失怎么办?→ 靠 redo log 恢复(见 §9)

**③ 为什么需要 redo log,不直接刷脏页?**
- 刷脏页是**随机 IO**(改哪页写哪,位置散),慢
- 写 redo log 是**顺序 IO**(往文件尾部追加),快
- **WAL(Write-Ahead Logging)**:先写日志(快),再异步刷数据(慢)→ 既快又安全

**④ redo log 什么时候写盘?**
由 `innodb_flush_log_at_trx_commit` 控制:
```
= 1: 每次 COMMIT 把 Log Buffer 刷到 redo log file 并 fsync(刷盘)  ← 最安全,生产必选
= 2: 每次 COMMIT 刷到 OS Page Cache(不 fsync)                    ← 崩溃丢 1 秒
= 0: 每秒由后台线程刷                                              ← 性能高,崩溃丢 1 秒
```

**⑤ binlog 什么时候写盘?**
由 `sync_binlog` 控制:
```
= 1: 每次 COMMIT 都 fsync binlog   ← 最安全,生产必选
= N: 攒 N 次再 fsync               ← 性能高,崩溃丢 N 个事务
```

**⑥ redo log 和 binlog 的区别**(高频):
| 维度 | redo log | binlog |
|------|---------|--------|
| 层级 | InnoDB 引擎层 | Server 层 |
| 类型 | 物理日志("页X偏移Y改成Z") | 逻辑日志("SQL" 或 "行变更事件") |
| 写入 | 循环写(覆盖老的) | 追加写(永不覆盖) |
| 用途 | 崩溃恢复 | 主从复制 + PITR |
| 谁写 | InnoDB | Server 层的执行器 |

**双 1 配置**(生产最强安全):`innodb_flush_log_at_trx_commit=1` + `sync_binlog=1`。代价:每次 COMMIT 都 fsync 两次,性能低。金融场景必选,日志类业务可降级。

> 🔑 金句:**写流程是"改内存(Buffer Pool 脏页)→ 写 redo log(顺序快)→ 写 binlog → 两阶段提交 → 异步刷脏页"。核心思想是 WAL:用顺序日志换随机 IO 的性能,同时保证崩溃不丢数据。**

## 5. InnoDB 内存架构(Buffer Pool 详解)⭐

Buffer Pool(Buffer Pool,缓冲池)是 InnoDB **最关键的内存结构**,直接决定性能。

### 5.1 Buffer Pool 装什么

```
┌──────────────────────────── Buffer Pool(缓冲池)────────────────────────────┐
│                                                                            │
│  ┌─────────────────┐ ┌─────────────────┐ ┌─────────────────┐              │
│  │ 数据页           │ │ 索引页           │ │ 自适应哈希索引    │              │
│  │ (表里的行数据)   │ │ (B+树节点)       │ │ (AHI,热点页加速) │              │
│  └─────────────────┘ └─────────────────┘ └─────────────────┘              │
│                                                                            │
│  ┌─────────────────┐ ┌─────────────────┐ ┌─────────────────┐              │
│  │ change buffer    │ │ 锁信息           │ │ 数据字典缓存     │              │
│  │ (二级索引缓存)   │ │ (行锁/表锁信息) │ │ (表/列定义)     │              │
│  └─────────────────┘ └─────────────────┘ └─────────────────┘              │
│                                                                            │
│  (redo log 在 Log Buffer 里,不在 Buffer Pool)                            │
└────────────────────────────────────────────────────────────────────────────┘
```

**关键比例**:数据页 + 索引页占 Buffer Pool 的 99%+。调 `innodb_buffer_pool_size` 主要就是为了多装这些。

### 5.2 改进版 LRU(防止全表扫污染)⭐

**朴素 LRU 的问题**:
- LRU(Least Recently Used,最近最少使用):新页加到头部,满了淘汰尾部
- 全表扫(如 `SELECT * FROM 大表`)会**把整个 Buffer Pool 冲掉**——扫一次几百万页全进 LRU,热点数据全被淘汰

**InnoDB 的改进:LRU 分两区**

```
   ┌─────────── young 区(新页,5/8)──────────┐┌── old 区(老页,3/8)──┐
   │  [热点页A][热点页B][热点页C]...           ││  [新读入的页]          │
   │  ↑ 访问频率高,常驻                        ││  ↑ 新页先进这里       │
   └──────────────────────────────────────────┘└───────────────────────┘
                              ↑
                       innodb_old_blocks_pct = 3/8(默认 37%)

新页读入流程:
  ① 新页从磁盘读 → 加到 old 区头部(不是 young 头!)
  ② 若 old 区的页被再次访问,且存活 > innodb_old_blocks_time(默认 1秒)→ 升级到 young 区
  ③ young 区满了 → 淘汰 young 尾部到 old
  ④ old 区满了 → 淘汰 old 尾部(真正丢出 Buffer Pool)
```

**为什么能防全表扫污染**:全表扫读的页先进 old 区,但**这些页短时间内不会再被访问**,达不到升级 young 的条件,很快被淘汰——**不会冲掉 young 区的热点**。

**`innodb_old_blocks_time`**:默认 1 秒。意思是"old 区的页必须活过 1 秒才能升级 young"。这就把"扫一次就丢"的全表扫页挡在 old 区。

> 🔑 金句:**Buffer Pool 用改进版 LRU(分 young/old 两区)防全表扫污染——新页先进 old 区,活过 `innodb_old_blocks_time` 才升级 young,这样大表扫描不会冲掉热点。**

### 5.3 Log Buffer

redo log 的内存缓冲区,默认 16M。

```
事务改数据 → 写 Log Buffer(内存)→ 按 flush 策略刷到 redo log file(磁盘)
```

`innodb_flush_log_at_trx_commit` 决定刷盘时机(见 §4 ④)。Log Buffer 小但够用——redo log 是顺序追加写,刷盘很快。

## 6. InnoDB 磁盘架构(表空间/段/区/页/行)

InnoDB 把数据**按层级组织**,从大到小:

```
┌─────────────────────────────────────────────────────────────┐
│  表空间(Tablespace)                                          │
│  ├─ 系统表空间(ibdata1)        ← 数据字典/双写缓冲/Change Buf │
│  └─ 独立表空间(order.ibd)      ← 每张表一个文件(默认)         │
│      │                                                       │
│      ▼                                                       │
│  段(Segment)                                                 │
│  ├─ 数据段(叶子节点)                                          │
│  ├─ 索引段(非叶子节点)                                        │
│  └─ 回滚段(undo log)                                          │
│      │                                                       │
│      ▼                                                       │
│  区(Extent)= 64 个连续页 = 1MB                               │
│  ← InnoDB 按"区"分配空间(不是按页,减少碎片)                 │
│      │                                                       │
│      ▼                                                       │
│  页(Page)= 16KB(默认)  ⭐ 最小 IO 单位                      │
│  ├─ 数据页  ├─ 索引页  ├─ undo 页  ├─ 系统页  ├─ blob 页     │
│      │                                                       │
│      ▼                                                       │
│  行(Row)                                                     │
│  └─ 实际的订单记录(一行 = 一条 order)                         │
└─────────────────────────────────────────────────────────────┘
```

**关键数字**(必背):
- **页 = 16KB**(默认,最小 IO 单位,即一次磁盘 IO 读一页)
- **区 = 64 页 = 1MB**(分配单位,InnoDB 一次至少给一个区)
- **段**:B+树的叶子节点 = 数据段,非叶子 = 索引段
- **每页存多少行**:16KB ÷ 1KB(行平均)≈ 15 行;3 层 B+树叶子数 1365²×15 ≈ 2000 万行

**为什么按页(16KB)而不是按行读**:
- 磁盘 IO 成本主要在"寻道 + 旋转"(机械盘),读 1 字节和读 16KB 时间几乎一样
- 一次读一页,顺便把相邻数据带进内存(局部性原理),下次大概率命中 Buffer Pool

**为什么按区(1MB)分配**:
- 按页分配会导致**碎片**(页散落在磁盘各处,磁头乱跳)
- 按"连续 64 页"分配 → 物理上连续 → 顺序 IO 快

## 7. 页与行记录的物理结构

### 7.1 一个数据页的内部结构

```
┌──────────────────────── 16KB 数据页 ────────────────────────┐
│  File Header(38 字节)                                       │
│  ├─ 页号 / 上一页 / 下一页(B+树叶子链表)                     │
│  └─ 页类型(数据页/索引页/undo页)                            │
├──────────────────────────────────────────────────────────────┤
│  Page Header(56 字节)                                       │
│  ├─ 本页有多少行 / 空闲空间起始位置                          │
│  └─ 所属段                                                  │
├──────────────────────────────────────────────────────────────┤
│  Infimum + Supremum(虚拟行,最小/最大,13 字节)               │
├──────────────────────────────────────────────────────────────┤
│  用户记录区(实际存 order 行,从下往上长)                     │
│  ┌────────────────────────────────────────────┐              │
│  │ 行3: {order_id:3, user_id:88, amount:299}  │ ← 最新插入   │
│  │ 行2: {order_id:2, user_id:99, amount:199}  │              │
│  │ 行1: {order_id:1, user_id:88, amount:99}   │              │
│  └────────────────────────────────────────────┘              │
├──────────────────────────────────────────────────────────────┤
│  空闲空间(Free Space,插入新行往这里长)                      │
├──────────────────────────────────────────────────────────────┤
│  页目录(Page Directory,稀疏目录,二分查找用)                  │
├──────────────────────────────────────────────────────────────┤
│  File Trailer(8 字节)                                       │
│  ├─ 校验和(Checksum,检测页是否损坏)                         │
│  └─ LSN(Log Sequence Number,日志序号,用于崩溃恢复)          │
└──────────────────────────────────────────────────────────────┘
```

**关键设计**:
- **记录从下往上长,空闲在中间**——插入新行往空闲区加,不用移动老数据
- **页目录(Page Directory)**:把页内行分组,每组记最大主键 → 页内**二分查找** → O(log N)
- **File Trailer 的 Checksum**:刷盘后校验,防止"页撕裂"(写一半断电,页损坏)

### 7.2 一行的物理结构(Compact 行格式)

```
┌─────────────────────────────────────────────────────────────┐
│  变长字段长度列表  │  NULL 标志位  │  记录头信息  │  列数据   │
│  (变长列的长度)    │  (哪些列NULL) │ (40 字节)    │          │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
                    记录头信息(40 字节)详解:
                    ├─ delete_mask: 1 = 已删除(还没清理)
                    ├─ min_rec_mask: B+树非叶子最小记录标记
                    ├─ heap_no: 本页内位置
                    ├─ record_type: 0普通/1B+树指针/2最小/3最大
                    ├─ next_record: ⭐ 指向下一行(页内单向链表!)
                    └─ ...
                    
列数据(实际存储):
  ├─ 隐藏列 row_id(6字节,无主键时)/ DB_TRX_ID(6字节)/ DB_ROLL_PTR(7字节)
  └─ 业务列(order_id, user_id, amount, ...)
```

**next_record 是页内的单向链表**——页内行不是数组,是链表(按主键顺序)。这就是为什么"页内查找用二分(通过 Page Directory)+ 链表遍历"。

**NULL 值怎么存**:
- NULL 不占数据空间(只在 NULL 标志位标 1)
- 但**定长列**(如 INT)即使 NULL 也占空间 → 所以生产建议字段 NOT NULL DEFAULT

**变长字段(varchar)**:
- 实际长度存在"变长字段长度列表"
- varchar(255) 以下用 1 字节记长度,以上用 2 字节

## 8. 后台线程体系

InnoDB 是多线程架构,**后台线程负责刷盘/清理/回收**:

| 线程 | 干什么 | 触发频率 |
|------|--------|----------|
| **Master Thread** | 总调度(优先级最高的后台任务:刷脏页/写redo/purge) | 每秒/每10秒 |
| **IO Thread** | 异步 IO(read/write/insert buffer/AIO) | 持续 |
| **Purge Thread** | 回收已提交事务的 undo log(不再需要的版本链) | 持续 |
| **Page Cleaner Thread** | 专门刷脏页(从 Master 拆出来,减少 Master 压力) | 持续 |

**Master Thread 的"秒级/十秒级"循环**(老版本):
```
每秒:
  - 刷 redo log(如果没刷)
  - 合并 change buffer(如果有)
  - 刷脏页(如果脏页比例超阈值)

每 10 秒:
  - 刷脏页(强制)
  - 合并 change buffer
  - 删除无用 undo log
```

**8.0 改进**:Page Cleaner 独立成线程组,刷脏页不再阻塞 Master。`innodb_page_cleaners` 控制线程数(默认 4)。

## 9. 三大日志协同 + 崩溃恢复详解

### 9.1 三大日志的协同(写流程全景)

```
事务 BEGIN
   │
   ▼ ① 改数据
   Buffer Pool 脏页(内存) ← 改这里
   undo log(记录改前快照,用于回滚 + MVCC)
   │
   ▼ ② COMMIT
   ┌── 两阶段提交 ──┐
   │ redo log(prepare)│ ← 阶段1
   │ binlog(写盘)     │
   │ redo log(commit)  │ ← 阶段2
   └─────────────────┘
   │
   ▼ ③ 后台异步
   Page Cleaner 线程:Buffer Pool 脏页 → .ibd 文件(随机 IO,慢)
   Purge 线程:删除不再需要的 undo 版本
```

**三日志分工**:
- **redo log**:保证"已 COMMIT 的事务崩溃后能恢复"(持久性 D)
- **undo log**:保证"未 COMMIT 的事务能回滚"(原子性 A)+ MVCC 版本链
- **binlog**:保证"主从一致"(从库靠 binlog 重放)

### 9.2 崩溃恢复(Crash Recovery)详解⭐

崩溃场景:MySQL 写到一半断电。重启后怎么办?

**重启流程**:
```
① 加载数据字典(知道有哪些表)
② 扫 redo log,重放所有"已 commit"的事务(redo)
③ 对所有"未 commit"的事务,用 undo log 回滚
④ 恢复完成,对外服务
```

**关键问题:redo log 怎么知道哪些该重放,哪些该回滚?**——靠**两阶段提交 + binlog 判断**。

**LSN(Log Sequence Number,日志序号)**:redo log 每条都有个单调递增的 LSN,记录"日志写到哪了"。崩溃时:
- `redo log 的最大 LSN`(已写日志)
- vs `每个数据页的 LSN`(该页最后一次刷盘对应的日志位置)
- 若页 LSN < redo LSN → 这页有未刷的修改 → 重放这段 redo

**prepare 状态事务怎么处理**:
```
扫到 redo log 某事务是 prepare 状态(没到 commit):
   查对应 binlog:
   ├─ binlog 完整写完了 → 认为已提交(可能客户端收到成功了)→ 重放 redo
   └─ binlog 没写完    → 认为未提交 → 用 undo log 回滚
```

**为什么这样设计**:
- binlog 完整 = 客户端大概率收到"成功",从库也会收到 → 必须提交,否则主从不一致
- binlog 没写 = 客户端没收到成功,从库也没收到 → 安全回滚

> 🔑 金句:**崩溃恢复 = 重放 redo log(已提交的) + 用 undo log 回滚(未提交的)。两阶段提交让"prepare 状态的事务"能靠 binlog 完整性判断该提交还是回滚,保证主从一致。**

## 10. 核心机制:Change Buffer / Doublewrite / AHI / 改进版 LRU

### 10.1 Change Buffer(写优化,仅二级索引)

**痛点**:UPDATE 一个**二级索引列**(如把 order 的 status 从 0 改成 1):
- 如果这页在 Buffer Pool → 直接改,快
- 如果这页**不在** Buffer Pool → 要从磁盘读 16KB 页到内存 → 改 → 慢(随机 IO)

**Change Buffer 的做法**:
- 二级索引页不在 Buffer Pool 时,**先把"这次改动"记在 Change Buffer**(不读页)
- 等下次这页被读时,**再合并(merge)Change Buffer 的改动**到这页

```
无 Change Buffer:
  UPDATE 二级索引列 → 读磁盘页(随机IO慢)→ 改 → 写redo

有 Change Buffer:
  UPDATE 二级索引列 → 直接记 Change Buffer(快)→ 写redo
  后台/下次读时 → 合并 Change Buffer 到真实页
```

**为什么只对二级索引,不对聚簇索引**:
- 聚簇索引(主键)的更新大多是**顺序的**(自增 ID),页本来就在内存
- 二级索引更新是**随机的**(user_id 分散),经常要读磁盘 → Change Buffer 才有用武之地
- 唯一索引**不能用** Change Buffer(唯一性检查必须读页)

> 🔑 金句:**Change Buffer 是二级索引写优化——页不在内存时先把改动缓存,等下次读再合并,避免随机 IO。只对"非唯一二级索引"有效。**

### 10.2 Doublewrite 双写缓冲(防页撕裂)⭐

**痛点**:刷脏页时,16KB 页要写磁盘。写到一半**断电** → 页只写了一半 → **页撕裂(Page Torn)** → 这页损坏 → 数据丢失。

**Doublewrite 机制**:
```
① 脏页刷盘前,先写到"双写缓冲区"(一块连续的磁盘空间,2MB)
② 写完双写缓冲 → 再写到 .ibd 文件的正确位置

崩溃恢复:
   若发现某页损坏(Checksum 不对):
   → 从双写缓冲区找这页的副本 → 恢复
```

**为什么是"双"写**:
- 第一份:连续空间的副本(2MB,放 128 个页)
- 第二份:实际数据文件位置
- 双写保证"至少有一份完整"

**性能影响**:多一次写,但因为双写缓冲是**连续空间(顺序 IO)**,开销很小(<5%)。**生产必开**(`innodb_doublewrite=ON`,默认开)。

> 🔑 金句:**Doublewrite 防"页撕裂"——刷脏页前先写一份到连续的双写缓冲区,断电时用副本恢复。代价是 5% 的写性能,换数据安全,生产必开。**

### 10.3 自适应哈希索引(Adaptive Hash Index, AHI)

**痛点**:B+ 树查询是 O(log N)(3 层 = 3 次 IO)。某些**热点页被等值查询几百万次**,能不能更快?

**AHI 的做法**:
- InnoDB **自动监控**哪些索引页被高频等值访问
- 在 Buffer Pool 里给这些页建**哈希索引**(O(1) 查询)
- 完全自动,无需配置

```
B+ 树查询: 3次 IO(O(log N))
AHI 命中:  1次内存查找(O(1))  ← 快
```

**配置**:`innodb_adaptive_hash_index=ON`(默认开)。

**什么时候关掉**:高并发场景下,AHI 的**全局锁竞争**反而拖慢(多线程读写 AHI 要锁)。某些 OLTP 高并发场景关掉反而快——但这是极端调优,一般别动。

### 10.4 改进版 LRU(见 §5.2)

略,已在 Buffer Pool 一节详述。核心:young/old 两区防全表扫污染。

## 11. 工业级落地:Buffer Pool 调优 + 关键参数

### 11.1 Buffer Pool 调优(最常被问)

| 参数 | 含义 | 怎么设 |
|------|------|--------|
| `innodb_buffer_pool_size` | Buffer Pool 总大小 | **物理内存的 60-70%**(专用 MySQL 服务器可到 75%) |
| `innodb_buffer_pool_instances` | Buffer Pool 实例数(减少锁竞争) | size ≥ 1G 时设 8-16 |
| `innodb_old_blocks_pct` | old 区比例 | 默认 37%(一般别动) |
| `innodb_old_blocks_time` | old→young 存活时间 | 默认 1000ms(防全表扫污染) |

**调优案例**(16G 服务器):
```ini
innodb_buffer_pool_size = 10G          # 16G × 65%
innodb_buffer_pool_instances = 8        # 10G/8 ≈ 1.25G 每实例
```

**怎么判断 Buffer Pool 够不够**:
```sql
SHOW STATUS LIKE 'Innodb_buffer_pool_read_requests';  -- 总请求
SHOW STATUS LIKE 'Innodb_buffer_pool_reads';          -- 没命中从磁盘读的次数
-- 命中率 = 1 - reads/read_requests,应 > 99%
```

命中率 < 95% → Buffer Pool 不够,加大或加机器。

### 11.2 redo / binlog 双 1 配置(金融必选)

```ini
innodb_flush_log_at_trx_commit = 1     # redo 每次 commit 刷盘
sync_binlog = 1                         # binlog 每次 commit 刷盘
innodb_doublewrite = ON                 # 双写防页撕裂
```

**代价**:每次 commit 两次 fsync,TPS 降低 20-30%。金融场景必选,日志类业务可降级。

### 11.3 慢日志 + 监控(运维标配)

```ini
slow_query_log = ON
long_query_time = 1
log_queries_not_using_indexes = ON      # 开发环境开,生产慎用(太多)

# 监控关键指标:
# - Innodb_buffer_pool_wait_free(>0 说明 Buffer Pool 压力大)
# - Innodb_row_lock_waits(行锁等待,死锁前兆)
# - Threads_running(并发,连接池打满前兆)
```

## 12. 面试连环追问(10 条纵深链)

### 追问链 1:MySQL 整体架构

- **Q1:MySQL 分几层?** → 客户端层 / Server 层(连接器/解析器/优化器/执行器)/ 存储引擎层。Server 跨引擎,引擎层各自实现存储/锁/事务。
- **Q2:binlog 属于哪层?redo log 呢?** → binlog 在 Server 层(所有引擎共用);redo/undo 在 InnoDB 引擎层。
- **Q3:为什么 MyISAM 不支持事务?** → 它没有 redo log / undo log,这两个在 InnoDB 引擎层。MyISAM 只有表级锁,崩溃恢复也弱。

### 追问链 2:一条 SELECT 的流程

- **Q1:一条 SELECT 经过哪些步骤?** → 连接器(鉴权)→ 解析器(建解析树)→ 预处理(语义检查)→ 优化器(执行计划)→ 执行器(调引擎)→ 引擎走 B+ 树 → 返回。
- **Q2:优化器基于什么选索引?** → 基于 cost(IO + CPU)。依赖统计信息(cardinality),陈旧会选错。
- **Q3:`SELECT *` 有什么问题?** → ①无法覆盖索引(强制回表)②传不需要的列③表结构变了影响。应明确指定列。
- **Q4:查询缓存为什么 8.0 删了?** → 命中率低(表一改缓存全失效)、维护成本高、并发锁竞争大。

### 追问链 3:写流程(高频深挖)

- **Q1:一条 UPDATE 内部发生什么?** → ①Buffer Pool 找/读页 ②改内存(脏页)③写 redo log(Log Buffer)④两阶段提交(redo prepare → binlog → redo commit)⑤异步刷脏页。
- **Q2:为什么不直接改磁盘?** → 内存纳秒级,磁盘毫秒级(差 10 万倍)。改内存 + 异步刷脏页 = 高吞吐。
- **Q3:脏页什么时候刷盘?** → 后台 Page Cleaner 线程异步刷。触发:脏页比例超阈值 / redo log 快满 / MySQL 正常关闭。
- **Q4:redo log 什么时候写盘?** → 由 `innodb_flush_log_at_trx_commit` 控制:1=每次commit刷盘(安全)/ 2=刷OS Cache / 0=每秒刷。

### 追问链 4:三大日志

- **Q1:redo/undo/binlog 区别?** → redo(引擎层,物理,崩溃恢复);undo(引擎层,逻辑,回滚+MVCC);binlog(Server层,逻辑,主从复制)。
- **Q2:什么是 WAL?** → Write-Ahead Logging,先写日志(redo log 顺序快),再异步刷数据(随机慢),崩溃靠日志恢复。
- **Q3:为什么有两阶段提交?** → 保证 redo 和 binlog 一致。崩溃时靠 binlog 完整性判断该提交还是回滚。
- **Q4:双 1 配置是什么?** → `innodb_flush_log_at_trx_commit=1` + `sync_binlog=1`,每次 commit 都 fsync,最安全,金融必选。

### 追问链 5:Buffer Pool

- **Q1:Buffer Pool 装什么?** → 数据页 + 索引页 + change buffer + AHI + 锁信息 + 数据字典缓存。
- **Q2:LRU 怎么改进的?** → 分 young/old 两区。新页先进 old,存活过 `innodb_old_blocks_time`(1秒)才能升级 young。防全表扫污染。
- **Q3:Buffer Pool 多大合适?** → 物理内存 60-70%,命中率(1 - reads/requests)应 > 99%。
- **Q4:Buffer Pool instances 是什么?** → 多实例减少锁竞争,size ≥ 1G 时设 8-16。

### 追问链 6:页和行结构

- **Q1:InnoDB 页多大?为什么?** → 16KB(默认)。一次磁盘 IO 读一页,16KB 是 OS 页(4KB)的整数倍 + 兼顾局部性。
- **Q2:页内行怎么组织?** → 单向链表(next_record)+ Page Directory(稀疏目录,二分查找)。
- **Q3:NULL 值怎么存?** → 定长列占空间(只在标志位标 NULL),变长列不占空间。所以建议 NOT NULL DEFAULT。

### 追问链 7:Change Buffer

- **Q1:Change Buffer 解决什么?** → 二级索引页不在内存时的写优化,先缓存改动避免随机 IO。
- **Q2:为什么只对二级索引?** → 聚簇索引顺序写,页常驻内存;二级索引随机写,常要读盘。唯一索引不能用(要读页检查唯一性)。
- **Q3:什么时候合并?** → 下次读这页时 / 后台线程定期 / MySQL 关闭前。

### 追问链 8:Doublewrite

- **Q1:什么是页撕裂?** → 16KB 页写到一半断电,页只写了一部分,损坏。
- **Q2:Doublewrite 怎么解决?** → 刷脏页前先写一份到连续的双写缓冲区,断电用副本恢复。
- **Q3:为什么不直接写两份到数据文件?** → 双写缓冲是连续空间(顺序 IO,快),数据文件位置是随机的(随机 IO,慢)。

### 追问链 9:崩溃恢复

- **Q1:崩溃后怎么恢复?** → 重放 redo log(已提交的)+ 用 undo log 回滚(未提交的)。
- **Q2:怎么判断哪些该重放?** → 靠 LSN(页 LSN vs redo LSN),页 LSN 小说明有未刷的修改。
- **Q3:prepare 状态怎么处理?** → 查 binlog 完整性:完整则提交重放,不完整则 undo 回滚。

### 追问链 10:架构级(架构师岗)

- **Q1:InnoDB 和 MyISAM 的本质区别?** → InnoDB 支持事务(有redo/undo)+ 行锁 + 崩溃恢复 + 聚簇索引;MyISAM 无事务 + 表锁 + 索引数据分离。
- **Q2:为什么 InnoDB 主键建议自增?** → 自增保证顺序追加到 B+树末尾,避免页分裂;UUID 随机插入导致频繁页分裂,写性能差。
- **Q3:一台 MySQL 服务器内存怎么分?** → Buffer Pool 60-70% + OS/连接/临时表/其他 30%。监控命中率调优。
- **Q4:MySQL 的瓶颈在哪?怎么扩展?** → 单机瓶颈:CPU/内存/IO。扩展路径:垂直升级(加内存/SSD)→ 读写分离 → 分库分表 → 用 NewSQL(TiDB)/NoSQL。

## 13. 金句速记卡

> 🔑 **架构分层**:Server 层(连接/解析/优化/执行,跨引擎)+ 存储引擎层(数据/索引/锁/事务,引擎自实现)。binlog 属 Server,redo/undo 属 InnoDB。

> 🔑 **SELECT 流程**:连接器→解析器→预处理→优化器→执行器→引擎→返回。优化器基于 cost,统计信息陈旧会选错索引。

> 🔑 **写流程**:改 Buffer Pool(脏页)→ 写 redo log → 两阶段提交(redo prepare+binlog+redo commit)→ 异步刷脏页。核心是 WAL。

> 🔑 **Buffer Pool**:数据页+索引页+change buffer+AHI;改进版 LRU 分 young/old 防全表扫污染;命中率应 > 99%。

> 🔑 **页结构**:16KB / 区 1MB / 段按 B+树节点分;页内行单向链表 + Page Directory 二分。

> 🔑 **三日志协同**:redo 保持久(崩溃恢复)+ undo 保原子(回滚+MVCC)+ binlog 保主从;两阶段提交保证 redo/binlog 一致。

> 🔑 **崩溃恢复**:重放 redo(已提交)+ undo 回滚(未提交);prepare 状态靠 binlog 完整性判断。

> 🔑 **Change Buffer**:二级索引写优化,页不在内存先缓存,避免随机 IO;唯一索引不能用。

> 🔑 **Doublewrite**:防页撕裂,刷脏页前先写连续双写缓冲区,生产必开。

> 🔑 **AHI**:自适应哈希索引,自动给热点页建哈希,O(1) 查询;高并发锁竞争时考虑关闭。
