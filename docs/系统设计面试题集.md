## 核心深入：Redis Lua 预扣库存（防超卖）

```
Redis Lua原子操作:

  -- KEYS[1] = "seckill:stock:iPhone16"
  -- KEYS[2] = "seckill:users:iPhone16"
  -- ARGV[1] = userId
  
  -- 检查是否已抢过(防重复)
  if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then
      return -2  -- 已抢过
  end
  
  -- 读库存
  local stock = tonumber(redis.call('GET', KEYS[1]))
  if stock <= 0 then
      return 0   -- 售罄
  end
  
  -- 原子扣减(关键!)
  redis.call('DECR', KEYS[1])
  redis.call('SADD', KEYS[2], ARGV[1])
  
  return 1  -- 抢成功

为什么用Lua:
  - 整段脚本Redis单线程原子执行
  - "读库存-判-扣"三步原子, 不会超卖
  - 比Java应用层"读-判-扣"安全(应用层有并发问题)

错误做法(应用层, 超卖!):
  stock = redis.get(stock)  // 读
  if (stock > 0) {          // 判
      redis.decr(stock)     // 扣
      // 两线程同时读到1, 都判>0, 都扣 → 超卖!
  }
```

## 关键设计点

| 设计点 | 方案 | 理由 |
|---|---|---|
| 防超卖 | Redis Lua 原子操作 | 单线程原子，应用层有并发问题 |
| 削峰 | MQ（RocketMQ） | DB 只承受 100 QPS |
| 防黄牛 | 验证码 + 用户限流 + IP 限流 | 多层防御 |
| Redis 兜底 | 本地缓存（Caffeine AtomicLong） | Redis 挂了短暂可用 |
| 库存预热 | 秒杀前加载到 Redis | 避免开抢瞬间打 DB |
| 异步通知 | MQ + 前端轮询/WebSocket | 用户异步等结果 |

## 面试连环追问

**Q1：怎么防超卖？**
> Redis Lua 原子操作。Lua 脚本在 Redis 单线程执行，"读-判-扣"原子不可分割。比 Java 应用层安全（应用层三步有并发）。

**Q2：Redis 挂了怎么办？**
> (1)Redis Cluster 高可用 + 哨兵自动切换；(2)本地缓存（Caffeine AtomicLong）兜底，启动时从 Redis 加载，Redis 挂了用本地短暂支撑；(3)极限降级：直接关闭秒杀（保命）。

**Q3：怎么防黄牛？**
> 多层：(1)前端验证码（防脚本）；(2)用户限流（单用户 1 次）；(3)IP 限流；(4)Redis SET 标记已抢；(5)行为分析（异常模式识别）。

**Q4：用户怎么知道抢中？**
> 异步。抢中的进 MQ，用户跳"等待页"前端轮询（或 WebSocket 推送）。后端消费 MQ 创建订单后更新状态，用户轮询到"抢中，去支付"。

**Q5：Redis 和 DB 库存怎么一致？**
> Redis 预扣是"临时扣"，DB 真扣（消费 MQ 时）。用户抢中但超时未支付 → 订单取消 → 回滚 Redis 库存（+1）。最终一致。

│       │                                                      │

## 核心深入：发号器（短码生成）

```
某创业项目发号器(雪花算法 + 62进制 + 加盐):

  步骤1: 雪花算法生成全局唯一ID
    时间戳(41bit) + 机器ID(10bit) + 序列号(12bit)
    = 1234567890
    
  步骤2: 62进制转换(短化)
    1234567890 / 62 = 商19912385 余20(对应字符'k')
    19912385 / 62 = ...
    → "dNZ7i" (5字符)
    
    为什么62进制:
      62 = 10数字+26小写+26大写
      6位62进制 = 62^6 ≈ 568亿种(够用)
      6位10进制 = 100万种(不够)
      → 62进制比纯数字短6倍
    
  步骤3: 加盐混淆(防遍历)
    不加盐: 1,2,3,4... → 爬虫枚举所有短链
    加盐: 用固定salt哈希打乱
      "dNZ7i" → HMAC("dNZ7i", "komall-salt") → "xK9pN"
      连续ID生成的短码不连续 → 不可预测
```

## 关键设计点

| 设计点 | 方案 | 理由 |
|---|---|---|
| 短码生成 | 雪花 ID + 62 进制 + 加盐 | 唯一+短+不可预测 |
| 读性能 | CDN + 本地 + Redis 多级缓存 | 99% 命中缓存 |
| 防穿透 | 布隆过滤器 | 不存在的短码直接拒 |
| 重定向 | 302（临时） | 每次访问能统计点击 |
| 点击统计 | 异步 MQ → ClickHouse | 不拖慢跳转 |

## 面试连环追问

**Q1：为什么用 62 进制？**
> 62 = 10 数字 + 26 小写 + 26 大写，6 位 62 进制有 62⁶≈568 亿种组合，比纯数字（6 位 10 进制 100 万种）短 6 倍。

**Q2：短码怎么保证不可预测？**
> 加盐混淆。生成的短码用 HMAC 加固定 salt 哈希一次，连续 ID 生成的短码不连续，爬虫无法枚举。

**Q3：为什么用 302 不用 301？**
> 301 永久重定向浏览器缓存，下次不访问短链服务（无法统计点击）；302 临时重定向每次都访问（能统计）。短链要统计点击，用 302。

**Q4：跳转高并发怎么扛？**
> 三级缓存：CDN（缓存 302 响应）→ Caffeine 本地 → Redis。99% 命中缓存。布隆过滤器防穿透。

# 题目 3：订单系统

## 需求与估算

- **场景**：某创业项目核心交易（下单 + 扣库存 + 扣余额）
- **规模**：日均订单 100 万，峰值 1 万 QPS
- **数据**：3 年累积 10 亿订单

## 完整架构图

```
某创业项目订单系统:

  用户 ──下单──▶ 订单服务
                  │
                  │ @GlobalTransactional(Seata AT)
                  ├─ 创建订单(订单库INSERT)
                  ├─ 调库存服务扣库存(Dubbo)
                  ├─ 调账户服务扣余额(Dubbo)
                  ├─ 发"订单创建"消息(RocketMQ事务消息)
                  │   → 积分服务异步加积分
                  │   → 优惠券服务异步发券
                  │   → 短信服务异步通知
                  └─ 返回"下单成功"(110ms)
                  
                  ↓ 订单状态: PENDING(待支付)

  状态机:
  PENDING ──支付──▶ PAID ──发货──▶ SHIPPED ──确认──▶ DONE
     │                 │
     │超时30min        │退款
     ▼                 ▼
  CANCELLED        REFUNDED
  (规则: 只能前进, 不能倒退)

  幂等(防重复):
  前端token ──▶ 后端Redis GETDEL ──▶ 第一次处理/重复拒绝
  + DB唯一索引(user_id, product_id, activity_id)
  + 状态机(支付时校验PENDING才能变PAID)

  分库分表:
  user_id % 16 → 路由到16个库
  每库按月分表(t_order_202407)
  ShardingSphere-JDBC路由透明
  聚合查询 → 剥到ClickHouse(OLAP)
```

## 核心深入：幂等三层防护

```
某创业项目下单接口幂等(防重复下单):

  问题场景:
    1. 用户狂点"下单" → 两次请求同时到 → 创建两个订单?
    2. 网络抖动重试 → 重复扣款?
    3. 支付回调重试 → 订单状态错乱?
  
  方案1: 幂等token(防用户狂点)
    前端进入页面 ──获取token──▶ 后端(Redis SETNX token)
    前端提交订单(token) ──▶ 后端
      后端: Redis GETDEL token
        ├── 成功(第一次) → 处理订单
        └── 失败(token已删) → 重复, 拒绝
  
  方案2: 业务唯一索引(DB兜底)
    订单表UNIQUE(user_id, product_id, activity_id, dt_minute)
    重复INSERT → DB唯一索引冲突 → 拒绝
  
  方案3: 状态机(防业务重复)
    支付回调: 校验订单状态
      PENDING → PAID(正常)
      PAID → 已经支付过(重复回调, 跳过)
      CANCELLED → 订单已取消(拒绝)

  生产组合用: token + 唯一索引 + 状态机
```

## 关键设计点

| 设计点 | 方案 | 理由 |
|---|---|---|
| 分布式事务 | Seata AT | 跨服务强一致，业务无侵入 |
| 防超卖 | FOR UPDATE 行锁 | 强一致扣减 |
| 幂等 | token + 唯一索引 + 状态机 | 三层防护 |
| 状态机 | PENDING→PAID→SHIPPED→DONE | 防非法跳转 |
| 异步 | RocketMQ 事务消息 | 加积分/通知异步解耦 |
| 超时取消 | RocketMQ 延迟消息（30min） | 自动取消未支付订单 |
| 海量存储 | 按 user_id 分 16 库 | 查"我的订单"只查一个库 |
| 聚合查询 | ClickHouse OLAP | 不让 OLTP 干 OLAP 的活 |

## 面试连环追问

**Q1：怎么保证幂等？**
> 三层：(1)token（前端获取，后端 GETDEL 防重复）；(2)唯一索引（DB 层防重）；(3)状态机（支付时校验 PENDING 才能变 PAID）。生产组合用。

**Q2：订单状态机怎么设计？**
> PENDING→PAID→SHIPPED→DONE，只能前进不能倒退。每次状态变更前校验"当前状态允许转到目标状态吗"。防非法跳转（如 PAID 不能回 PENDING）。

**Q3：订单 30 分钟未支付怎么取消？**
> RocketMQ 延迟消息。下单时发延迟 30 分钟消息，30 分钟后消费：检查还是 PENDING（没支付）→ 改 CANCELLED → 释放库存/余额。

**Q4：10 亿订单怎么存？**
> 按 user_id 分 16 库（ShardingSphere）。查"我的订单"只查一个库（user_id 路由）。聚合查询（全网订单总数）剥到 ClickHouse。

# 题目 4：Feed 流 / 朋友圈

## 需求与估算

- **场景**：某创业项目"关注"功能（类似朋友圈）
- **规模**：日活千万，大 V 粉丝百万
- **挑战**：大 V 发帖，百万粉丝收件箱要更新（写放大）

## 完整架构图

```
某创业项目Feed流(推拉混合模式):

  普通用户(粉丝<10万): "推"(写扩散)
  ┌────────────────────────────────────────────┐
  │ 张三发帖                                   │
  │   └─ 写自己的Timeline                      │
  │   └─ 【推】给所有粉丝的收件箱(Redis List) │
  │       粉丝A收件箱: [张三的帖子]            │
  │       粉丝B收件箱: [张三的帖子]            │
  │   粉丝读 → 直接读收件箱(已聚合)           │
  │                                            │
  │ 适合: 粉丝少, 写开销可控                   │
  └────────────────────────────────────────────┘

  大V(粉丝>10万): "拉"(读扩散)
  ┌────────────────────────────────────────────┐
  │ 明星发帖                                   │
  │   └─ 只写自己的Timeline(不推给百万粉丝!)  │
  │   粉丝读 → 读自己收件箱 +                  │
  │            拉关注的大V最新帖(合并)         │
  │                                            │
  │ 适合: 粉丝多, 写放大严重(推百万次太贵)    │
  └────────────────────────────────────────────┘

  混合模式(生产):
    粉丝<阈值 → 推
    粉丝≥阈值 → 拉
    兼顾写性能和读性能

  存储:
    Timeline: MySQL(按用户+时间) + Redis缓存
    收件箱: Redis List(每用户一个, LRU保留最近1000条)
    大V帖: 单独存, 读时拉
```

## 关键设计点

| 设计点 | 方案 |
|---|---|
| 普通用户 | 推（写扩散），发帖时推给所有粉丝收件箱 |
| 大 V | 拉（读扩散），只写 Timeline，粉丝读时拉 |
| 阈值 | 粉丝 > 10 万用拉，否则推 |
| 收件箱 | Redis List，LRU 保留最近 1000 条 |
| 排序 | 按时间（或按权重，如算法推荐） |

## 面试连环追问

**Q1：为什么大 V 用拉不用推？**
> 大 V 百万粉丝，推 = 写放大百万倍（一次发帖写百万收件箱），性能扛不住。拉 = 只写自己 Timeline，粉丝读时合并，读开销可控。

**Q2：普通用户怎么读 Feed？**
> 直接读 Redis 收件箱（发帖时已聚合好），O(1) 快。收件箱用 List，LRU 保留最近 1000 条。

**Q3：怎么保证 Feed 实时性？**
> 推模式实时（发帖立即进收件箱）。拉模式有秒级延迟（读时聚合）。**普通用户实时性高（推），大 V 秒级延迟（拉）可接受**。

# 题目 5：IM 即时通讯系统

## 需求与估算

- **场景**：某创业项目客服系统（用户 ↔ 客服）
- **规模**：日活 100 万，并发在线 10 万
- **挑战**：消息可靠投递 + 在线状态 + 消息顺序

## 完整架构图

```
某创业项目IM系统:

  用户A ──发消息──▶ IM网关(WebSocket长连接)
                       │
                       ▼
                  消息服务
                       │
           ┌───────────┼───────────┐
           ▼           ▼           ▼
       消息存储    在线状态      消息推送
       (MySQL     (Redis      (MQ推送
       +MongoDB)  存在线)     到接收方)
           │
           │ 消息ID(全局递增, 保证顺序)
           │ 消息状态(发送/送达/已读)
           │
           ▼
       接收方B(在线) → WebSocket推送
       接收方B(离线) → 离线存储, 上线后推送

  消息可靠投递(核心):
    用户A发消息 → 消息服务存DB → 返回A"已发送"
    消息服务推送B → B收到回ACK → 标记"已送达"
    B读消息 → 回"已读" → 标记"已读"
    (类似微信的"发送✓ 送达✓✓ 已读")

  在线状态:
    用户登录 → Redis SET online:user:1001 "connection_id"
    用户登出 → Redis DEL
    发消息前查在线状态决定推送方式

  消息顺序:
    单聊: 用全局递增消息ID(发号器)
    同一会话按ID排序, 保证顺序
```

## 关键设计点

| 设计点 | 方案 |
|---|---|
| 长连接 | WebSocket（双向实时） |
| 消息存储 | MySQL（结构化）+ MongoDB（海量历史） |
| 在线状态 | Redis（key=online:user:xxx） |
| 消息推送 | MQ 异步推到接收方 |
| 消息顺序 | 全局递增消息 ID（发号器） |
| 可靠投递 | 存储后推送 + ACK 确认 + 离线补偿 |

## 面试连环追问

**Q1：怎么保证消息不丢？**
> (1)发送方：消息先存 DB 再返回"已发送"（存了才回，不存不回）；(2)接收方：收到回 ACK，没 ACK 重试推送；(3)接收方离线：消息存离线队列，上线后推送。**存储+ACK+离线补偿**三重保证。

**Q2：怎么保证消息顺序？**
> 全局递增消息 ID（发号器生成）。同一会话按 ID 排序，前端按序展示。

**Q3：群聊怎么设计？**
> 写扩散（小群，给每个成员存一份）+ 读扩散（大群，存一份，成员读时拉）。类似 Feed 流的推拉模式。

# 题目 6：延迟任务系统

## 需求与估算

- **场景**：订单 30 分钟未支付自动取消、定时推送、会员到期提醒
- **规模**：千万级延迟任务，精度秒级

## 完整架构图

```
某创业项目延迟任务系统:

  方案选型:
  ┌──────────────────────────────────────────────┐
  │ 方案1: Redis ZSet(简单, 中小规模)           │
  │  ZADD delay_tasks <到期时间戳> taskId        │
  │  定时扫描: ZRANGEBYSCORE 0 <now>             │
  │  到期的取出执行 + ZREM                        │
  │  优点: 简单    缺点: 扫描开销                │
  ├──────────────────────────────────────────────┤
  │ 方案2: 时间轮(高效, Kafka/Netty用)          │
  │  环形数组(如360格), 每格存任务链表           │
  │  指针每秒转一格, 转到格执行                  │
  │  优点: O(1)添加/到期                         │
  │  缺点: 长延迟需多层时间轮                    │
  ├──────────────────────────────────────────────┤
  │ 方案3: MQ延迟消息(RocketMQ)                 │
  │  RocketMQ原生18级延迟(1s/5s/...2h)          │
  │  发延迟消息, 到期自动消费                    │
  │  优点: 开箱即用  缺点: 延迟级别固定         │
  ├──────────────────────────────────────────────┤
  │ 方案4: 数据库轮询(兜底)                     │
  │  定时扫"到期未处理"的任务                    │
  │  优点: 简单可靠  缺点: 精度差                │
  └──────────────────────────────────────────────┘

  某创业项目方案(混合):
    订单超时(30分钟固定) → RocketMQ延迟消息(开箱即用)
    自定义延迟(灵活) → Redis ZSet(中小规模) / 时间轮(大规模)
    兜底 → DB轮询(防止MQ/ZSet任务丢失)

  时间轮原理:
    ┌──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┐
    │  │  │任│  │  │  │  │  │  │  │  │  │ ← 第3格有任务
    └──┴──┴──┴──┴──┴──┴──┴──┴──┴──┴──┴──┘
         ↑指针(每秒转一格)
    指针转到第3格 → 执行该格所有任务
    
    添加任务: 算到期在第几格 → 放那格
    O(1)添加, O(1)到期(指针自然到)
```

## 关键设计点

| 设计点 | 方案 |
|---|---|
| 固定延迟 | RocketMQ 延迟消息（18 级） |
| 自定义延迟 | Redis ZSet（中小）/ 时间轮（大） |
| 兜底 | DB 轮询（防丢失） |
| 精度 | 秒级 |
| 可靠 | 任务持久化 + ACK + 重试 |

## 面试连环追问

**Q1：为什么用时间轮不用定时器？**
> 大量定时任务用 Timer/ScheduledThreadPool 每个任务一个定时器，内存爆炸。时间轮所有任务共享一个指针，O(1) 添加/到期，适合海量任务。

**Q2：时间轮怎么处理长延迟？**
> 多层时间轮。秒级轮（60 格）+ 分钟轮（60 格）+ 小时轮（24 格）。任务先入小时轮，到期降到分钟轮，再降到秒轮。

# 题目 7：排行榜系统

## 需求与估算

- **场景**：商品销量榜、用户积分榜、直播打赏榜
- **规模**：千万用户实时排行，Top N 查询
- **挑战**：实时更新 + Top N 快速查询

## 完整架构图

```
某创业项目排行榜(Redis ZSet):

  数据结构: Redis Sorted Set(ZSet)
    member: 商品ID / 用户ID
    score: 销量 / 积分 / 打赏金额

  写(更新分数):
    ZINCRBY product:sales:rank 1 "iPhone16"
    (原子加分数, O(logN))

  读(查Top10):
    ZREVRANGE product:sales:rank 0 9 WITHSCORES
    (从高到低取前10, O(logN+M))

  读(查某商品排名):
    ZREVRANK product:sales:rank "iPhone16"
    (查排名, O(logN))

  定时快照(持久化):
    每5分钟ZREVRANGE全量 → 存MySQL(防Redis挂数据丢)

  分时段排行:
    日榜: product:sales:rank:20240704
    周榜: product:sales:rank:2024-W27
    月榜: product:sales:rank:202407
    (用不同key, Redis ZSet独立)
```

## 关键设计点

| 设计点 | 方案 |
|---|---|
| 数据结构 | Redis ZSet（跳表+哈希表） |
| 更新分数 | ZINCRBY（原子，O(logN)） |
| Top N | ZREVRANGE（O(logN+M)） |
| 查排名 | ZREVRANK（O(logN)） |
| 持久化 | 定时快照到 MySQL |

## 面试连环追问

**Q1：为什么用 ZSet？**
> ZSet 底层跳表+哈希表。跳表按 score 有序（范围查询快，Top N O(logN+M)），哈希表 member→score（等值查询 O(1)）。**两者结合，排行榜场景完美**。

**Q2：千万用户全量排行，内存够吗？**
> 千万 member × (member 字符串+score 8 字节+指针) ≈ 几 GB，Redis 单实例够。如果更大，按维度分片（如按类目分排行榜）。

**Q3：Redis 挂了排行榜数据怎么办？**
> 定时快照（每 5 分钟 ZREVRANGE 全量存 MySQL）。Redis 挂了从 MySQL 恢复最近快照 + 实时增量从业务日志重放。

# 题目 8：文件存储系统

## 需求与估算

- **场景**：某创业项目商品图片、用户头像、订单凭证上传
- **规模**：日均上传 100 万文件，单文件最大 100MB
- **挑战**：大文件上传 + 秒传 + 断点续传

## 完整架构图

```
某创业项目文件存储系统:

  上传流程:
  ┌──────────────────────────────────────────────────────────┐
  │ ① 客户端计算文件MD5                                       │
  │     MD5 = "abc123def456..."                              │
  │                                                          │
  │ ② 问服务端"这个MD5传过吗"(秒传检查)                      │
  │     服务端查DB: 文件MD5存在?                              │
  │     ├── 存在 → 秒传(直接返回URL, 不传文件!)              │
  │     └── 不存在 → 继续                                    │
  │                                                          │
  │ ③ 分片上传(大文件)                                       │
  │     文件切成1MB一片                                       │
  │     并发上传各片(每片独立MD5校验)                         │
  │     断点续传: 已传的片跳过(用MD5检查)                    │
  │                                                          │
  │ ④ 合并分片                                               │
  │     所有片上传完 → 服务端合并 → 计算总MD5校验            │
  │                                                          │
  │ ⑤ 存储到对象存储                                         │
  │     阿里云OSS / 腾讯云COS / 自建MinIO                    │
  │     返回URL                                              │
  │                                                          │
  │ ⑥ 写元数据                                               │
  │     DB: file_id, MD5, size, url, uploader, time          │
  └──────────────────────────────────────────────────────────┘

  CDN加速(读):
    用户访问图片URL → CDN边缘节点 → 命中直接返回
    未命中 → 回源OSS → 缓存到CDN → 返回

  存储:
    热数据: OSS标准存储
    冷数据(3个月未访问): OSS低频存储(省钱)
    归档(1年未访问): OSS归档存储(更省钱)
```

## 关键设计点

| 设计点 | 方案 |
|---|---|
| 秒传 | MD5 校验，相同文件不重复传 |
| 断点续传 | 分片上传 + 每片 MD5 |
| 大文件 | 分片并发上传 |
| 存储 | 对象存储（OSS/COS/MinIO） |
| 加速 | CDN 边缘缓存 |
| 冷热分离 | 热标准/冷低频/归档 |

## 面试连环追问

**Q1：秒传怎么实现？**
> 上传前客户端算文件 MD5，问服务端"这个 MD5 存在吗"。存在说明之前有人传过同样文件 → 直接返回 URL（不传文件）。**相同文件只存一份**（去重）。

**Q2：断点续传怎么实现？**
> 分片上传。文件切 1MB 一片，每片独立 MD5。上传中断后恢复，已传的片（MD5 匹配）跳过，只传未完成的。**提升大文件上传可靠性**。

**Q3：怎么去重？**
> MD5 相同的文件只存一份（物理去重）。DB 记录"MD5 → 文件位置"映射，多个用户引用同一 MD5 共享存储。**省存储成本**。

## 通用答题技巧

1. **先问清楚需求**（不要假设）——用户量/QPS/场景/数据规模
2. **先画架构图再深挖**（不要直接跳细节）
3. **容量估算**（展现工程感）——QPS = 用户数 × 频次 / 86400
4. **深入设计 1-2 个核心点**（不要面面俱到，深挖最难的）
5. **讨论权衡**（CAP/性能/成本，不回避缺点）
6. **监控运维**（展现生产经验）——告警/容灾/扩展
