# 模块一：秒杀系统要解决什么

## 📖 原理讲解 + 工程实现

### 1.1 普通下单 vs 秒杀下单——量级差 10 倍

**普通下单场景**：某创业项目日常峰值 1 万 QPS，MySQL 单机扛得住（5 千 QPS/实例 + 主从读分担）。

**秒杀场景**：双 11 开抢瞬间，100 万人同时点"立即抢购"，峰值 **10 万 QPS**。

**量级差 10 倍**，但更致命的是**瞬时洪峰**——10 万 QPS 不是均匀分布，而是开抢后 1 秒内集中涌入（用户都盯着倒计时 00:00:00 同时点按钮）。

**直接打 DB 的后果**：
- 10 万 QPS 打 MySQL（能力 1 万 QPS）
- DB 连接池瞬间占满（500 个连接全占满）
- CPU 100%（锁竞争 + 大量 SQL）
- 雪崩：整个订单服务挂掉，所有用户都失败

**结论**：秒杀系统不能让流量直接打 DB，**必须层层削减**。

### 1.2 三个核心挑战

**挑战 1：瞬时高并发**（10 万 QPS 洪峰）
- 单机 MySQL 扛不住（连接池满 + CPU 100% + 锁竞争 + 雪崩）
- 必须层层削减流量

**挑战 2：防超卖**（库存 1000 件，不能卖 1001 件）
- 高并发下"读-判-扣"三步非原子 → 超卖
- 超卖 = 资损（多卖的商品发不出货，要赔钱 + 信任崩塌 + 法律风险）

**挑战 3：防黄牛**（脚本/羊毛党）
- 黄牛用脚本 0.01 秒抢一次，真人根本抢不到
- 不能让脚本把库存抢光

### 1.3 秒杀系统的核心思想——层层削减（漏斗模型）

**核心理念**：像漏斗一样，每一层都削减流量，最终只有少量请求到 DB。

```
100万用户 → 前端削减到20万 → 网关削减到1万 → Redis预扣削减到1000 → DB处理1000
```

**为什么这样设计**：
- **DB 最脆弱**（最扛不住并发）→ 让最少的请求到 DB
- **前端/网关/Redis 抗并发**（无状态，可水平扩展）→ 让它们承担大部分流量
- **MQ 削峰填谷**：把瞬时洪峰削成 DB 能承受的平稳流量

> 🔑 **核心认知**：秒杀系统不是"让 DB 扛住 10 万 QPS"，而是"让 DB 只处理 1000 个真实下单请求"。其他 99 万请求在前端/网关/Redis 就被挡掉了。

## 🔥 面试连环追问

### 追问链 1：秒杀基础

**Q1：秒杀系统和普通下单有什么区别？**

> 量级差 10 倍以上（普通 1 万 QPS，秒杀 10 万+），且瞬时洪峰集中（开抢后 1 秒涌入）。普通下单 DB 直接扛，秒杀必须层层削减流量，最终只让少量请求到 DB。

**Q2（追问）：秒杀的三个核心挑战？**

> (1)瞬时高并发（10 万 QPS 洪峰，DB 扛不住）；(2)防超卖（库存 1000 不能卖 1001，超卖 = 资损）；(3)防黄牛（脚本抢光库存）。核心解法是层层削减流量。

**Q3（追问）：为什么不能直接加机器让 DB 扛？**

> (1)成本（10 倍机器只为 1 秒洪峰，浪费）；(2)DB 扩展性差（加从库分担读，但写还是主库单点）；(3)即使加机器也扛不住瞬时 10 万 QPS 的锁竞争。**秒杀的核心是削减流量，不是扩容 DB**。

# 模块二：完整架构——7 层防御

## 📖 原理 + 工程

### 2.1 第 1 层：前端削减（挡 80% 流量）

**6 个手段**：

**手段 1：按钮置灰**（防重复提交）
- 用户点"抢购"后按钮立即变灰，3 秒后才能再点
- 防止用户狂点（一次点击只发一个请求）

**手段 2：验证码**（防脚本自动化）
- 开抢前弹出滑块/算术验证码
- 脚本难自动过 → 挡掉脚本流量

**手段 3：倒计时**（防提前请求）
- 按钮显示倒计时（距开抢 00:00:30）
- 倒计时结束前按钮不可点
- 防止用户提前刷接口

**手段 4：页面静态化 + CDN**（防后端被打）
- 秒杀活动页（HTML/CSS/JS/图片）放 CDN
- 用户访问页面不查后端，CDN 直接返回
- 只有"抢购"动作才请求后端

**手段 5：静态库存显示**（防查库存打 DB）
- 库存数字前端写死（"仅剩 1000 件"）
- 或前端定时拉（每 5 秒查 Redis，不查 DB）

**手段 6：答题/问卷**（阿里双 11 经典手段）
- 抢购前要回答一个简单问题（如"3+5=?"）
- 既防脚本，又错开用户点击时间（削峰）

### 2.2 第 2 层：接入层限流（OpenResty + Nginx）

**3 种限流**：

**限流 1：IP 限流**（防爬虫/分布式脚本）
```nginx
limit_req_zone $binary_remote_addr zone=seckill:10m rate=1r/s;
# 单IP每秒1次, 超过拒绝
```

**限流 2：用户限流**（防单用户多账号）
- 单用户 ID 每秒只能请求 1 次

**限流 3：全局令牌桶**（防总流量过载）
- OpenResty 用 shared_dict 实现令牌桶
- 总 QPS 限制在网关能承受的范围

### 2.3 第 3 层：网关鉴权限流（Spring Cloud Gateway + Sentinel）

**职责**：
- **鉴权**：JWT 验证，未登录拒绝
- **接口限流**：Sentinel 按 API 限流（秒杀接口 1 万 QPS）
- **黑名单**：已知黄牛 IP/用户拒绝
- **熔断降级**：下游故障返回兜底

### 2.4 第 4 层：应用层 + 本地缓存预减（Caffeine）

**本地缓存预减库存**（Redis 兜底前先挡一层）：
```java
// 应用启动时从Redis加载库存到本地
private AtomicLong localStock;

public Result seckill(Long userId, Long productId) {
    // ① 本地预减(原子)
    long remain = localStock.decrementAndGet();
    if (remain < 0) {
        return Result.fail("售罄");  // 本地售罄直接拒绝
    }
    // ② 本地有库存才查Redis
    // ...
}
```

**价值**：售罄后本地直接拒绝，不查 Redis（减 Redis 压力）；Redis 挂了本地短暂兜底。

### 2.5 第 5 层：Redis 预扣库存（核心！防超卖）

**这是秒杀系统的最核心环节**。用 Redis Lua 原子操作判断"还有库存吗 + 用户抢过吗 + 扣减"。

### 2.6 第 6 层：MQ 削峰（RocketMQ）

**只有 Redis 预扣成功的 1000 个请求进 MQ**。DB 按自己能力（100 QPS）消费，10 秒消费完。

### 2.7 第 7 层：DB 最终扣减（强一致）

消费 MQ 消息时，用 FOR UPDATE 行锁扣库存 + 创建订单，保证最终强一致。

# 模块三：Redis 预扣库存——防超卖的核心

## 📖 原理 + 工程

### 3.1 为什么用 Redis 不直接用 DB

**DB 扣库存的问题**：
- FOR UPDATE 行锁，并发时锁等待严重
- 1 万个请求同时争锁，DB 连接池占满
- DB 扛不住 10 万 QPS

**Redis 扣库存的优势**：
- **单线程**，无锁竞争（天然串行）
- **内存操作**，10 万+ QPS 轻松
- **Lua 原子**，"读-判-扣"一气呵成

### 3.2 为什么用 Lua 不用应用层代码

**应用层代码的问题**（超卖根因）：
```java
// ❌ 错误做法(超卖!)
Long stock = redis.get("seckill:stock:iPhone16");  // 读
if (stock > 0) {                                    // 判
    redis.decr("seckill:stock:iPhone16");           // 扣
}
// 线程A读到stock=1, 线程B也读到stock=1(同时!)
// 两人都判断>0, 都扣减 → stock=-1 → 超卖!
```

**根因**：应用层"读-判-扣"是**三步非原子**，中间能被其他线程插入。

**Lua 脚本的优势**：
- Redis 执行 Lua 是**单线程原子**的（执行期间不处理其他命令）
- "读-判-扣"在 Lua 里一气呵成，不会被插入
- **绝对不会超卖**

### 3.3 完整 Lua 脚本（生产可用）

```lua
-- KEYS[1] = "seckill:stock:iPhone16"     库存key
-- KEYS[2] = "seckill:users:iPhone16"      已抢用户集合key
-- ARGV[1] = userId                        用户ID

-- ① 检查是否已抢过(防重复抢)
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then
    return -2  -- 已抢过, 拒绝
end

-- ② 读库存
local stock = tonumber(redis.call('GET', KEYS[1]))
if stock == nil then
    return -1  -- 活动不存在
end

-- ③ 判断库存
if stock <= 0 then
    return 0   -- 售罄
end

-- ④ 原子扣减(关键!)
redis.call('DECR', KEYS[1])
redis.call('SADD', KEYS[2], ARGV[1])  -- 标记已抢

return 1  -- 抢成功
```

**返回值含义**：1=抢成功 / 0=售罄 / -1=活动不存在 / -2=已抢过

### 3.4 库存预热

秒杀开始前，把库存加载到 Redis：
```bash
redis-cli SET seckill:stock:iPhone16 1000
redis-cli DEL seckill:users:iPhone16
```

## 🔥 面试连环追问

### 追问链 3：Redis 预扣

**Q1：为什么用 Redis Lua 不用应用层扣库存？**

> 应用层"读-判-扣"三步非原子，并发时两人同时读到 stock=1 都扣减 → 超卖。Redis Lua 在单线程里原子执行（执行期间不处理其他命令），"读判扣"一气呵成，绝对不会超卖。

**Q2（追问）：Redis Lua 为什么原子？**

> Redis 单线程（命令串行）+ Lua 脚本是一个整体（Redis 当一个命令执行）。执行 Lua 期间不切换到其他命令，脚本内的操作不会被其他线程插入。

**Q3（追问）：Redis 预扣了，DB 还要扣吗？**

> 要。Redis 预扣是"临时扣"（快速削减流量 + 防超卖），DB 是"真扣"（强一致最终结果）。消费 MQ 时用 FOR UPDATE 真扣库存 + 创建订单。Redis 预扣 + DB 真扣 = 最终一致。

### 追问链 4：库存一致性

**Q1：Redis 和 DB 库存怎么一致？**

> Redis 是预扣（临时），DB 是真扣（最终）。消费 MQ 时 DB 真扣。如果用户抢中但 30 分钟未支付 → 订单取消 → 回滚 Redis 库存（+1）让其他用户抢。最终一致。

**Q2（追问）：用户抢中了但 DB 扣减失败（如 DB 挂了）怎么办？**

> MQ 重试机制。DB 扣减失败消息留在 MQ，重试消费。多次失败进死信队列，人工补偿（给用户发"系统繁忙，请重抢"）。

# 模块四：MQ 削峰——异步下单

## 📖 原理 + 工程

### 4.1 为什么需要 MQ 削峰

**问题**：Redis 预扣成功 1000 个，如果直接调 DB 创建订单：
- 1000 个请求同时打 DB（虽然比 10 万好，但仍是瞬时洪峰）
- DB 扛 1000 并发下单（连接池/锁竞争）还是吃力

**MQ 削峰**：1000 个请求先进 MQ，DB 按自己能力（100 QPS）消费，10 秒消费完。DB 按自己节奏，不被打爆。

### 4.2 异步下单的用户体验

**用户视角**：
- 点"抢购" → 提示"抢购成功，正在创建订单..."
- 跳转"等待页"，前端轮询订单状态
- 几秒后订单创建完成 → "抢中！去支付"

**为什么可接受**：秒杀场景用户有心理预期（"抢的人多，等几秒正常"）。

### 4.3 前端轮询 vs WebSocket 推送

**前端轮询**（简单）：前端每 2-3 秒查一次"订单创建了吗"。简单，但有空轮询开销。

**WebSocket 推送**（高效）：订单创建完，服务端主动推"抢中了"。高效，但实现复杂。

**某创业项目选择**：轮询（简单可靠），3 秒一次，最多轮询 30 秒。

# 模块五：防黄牛（多层防御）

## 📖 原理 + 工程

### 5.1 黄牛的攻击方式

**攻击 1：脚本自动化**——黄牛写脚本，0.01 秒点一次，真人根本抢不到。
**攻击 2：多账号**——黄牛注册大量账号，每个账号都抢，把库存抢光。
**攻击 3：分布式 IP**——黄牛用代理池（百万 IP），单 IP 限流无效。

### 5.2 防御手段（5 层）

**防御 1：验证码**（防脚本自动化）
- 开抢前弹滑块/算术验证码
- 脚本难自动过 → 挡掉脚本流量

**防御 2：用户限流**（防多账号）
- 单用户只能参与 1 次
- Redis SET 标记已抢（`SISMEMBER seckill:users`）

**防御 3：IP 限流**（防分布式脚本）
- 单 IP 每秒 1 次
- 配合行为分析（同 IP 多账号 = 可疑）

**防御 4：设备指纹**（防多账号同设备）
- 收集设备指纹（浏览器特征）
- 同设备多账号 = 可疑

**防御 5：行为分析**（AI 识别异常）
- 异常模式：同 IP 多账号、注册时间集中、点击频率异常
- 用 ML（Machine Learning，机器学习）模型识别

## 🎨 图解

### 图 5-1：黄牛防御 5 层

```

  黄牛攻击                       防御
  ────────                       ────
  脚本自动化(0.01秒/次)   →     验证码(滑块/算术)

    限购(实名认证, 一人一件)
```

# 模块六：容灾与降级

## 📖 原理 + 工程

### 6.1 Redis 挂了怎么办

**应急**：
- **本地缓存兜底**：Caffeine AtomicLong 预减（启动时从 Redis 加载），Redis 挂了用本地短暂支撑
- **极限降级**：直接关闭秒杀（返回"系统繁忙"），保命不保业务

### 6.2 MQ 挂了怎么办

**应急**：
- **本地消息表兜底**：消息存本地 DB，定时重发
- **同步降级**：MQ 挂了走同步创建订单（慢但不丢）

### 6.3 DB 挂了怎么办

**应急**：
- **MHA 自动切换**：从库提升为新主库，秒级恢复
- **暂停消费 MQ**：DB 挂了停止消费，消息留 MQ 等 DB 恢复

### 6.4 三级降级策略

| 级别 | 触发 | 措施 |
|---|---|---|
| **L1 自动降级** | Redis/MQ 故障 | 熔断兜底数据 |
| **L2 半自动** | 大促过载 | 配置开关关非核心 |
| **L3 手动** | 极端情况 | 关闭秒杀（保命） |

---

## 🎨 图解

### 图 6-1：容灾降级体系

```
某创业项目秒杀容灾:

  Redis挂了:
    本地缓存(Caffeine)兜底 → 短暂支撑
    极限: 关闭秒杀(保命)

  MQ挂了:
    本地消息表兜底 → 定时重发
    同步降级: 走同步创建订单(慢但不丢)

  DB挂了:
    MHA自动切换从→主 → 秒级恢复
    暂停消费MQ → 消息留MQ等DB恢复

  三级降级:
    L1自动: Redis/MQ故障 → 熔断兜底
    L2半自动: 过载 → 配置开关关非核心
    L3手动: 极端 → 关闭秒杀

  核心原则: 保命优先, 数据一致其次, 体验最后
            (宁可关闭秒杀, 不能超卖资损)
```

## 🔥 面试连环追问

### 追问链 7：容灾

**Q1：Redis 挂了怎么办？**

> (1)本地缓存（Caffeine AtomicLong）兜底；(2)极限降级：关闭秒杀。核心原则：保命优先（宁可关闭秒杀，不能超卖资损）。

**Q2（追问）：为什么宁可关闭秒杀也不能超卖？**

> 超卖是资损（多卖的商品发不出货，要赔钱 + 信任崩塌）。关闭秒杀只是损失本次活动的销售额（可改期重做）。资损 > 损失销售额，所以保命优先。
