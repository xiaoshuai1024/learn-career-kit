## 一、服务拆分与微服务基础

### Q1：什么是微服务？为什么要微服务化？

**答**：微服务是把单体应用拆成多个独立部署、独立技术栈、独立数据库的小服务。单体是所有功能在一个进程，微服务每个服务一个进程，通过 RPC/HTTP 通信。

**为什么要拆**：单体有 5 个痛点——
1. 代码耦合（改一处影响全局，新人 3 个月才上手）
2. 技术栈绑定（换不了语言）
3. 扩容不灵活（只能整体扩）
4. 可靠性差（一挂全挂）
5. 团队冲突（同一代码库）

**连环追问**：
- **Q：微服务不是银弹，引入了什么新问题？**
  > 7 大分布式复杂性：服务发现、配置管理、API 网关、远程调用、熔断降级、链路追踪、分布式事务。整套微服务治理体系就是为解决这些。
- **Q：你们某创业项目怎么拆的？**
  > 按 DDD 限界上下文拆：用户/商品/订单/库存/支付/营销。每个独立 DB，Dubbo/OpenFeign 互调。核心交易用 Seata 保证分布式事务，异步链路（下单后加积分）用 RocketMQ 事务消息。
- **Q：微服务拆得越细越好吗？**
  > 不是。拆太细导致服务数量爆炸（运维成本激增、调用链变长、分布式事务复杂）。**某创业项目按"团队边界 + DDD 限界上下文"拆，6-10 个服务为宜**，不过度拆分。

**🔑 金句**：微服务用"拆分"换灵活性、可扩展，但引入分布式复杂性。拆分依据是业务边界（DDD 限界上下文），不是越细越好。

---

### Q2：单体、集群、SOA、微服务、云原生的演进？

**答**：
- **单体**：所有功能一个进程（简单但耦合）
- **集群**：单体多实例 + LB（解决单点，但代码仍耦合）
- **SOA**：面向服务架构（服务通过 ESB 企业服务总线通信，重）
- **微服务**：SOA 的轻量化，去 ESB，服务独立、用轻量协议（REST/RPC）
- **云原生**：微服务 + 容器（K8s）+ DevOps + 持续交付

**连环追问**：
- **Q：微服务和 SOA 区别？**
  > SOA 用 ESB（企业服务总线）做集中式集成，重；微服务去中心化，服务间点对点轻量通信（REST/RPC）。微服务更轻、更独立。

## 二、服务注册与发现

### Q3：服务注册发现是什么？为什么需要？

**答**：服务启动时把地址（IP:Port）注册到注册中心，调用方从注册中心拉地址，而不是硬编码 IP。解决 IP 变更/扩缩容/宕机感知问题。

**连环追问**：
- **Q：主流注册中心怎么选？**
  > Nacos（国内主流，默认 AP，可配 CP，集成配置中心）、ZooKeeper（CP 强一致，Kafka 协调用）、Eureka（AP，已停更）、Consul（CP，多数据中心）。某创业项目用 Nacos（生态成熟，Spring Cloud Alibaba）。
- **Q：注册中心选 AP 还是 CP？为什么？**
  > **AP**。注册中心挂了不能让整个系统瘫痪。AP 保证注册中心可用，调用方有本地缓存，即使短暂不一致也能调（基于旧地址）。CP 的话网络分区时新服务注册不了，可用性差。
- **Q：Nacos 健康检查怎么做？**
  > 心跳机制。服务每 5 秒发一次心跳，Nacos 15 秒没收到标记不健康（下线），30 秒没收到剔除实例。客户端订阅变更（Nacos 主动推送更新）。
- **Q：服务实例宕机了，调用方怎么感知？**
  > (1) Nacos 健康检查（30 秒剔除）→ 推送给订阅者；(2) 调用方本地 LB（Ribbon/LoadBalancer）有主动健康探测；(3) 调用失败重试下一台（客户端容错）。
- **Q：注册中心挂了，Consumer 还能调 Provider 吗？**
  > **能**。Consumer 本地缓存了 Provider 地址列表。注册中心挂了，Consumer 用本地缓存的地址继续调。这是选 AP 注册中心的原因——注册中心故障不影响业务。

**🔑 金句**：注册中心选 AP 不选 CP（高可用优先），调用方有本地缓存兜底。

---

### Q4：AP 和 CP 注册中心的区别（网络分区时）？

**答**：
- **CP（ZooKeeper）**：网络分区时，Leader 无法复制到 follower，**拒绝写入**（保证强一致），新服务注册不了（可用性受损）。
- **AP（Nacos/Eureka）**：分区时各节点独立接受注册，**可能有短暂不一致**（最终一致），但注册中心永远可用。

**连环追问**：
- **Q：为什么服务发现不要求强一致？**
  > 调用方有本地缓存，注册表短暂不一致（某个新服务暂时发现不了）影响小，可容忍。但注册中心不可用是灾难（所有调用都受影响）。**所以选 AP**。

## 三、配置中心

### Q5：配置中心解决什么问题？

**答**：集中管理所有服务的配置（不散在各机器）、动态刷新（不重启）、环境隔离（dev/test/prod）、权限管控（密码不入代码库）。

**连环追问**：
- **Q：Nacos 配置动态刷新原理？**
  > 长轮询。服务对 Nacos 的配置建立长轮询连接，Nacos 配置变更时立即推送，服务收到后更新 `@RefreshScope` 标记的 Bean，不重启生效。
- **Q：数据库密码能放配置中心吗？**
  > 谨慎。配置中心存敏感信息要加密（Nacos 支持），最好配权限（Apollo 有完善的 namespace 权限）。生产敏感配置可用专门的密钥管理（Vault）。
- **Q：Nacos vs Apollo？**
  > Nacos 集成注册发现+配置（一站式，Spring Cloud Alibaba 主流）；Apollo 专注配置中心，权限/灰度发布/审核完善（携程开源，适合对配置管理要求高的团队）。

**🔑 金句**：配置中心 = 集中管理 + 动态刷新（长轮询）+ 环境隔离 + 权限管控。

## 四、API 网关

### Q6：为什么用 API 网关？

**答**：统一入口，做路由/鉴权/限流/熔断/日志/跨域/灰度/协议转换。客户端只记网关地址，不用记每个服务；鉴权限流统一处理，不用各服务重复写。

**8 大职责**：
1. 路由转发（/api/order → 订单服务）
2. 鉴权（统一验 token）
3. 限流（Sentinel）
4. 熔断降级
5. 日志监控
6. 协议转换（HTTP → Dubbo）
7. 跨域处理（CORS）
8. 灰度发布

**连环追问**：
- **Q：Spring Cloud Gateway 怎么工作？**
  > Route（路由）+ Predicate（匹配）+ Filter（处理）。请求来匹配 Predicate，走 Filter 链（前置 Filter 做鉴权限流），转发到后端，后置 Filter 改响应，返回。
- **Q：网关和 OpenResty 什么关系？**
  > 分层。OpenResty（Nginx+Lua）做接入层网关（性能最高，做粗粒度限流/灰度/负载均衡），Spring Cloud Gateway 做业务网关（细粒度鉴权/协议转换/聚合）。生产两层都有。
- **Q：网关挂了怎么办？**
  > 网关是单点风险。生产用多实例 + 负载均衡（客户端 → SLB → 多个网关实例）。配合健康检查，挂一台自动摘除。
- **Q：网关怎么做鉴权？**
  > 网关层统一验 JWT token。客户端请求带 Authorization Header，网关解析验签 + 检查过期，验过把用户信息塞到 Header 传给后端（后端不用重复验）。

**🔑 金句**：网关 = 统一入口，做路由/鉴权限流/熔断/日志/灰度。生产分层：OpenResty 接入层 + Spring Cloud Gateway 业务网关。

## 五、服务间调用（Dubbo / OpenFeign）

### Q7：Dubbo 和 OpenFeign 怎么选？

**答**：看场景。
- **内部高频调用**（订单→库存，QPS 高）选 **Dubbo**（TCP 长连接+Hessian2，性能高 2-3 倍）
- **跨语言调用**（Java→Go）选 **OpenFeign**（HTTP 通用）或 Dubbo3 Triple
- **Spring Cloud 体系** 选 **OpenFeign**（Spring 官方标配）
- **对外开放 API** 选 **OpenFeign**（RESTful，外部易接入）

某创业项目混合用：内部核心调用（订单→库存/账户）用 Dubbo，跨语言调用（订单→支付[Go]）用 OpenFeign。

**连环追问**：
- **Q：Dubbo 性能为什么比 OpenFeign 高？**
  > (1) TCP 长连接（不重复握手）；(2) Hessian2 二进制序列化（比 JSON 紧凑快）；(3) Netty NIO 多路复用；(4) 协议头极简（Dubbo 16 字节 vs HTTP 几十到几百字节）。
- **Q：Dubbo 自带这么多组件，OpenFeign 却要集成？**
  > 治理哲学不同。Dubbo 设计于 Spring Cloud 之前（2011），那时没有 Spring Cloud 生态，必须自带。OpenFeign 设计于 Spring Cloud 时代，借生态更解耦。Dubbo 全家桶适合"想一揽子搞定"，OpenFeign 适合"按需组装"。
- **Q：能不能 Dubbo 和 OpenFeign 混用？**
  > 能，且推荐。某创业项目就是混合：内部高频核心调用（订单→库存/账户）用 Dubbo（性能）；跨语言或对外（订单→支付[Go]、对外的开放 API）用 OpenFeign（通用）。
- **Q：Java 调 Go，Dubbo 行不行？**
  > Dubbo2 不行（自定义协议，Go 没好客户端）。Dubbo3 的 Triple 协议（HTTP/2+gRPC）可以跨语言。或者用 OpenFeign（HTTP 通用，Go 直接写 HTTP 服务端）。

**🔑 金句**：Dubbo 全家桶重治理+性能高（内部高频），OpenFeign 组装式+跨语言（Spring 标配）。生产混用按场景选。

### Q8：Dubbo 的工作流程？

**答**：4 角色——Provider（暴露服务）/Consumer（调用）/Registry（注册发现）/Monitor（监控）。

**10 步流程**：
1. Provider 启动 → 注册到 Registry
2. Consumer 启动 → 从 Registry 订阅
3. Registry 推送 Provider 地址给 Consumer
4. Consumer 调用 → 本地代理（Stub）
5. Stub → 负载均衡选 Provider
6. LB → 集群容错（重试/熔断）
7. 容错 → 路由
8. 路由 → 协议层（DubboProtocol）
9. 协议 → 序列化 + 编码 → 网络发送
10. Provider 接收 → 解码 + 反序列化 → 业务执行 → 返回

**连环追问**：
- **Q：Dubbo 的负载均衡算法？**
  > Random（默认，按权重随机）、RoundRobin（轮询）、LeastActive（最少活跃数）、ConsistentHash（一致性哈希）。
- **Q：什么时候用 LeastActive？**
  > Provider 处理能力差异大时。LeastActive 选活跃数最少的（最闲的），让快的 Provider 多干。某创业项目库存服务机器配置不同，用 LeastActive。
- **Q：一致性哈希什么时候用？**
  > 缓存类调用。相同参数路由到同一 Provider，该 Provider 本地缓存命中率高。某创业项目商品详情查询用 ConsistentHash，同一商品的请求都到同一台，本地 Caffeine 命中率 90%+。
- **Q：Dubbo 容错模式？**
  > Failover（默认，失败重试，适合幂等）、Failfast（快速失败，非幂等扣款）、Failsafe（忽略异常，日志）、Forking（并行调多个，最快返回）。
- **Q：扣款接口为什么必须 Failfast？**
  > 扣款非幂等（重试会双扣）。Failfast 失败立即报错，让上层处理。如果 Failover 重试，第一次扣成功了但响应丢了，重试再扣一次 = 双扣。
- **Q：Dubbo 服务降级怎么做？**
  > `mock="return null"`（返回 null 降级）或 `mock="com.komall.MockStockService"`（自定义 Mock 类）。Provider 故障时 Consumer 走 mock。

**🔑 金句**：Dubbo 4 角色 + 10 步调用；扣款必 Failfast（重试双扣）；缓存类调用用一致性哈希（提高本地缓存命中）。

### Q9：什么是 Dubbo 的 SPI 机制？

**答**：SPI（Service Provider Interface）是面向接口编程、运行时动态加载实现。Dubbo 几乎所有核心组件（Protocol/Serialization/LoadBalance/Cluster/Router/Transport/Registry）都是 SPI 扩展点，**改配置即可替换实现**。

**Dubbo SPI vs Java SPI**：
- Java SPI：一次性加载所有实现（浪费），不能按 key 选
- Dubbo SPI：按 key 加载（`META-INF/dubbo/接口名`，key=value 格式）+ 按需加载 + 支持 DI + AOP Wrapper

**连环追问**：
- **Q：Dubbo 哪些组件是 SPI？**
  > 几乎所有核心组件：Protocol（协议）、Serialization（序列化）、LoadBalance（负载均衡）、Cluster（容错）、Router（路由）、Transport（传输）、Registry（注册中心）、Threadpool（线程池）。
- **Q：怎么切换负载均衡策略？**
  > 改配置（不重打包）：`<dubbo:reference loadbalance="roundrobin" />`。Dubbo SPI 按 `loadbalance=roundrobin` 加载 RoundRobinLoadBalance。
- **Q：@Adaptive 是什么？**
  > 自适应扩展。带 @Adaptive 的接口，Dubbo 动态生成代理类，代理类根据 URL 参数运行时决定用哪个实现。例：URL protocol=dubbo 用 DubboProtocol，protocol=http 用 HttpProtocol。
- **Q：某创业项目生产怎么用 SPI？**
  > 默认配置为主（dubbo 协议/hessian2/random/failover）。特殊场景：序列化换 Kryo（处理 BigDecimal 更好）；负载均衡用一致性哈希（灰度发布时同一用户路由到同一 Provider）。改配置即可，不改代码。

**🔑 金句**：Dubbo 所有核心组件都是 SPI，改配置即可替换实现（不改代码）。这是 Dubbo 灵活性的根基。

### Q10：OpenFeign 怎么工作？

**答**：开发者写接口 + 注解，Feign 用 JDK 动态代理生成实现。调用时：
1. JDK 动态代理拦截
2. Contract 解析 Spring MVC 注解（@PostMapping 等）
3. Encoder 编码请求体（Jackson → JSON）
4. LoadBalancer 从注册中心选实例
5. Interceptor 加鉴权/TraceId
6. Client 发 HTTP 请求（默认 JDK HttpURLConnection，生产换 OkHttp）
7. Decoder 解码响应

**连环追问**：
- **Q：为什么 FeignClient 只能是接口？**
  > 因为 Feign 用 JDK 动态代理（基于接口）。JDK 动态代理只能代理接口（要代理类得用 CGLIB）。Feign 在容器启动时为每个 @FeignClient 接口生成代理对象注入。
- **Q：Feign 的 URL 怎么解析？name=stock-service 怎么变成 IP？**
  > name 是服务名。Feign 集成 LoadBalancer，LoadBalancer 从注册中心（Nacos）查 stock-service 的所有实例，按负载均衡策略（默认轮询）选一个，拼成完整 URL。
- **Q：Feign 怎么传 TraceId？**
  > RequestInterceptor。自定义拦截器，在请求发出前从当前上下文（MDC）读 TraceId，塞到 HTTP Header（X-Trace-Id）。Provider 端的过滤器从 Header 读 TraceId 放到自己的 MDC。
- **Q：Feign 怎么做熔断降级？**
  > 配 fallback 类。@FeignClient(fallback = StockFeignFallback.class)，fallback 类实现同一接口。Feign 调用失败（超时/拒绝/熔断）时走 fallback 返回兜底数据。fallbackFactory 能拿到异常对象（按异常类型不同降级）。
- **Q：Feign 默认用什么 Client？要换吗？**
  > 默认 JDK HttpURLConnection（无连接池，性能差）。生产换 OkHttp 或 Apache HttpClient（带连接池，性能好）。配置 `feign.okhttp.enabled=true`。

**🔑 金句**：Feign = 接口+注解+JDK 动态代理，集成 Spring Cloud 生态（LoadBalancer/Resilience4j/Nacos）。生产换 OkHttp + fallbackFactory。

## 六、熔断降级（微服务场景）

### Q11：微服务的雪崩怎么发生？怎么防？

**答**：微服务链路长（4-5 层调用），下游故障通过资源耗尽放大成全局故障。

**雪崩机理**（积分服务挂了）：
```
积分挂 → 账户等积分超时 → 账户线程池满 → 库存等账户超时 → 库存满 → 订单满 → 全挂
```

**防范**：按**调用关系**配熔断。订单调库存慢了，订单熔断库存（保护订单自己），而不是全局限流。Sentinel 支持按"资源 + 调用者"维度熔断。

**连环追问**：
- **Q：微服务的雪崩和单体有什么不同？**
  > 微服务链路长（4-5 层调用），故障传播更广；依赖网状复杂，一处故障多处受影响；共享资源被一个故障拖垮。雪崩放大效应更强。
- **Q：积分服务挂了，怎么不影响下单？**
  > 积分服务熔断 + 降级。下单调积分失败时返回降级（如"积分稍后补发"），主链路（下单扣库存扣余额）正常。积分异步补偿（MQ 重试）。
- **Q：限流/熔断/降级三者区别？**
  > 限流防患于未然（事前，入口限速防过载）；熔断及时止损（事中，下游故障主动断）；降级壮士断腕（事后，全局压力牺牲非核心）。

**🔑 金句**：微服务按调用关系配熔断（A 调 B 慢，A 熔断 B 保护自己），不是全局限流。

## 七、链路追踪

### Q12：微服务为什么需要链路追踪？

**答**：一次请求跨多个服务，出问题不知道慢在哪。链路追踪给每个请求一个 TraceId 贯穿所有服务，记录每一跳（Span）的耗时和父子关系，可视化定位瓶颈。

**核心概念**：
- **Trace**：一次完整请求，跨多个服务
- **Span**：一次操作（一个服务内的处理）
- **TraceId**：全局唯一，贯穿整个链路
- **SpanId**：单跳标识，父子关系（ParentSpanId）

**连环追问**：
- **Q：TraceId 怎么跨服务传播？**
  > 通过请求头（HTTP Header 或 RPC Context）。每跳从 Header 读 TraceId，创建自己的 Span（记录父 SpanId），调下游时再通过 Header 传下去。
- **Q：SkyWalking 怎么做到无侵入？**
  > Java Agent 字节码增强。启动时加载 Agent，在类加载时拦截 HTTP/RPC/MQ 调用方法，自动注入 TraceId 传递逻辑，业务代码不用改。
- **Q：除了排错还能干嘛？**
  > (1) 性能分析（找慢节点）；(2) 拓扑发现（自动画出服务依赖图）；(3) 容量规划（各服务 QPS/RT 统计）；(4) 告警（某 Span 错误率突增）。
- **Q：主流方案怎么选？**
  > SkyWalking（Apache，国产，无侵入字节码增强，国内主流）、Zipkin（Twitter，简单）、Jaeger（CNCF，云原生）、Pinpoint（字节码增强，韩国）。

**🔑 金句**：TraceId 贯穿全链路，Header 传播，SkyWalking 字节码增强无侵入。

## 八、Service Mesh（服务网格）

### Q13：Service Mesh 是什么？和 Spring Cloud 区别？

**答**：Sidecar 边车模式。每个服务旁边部署代理（Envoy），所有流量经过 Sidecar，治理逻辑都在 Sidecar。**业务代码零侵入**，多语言统一，升级独立。

**vs Spring Cloud**：
- Spring Cloud：SDK 模式，治理代码嵌在业务里，多语言要重写 SDK
- Service Mesh：Sidecar 模式，治理在 Sidecar，业务零侵入，多语言统一

**连环追问**：
- **Q：Istio 怎么拦截流量？**
  > iptables 透明拦截。Pod 启动时 Istio 注入 iptables 规则，把所有出入流量重定向到 Envoy Sidecar，业务无感知（以为在直连）。
- **Q：Service Mesh 会不会替代 Spring Cloud？**
  > 长期是趋势（多语言+零侵入+独立升级），但短期国内仍是 Spring Cloud 主导（Service Mesh 复杂度高，要 K8s 前提）。大规模（几百服务）+ 多语言团队适合 Service Mesh，小团队 Spring Cloud 更划算。
- **Q：Sidecar 多一跳会不会慢？**
  > 会增加 1-2ms 延迟（本地 Sidecar 转发）。但相比业务 RT（几十 ms），影响小。性能极致敏感场景要权衡。

**🔑 金句**：Service Mesh = Sidecar 边车模式，业务零侵入 + 多语言统一 + 升级独立。趋势但复杂度高，大规模多语言团队适用。

## 九、Spring Cloud Alibaba 全家桶

### Q14：Spring Cloud Alibaba 包含哪些组件？

**答**：国内主流微服务全家桶——

| 能力 | 组件 |
|---|---|
| 服务注册发现 | Nacos |
| 配置中心 | Nacos |
| API 网关 | Spring Cloud Gateway |

| 链路追踪 | SkyWalking |

**连环追问**：
- **Q：Sentinel 和 Hystrix 区别？**
  > Sentinel（阿里）支持限流+熔断+降级+系统自适应，动态规则（接 Nacos 热更新），自带控制台；Hystrix（Netflix）只熔断+降级，无限流，已停维护。
- **Q：为什么选 Spring Cloud Alibaba 不选 Spring Cloud Netflix？**
  > Netflix 组件（Eureka/Hystrix/Zuul）大都停更或停止维护。Alibaba（Nacos/Sentinel/Seata）活跃维护，国内生态成熟，文档中文全。

**🔑 金句**：Spring Cloud Alibaba = Nacos + Sentinel + Seata + RocketMQ + SkyWalking 全家桶，国内主流。

## 十、生产级架构

### Q15：设计一个生产级高可用高并发微服务架构？

**答**：13 层纵深防御 + 6 大设计原则。

**13 层**（从外到内）：
1. CDN（静态资源就近返回）
2. DNS 智能解析
3. Anycast IP / LVS（四层 LB）
4. WAF + Anti-DDoS
5. Nginx/OpenResty（七层 LB + 粗限流 + 灰度）
6. API 网关（鉴权 + 细限流 + 熔断）
7. 微服务集群（DDD 拆分 + Dubbo/Feign 互调）
8. 缓存层（Caffeine + Redis 多级）
9. 消息队列（RocketMQ 异步解耦）
10. 数据库（MySQL 主从 + 读写分离 + 分库分表 + MHA）
11. 搜索/OLAP（ES + ClickHouse + Canal 同步）
12. 分布式事务（核心 Seata + 异步 MQ 事务消息）
13. 治理运维（Nacos + Sentinel + Seata + SkyWalking + Prometheus + ELK + K8s + GitLab CI）

**6 大设计原则**：
1. **纵深防御**：每一层都假设上一层会挂，都有兜底
2. **读写分离 + 多级缓存**：DB 只处理写和强一致读
3. **异步化解耦**：核心同步 + 非核心异步（MQ）
4. **核心/非核心隔离**：核心独立 DB/线程池/SLA 99.99%
5. **柔性可用**：自动/半自动/手动三级降级
6. **可观测性**：Metrics + Logging + Tracing 三支柱

**连环追问**：
- **Q：你这个架构的核心设计思想是什么？**
  > 纵深防御 + 读写分离 + 异步解耦 + 核心隔离。每一层都假设上一层会挂，都有兜底；读路径多级缓存让 DB 几乎不扛读；写路径同步核心 + 异步非核心；核心链路物理隔离 SLA 99.99%，非核心可被降级。
- **Q：为什么 Nginx 前面还要有 LVS（四层 LB）？**
  > Nginx 是七层（看 HTTP），能做复杂路由但单机性能有上限（10 万并发）。LVS 是四层（只看 IP+Port 转发），性能极高（百万级并发）且稳定。LVS 把流量分发到多个 Nginx，Nginx 再做七层处理。**四层扛量，七层做策略**。
- **Q：双机房怎么保证一致性？**
  > 同城双活用半同步复制（主库写完等至少一个从库确认才返回），延迟 ms 级。异地多活用单元化部署（按用户路由到对应单元，跨单元用最终一致）。强一致用同城双活，全球部署用异地多活（按用户分片）。
- **Q：双 11 峰值怎么扛？**
  > (1) 容量预估（去年同期 × 增长）+ 压测验证；(2) 提前扩容（K8s HPA + 手动扩）；(3) 限流兜底（Sentinel）；(4) 降级非核心（关评论/推荐）；(5) MQ 削峰（秒杀请求先进 MQ）。**核心是"让 DB 不爆"**。
- **Q：核心服务挂了怎么应急？**
  > (1) 告警触发（Prometheus + AlertManager）；(2) 熔断降级（自动兜底）；(3) 切流量（摘除故障节点）；(4) 回滚（最近发版有问题）；(5) 扩容（瓶颈是容量）；(6) 限流（保护下游）。有标准 SOP。

**🔑 金句**：13 层纵深防御 + 6 大设计原则。核心是"让 DB 不爆"——MQ 削峰 + 缓存挡量 + 读写分离 + 核心隔离。
