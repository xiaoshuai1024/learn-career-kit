## 第一阶段：原理讲解 + 工程化实现

### 1. 为什么需要监控预警——一个真实事故推演

> **场景**：你的电商平台（赛微瑞云的政企客户也同理）正在跑，某天下午 3 点开始，用户反馈"下单特别慢"。
>
> **没有监控时**：
> - 客服接到投诉 → 提工单 → 运维打开服务器 → `top` 看 CPU → 正常 → `tail -f` 看日志 → 没报错 → 一头雾水
> - 半小时后发现是 MySQL 慢查询导致，但已经影响了 2000+ 订单
> - 老板问"为什么 30 分钟才发现？"——你答不上来
>
> **有监控时**：
> - 下午 3:02，Prometheus 检测到订单接口 P99 延迟从 200ms 飙到 3000ms
> - Alertmanager 自动发钉钉告警（P1 级别）："订单服务 P99 延迟超阈值，当前 3000ms > 阈值 500ms"
> - 你打开 Grafana 大盘 → 看到 MySQL 慢查询数同期飙升 → SkyWalking 链路追踪定位到是一条 `SELECT * FROM order WHERE created_at BETWEEN ...` 全表扫描
> - 3:05 定位根因，3:10 加索引修复——**8 分钟发现+定位+修复**，只影响了 50 个订单
>
> **监控的本质**：不是"出了事能查"，是**"出事之前或刚出事时就自动告诉你"**——从被动救火变成主动发现。

> 🔑 **金句**："监控不是出了事故才去查的工具，是让事故在酿成大祸之前就被自动发现的体系。没有监控的系统就像闭眼开车——你以为在直道上，其实已经偏了。"

### 2. 可观测性三支柱（Observability Three Pillars）

> **可观测性（Observability）**：由 Google SRE 提出，指从系统外部行为推断内部状态的能力。三个支柱缺一不可。

```
                    ┌─────────────────────────────────┐
                    │        可观测性 Observability      │
                    │   "从外部行为推断内部状态"          │
                    └────────┬──────────┬──────────┬────┘
                             │          │          │
                    ┌────────▼──┐ ┌─────▼────┐ ┌───▼──────┐
                    │  Metrics  │ │  Traces  │ │  Logs    │
                    │  指标监控  │ │ 链路追踪  │ │ 日志收集  │
                    │(多少/多快) │ │(哪一步慢) │ │(报什么错) │
                    └─────┬─────┘ └────┬─────┘ └────┬─────┘
                          │            │            │
                     Prometheus   SkyWalking      ELK
                     Grafana      Jaeger/Zipkin   EFK
```

| 支柱 | 回答什么问题 | 典型工具 | 数据特征 |
|------|-------------|---------|---------|
| **Metrics（指标）** | 系统现在"多少、多快、有没有错" | Prometheus + Grafana | 数值型时序数据（CPU 60%、QPS 1200、P99 200ms） |
| **Traces（链路追踪）** | 一个请求经过哪些服务、卡在哪一步 | SkyWalking / Jaeger | 树形调用链（Trace → Span → Span） |
| **Logs（日志）** | 具体发生了什么、报了什么错 | ELK（ES + Logstash + Kibana） | 文本（异常堆栈、业务日志、访问日志） |

> **三者关系（面试高频）**：Metrics 告诉你**"有问题"**（P99 飙了）→ Traces 告诉你**"问题在哪"**（卡在 MySQL 查询那一步）→ Logs 告诉你**"具体什么错"**（SQL 语法错误 / 连接池满）。三者形成**发现→定位→诊断**的闭环。

> 🔑 **金句**："Metrics 发现问题、Traces 定位问题、Logs 诊断问题——三者形成闭环，缺一个就像看病只有体温计没有 CT 和验血。"

### 3. Prometheus——指标监控的核心

#### 3.1 什么是 Prometheus

**Prometheus**（普罗米修斯）：SoundCloud 于 2012 年开源的**时间序列数据库 + 监控系统**，CNCF（Cloud Native Computing Foundation，云原生计算基金会）第二个毕业项目（仅次于 Kubernetes），现已成为**云原生监控事实标准**。

> **缩写**：Prometheus 不是缩写，是希腊神话中"先见之明"的神——取"提前发现问题"之意。

#### 3.2 架构（ASCII 图必背）


**核心组件**：

| 组件 | 职责 | 关键点 |
|------|------|--------|
| **Prometheus Server** | 核心服务，拉取+存储+查询指标 | 内置 TSDB（Time Series Database，时间序列数据库） |
| **Exporters** | 被监控目标的指标暴露器 | node_exporter（主机）、mysqld_exporter（MySQL）、Spring Boot Actuator（Java 应用） |
| **Pushgateway** | 短生命周期任务的指标中转 | 临时任务（如 Cron Job）先推到 Pushgateway，Prometheus 再从 Pushgateway 拉 |
| **Alertmanager** | 告警引擎 | 去重、分组、路由、抑制、静默 |
| **Grafana** | 可视化大盘 | 数据源接 Prometheus，画折线图/仪表盘 |

#### 3.3 Pull 模型 vs Push 模型（面试高频对比）

| 维度 | Pull（Prometheus） | Push（StatsD/Datadog） |
|------|-------------------|----------------------|
| 谁主动 | **服务端主动拉**（Prometheus → 目标） | **客户端主动推**（应用 → 监控服务） |
| 优点 | ① 知道谁没响应（目标挂了立刻发现）；② 控制采集频率；③ 目标可以不装 agent | ① 穿越防火墙简单；② 短任务友好 |
| 缺点 | 需要服务端能访问目标（NAT/防火墙可能挡） | 目标挂了不知道（推不上来=没数据=发现不了故障） |
| 关键认知 | Prometheus 选 Pull 是因为**"目标挂了能立刻发现"**——Push 模型下目标宕机不会触发告警（只是没数据） | — |

> 🔑 **金句**："Prometheus 选 Pull 不选 Push，核心原因不是性能而是**故障可见性**——Pull 模型下目标挂了会变成 scrape failed 立即告警；Push 模型下挂了只是没数据，容易被忽略。"

#### 3.4 四种指标类型（必背，面试高频）

| 类型 | 全拼 | 含义 | 例子 | PromQL 聚合 |
|------|------|------|------|------------|
| **Counter** | 计数器 | **只增不减**（重启归零） | 请求总数、错误总数、订单创建数 | `rate()` 求每秒速率 |
| **Gauge** | 仪表盘 | **可增可减**的瞬时值 | CPU 使用率、内存占用、连接池活跃数 | 直接用，不需 rate |
| **Histogram** | 直方图 | 按桶（bucket）统计**分布** | 请求延迟分布（多少请求 < 100ms / < 500ms / < 1s） | `histogram_quantile()` 求分位数 |
| **Summary** | 摘要 | 客户端预计算的**分位数** | 直接给出 P50/P90/P99 | 直接读，不需服务端算 |

**Counter vs Gauge 速记**：
```
Counter（计数器）          Gauge（仪表盘）
  ▲ 值                      ▲ 值
  │      ╱╱                 │   ╱╲    ╱
  │    ╱╱                   │  ╱  ╲╱╲╱
  │  ╱╱                     │ ╱
  │╱___________             │___________
   只增不减（重启归零）         可增可减（瞬时值）
   请求总数/错误总数           CPU%/内存/连接数
```

**Histogram vs Summary 对比（面试追问点）**：

| 维度 | Histogram | Summary |
|------|-----------|---------|
| 分位数计算 | **服务端算**（PromQL `histogram_quantile()`） | **客户端预算**（应用端算好直接发） |
| 灵活性 | ✅ 高——可后聚合不同分位数 | ❌ 低——客户端预设了哪些就是哪些 |
| 资源开销 | 客户端轻（只存桶计数） | 客户端重（流式算法维护分位数） |
| 推荐 | **生产推荐 Histogram**（可后聚合+跨实例合并） | Summary 不能跨实例聚合算分位数 |

> **务实建议**：Spring Boot Actuator 默认用 **Micrometer**（指标门面，类似 SLF4J 之于日志）→ 默认发布 Histogram 类型 → Prometheus 服务端用 `histogram_quantile(0.99, ...)` 算 P99。**面试直接说"我用 Micrometer + Histogram + histogram_quantile"即可**。

#### 3.5 PromQL 速查（面试可能让你写查询）

```promql
# 1. 每秒请求量（QPS）——Counter 用 rate
rate(http_server_requests_seconds_count[5m])

# 2. P99 延迟——Histogram 用 histogram_quantile
histogram_quantile(0.99, rate(http_server_requests_seconds_bucket[5m]))

# 3. 错误率——错误数 / 总数
sum(rate(http_server_requests_seconds_count{status=~"5.."}[5m])) 
/ sum(rate(http_server_requests_seconds_count[5m]))

# 4. CPU 使用率
100 - (avg by(instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100)

# 5. 内存使用率
(node_memory_MemTotal_bytes - node_memory_MemAvailable_bytes) / node_memory_MemTotal_bytes * 100
```

### 4. Grafana——可视化大盘

**Grafana**：开源的可视化平台，不生产数据，只展示——接 Prometheus（指标）、ES（日志）、SkyWalking（链路）等数据源，画成折线图/仪表盘/热力图。

**大盘设计原则（Google SRE 黄金信号 Four Golden Signals）**：

> **Google SRE 黄金信号**：Google《SRE Book》提出的四个最核心监控维度——衡量一个服务健康不健康，看这四个就够了。

| 信号 | 全拼 | 含义 | 典型指标 | 异常意味着 |
|------|------|------|---------|-----------|
| **Latency** | 延迟 | 请求多快返回 | P99/P95/P50 响应时间 | 慢了——性能瓶颈或下游拖累 |
| **Traffic** | 流量 | 多少请求进来 | QPS/TPS/并发数 | 涨了——可能是大促也可能是攻击 |
| **Errors** | 错误 | 多少请求失败 | 5xx 错误率/业务错误率 | 高了——代码 bug 或依赖故障 |
| **Saturation** | 饱和度 | 资源利用率 | CPU%/内存%/磁盘%/连接池 | 满了——快扛不住了 |

> **关键认知**：黄金信号的核心思想是**"不要什么指标都看，盯住这四个维度就够了"**——每个微服务的大盘，第一行永远是这四个信号的概览仪表盘。

> 🔑 **金句**："监控大盘不是指标越多越好——Google SRE 黄金信号告诉我们，盯住延迟、流量、错误、饱和度四个维度就能判断服务健不健康。大盘第一行永远是这四个仪表盘。"

**大盘设计实操建议**：
- **第一层（概览）**：黄金信号四仪表盘——一眼看服务整体健不健康
- **第二层（下钻）**：按接口/实例/租户维度拆分——哪个接口慢、哪个实例异常
- **第三层（依赖）**：下游 MySQL/Redis/MQ 的关键指标——是自己的问题还是下游拖累

### 5. SkyWalking——分布式链路追踪

#### 5.1 为什么需要链路追踪

> **场景**：用户下单 → 经过网关 → 订单服务 → 调用库存服务 → 调用支付服务 → 写 MySQL → 发 MQ。整个链路 7 个服务，P99 延迟 3 秒。
>
> **没有链路追踪**：你知道"下单慢了"，但不知道**卡在哪一步**——是 MySQL 慢？还是支付服务超时？还是 MQ 积压？
>
> **有链路追踪**：打开 SkyWalking → 输入 TraceId → 看到一棵调用树：

```
Trace: 下单请求 (总耗时 3000ms)
│
├── Gateway [10ms] ──────────────────────────── ✅ 正常
│   └── OrderService.createOrder() [2980ms] ──── 🔴 这里慢！
│       ├── InventoryService.deduct() [50ms] ── ✅ 正常
│       ├── PaymentService.pay() [2800ms] ────── 🔴 🔴 支付服务超时！
│       │   └── MySQL.execute() [2790ms] ─────── 🔴 🔴 🔴 SQL 慢查询！
│       └── MQ.send() [80ms] ─────────────────── ✅ 正常
```

**一眼定位**：支付服务里的 MySQL SQL 执行了 2.79 秒，整个链路的瓶颈就在这。

#### 5.2 核心概念

| 概念 | 全拼 | 含义 |
|------|------|------|
| **Trace** | 追踪 | 一个完整请求的全链路（一个 TraceId） |
| **Span** | 跨度 | 链路中的一个操作（如一次 HTTP 调用、一次 SQL 执行） |
| **TraceId** | 追踪 ID | 贯穿全链路的唯一 ID，通过 HTTP Header / MQ Header 传播 |
| **SpanId** | 跨度 ID | 每个 Span 的唯一 ID + 父 SpanId，组成树形结构 |

**TraceId 跨服务传播原理**：
```
用户请求
  │ Header: X-Trace-Id = abc123（网关生成）
  ▼
Gateway ──HTTP──▶ OrderService
                   │ Header: X-Trace-Id = abc123（透传）
                   │ X-Span-Id = span-2（新生成）
                   ▼
                 MySQL.execute()
                   │ Header: X-Trace-Id = abc123（继续透传）
                   │ X-Span-Id = span-3
```

> **关键技术**：TraceId 通过 **HTTP Header**（通常用 `sw8` 或 W3C `traceparent`）在服务间传播。Spring Cloud 中通常由 **SkyWalking Agent** 自动注入（字节码增强），业务代码无感知。

#### 5.3 SkyWalking vs Jaeger vs Zipkin（选型对比）

| 维度 | SkyWalking | Jaeger | Zipkin |
|------|-----------|--------|--------|
| 来源 | Apache（华人吴晟主导） | Uber → CNCF | Twitter |
| 语言 | Java | Go | Java/Scala |
| 埋点方式 | **Agent 字节码增强（无侵入）** | SDK 手动埋点 | SDK 手动埋点 |
| UI | ✅ 丰富（拓扑图+慢调用分析） | 一般 | 简洁 |
| 告警 | ✅ 内置告警 | ❌ 需配 Prometheus | ❌ 需配 Prometheus |
| 国内生态 | ✅ **国内主流**（华为/阿里贡献） | 国际主流 | 老牌但式微 |

> **选型建议**："国内 Java 项目我选 SkyWalking——Agent 字节码增强零侵入，业务代码不用改一行；拓扑图自动生成服务依赖；内置告警不用额外接。Jaeger 适合 Go 生态或偏好手动精细埋点的场景。"

> 🔑 **金句**："SkyWalking 最大优势是 Agent 字节码增强——Java 应用启动时加一个 `-javaagent:skywalking-agent.jar` 参数，业务代码一行不改就能自动追踪全链路。这叫'无侵入可观测性'，是 APM（Application Performance Monitoring，应用性能监控）的最佳实践。"

### 6. ELK——日志收集

**ELK** = **E**lasticsearch + **L**ogstash + **K**ibana（有时加 Filebeat 变 EFK）。

| 组件 | 职责 | 在电商订单系统中的角色 |
|------|------|----------------------|
| **Elasticsearch** | 全文搜索引擎（分布式，基于 Lucene） | 存储所有服务日志，支持按 TraceId/orderId/userId 搜索 |
| **Logstash / Fluentd** | 日志采集+过滤+转发 | 从各服务器收集日志 → 解析 JSON → 发到 ES |
| **Kibana** | 可视化界面 | 搜日志、看日志趋势、建日志大盘 |
| **Filebeat**（EFK 的 F） | 轻量日志文件采集器 | 比 Logstash 更轻，装在每个应用服务器上读日志文件 |

**ELK 架构**：
```
应用服务器 A ──┐
应用服务器 B ──┼──▶ Filebeat ──▶ Logstash ──▶ Elasticsearch ──▶ Kibana
应用服务器 C ──┘    (轻量采集)    (过滤解析)    (存储+搜索)       (可视化)
```

**结构化日志（面试加分点）**：
```
# ❌ 非结构化日志（ELK 搜不了）
2026-08-04 15:03:22 ERROR 订单创建失败，用户张三，订单号 NO20260804001

# ✅ 结构化日志（JSON，ELK 可按字段搜索）
{"timestamp":"2026-08-04T15:03:22Z","level":"ERROR","service":"order-service",
 "traceId":"abc123","orderId":"NO20260804001","userId":"user_zhangsan",
 "message":"订单创建失败：库存不足","product":"iPhone 16 Pro"}
```

> **务实建议**：Spring Boot 用 **Logback + logstash-logback-encoder** 输出 JSON 格式日志，每条日志自动带 TraceId（SkyWalking 注入 MDC），ELK 搜 TraceId 一秒找到全链路所有日志。

### 7. Alertmanager——告警引擎

#### 7.1 告警分级（面试可能让你设计）

| 级别 | 含义 | 通知方式 | 响应时间 | 例子 |
|------|------|---------|---------|------|
| **P0** | 系统不可用 / 资损 | **电话** + 钉钉 + 短信 | **5 分钟** | 支付服务全部 503、数据库宕机 |
| **P1** | 核心功能严重降级 | 钉钉（@值班人） | **15 分钟** | 订单接口 P99 > 2s、错误率 > 5% |
| **P2** | 非核心功能异常 | 钉钉（群消息） | **1 小时** | 搜索服务慢、报表延迟 |
| **P3** | 预警信号 | 邮件 | **次日处理** | CPU > 70%、磁盘 > 80% |

#### 7.2 告警的三大敌人

| 敌人 | 含义 | 后果 | 解法 |
|------|------|------|------|
| **告警风暴** | 一个 DB 挂了 → 100 个服务同时报错 → 100 条告警 | 值班人被淹没，真正重要的告警被忽略 | **分组（Grouping）**：同源告警合并成一条 |
| **告警抖动** | 服务在阈值边缘反复横跳 → 告警反复触发+恢复 | 钉钉群被刷屏 | **抑制（Inhibit）+ for 持续时间**：`for: 5m` 表示持续 5 分钟才告警 |
| **狼来了** | 告警太多 + 大量误报 | 值班人麻木，真告警也被忽略 | **告警治理**：定期审查告警规则，误报率 > 10% 的规则必须调优 |

**Alertmanager 告警规则示例**（Prometheus 规则文件）：
```yaml
# P1 告警：订单接口 P99 延迟 > 500ms 持续 5 分钟
- alert: OrderServiceHighLatency
  expr: histogram_quantile(0.99, rate(http_server_requests_seconds_bucket{service="order-service"}[5m])) > 0.5
  for: 5m                          # 持续 5 分钟才触发（防抖动）
  labels:
    severity: p1                   # 告警级别
  annotations:
    summary: "订单服务 P99 延迟超阈值"
    description: "当前 P99 = {{ $value }}s，阈值 0.5s"
```

> 🔑 **金句**："好的告警系统不是'什么报什么'——是'分组防风暴、for 防抖动、治理防狼来了'。最差的监控是天天告警没人看，比没有监控更危险。"

```java
@Service

    public Order createOrder(OrderRequest req) {
        // ... 创建订单逻辑 ...
        orderCounter.increment();  // 每创建一个订单 +1
        return order;
    }
}
```

## 第二阶段：面试连环追问

### 追问链 1：监控体系设计

```
Q: 你的监控系统怎么搭的？
│
├─ A: 可观测性三支柱——Metrics(Prometheus) + Traces(SkyWalking) + Logs(ELK)
│
├─ Q: Prometheus 为什么用 Pull 不用 Push？
├─ A: Pull 模型下目标挂了立刻变成 scrape failed 触发告警；
│   Push 模型下挂了只是没数据，容易被忽略。
│
├─ Q: 那短任务（Cron Job）怎么监控？它结束了你怎么 Pull？
├─ A: 用 Pushgateway。短任务把指标推到 Pushgateway，Prometheus 从 Pushgateway 拉。
│   注意 Pushgateway 不做数据过期，任务消失后旧数据还在，要定期清理。
│
├─ Q: 四种指标类型分别什么场景用？
├─ A: Counter 只增不减（请求总数）用 rate 算 QPS；Gauge 可增可减（CPU/内存）直接用；
│   Histogram 按桶统计分布（延迟分布）服务端算分位数；Summary 客户端预算分位数。
│   生产推荐 Histogram——可后聚合+跨实例合并。
│
├─ Q: P99 延迟怎么算？
├─ A: histogram_quantile(0.99, rate(http_server_requests_seconds_bucket[5m]))
│   Histogram 存的是桶（le=0.1 有多少个、le=0.5 有多少个），服务端按桶插值算分位数。
│
└─ Q: 为什么不用平均值而是 P99？
    A: 平均值会被大量快请求稀释——1000 个请求里 990 个 10ms、10 个 3s，
       平均值 40ms 看起来正常，但那 10 个慢请求的用户体验极差。
       P99 专盯长尾——99% 的请求比这个值快，剩下 1% 的慢请求才是优化的目标。
```

### 追问链 2：告警设计

```
Q: 你的告警怎么设计的？
│
├─ A: 四级——P0 电话（系统不可用/资损）、P1 钉钉@值班人（核心降级）、
│   P2 钉钉群（非核心异常）、P3 邮件（预警信号）
│
├─ Q: 告警风暴怎么处理？
├─ A: Alertmanager 分组（Grouping）——同一个数据库挂了导致 100 个服务报错，
│   合并成一条告警。规则是按 alertname + cluster 分组。
│
├─ Q: 告警反复触发恢复（抖动）怎么办？
├─ A: 两招——① Prometheus 规则加 for: 5m（持续 5 分钟才告警）；
│   ② Alertmanager 抑制（Inhibit）——高级别告警触发时自动静默低级别。
│
├─ Q: 告警太多没人看了怎么办？
├─ A: 这叫"告警疲劳"——最差的监控是天天告警没人看。
│   定期治理：误报率 > 10% 的规则必须调优（调阈值或删规则）。
│   好告警的标准：可执行（收到就知道该干嘛）+ 低误报 + 有意义（不是噪音）。
│
└─ Q: 你怎么定义"好的告警"和"坏的告警"？
    A: 好告警 = 收到就行动（系统真出问题了）；坏告警 = 收了就忽略（噪音）。
       判断标准：如果一条告警值班人看到后什么都不做，这条告警应该删掉。
       Google SRE 建议：告警应该指向人类行动，不指向自动修复——
       如果能自动修复（如 HPA 扩容），那不应该告警，应该直接做。
```

### 追问链 3：链路追踪

```
Q: 分布式链路追踪怎么做的？
│
├─ A: SkyWalking Agent 字节码增强——Java 应用加 -javaagent 参数，
│   自动注入 HTTP Client/MySQL Driver/MQ Client，业务代码零侵入。
│
├─ Q: TraceId 怎么跨服务传播的？
├─ A: 网关生成 TraceId → 写入 HTTP Header（sw8 协议）→ 
│   下游服务 Agent 从 Header 提取 TraceId → 继续传播。
│   同一个 TraceId 贯穿全链路，SkyWalking UI 按它拼出调用树。
│
├─ Q: 如果有个服务没装 Agent，链路断了吗？
├─ A: 会断。未装 Agent 的服务不会传播 TraceId，它的下游看不到上游的 Trace。
│   解决：要么所有服务装 Agent，要么在关键服务手动加 SDK 埋点。
│   生产建议：CI/CD 镜像里统一加 Agent 参数，强制所有服务接入。
│
└─ Q: SkyWalking 和 Jaeger 怎么选？
    A: 国内 Java 项目选 SkyWalking——Agent 无侵入、拓扑图自动生成、内置告警。
    Go 生态或需要精细手动埋点选 Jaeger。Zipkin 老牌但功能不如前两者。
```
